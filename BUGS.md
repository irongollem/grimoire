# Bugs

- [x] DM-assigned characters were read-only for the player — every sheet control silently failed (#516, High). A character built in `PartyMemberForm` has `user_id = DM`, `owner_user_id = null`; linking a player via `campaign_members.party_member_id` granted SELECT (extended in `20260519000002`) but **not** UPDATE — `party_members_player_update` required `owner_user_id = auth.uid()` or campaign DM. So a player who was *assigned* (not assumed) a character tapped Damage/Heal/a condition/Short Rest and every `useUpdatePartyMember` mutation matched 0 rows (`.single()` threw), buttons looked dead. Chose to **extend UPDATE to the linked member** (over read-only+force-assume) because the DM deliberately set up a DM-managed assignment — forcing "assume" would deep-copy the character and break that link. Fixed in `20260711000019_party_member_linked_update.sql`: `party_members_player_update` now also allows a member whose OWN `campaign_members.party_member_id` points at the row (`cm.user_id = auth.uid()`), on both `using` and `with check`. Scope is tighter than SELECT (which lets any member see a char *any* member links to) — UPDATE is the caller's own linked char only. Pure RLS fix, no client change (the sheet already issues the mutations). Verified by impersonation in a rolled-back tx: the linked player's HP write lands (`row_count=1`, `current_hp=12`); a different campaign player not linked to that char is blocked (`current_hp` unchanged). Advisor byte-identical to before (no new SECURITY DEFINER surface). Applied to remote. (`supabase/migrations/20260711000019_party_member_linked_update.sql`)

- [x] Player not ejected when removed from a campaign mid-session + membership live-sync never fired (#535, closes it). Two problems: (1) `campaign_members` was **not in the `supabase_realtime` publication at all** (`in_realtime_pub=false`), so the `campaign_members` handler added to `useCampaignLiveSync` in the prior batch never fired — display-name renames and add/remove silently didn't propagate despite the handler existing. (2) No eject: a player the DM removed mid-session kept a dead session whose queries returned empty under RLS, showing blank content instead of redirecting out. Fixed in `20260711000018_realtime_campaign_members.sql` — `alter table campaign_members replica identity full` (so a DELETE payload carries the old row's `user_id`/`campaign_id`, not just the PK) + add it to `supabase_realtime`. Client: new `usePlayerRemovalGuard` (mounted in `PlayerLayout` only — the DM layout must never eject when it removes a player, that's someone else's row) subscribes to `campaign_members` DELETE for the active campaign and, when `payload.old.user_id === auth.user.id`, shows a sticky "You have been removed from {campaign} by the DM" toast, clears the active campaign + localStorage, `refreshMembership()` (re-derives role from any remaining membership — earliest-joined, or none), and routes to `play`/`dashboard`/`login` accordingly. Verified `campaign_members` now shows `replica_identity=full` + `in_pub=true`; `vue-tsc -b` ok. Applied to remote. (`supabase/migrations/20260711000018_realtime_campaign_members.sql`, `src/composables/usePlayerRemovalGuard.ts`, `src/layouts/PlayerLayout.vue`)

- [x] Player-to-player sale never paid the seller + claim was a check-then-write race (#512, critical — money vanished).
