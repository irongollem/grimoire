# Combat: Encounter Builder, Runner & Bestiary

## Overview

The combat features span three interconnected modules: the **Bestiary** (a custom monster compendium), the **Encounter Builder** (pre-combat setup), and the **Encounter Runner** (live combat tracker). Together they form a full DM-facing combat management system with real-time player sync.

Routes:

- `/monsters` — Bestiary list
- `/monsters/:id` — Monster stat block: a modal over the bestiary on tablet and up, a full-screen takeover on phones; `?edit=true` is the full editor at every width
- `/encounters` — Encounter list
- `/encounters/new` — New encounter builder
- `/encounters/:id` — Encounter sheet (read) or editor (`?edit=true`)
- `/encounters/:id/run` — Live runner
- `/play/encounter` — Player encounter panel (player portal)
- `/play/bestiary` — Player bestiary (discovered monsters + wild forms)

## Bestiary (Monster Builder)

### DM View

The Bestiary (`/monsters`) is the DM's custom monster compendium. It is a union of three sources rendered as a single unified list:

1. **Static SRD 5.1 bundle** — built into the client, no network fetch required. ~322 SRD monsters are available immediately on a fresh account.
2. **Open5e imported monsters** — the DM can sync monsters from any Open5e source document (Tome of Beasts, Creature Codex, etc.) via the "Sync from Open5e" button. Source selection is a persistent popover; leaving all sources unchecked imports everything. Deduplication rule: if a DB row exists with the same name as a static SRD entry, the DB row wins, so edits survive re-syncs.
3. **Custom monsters** — created directly in the app.

The shared `library_monsters` table behind the Open5e-sourced content is seeded dual-edition by `npm run seed-library-monsters` — 325 `srd-2014` + 331 `srd-2024` rows (see the SRD seed pipeline note in `items-spells-crafting.md`, #560). Every library row carries a `description` (Tiptap JSON, the lore beside the sheet's stat block; `notes` is "DM Notes" and stays empty on library rows): Open5e v1 lore where the book is open content and Open5e has it, otherwise original text written for Grimoire on 4 Oct 2026, never paraphrased from a book. Library reads never carry it (`LIBRARY_MONSTER_COLUMNS` in `useMonsters.ts`: no list or picker renders it, and 3,541 lore texts are megabytes); `MonsterSheet` reads it for the one creature on screen through `useLibraryMonsterDescription`. It feeds the monster embedding like a homebrew monster's does, and **Customize** fetches it and copies it into the DM's own monster.

**List filters** (stored in `useMonstersUiStore`):

- Text search
- Source: All / Custom / This campaign / each enabled book, a select on desktop and in the phone's filter sheet. Custom is every own monster in scope (general and the active campaign's); This campaign is only the active campaign's own (`campaign_id` = it), for a DM who wants that campaign's creatures without their whole homebrew library (`p_source = 'campaign'` in `browse_monsters`, `20261112145736`)
- Monster type: dropdown covering all 14 standard D&D creature types

The list is also implicitly scoped by campaign (below) — general monsters plus the active campaign's own, with no "show all campaigns" override the way the Item Vault has one (`items-spells-crafting.md`); switching the active campaign changes which custom monsters appear.

**Campaign scope (`campaign_id`, #597).** Custom monsters gained a nullable `campaign_id` (migration `20260809000003`), following the same rule `items`/`species`/`locations` already use: `NULL` means available in every campaign, a set value means visible only while that campaign is active. A `CampaignScopeField` control in the editor ("General — all campaigns" vs "Campaign — _active campaign name_") writes it; new monsters default to the active campaign. Existing rows were deliberately **not** backfilled — a monster's original campaign can't be recovered from the data (no authored-in-campaign timestamp, and an encounter reference only proves where a creature was _used_, not where it belongs), so a wrong guess was judged worse than leaving it visible everywhere until the DM re-scopes it by hand (see the migration's own comment for the full reasoning).

Anything that resolves an **already-stored** monster id rather than letting the DM pick one — an encounter's `combatants[].monster_id`, a quest's `quest_refs`, a companion's source monster, a wildshape form, a loot table's `monster_ids` — resolves through `useMonstersByIds`, which applies no scope filter at all. A scoped-away monster must still resolve wherever it's already referenced, or it silently disappears from a fight or sheet with no error. Pickers (`useMonsterIndex` and the Bestiary's server browse `browse_monsters`: this list, the encounter builder's Combatants/Events search, the quest editor's monster link search, the loot table's monster picker) always stay scoped to general + active campaign.

**Monster creation and editing** (`MonsterDetail.vue`):

Each monster stores a full `stat_block` JSONB object with:

- Basic: name, size, monster_type, alignment, CR, habitat, source, tags
- Scope: the `CampaignScopeField` control described above
- Lair location: optional `lair_location_id` FK to `locations` (migration `20260720000001`, #168) — picked via `EntityCombobox` next to the Habitat field; rendered on `MonsterSheet`/`MonsterSheetMobile` as a nav link to `/locations/:id`. User monsters only; SRD monsters have no FK, and a lair set in another campaign simply doesn't render (the link resolves against the active campaign's location tree)
- Combat: AC, HP (with dice expression), speed, initiative, and (2024 monsters only, #559) `initiative_bonus` — a new key on the `stat_block` JSONB (`MonsterStatBlock.initiative_bonus`; no migration needed since it rides inside the existing JSONB column), editable in `StatBlockEditor` and shown in `StatBlockPanel`. Import maps it only for 2024-ruleset creatures; 2014 creatures and everything else fall back to their DEX modifier.
- Ability scores: STR/DEX/CON/INT/WIS/CHA
- Derived: saving throws, skills, senses, languages
- Ability/save rolling: `StatBlockPanel` wires `AbilityScoreTable`'s `roll-ability`/`roll-save` emits to `usePromptedRoll`, so clicking an ability or save in a monster/NPC sheet rolls it and posts to campaign chat attributed to the creature (`:name` prop). Right-click / long-press opens the advantage-disadvantage picker (`v-roll-mode`). `AbilityScoreTable` only emits — a consumer that renders it without both listeners silently swallows every click (the original bug: tooltips worked on `/monsters/:id`, clicks did nothing); if you add a new consumer, wire both.
- Defenses and structured actions (#1017): `stat_block.defenses` (`Defenses`, `src/types/statBlock.types.ts`) holds resistances, immunities and vulnerabilities as `DamageDefense[]` (damage types plus an optional `unless` of magical, silvered or adamantine, or a `note`), `condition_immunities` as SRD condition names, and `notes` for source text that named neither. It replaces the four old strings. Every action, trait, reaction and legendary entry is a `StatBlockEntry`: its prose `description` stays the display truth, and a `structured` payload (kind, attack, save, options, recharge, uses, multiattack steps, legendary cost) sits beside it for the combat resolver. A structure is only kept if it passes the prose check against the description; one that fails becomes `kind: "other"` with a `review` reason, so the runner offers no roll for it. `source` records who set it: `parsed` (deterministic parser), `extracted` (an agent, backfill only, after the prose check) or `manual` (a DM in the editor, never overwritten by the parser). Nothing parses prose at render time any more: `StatBlockPanel`, the cards and Scriptorium format `defenses` with `formatDefenseList` / `formatConditionImmunities` (`src/rules/statBlock/parseDefenses.ts`), and the card orders entries by `structured.kind` and `structured.recharge`. An `options` entry ("uses one of the following breath weapons") holds one attack or save per choice; recharge, uses and legendary cost stay on the entry. A save that imposes conditions may also say what ends each of them (#1050, per condition since #1055): `save.conditions` is a list of `{ name, ends? }`, each `ends` an `AppliedCondition.ends` as authored, read from the prose by `src/rules/statBlock/parseEnds.ts` and held to it by the same prose check. "Can repeat the saving throw at the end of each of its turns, ending the effect" is save ends; a stated minute beside it becomes the save end's cap (`remaining`: save ends or ten rounds, whichever comes first, counted down like a rounds end); "until the end of its next turn" is the bearer's turn and "until the end of the cloaker's next turn" the source's; "for 1 minute" is ten rounds, an hour or longer is left to the DM. A repeat that names a condition ("ending the restrained condition on itself") ends only that one, so the Alp's Frightened keeps its minute while Restrained is save ends; one that says "the effect" ends every condition no named repeat claims. Each condition otherwise takes its own stated duration ("poisoned for 1 minute and knocked prone" ends the poison and leaves prone to the DM), and a progressive save ("must repeat the saving throw at the end of its next turn", "Second Failure") gives none an end. A save-ends repeat of the same save names only its edge, and takes the save's ability and DC when applied, so editing the DC cannot leave a stale copy; a repeat that is another save ("can make a DC 15 Constitution saving throw" after a Dexterity save) carries its own. The roll editor sets it per condition under the save's conditions (with a "Max rounds" cap on a save end), and the "Rolls as" line says it. Writers produce prose and code structures it: the editor (`StatBlockEntrySection`, with a "Rolls as" line and a manual override), Open5e import and seed (which keep `extracted` and `manual` structures across a re-seed, and put back the "(Costs N Actions)" Open5e strips from SRD legendary names), document import, the AI monster generator and the MCP `create`/`update` tools (server side, through the same `src/rules/statBlock/` modules, which is why they use relative `.ts` imports). The library's unreadable remainder was extracted by agents and lives in `scripts/stat-blocks/library-extracted-actions.json`, keyed by row, list, index, name and a hash of the prose, so a changed description makes its extraction stale rather than wrong. A write guard on all five stat-block tables (`private.guard_stat_block_shape`, `20261010004946`) keeps the stored shape structured: old defense prose is refused ("reload the app"), because only the app's parser can structure it, empty old strings are dropped, a missing `defenses` is filled in empty, an entry without `structured` is kept as prose with nothing to roll (`kind: "other"`) until the editor re-parses it, and a save in the pre-#1055 shape (names plus one `ends`) is given that end per condition (`20261013141635`). The guard is not a definer, so its `private` helpers keep their EXECUTE grant: revoking it fails every DM's save, which `stat_block_shape_guard.test.sql` checks by writing as a signed-in user. `npm run stat-blocks:structure` converts existing rows (`--check` by default; a production write needs `--write --production --yes-production`).
- Trait sections: Traits, Actions, Bonus Actions, Reactions, Legendary Actions, Lair Actions, Mythic Actions
- Spellcasting block (spell list per level)
- Portrait image with focal point (for `FocalImage` focal-aware display)
- A second image, the **cutout** (`cutout_url`, #917): the creature alone on a transparent background, which Scriptorium books prefer. Edited on a Picture / Cutout tab over the same image block (`useArtTabs`); the Cutout tab has no focal point or Mini button, and warns when an upload has no transparent pixels. Every other surface shows the picture. Library monsters carry it on `library_monster_art` / `_canonical`, merged per field, so an override of one image keeps the other's canonical art.
- **Generating the cutout from the picture (#917 story 5).** The Cutout tab's "Cut out from picture" button (`EntityImageBlock`'s `cutoutFrom` prop, hidden for shared/library monsters) is not the general "Generate with AI" flow — it sends the monster's _existing_ `image_url` to the `generate-cutout` edge function, which passes it to OpenAI's image-edit endpoint (`background: "transparent"`, `boostStyle: false`) asking for the same figure with everything else removed, so the cutout always matches the picture rather than being reimagined from a text prompt. OpenAI only (Gemini has no `background` parameter) and platform-keys-only like Simulacrum — no BYOK discount. Priced as `entity_cutout` (50 credits before multipliers) in `ai_generation_credit_costs`. Client: `src/ai/useCutoutGeneration.ts`; logged to the Gallery under the `monster_cutout`/`npc_cutout` kinds (`useImageGenerationLog.ts`), targeting `cutout_url` rather than the kind's default column.
- Deleting a monster (or an item, trap or location) removes its image files only when nothing else still uses them (`deleteUnreferencedByPublicUrl`, `src/lib/storage/deleteUnreferenced.ts`): duplicates, campaign copies, promoted NPCs, library clones and Gallery entries share files.

**Copying to another campaign (#598).** Re-scoping _moves_ the row; copying makes a second, independent one in a campaign the account DMs, reachable from the Select surface's bar and from the detail editor's own actions. The rules — which cross-entity references travel, which are dropped and named, which are reported rather than dropped, and why the copy neither suffixes its name nor navigates afterwards — are written once in `items-spells-crafting.md` ("Copying to another campaign"). Monster-specific notes: `lair_location_id` is cleared when the lair belongs to a campaign the target cannot see; the copy is queued for embedding like any new monster; and `monsters` is one of only two of the eight tables carrying `enforce_quota`, so an over-limit copy opens the editor's existing paywall. The action sits beside Duplicate on the desktop action bar and in `MonsterEditMobile`'s overflow sheet — both, deliberately, so the two surfaces of one editor cannot drift apart.

### DM notes on monsters and encounters

Your own monsters carry the always-open, autosaving `DmNoteBox` (`monsters.notes`) on their page; library monsters have none. An encounter's note is the DM's private `entity_notes` row, on the encounter's detail page and on the run screen (`EncounterRunner`), so a note can be jotted mid-fight and read in the docked scratchpad. See [dm-notes.md](dm-notes.md).

### Reading one monster (`/monsters/:id`)

The same arrangement as the NPC tracker, built on the same components — read that section of `npcs.md` for the reasoning; only what differs is repeated here.

`/monsters/:id` is a **child route of `/monsters`**, so on tablet and up `MonstersView` stays mounted and `MonsterDetailModal` opens over the bestiary grid, leaving scroll position and the revealed page of the infinite scroll untouched. `?edit=true` keeps the full page at every width, and phones keep the `MonsterSheetMobile` takeover. `useDetailModal("/monsters")` decides, and both `MonstersView` (`showList`) and `MonsterDetailView` (`asModal`) ask it.

Two things differ from NPCs:

- **Portrait | stat block | lore, then the moves.** `MonsterSheet`'s top row puts the description beside the stat block, where it is read first and keeps a readable measure; on Vellum it opens with the drop-cap initial (`.lore`). Below that, each `TraitList` / `SpellcastingList` block is its own box in the stat block panel's border, packed in two CSS columns so a long traits box leaves no hole. Trait prose is `text-body` (the theme's reading face), never `font-stat`: it is read beside the lore, and two faces for two kinds of prose was the bug. A plain-text trait's newlines are paragraphs; a rich-text one runs its first paragraph in after the name. Both boxes are shared with the NPC combat tab and the phone sheets.
- **The body scrolls, not the sheet.** `MonsterSheet` flows as one column rather than managing a fixed portrait beside a scrolling pane, so the modal is used _without_ `contained` and `EntityDetailModal`'s body owns the scrolling. `NpcSheet` is the other case. The portrait's cap is `max-h-112` rather than a `vh` measurement for the same reason — see the comment in `MonsterSheet.vue`.
- **The picture keeps its 2:3 shape on a wide screen (#1193).** From `lg` the portrait is a 16rem column (18rem at `xl`) holding the whole painting, not a narrow column stretched to the stat block's height, which used to crop it to a strip so a laptop showed less of the monster than a phone. The modal is `EntityDetailModal size="2xl"` (`max-w-6xl`) so the stat block and lore keep their measure beside it; the admin art preview uses the same size for a monster. On a phone, tapping the hero of `EntitySheetMobile` (monster, NPC and spell sheets alike) opens the picture full size, as their desktop sheets already did.
- **A monster may be a shared library row.** `MonsterDetailModal` folds the DM's `library_monster_art` override in over the canonical `image_url`, exactly as `MonsterDetailView` does for the page — the sheet takes a finished monster and does not know the art tables exist. `useResolvedMonster` is seeded from whichever bestiary cache already holds the row (library by prefix, then the DM's own), normalised the same way the fetch normalises it, so the modal opens populated instead of spinning over a card that is already on screen behind it.
- **An admin's art edit on a library monster is the library's art (#965).** For any other DM, picture, cutout and focal-point edits on a shared row are a personal override in `library_monster_art`. For the app admin they write `library_monster_art_canonical` and the `library_monsters` row for every id showing the same picture (editions and other publishers' copies share one picture since #955), and clear the admin's own override fields so nothing shadows them (`writeCanonicalLibraryArt`). An admin's upload on a shared row goes under `monster-images/srd/`. There is no separate "publish my art" step. The monster grids merge the same layers the detail view does (`withLibraryArtAll`), so an override shows on the card as well as in the modal.

Saving an existing monster returns to the bare `/monsters` list at every width. Desktop used to land on `/monsters/:id` (the bestiary with the saved stat block open over it), which reopened the sheet the DM had come from and read as being sent back into the record; see the Sanctioned Exceptions entry in `CLAUDE.md` before changing it back.

**Template presets** — `src/data/monsterTemplates.ts` ships 12 SRD stat block presets (e.g. Goblin, Dragon, Lich) that pre-populate the form.

**AI monster generator** — `MonsterGeneratorPanel.vue` is accessible from the Bestiary toolbar ("Generate" button) and creates a stat block from a text prompt.

**Read-only sheet view** (`MonsterSheet.vue`) is shown by default when navigating to an existing monster; the Edit button switches to the editable form (`MonsterDetail.vue`). The URL query `?edit=true` also activates the editor directly.

**Visibility / discovery system** — the DM can share individual monsters with specific players or the whole party, through `MonsterRevealControl` (#741). It is the app's one reveal control, mounted on the bestiary list card (`overlay` form), the detail header, and the mobile app bar and action bar — before this, the only monster reveal that offered a stat-block gate was on a phone.

- **Who** — per-party-member toggles plus a "Whole party" shortcut, and "Hide from all players" to revoke
- **What** — "Full stat block": off, the player sees name, art and CR only

Monsters are the **second storage model**: there is no `player_visible_to` column but a `discovered_monsters` row, whose absence means "not discovered" and whose `visible_to === null` means "everyone". `useMonsterVisibility` already exposed exactly the four `RevealAdapter` operations, so it satisfies the interface as-is and the control never learns which model it is talking to (see `src/lib/reveal.ts`).

This powers the player bestiary (see Player View below).

### Player View

Players see only monsters the DM has shared with them, via their Bestiary tab at `/play/bestiary`. This view is deliberately **not** filtered by the campaign scope above: the player projection reads (`fetchPlayerVisibleMonsters`) skip it on both branches (SRD and custom), because the `get_player_visible_monsters` projection it queries is already gated on this campaign's `discovered_monsters` — a row reaching a player is one the DM revealed here, and re-filtering it by `campaign_id` would only risk hiding a creature the party has already met. The projection returns `campaign_id` as `null` regardless of the row's real scope, the same way it nulls `lair_location_id` — DM-side library organisation with no player-facing meaning, and passing it through would hand a player the uuid of a campaign they are not in whenever a creature discovered here happens to be scoped elsewhere. Note that widening `monsters` at all requires recreating this projection in the same migration: it is `returns setof monsters` with a positional column list, validated only when it executes, so a forgotten recreate breaks every player read rather than the deploy (see `player_projections.test.sql`, which executes all six projections in CI for exactly this reason).

**Bestiary tab:**

- Grid of monster cards (`MonsterFormCard.vue`) — one card per discovered creature
- Each card shows name, image, type, CR color badge
- Clicking opens a lightbox with:
  - Focal-aware portrait
  - Name, size/type/alignment
  - If `reveal_stats` is true: AC, HP, Speed, full ability score table, trait sections (with inline roll buttons for attack and damage)
  - Player notes widget (personal annotations about the creature, stored per-player)
- Searchable with debounced input
- Hidden combatants are filtered server-side; the player never sees them

**Wild Forms tab** (Druids and Rangers only — class detection is automatic):

- Shows "Pinned by DM" and "Eligible Forms" sections
- Eligible forms are beasts from discovered monsters that meet the druid's CR and speed-type constraints (calculated from level and Circle of Moon subclass)
- DM preview mode shows an "unshared eligible beasts" banner with a batch-share button
- Pinned forms are stored via `usePinnedForms` / `useTogglePinnedForm`
- Lightbox shows full stat block and roll buttons; also works as a wildshape picker for the runner

## Encounter Builder

The builder (`EncounterDetail.vue`) is the pre-combat setup form. It has two modes: a full edit form and a read-only sheet (`EncounterSheet.vue`). The URL query `?edit=true` switches to the editor; the sheet also has an inline Edit button.

### Encounter metadata

- **Name** and **Rich text description** (Tiptap, scene-setting notes, terrain, objectives)
- **Location** — optional link to a campaign location (EntityCombobox)
- **Quest link** — assignable to a quest for filtering in the encounter list

### Party Members and Companions

- Checkbox selection of party members from the Party Tracker
- Companions are shown in a separate subsection. A **pet** (a companion type, #1115) is left out of the roster entirely, the auto-select, the generator, the difficulty calculation and the lobby: it ignores combat and nobody commands it. `buildRunCombatants` and the runner's lobby watch also skip a pet even if a stale row says ready; the database refuses a ready pet (`companions_pet_never_fights`)
- New encounters auto-select **all** party members and companions by default (`EncounterDetail.vue` watches `party`/`companions` once on load); the DM unchecks anyone not present rather than building the roster from scratch. Companion auto-select is #569 — a companion's `combat_ready` flag (see Data Model / Runner below) plays no part in the builder, it's a runtime-only gate applied at combat start
- Each selected member/companion gets a faction assignment dropdown (colour-coded by faction colour)
- Player initiative starts blank each encounter (no longer pre-seeded from `party_members.current_initiative`, which carried stale values between fights — see #504). The stored value is also cleared when the encounter goes live, ends or is abandoned, and the runner ingests rolls only while the encounter is live (#973: a last-week roll used to come in on the first resync). Players roll their own from the player encounter panel; the runner ingests the value live via its `party_members` subscription. One residual case is knowingly accepted: DM closes the runner mid-live, a player rolls, DM reopens. Fixing it properly needs encounter-scoped initiative, which #504's fresh-roll design deliberately avoided — so it is left open rather than reintroducing the stale-seed behaviour that made #504 necessary in the first place. The DM's "Roll Initiative" still fills in anyone who hasn't rolled (it skips **every** combatant that already has a value, not just players)

### Combatants (`EncounterCombatants.vue`)

The enemy/ally/neutral roster. Each combatant definition (`CombatantDef`) stores:

- Monster or NPC reference (mutually exclusive)
- Count (how many instances to spawn)
- Faction assignment
- Optional custom name (overrides the source name in the runner)

Multiple combatant slots can point to the same monster with different counts or factions.

The monster-search picker here (and in the Events panel's spawn action) is scoped to general + the active campaign (`pickableMonsters`, #597). `EncounterDetail.vue` separately loads an unscoped `monsters` list (`includeAllScopes: true`) for naming/rendering combatants already on the roster, so a monster the DM later re-scopes to another campaign still shows its real name and CR here instead of "Unknown".

### Factions (`EncounterFactions.vue`)

Encounters ship with four default factions:

| ID        | Name    | Default colour | Hostile to        |
| --------- | ------- | -------------- | ----------------- |
| `players` | Players | Navy           | `enemy`           |
| `enemy`   | Enemy   | Dark red       | `players`, `ally` |
| `ally`    | Ally    | Dark green     | `enemy`           |
| `neutral` | Neutral | Dark grey      | _(none)_          |

The DM can add custom factions, each with a name and hex colour. Faction colour appears as a left border stripe on every combatant row in the runner.

### Events (`EncounterEvents.vue`)

Pre-scripted automation that fires automatically or on demand during the run. Each event has:

**Triggers** (one per event):

- `round_start` — fires when the specified round begins
- `combatant_hp_pct` — fires when a specific combatant's HP drops to or below a percentage
- `combatant_dies` — fires when a specific combatant reaches 0 HP
- `manual` — never auto-fires; DM clicks ▶ in the runner sidebar

**Actions** (one per event):

- `spawn_combatants` — adds N combatants of a chosen faction, with automatic initiative if combat is already started. Each spawn (`SpawnDef`) carries an optional `kind: "monster" | "npc"` (#604) selecting which roster its id resolves against — absent means `"monster"`, so every event authored before #604 keeps working untouched. The builder's own Add/Edit form only offers a monster picker for this action; an NPC spawn can currently only be produced by the complication generator below, though the summary line for an existing event renders either kind correctly
- `broadcast_message` — posts a system message to the campaign chat
- `environment_effect` — pins a hazard or terrain change (label + description) that stays "in play" for the rest of the fight once fired (#604). Carries no mechanical payload on purpose — no conditions, no damage, no forced movement. Firing it only posts the description to chat; which creatures a collapsing floor actually restrains stays a DM call made with the existing condition picker. Not authorable in the builder form — generator-only, same as an NPC spawn

**Options:**

- `fire_once` — if checked, the event is greyed out after firing and won't repeat
- `is_player_visible` — when set, fired events appear as parchment-style narrative beat callouts in the player's combat panel (`PlayerEncounterPanel`). If the event has a `broadcast_message` action, that message text is shown prominently; the event name is shown as a smaller label below it. Events appear in the order they were defined and remain visible for the rest of the encounter.

### Mid-fight Complication / Reinforcement Generator (#604)

Mid-fight, a DM can ask for one of two things without leaving the runner: a **complication** — something that changes the shape of the fight without just adding more HP to grind through — or **reinforcements** — pressure to restore when the party is winning too easily. Both are proposals, never applied automatically: the whole point of this feature is that nothing happens in the fight the DM did not explicitly approve — the model is never asked for a trigger, the client never reads one from it, and a generated proposal only joins the encounter as an unfired event the DM still has to press ▶ on.

**One edge function, two modes.** `supabase/functions/generate-complication/index.ts` picks between the `complication` and `complication_reinforcements` rows in `ai_system_prompts` by the `mode` the client sends. Two rows rather than one prompt with a mode switch, so an admin tuning the reinforcement wording can't break complications by accident (seeded in migration `20260805000004_complication_generator_ai.sql`, alongside the `complication_generation` credit cost — 1 credit for either mode, sharing the `ai_generation` rate-limit bucket rather than a higher per-press price, because a DM pressing the button several times hunting for a complication they like is expected use, not abuse). Server-path only, like `generate-loot` — the candidate blocks below come from service-role reads the browser can't make, and `useComplicationGeneration.ts` throws immediately in local-key mode rather than attempting a weaker client-direct path.

**The fight, as sent by the client.** Rather than reading `encounter_state` server-side, the edge function takes an `EncounterSnapshot` (name, round, faction names, and up to 30 combatants as name/side/HP%) built by `useComplicationGeneration.buildSnapshot()` from the live `useEncounterRunStore`. This is deliberate: the store is the live truth, while the DB row lags behind it by up to the 300ms `useEncounterLive` debounce, and a DM who hasn't gone live yet has no row at all. Trusting the client here costs nothing — it's the DM's own encounter, the snapshot grants no privilege, and it only flavors a proposal the DM must still approve. HP is sent as a rounded percentage rather than exact numbers: the model needs "badly hurt" vs. "untouched," not DM-side bookkeeping detail.

**Grounding.** One embedding query — the DM's typed steer if they gave one, else the encounter name plus up to 10 combatants' names, else the literal string "a mid-combat complication" — feeds both `retrieveCampaignEntities` (npcs/locations/factions, #600) and `retrieveMonsterCandidates` (bestiary, #595) in parallel, in one try/catch: a proposal with real NPCs but hallucinated creatures is a worse failure than a fully ungrounded one, so retrieval failing degrades both corpora together rather than one silently. Reinforcements lean harder on the bestiary than complications do (`MONSTERS_PER_SIDE`: 12/side vs. 6/side), since a complication is as likely to be a hostage or a collapsing exit as a creature.

**Bestiary retrieval, shared.** `retrieveMonsterCandidates` moved out of `generate-encounter` into `supabase/functions/_shared/monsterRetrieval.ts` when this generator became its second consumer — the alternative was a second copy of the custom/library merge-and-dedupe that would have drifted the first time either the tie-break or the unembedded window changed. `generate-encounter`'s compact-index fallback (a name-ordered slice of the whole bestiary used when retrieval is unavailable) deliberately did _not_ move: encounter _building_ must always offer some creatures, but a mid-fight complication has no such duty — if retrieval is down it just generates narration with no creature candidates.

**Resolution (`src/ai/resolveGeneratedComplication.ts`).** The model returns creature _names_, not ids. Each name is checked against the runner's own loaded rosters (`store.availableMonsters` first, then `store.availableNpcs` — a name in both is almost always a homebrew stat block written for that NPC, and combat needs the stat block); an unmatched name is never dropped or turned into a stub — it comes back as `{ kind: "unmatched", name, reason }` so the preview can show the DM exactly what the model asked for and why it can't land. `side` resolves against the encounter's _own_ factions (never trusted as an id from the model) by name or id, falling back to the `enemy` faction when unspecified or unrecognised. Every count is clamped to 8 per entry and every proposal to 6 entries (`MAX_COUNT_PER_ENTRY` / `MAX_REINFORCEMENT_ENTRIES`) regardless of what the model asked for, and anything the clamp or the resolution silently changed is surfaced in a `warnings[]` list rather than just quietly happening — a proposal that lost half its content on the way through must not look complete.

**The event this becomes.** `buildComplicationEvent()` always produces `trigger: { type: "manual" }` and `fire_once: true`. `checkEvents()` only auto-fires non-manual triggers, so a generated event physically cannot go off on a round boundary while the DM is still deciding about it — it can only fire from the ▶ button, exactly like a hand-authored manual event. Confirming a proposal calls `store.addGeneratedEvent()`, which pushes the event onto `store.events` **unfired**, identical to a hand-authored one.

**Store support for what the event carries.** `spawnFromDef()` now branches on `SpawnDef.kind`: absent (every pre-#604 event) means monster, `"npc"` calls `addNpc()` instead. `executeEvent()` handles the new `environment_effect` action by posting its label + description to the pending-broadcast queue, the same path `broadcast_message` uses. `activeEnvironmentEffects` is a computed derived from `eventsFired` ∩ each fired event's `environment_effect` actions — no new persisted field, so there is nothing extra to add to live-sync: the hazard list falls out of state (`events`, `eventsFired`) that already syncs.

**DM-facing surface.** The **Twist** menu in the runner's top bar (`RunnerGenerateMenu.vue`) and two entries in the phone header's overflow menu open `ComplicationGeneratorDialog.vue` in the matching mode; `EncounterRunner` owns the dialog for both. They used to be two buttons heading the EVENTS column, which then had to render for every fight so the buttons stayed reachable in the common case of an encounter with no scripted events; that cost every fight a 200px column (30 Oct 2026), so the generators moved to where a run's other actions live and the events strip draws only what the encounter has. The dialog is a preview-then-confirm gate, and that gate is the feature's whole safety story: it shows the narration, every resolved reinforcement with its side, the hazard, every `warnings[]` line, and the unmatched names struck through — and only on **Add to Events** does anything reach the encounter. Regenerate and Discard cost nothing but a credit.

### Boss Mechanics

A dedicated card in the builder for boss-fight features:

- **Lair Actions** — a checkbox enables lair action support for this encounter. When enabled, the DM picks a "lair owner" from the encounter's combatant list. In the runner, a persistent panel appears at initiative 20 each round listing the owner's lair actions (sourced directly from their stat block `lair_actions` array). Clicking one marks it as fired for that round and posts a chat message.
- **Legendary Actions** — enabled automatically on any combatant whose monster stat block has a `legendary_actions` array. No builder toggle needed. The runner primes a pool of 3 actions (5e default). The pool resets at the start of that combatant's turn.

### Loot (`EncounterLoot.vue`)

Pre-planned loot attached to the encounter:

- Linked vault items (with quantity controls, drop-to-chat button)
- Currency pools (gold/silver/copper amounts)

There is no art-object control here. Art objects are vault items (`item_type = 'art_object'`, commit `183ec567`) placed through the encounter's `item_ids` like any other loot; the encounter-level `art_objects` column that the old inline editor wrote was dropped in `20260924210351` (#909).

### Traps (`EncounterTraps.vue`)

A list of trap references (from the Traps module — see dungeon-craft.md). Each trap shows in the runner's DM Tools sidebar. Clicking a trap in the sidebar opens its detail panel so the DM can reference trigger, save DC, and damage expressions mid-combat.

Traps gained the same `campaign_id` scope as monsters (#597, dungeon-craft.md's Traps section). The trap-search picker here (`pickableTraps`) is scoped to general + the active campaign; the encounter's already-linked `trap_ids` resolve against an unscoped `allTraps` list so a trap re-scoped to another campaign later doesn't drop out of an encounter that already references it.

### Difficulty Analysis (`EncounterDifficulty.vue`)

Shown on the read-only encounter sheet, computed live in the editor, and used for the difficulty colour and label on each row of the Encounters list. All three call one pure function, `encounterDifficulty()` in `src/lib/encounters/difficulty.ts` (lookups built by `difficultyLookups()`). Until 25 Sep 2026 the list worked it out separately: every player counted as level 3, and NPC enemies, allies, companions and traps were left out, so an encounter against a level 6 party read Deadly in the list and Easy on its own page. Implements the 5e DMG XP budget system:

- Raw XP summed from all enemy CRs
- Count multiplier applied (1× to 4× based on number of monsters)
- Party size adjustment: < 3 players bumps the multiplier tier up; > 5 bumps it down
- Ally offset: ally XP subtracted (with its own multiplier) from net XP
- Trap/hazard XP added flat
- Net XP compared against per-level thresholds for each party member
- Labels: Trivial / Easy / Medium / Hard / Deadly / Legendary
- Threshold bar visualisation with a net-XP marker dot
- Enemy breakdown list: name, CR, XP per entry

### AI Encounter Generator

The "Generate" button on the Encounters list (`EncountersView.vue`) opens a right-side slide-in panel (`EncounterGeneratorPanel.vue`, mounted in `AiGeneratorPanels.vue`, toggled via `ui.encounterGeneratorOpen`) — the same pattern as every other AI generator panel in the app. The DM provides:

- **Concept** — a free-text prompt (e.g. "Goblin ambush on the forest road, levels 3–5, a betrayal mid-fight")
- **Difficulty** — Auto / Easy / Medium / Hard / Deadly

Generation is dual-path like the other generators (`useEncounterGeneration.ts`): by default it calls the `generate-encounter` edge function; in local-vault BYOK mode (`grimoire_key_local_mode === "local"` in `localStorage`) it calls the model directly from the browser instead.

**Server-side context building.** Rather than trusting a context payload from the request body, the edge function builds the model's context itself from the campaign's own data and passes it as constraints alongside the difficulty:

- **Party summary** — one line per party member, e.g. "Level 5 Fighter/Rogue". Multiclass characters use the sum of `character_classes.levels` (the authoritative level) and their class names joined with "/"; a character with no `character_classes` rows falls back to `party_members.level`/`class`. With no party members at all, the summary is "Party: unknown — assume 4 characters of level 3".
- **Candidate monster block** — the monsters the model is told it may use, one per line as `Name|CR|type`, wrapped in `---BEGIN AVAILABLE MONSTERS---`/`---END AVAILABLE MONSTERS---` markers and included only when at least one row exists. The system prompt instructs the model to prefer the DM's own creations by exact name when one fits thematically, and to use the exact name shown since resolution is by name. As of #595 this block is normally populated by semantic retrieval rather than a flat dump of the bestiary — see below. It falls back to the pre-#595 compact index — the campaign owner's own homebrew that's either scoped to this campaign or left global (`campaign_id`, #597), filtered further by the campaign's ruleset and excluding Open5e-imported rows (the model already knows standard 5e monsters), capped at 200 rows via `MAX_CUSTOM_MONSTERS` — whenever retrieval is unavailable for any reason.

**Monster retrieval (#595).** Before #595 the candidate block _was_ the compact index above, and it only ever reached the DM's own homebrew — the model had no reliable way to reach the shared `library_monsters` table. That table holds 3,541 rows, but only 656 are WotC SRD; the other ~2,885 come from Kobold Press, EN Publishing and eight more sources the model may know as concepts from training but not by exact name — and resolution is by name (see below), so those ~2,885 were effectively invisible to the generator. #595 replaces the paste-the-whole-index approach with retrieval: the edge function embeds the DM's flavor prompt with the platform's embedding provider, then calls two `SECURITY INVOKER` nearest-neighbour RPCs — `match_custom_monsters` and `match_library_monsters` (`supabase/migrations/20260803000001_rag_monster_embeddings.sql`) — each returning up to 15 rows (`RETRIEVAL_PER_SIDE`), and unions the two into the same `Name|CR|type` candidate block described above. The result is typically _smaller_ than the old pasted index and, unlike the old 200-row cap, does not scale with how much homebrew the DM has written.

**Campaign-aware since #597.** `match_custom_monsters` takes `p_campaign_id` alongside `p_owner_id` and its `WHERE` mirrors `match_custom_items`' shape (`20260805000005`), verbatim: campaign rows plus the campaign owner's global (null-campaign) rows — a DM's homebrew is only retrieved when it's scoped to the requesting campaign or left global. Before this, retrieval filtered on ownership alone, so a monster the DM scoped to a _different_ campaign of theirs could still surface as a suggestion here — a subtle failure, since the suggestion looks perfectly good. `retrieveMonsterCandidates` (`MonsterRetrievalArgs.campaignId`) threads the id through from both callers (`generate-encounter` and the complication generator), and the unembedded-append query in `monsterRetrieval.ts` applies the same `campaign_id` predicate, or a DM's newest homebrew could bypass the gate entirely on its way through that fallback path.

**Name repair (#1061).** The client resolves a combatant by exact name, so a near miss ("Skeletal Archers", "Dire Wolf Alpha") used to reach the DM as unmatched. After the model answers, `generate-encounter` puts each combatant name that is not exactly one of the creatures the prompt offered to a small judgment model (TypeSafe's Jev, `supabase/functions/_shared/nameRepair.ts`) as a pick-one over the closest offered names plus "none of these", and rewrites the name to the offered row's exact name when the pick has at least 0.7 probability. `generate-complication` does the same for reinforcement names against the creatures and NPCs it offered. It runs only when a `typesafe` platform key exists, costs the user nothing, and is recorded once per generation as a delta-0 `entity_judgment` row. It never invents a row: it only maps a near miss onto a name the prompt offered, and any failure, cap or timeout leaves the name as the model wrote it. Live check on 15 Nov 2026 with 14 invented output names against 15 offered monsters: 13 right, no wrong repair ("Skeletal Archers" to Skeleton Archer, "The Lurker in the Mine" to Mine Lurker, "Rat Swarm" to Swarm of Rats; "Hobgoblin Warlord", "Owlbear" and "Wight" left alone). The one miss left "Cultist" unrepaired when "Cult Fanatic" was meant, which is the safe side.

**Getting the corpus embedded in the first place.** `supabase/functions/embed-monsters/index.ts` is the endpoint that actually writes embeddings, in two modes: `mode: "batch"` (admin-only, driven in bounded pages of 100 rows per call by `useEmbeddingBackfill.ts` — see Switching vendor below; each page is stored twenty rows per statement by `_shared/embeddingUpsert.ts`, because an update into a full HNSW index blew PostgREST's eight-second statement timeout at 100) and `mode: "single"` (fire-and-forget after any monster create/update, via `queueMonsterEmbedding()` in `src/composables/monsters/useMonsters.ts`, so a DM's save never waits on an embedding call to finish; and **awaited**, not fired-and-forgotten, after a `create`/`update` through the MCP server — `queueEmbedding()` in `_shared/mcp/tools.ts`, driven by each entity's `embedOnWrite` in the MCP registry, because an edge isolate may be torn down the moment it returns and would drop an unawaited request, leaving a hook that looks wired and does nothing). Both build the embedded text from one shared function, `buildMonsterEmbedText()` (`supabase/functions/_shared/monsterEmbedText.ts` — name, then size/type/CR, then tags, then habitat, then a word-boundary-truncated description, each clause omitted rather than left dangling when its source field is empty), so `monsters` and `library_monsters` rows land in the same region of the embedding space and stay comparable. A SHA-256 hash of that text (`monsterEmbedHash()`) is stored as each row's `source_hash`; a row whose hash and `embedding_model` are unchanged is skipped, so an edit that didn't touch anything semantically relevant costs no provider call.

Custom and library monsters get a **guaranteed 15-row share each** rather than one merged top-30 ranking — with 3,541 library rows in play, a single ranking would crowd out the DM's ~98 homebrew monsters almost every time, making the feature worst at exactly the thing it should be best at: surfacing the DM's own creations.

The **enabled-sources gate** (`campaign_enabled_sources`) is applied inside `match_library_monsters`'s `WHERE` clause, before the similarity ordering runs — never as a filter on the already-ranked top-K. Filtering after ranking would silently shrink (potentially to zero) the candidate set for a DM who has enabled few sources, and surfacing a disabled source's content into a campaign is the exact licensing mistake #567 and #583 fixed. When a campaign has enabled no sources at all, the library query is skipped entirely rather than called with an empty array.

**Graceful degradation is the whole design.** No embedding vendor enabled, more than one enabled, a missing platform key, an embedding API failure, an RPC error, or nothing matching — every one of these is caught by a single try/catch around the retrieval block and falls back to the pre-#595 compact index; retrieval can only cost recall, never take the feature down. The **truncation note** ("this is the first N of M custom monsters…") is only ever emitted on that fallback path — a relevance-ranked retrieval set is not a partial alphabetical slice, so telling the model it's "incomplete" would be misleading there.

A custom monster with no embedding row cannot be returned by `match_custom_monsters` — that's exactly the DM's newest homebrew, made during a backfill window or before embed-on-write has run for it. Those are appended to the candidate block explicitly (capped at 25, `MAX_UNEMBEDDED_APPEND`) and de-duplicated by name against the retrieved set, so a DM's latest creation never silently vanishes from suggestions.

**Vendor-agnostic, but platform-wide — never per-campaign or BYOK.** Embedding vectors from different models are not comparable — cosine distance between an OpenAI vector and a Gemini vector is meaningless — so exactly one embedding vendor can be active at a time, for the whole platform, configured in `provider_config.embedding_model` / `embedding_enabled`. Of the three vendors the app integrates, only OpenAI and Gemini have an embeddings endpoint at all (Anthropic has none). Three separate guards enforce "exactly one": the `embedding_model` column plus a same-model predicate in both RPCs (`p_embedding_model`, so a query never compares vectors across models); a partial unique index (`provider_config_single_embedding_vendor`, on `(true) where embedding_enabled`) that turns two enabled vendors into a constraint violation rather than a silent bug; and `resolveEmbeddingProvider()` (`supabase/functions/_shared/embeddings.ts`) throwing an `EmbeddingProviderConfigError` if zero or more than one row comes back enabled, rather than picking one arbitrarily.

**Switching vendor is one admin action.** `set_embedding_provider()` — a `SECURITY INVOKER` RPC, since `provider_config`'s own RLS already gates writes on `app_metadata.role = 'admin'` — flips `embedding_enabled`/`embedding_model` atomically in a single `UPDATE`, so the invalid two-enabled state can't exist even transiently. `EmbeddingVendorControl.vue` (admin panel) calls it and then immediately runs the backfill (`useEmbeddingBackfill.ts`, shared with the standalone "Re-embed" button in `MonsterEmbeddingBackfill.vue`; since #600 the same driver also sweeps the npc/faction/location/note embeddings and both item corpora via `embed-content` — eight targets in one run, see world-building.md and dungeon-craft.md) to completion. A model-only change (e.g. `text-embedding-3-small` → `text-embedding-3-large`) needs exactly the same re-embed, for the same reason — the resulting vectors are just as incomparable to the old ones, so there is no special-casing for "same vendor, different model." While re-embedding is in progress, rows still keyed to the old model are simply not eligible for `match_*` (their `embedding_model` no longer matches the configured one) and fall back to the compact index — degraded, not broken.

**Cost and tracking.** Embedding the whole ~3,541-row corpus once against `text-embedding-3-small` ($0.02 / million input tokens, per `ai_model_pricing`) costs on the order of $0.011; a single per-generation query embedding (one short prompt) costs on the order of $0.0000006. Both are recorded via `recordFreeGeneration()` — a `delta: 0` row in `ai_credit_ledger` with `is_byok: false`, because the platform key paid for the call, not the user — so the spend is visible in cost reporting without charging anyone. `ai_generation_credit_costs` seeds the same story explicitly (`monster_embedding`, 0 credits), and `ai_model_pricing` carries rows for `text-embedding-3-small`, `text-embedding-3-large`, and `gemini-embedding-001` so a vendor flip always has pricing ready. All of this is separate from the encounter generation's own cost, which is unchanged — still 1 credit, see Credit cost below.

**Side tables, not columns.** Embeddings live in `library_monster_embeddings` / `monster_embeddings`, keyed on `library_monster_id`/`monster_id` with `on delete cascade`, rather than as a `vector(1536)` column on `library_monsters`/`monsters` directly. Two call sites would have regressed if it were a column: a `select("*")` over `library_monsters` would carry a ~6 KB vector per row, roughly 21 MB across 3,541 library rows, into every full-row read; and `get_player_visible_monsters` returns `SETOF monsters` — a new column there would silently start shipping raw embedding vectors to players through a projection that exists specifically to strip DM-only data.

**Where the enabled-sources gate is actually tested.** `supabase/tests/monster_retrieval.test.sql` (pgTAP, runs in CI's `database` job) plants a hermetic `t595-*` fixture and asserts the gate is a `WHERE` predicate applied _before_ the similarity ranking. The fixture's shape is the point: a post-filter implementation does not leak disabled rows, it drops them too — just after they have already consumed the top-K. So the disabled source gets **three** rows at distance 0 and the query asks for `match_count = 2`; filter-first returns the distant enabled monster, filter-after returns nothing at all. The same file covers the ruleset and `embedding_model` gates, concept dedup happening before the limit, the `on delete cascade`, and `match_custom_monsters` owner _and_ campaign scoping (#597) — including the case that pins down campaign scope is doing real work: two campaigns owned by the same DM, where a monster scoped to the _other_ one is excluded, so the exclusion can't be explained by the ownership check alone. The caller-side half — which slugs are passed, that the library RPC is **not called at all** when a campaign has enabled nothing, the homebrew-first merge order, and that a failed `campaign_enabled_sources` read throws rather than being read as "no sources" — is in `supabase/functions/_shared/monsterRetrieval.test.ts`, because those are properties of the TypeScript, not of the query plan.

**pgvector lives in `extensions`, and the RPCs' `search_path` must say so.** `20260803000001` originally created the extension in `public`; `20260805000006` relocated it to clear the security advisor's `extension_in_public` finding. That migration had to repin all eight `match_*` RPCs to `SET search_path = public, extensions` in the same change, because a `language sql` body resolves `<=>` against its pinned path at first execution — with `= public` alone it raises `operator does not exist: extensions.vector <=> extensions.vector`. **That failure is invisible:** every generator wraps retrieval in a try/catch that degrades to an ungrounded prompt, so the symptom is not an outage but silently worse output across encounters, loot, complications and note/entity grounding at once. Any new `match_*` RPC must pin `public, extensions` from the start; the migration ends with a `DO` block that aborts the deploy if a pgvector-dependent function in `public` is missing `extensions` from its path.

This is deliberately server-side rather than client-supplied as #337 originally specified: a client-supplied context payload could be inflated to drive up generation cost, or spoofed to steer the model toward monster names that don't actually exist in the DM's bestiary. **The local-key (BYOK) path cannot build any of this** — the party summary, the compact-index fallback, and the #595 retrieval block are all DB reads (and, for retrieval, a platform-embedding-provider call) done with the edge function's service-role access, which the browser doesn't have. It generates from the campaign setting and the difficulty constraint alone; this is a deliberate parity gap, not an oversight.

**Name resolution (`resolveGeneratedCombatants.ts`).** The AI returns monster names, not ids, so the app resolves each against the DM's bestiary (`useMonsterIndex()`, scoped to general + the active campaign since #597 — the same picker rule as the manual builder's Combatants search above) through a three-tier cascade — exact name → case-insensitive → normalized (lowercased, alphanumeric-only, with a single trailing "s" dropped, so "Goblins" matches "Goblin" and "dire-wolf" matches "Direwolf") — stopping at the first tier that produces any candidate. Among tied candidates within that tier, the DM's own homebrew (non-empty `user_id`) is preferred over a same-named shared-library monster. A match becomes a `CombatantDef` with `faction_id: "enemy"` and, when the AI supplied a role, `custom_name` set to `"{Monster Name} ({Role})"`.

**Ambiguous names get a version picker, not silent resolution (#601).** 660 library names exist in more than one sourcebook, each copy with its own stat block (publishers rebalance), so a name can resolve to a different version than the one retrieval showed the model — and the client cannot know which copy the model budgeted against, because `20260803000003`'s concept dedup happens server-side and only `Name|CR|type` reaches the prompt. Decision (of #601's three options): **surface and swap** — `resolveGeneratedCombatants` returns every same-tier candidate alongside each match, and the generator panel shows a per-row `EntityCombobox` (labelled source + CR) whenever there is more than one, so the DM sees which stat block will be used and can swap it before "Create Encounter" (`swapCombatantVersion` rebuilds the def, including the role suffix, around the picked version). The encounter stores the actually-picked `monster_id`, so the builder's XP-budget analysis reflects the real stat block with no further plumbing. Option 1 (the model echoing an opaque id for retrieval-sourced candidates) was deliberately deferred until name/version mismatches demonstrably matter in practice — it complicates the training-knowledge fallback path, which must keep working: a name the model knew but that isn't in the candidate block still resolves by name, and an unmatched name still degrades to "add manually".

`parseEncounterAiResult.ts` is the validation boundary for the raw model response before any of this runs — it drops any combatant entry with no usable name, defaults a missing/invalid `difficulty` to `medium` (the badge is cosmetic; the combatants are what matter), and throws if the combatants array ends up empty, which the panel shows as an error state with no encounter created.

**Unmatched names are not turned into stub combatants.** `EncounterRunView.vue` builds run combatants with `if (entry.monster_id) … else if (entry.npc_id) …` and no `else` branch, so a `CombatantDef` with a null `monster_id` would render fine in the builder but be silently dropped the moment the DM runs the encounter. Unmatched entries are instead listed in the panel under "Not in your Bestiary — add these manually," and folded into the created encounter's description as an "Add manually: …" line alongside the AI's Environment/Tactics/Twist text, so they aren't lost once the panel closes.

**Creating the encounter.** "Create Encounter" persists the result — name, matched combatants, default factions, and every current party member **and companion** auto-selected (companions come along too, matching what `EncounterDetail` does for a hand-built new encounter — "start with the whole party, bench whoever shouldn't join"; they also count as allies in the difficulty calculation, so leaving them out would make the generated encounter read as harder than the identical one built by hand) — and the button becomes "Open Encounter →", which navigates straight into the **editor** (`/encounters/:id?edit=true`), not the read-only sheet. It does not auto-navigate on create; only "Open Encounter →" does. A generated encounter is a draft: the DM still has to review the AI's picks, swap what doesn't fit, and hand-add anything that wasn't in the Bestiary — all edit-mode work, unlike the Roll Table Generator's create-then-"View Table →" link, which points at a view because a generated table is finished on arrival and this isn't.

**Credit cost.** The system prompt is stored in `ai_system_prompts` (`generator_type = 'encounter'`); the credit cost is `encounter_generation` in `ai_generation_credit_costs` (1 credit). Both seeded in migration `20260802000002_encounter_generator_ai.sql`. Cost is multiplied by the active text provider's `text_multiplier`, same as every other text generator. BYOK generations are charged 0 credits but still recorded as a BYOK ledger line through the credit hold (`_shared/pipeline/creditHold.ts`), so generation history stays complete even when nothing was spent. The #595 retrieval step layered on top is separately zero-cost by design — see Monster retrieval above for how its own (platform-paid) spend is still tracked as a free ledger line (`hold.free`).

- `EncounterRunner.vue` — shell: top bar, layout wiring, Go Live, end and abandon as commands to the server (`useFightCommands`)
- `RunnerCombatantList.vue` — the initiative order list (desktop grid rows / mobile cards)
- `RunnerInitiativeField.vue` — initiative input + per-combatant roll button, shared by `RunnerCombatantRow.vue` and `RunnerCombatantCard.vue`. Note the desktop grid template lives in **both** `RunnerCombatantList.vue` (header) and `RunnerCombatantRow.vue` (rows) — they must be changed together or the columns drift apart
- `RunnerEntityDetail.vue` — slide-in stat block panel
- `RunnerDmTools.vue` — events + traps sidebar
- `RunnerBossMechanics.vue` — surprise panel, lair actions, legendary actions
- `RunnerSpawnPanel.vue` — mid-encounter spawn form
- `RunnerSurprisePanel.vue` — the pre-combat Surprise strip (above the list on desktop, in the tools sheet on a phone)
- Phone only: `RunnerPhoneHeader.vue`, `RunnerTurnBar.vue`, `RunnerToolsSheet.vue`, `RunnerCombatantSheet.vue` (see "The runner on a phone" below)

### Initialisation and State Persistence

**Every run is a row, and the server holds the fight (#1201 stage 2c).** Opening the run view sends `open` to `encounter-command`, and the server builds the first roster (#1021 row 16, below). The answer is the fight: a new one, or the one already under way (a reload, a second device, a run started on a phone), and the store is built from the answer (`EncounterRunSurface`, `store.startFight`). There is no longer a run that exists only in the browser: the runner stops pushing the whole fight as a blob and sends commands. The open runs once per mount and encounter (a refetch, or the reset End combat does, never opens a second fight); it waits only for what the store needs after the answer (the encounter, its monsters with art, the NPCs, the traps), since the server reads the party itself. A failed open shows "Couldn't open this fight" with Try again, never a blank screen. The store outlives the component, so a remount (the battle map and back, a quest tool reopening) keeps the run.

**Commands, confirmed plus pending (`src/lib/encounters/fightSync.ts`, `src/stores/encounterRunLink.ts`, `useFightCommands`).** Every change to the fight is `store.dispatch(command)`. The click shows at once: the store applies the command to what it shows with the engine and queues it behind. What the screen shows is always the last fight the server **confirmed** (with its row `version`) with the batches still **pending** replayed on top through `applyFightCommand`, so the server's state is the truth and a reply that differs simply replaces what was shown. Two DMs dealing 4 and 3 to a creature at 20 both end on 13: whichever order the server saw them in, each screen lays its own unanswered command over the server's state afresh. When a reply arrives it becomes the confirmed fight (unless a read already brought a newer version) and its batch leaves the list. When a ring says the row changed (another device, a player moving their token) the followed read (`liveRevision`) goes to `store.observed`: a row with a newer version becomes the confirmed fight, one with an older or equal version is ignored, and batches whose ids are among the row's `applied_command_ids` are marked folded, so a read that already holds a batch the reply has not yet announced does not lay it over a second time.

- **Dice the browser cannot know.** The command is applied first with dice that record being asked (the reducer rolls a d6 per recharge at a turn start, a d20 per creature when initiative is reshuffled). A command that asked, or one that spawned through an event (the ids are the server's to make), is thrown away and sent on its own batch; the fight is `busy` (`store.busy`) until the answer arrives, and the turn buttons are disabled with the button's own loading state. Everything else shows instantly.
- **One request at a time, in order.** Commands not yet sent are merged into the next batch (at most 50; a synchronous burst is one batch). A batch has an id made once (`crypto.randomUUID()`) and is **sealed** when handed to the network, so nothing joins it; after a network failure, a 5xx or a 409 "kept changing" it is sent again with the SAME id, with backoff (half a second doubling to ten; it stops when the queue is empty, so it is not a poll), so a reply lost after the server applied it cannot apply it twice. While requests fail the DM keeps working and the queue flushes when the connection returns. A 409 "ended", a 403, a 404 or a 400 stops the queue, drops what is pending, re-reads the fight and tells the DM with a toast; a fight that ended or is gone leaves the runner for the encounter.
- **Effects are shown once.** The effects the DM sees (conditions due, concentration checks, recharge lines) come from the optimistic apply, and from a reply only what the optimistic apply did not already raise (each effect the batch showed cancels one equal effect in the reply), so a concentration check is not raised twice, while what the server added on its own (a player's sheet ingested before the commands) is shown. A command that waited for the server shows its effects from the reply. Broadcasts (an event's chat line) and character-row patches (`player_persist`) are the server's job: the browser no longer posts chat lines for fired events and no longer writes `party_members` for the fight.
- **The players' own changes.** A `party_members` ring (and a reconnect) makes the runner send `sync_party`, alone, and take the server's answer: the server reads the characters' rows itself (HP, temp HP, conditions, concentration, Wild Shape, death saves, player-rolled initiative) and the fight takes them, so the browser has nothing to guard against stale reads. `useRunnerPartySync` and its timing guards are gone. A "live" ingest of initiative means the players' screens are in the fight (`is_running`), the lobby included.
- **Lifecycle commands** go alone after the queue has drained (`useFightCommands.lifecycle`, which refuses with "Your last changes have not reached the server yet" after 15 seconds offline rather than send End combat past unsent commands): Go Live (the browser ensures the campaign session with its announcement and toast, discovers revealed monsters, and sends `go_live { sessionId }`), Go Live off (`go_private`: the players leave the fight, which goes on), End combat (`end_combat { siteId }`, after which the browser only releases the audio, resets the store and routes) and Abandon (`abandon`). The encounter page's Stop and Restart send `abandon` (`abandonFight`), and clear this tab's run so the next Run is a new fight; running another encounter needs nothing of its own, because `go_live` stops the campaign's other live fight.
- **The prepared list** (`usePreparedEncounters`) hides an encounter once its fight has started (its row's `current_round` is above 0), not merely because a row exists: an opened but unstarted lobby is still prepared.

Party member HP, conditions, death saves, and curses are seeded from `party_members` at init. Monster HP is initialised from the stat block's `hit_points` field (integer part only), through `combatStats()` (`src/rules/encounterCombatLogic.ts`), which every builder shares. A source with no hit points to read (an NPC written without a stat block, a monster whose HP line is blank) still joins, on stand-ins (10 HP for an NPC, 1 for a monster, AC 10), and the combatant is marked `placeholder_stats`. Both pickers used to hide stat-less NPCs, so a DM could not put the innkeeper in a bar fight at all (30 Oct 2026). When the DM writes the stat block mid-fight, the run takes the real numbers: `EncounterRunSurface` keeps `store.availableNpcs` current from `useNpcs` (it used to be set once, at init, so the NPC's sheet in the runner never showed the new stats either) and merges re-read monsters as before, and after each it calls `store.adoptStatBlocks()`, which sends an `adopt_stats` command. `adoptStatBlock()` carries damage already taken over to the real maximum, leaves a downed combatant at 0, never touches a rolled initiative, and only ever adopts once. Companions selected on the encounter are seeded from `companions` the same way (`c-{compId}` instance ids), except any with `combat_ready === false` are skipped entirely (#569): benching a companion in the party tracker or player portal keeps it out of the initial roster without touching the encounter's stored `companion_ids`.


The fresh-init path is built by `buildRunCombatants()` (`src/rules/fight/roster/buildRoster.ts`, extracted from `EncounterRunView.vue` so the resolution rule is unit-testable, alongside `legendaryActionCaps()` for the legendary-action pool priming that follows it). Every roster it's given — the monsters read by id with `useMonstersByIds` (no scoping), `useTraps()`, `useParty()`, `useCompanions()`, `useNpcs()` — must be **unscoped** (`includeAllScopes: true` where the composable supports it): an encounter's `combatants[].monster_id` and `trap_ids` are stored references that outlive any later campaign re-scoping (#597), so resolving them against a campaign-filtered bestiary would silently drop a creature the DM deliberately put in this fight, with no error and no toast. A reference that resolves to nothing is still skipped rather than faked — a genuinely deleted monster has no stat block to run.

#### `encounter-command`: the server advances a fight (#1201)

`supabase/functions/encounter-command/` applies a batch of commands to a live fight with the same pure rules the browser runs (`src/rules/fight`: `applyFightCommand`, `fireFightEvent`, `ingestPartyRow`). `handler.ts` is pure with its effects injected (`runBatch`); `index.ts` wires the database in. **The runner sends every change to the fight through it** (see "Initialisation and State Persistence" above). The lifecycle (opening, going live, going private, ending, abandoning) is in the function, below.

- **Request:** `{ encounterId, batchId, commands }`, 1 to 50 commands, each a `FightCommand` (the reducer's commands plus the fight's own, see "Every change to a fight is a command" below; the accepted list is checked against the union at compile time), body under 200,000 characters. Any of them mix freely in one batch; `add_combatants` is checked for 1 to 30 entries each with a non-empty `instance_id`, a `type` of `player` or `monster`, a `name`, and numeric `hp` and `max_hp`. The one exception is `{ type: "sync_party" }` (only ingest the party rows): it is the server's own, not an engine command, and is sent alone. Caller must be the campaign's owner or a `campaign_members` row with role `dm`; the campaign is derived from the encounter, never from the request.
- **The version rule:** `encounter_state.version` is raised by one by a trigger on every update, from the stored row, and no writer can set it. A batch saves with `update ... where version = the one it loaded`; zero rows back means another writer (a second device, the browser) got there first. The batch then loads the fresh row and works everything out again on top of it, up to 4 attempts, and fails with a 409 after that. Dice (`secureDie`) are rolled inside the attempt that is saved, so a retried attempt rolls again.
- **The batch id:** `applied_command_ids` keeps the newest 64 ids, written in the same update as the state. A batch whose id is already there is answered with the current state and `applied: false`, so a lost reply can be retried safely.
- **What the server ingests:** before the commands, every player combatant's `party_members` row goes through `ingestPartyRow` (HP, temp HP, conditions, concentration, wild shape, death saves, initiative), because a server has no browser to do it. Initiative counts as "live" while the players' screens are in the fight (`is_running`), the lobby included, since a player rolls there; a row read before the lobby opens still carries last session's roll. Settings come from where the runner reads them: events and lair settings from the `encounters` row, the edition from `campaigns.game_system`, Random Initiative Each Round from `campaign_rules` (`random_initiative`, off when no row exists), and the monsters and NPCs the events spawn from `library_monsters` / `monsters` and `npcs`.
- **What the server performs, after a successful save and once per batch:** `player_persist` effects are written to `party_members`, and `broadcast` effects are posted to the campaign chat as system messages from "⚔ Encounter". The engine's effects are also returned for the caller to show (conditions due, concentration saves owed, recharges, spawns). A failed effect is reported in `effectFailures`; the saved state stands.

- **A run is a row from the moment it is opened, and the row says what state it is in.** `is_running` means only that the players' screens are in this fight (Go Live). `encounter_state.ended_at` (migration `20261119121047`) says the fight is over: End combat and Abandon set it, and opening a new fight on the row clears it. A row that is not running and not ended is a fight being set up or played in private.
- **Lifecycle commands**, each sent alone (mixed with anything else is a 400), each through the same load, batch-id check, version-checked save and retry as a fight command. The response carries `is_running` and `ended_at` beside the state.
  - `open { playedMemberId? }`: with no row, builds the roster (1 to 60 combatants, else 400) and inserts one (round 0, turn 0, not running, not ended, `user_id` the caller, `campaign_id` from the encounter) with the legendary pools primed (`legendaryActionCaps`); with a row whose fight has not ended, changes nothing and returns it as it is (a reload or a second device must not reset a fight under way, so `applied` is false); with a row whose fight ended, resets it to a new fight on a freshly built roster (round 0, turn 0, fired events, lair rounds, spheres of darkness, session and start time cleared, applied ids reduced to this batch).
  - `go_live { sessionId }`: needs a row that has not ended. While the fight has not started (round 0) every player combatant's initiative is blanked, on the fight and on the character's `party_members.current_initiative`; once combat has started those rolls are the turn order and stay. Writes `is_running: true`, `session_id`, `started_at` on the row, then stops every other running fight of the campaign (one live fight per campaign).
  - `end_combat { siteId? }`: needs a row that has not ended. Ingests the players' own rows first (so a sheet healed meanwhile is not overwritten), then writes `endOfFightPatches` (`src/rules/fight/fightEnd.ts`): each player's hit points, conditions without their `due` flags, curses, death saves and a blank initiative on `party_members`; each companion's hit points and conditions; the party's standing in `campaigns.explore_party`, from the saved roster's token positions. The row gets `is_running: false` and `ended_at`. In a campaign with the Experience Points rule (`xp_levelling`), it then gives the fight's XP (#1021 row 27): `fightXp` (`src/rules/fight/fightXp.ts`) sums the challenge-rating XP of every foe on a side opposed to the party and at 0 hit points, read from the stat blocks the foes came from, and shares it equally (rounded down) among the party members in the fight, down or not; companions, allies, neutrals and bystanders take and give nothing. Adding XP is not a value, so `public.award_fight_xp` (service role only, `20261119191615`) gives it once per fight, keyed on `encounter_state.xp_awarded_at`, which reopening the encounter clears; a retried End combat asks again and the database answers with nothing. It posts a ⭐ chat line with the total and the share. `siteId` is the site the fight is anchored in, resolved by the caller through the map stack (the server does not repeat that resolution); it is used only when it is a place of this campaign.
  - `go_private`: needs a row that has not ended. Writes `is_running: false` and nothing else: the players' screens leave the fight, which goes on (the DM turned Go Live off).
  - `abandon`: needs a row that has not ended. Blanks the players' initiatives on their rows, sets `is_running: false` and `ended_at`, and writes no hit points, conditions or curses.
  - Any fight command on an ended fight is a 409; with no row at all it stays a 404. A batch id already applied is answered before the ended check, so a retried End combat is answered, not refused.
- **Order of writes:** the fight's row first (version-checked), then the other tables. A write after the save that keeps failing is retried three times and then reported in `effectFailures`; the saved fight stands.
- **The server builds the first roster (#1021 row 16):** a table with no DM browser (the AI table) needs it there. `loadRoster` (`supabase/functions/_shared/fightRoster.ts`) reads, scoped to the campaign in every query: the party minus the fallen and retired (`activeMembers`, `src/lib/party/`), the encounter's companions, monsters with the library art merged for the caller (`src/lib/library/monsterArtLayers.ts`), NPCs, the fielded members' species, gear and class rows; then the shared rules build it (`src/rules/fight/roster/`: `foughtEncounter`, `buildRunCombatants`, `bystandersOf`, `legendaryActionCaps`), the same the browser ran before. A character's armour class is their gear's (`calculateAc`), never a Wild Shape form's, which rides on the combatant's `wildshape`. `playedMemberId` names the AI table's played character (refused unless one of the active party): the party is that character and the members the AI plays, and the NPCs in the encounter's place join as bystanders; a fight that was already under way gets late bystanders from the browser (`lateBystanders` over the answered roster). Nothing is built on a resume. The browser also starts the campaign session (`ensureCampaignSession`, which announces it) and passes its id to `go_live`, and discovers monsters when the fight goes live.

- **Resolving commands (#1201 stage 3): the server rolls and adjudicates an action.** An attack was resolved only in the DM's browser, so a server with no browser could not make a goblin attack. Five more commands join the accepted list (`ResolvingCommand`, `resolve.ts`, held equal to its union by `ALL_RESOLVING_COMMANDS_LISTED`); they mix with ordinary commands in one batch and are applied in order with them (a condition applied before an attack is on the target when the attack is rolled). The steps are not written twice: `src/rules/fight/resolution/` holds them, and both the browser (`useActionResolution`) and the function run it, with the dice, the lookups and the fight injected (`ResolutionContext`).
  - `resolve_attack { attackerId, list, action, targetId, withinFiveFeet?, penalty?, magical?, faces? }`: `list` and `action` name the stat-block entry as the runner names it (`actionUseKey`: `actions/Bite`). Rolls to hit (advantage and disadvantage from both sides' conditions, the 2024 exhaustion penalty), compares with armour class, on a hit rolls each damage part (dice doubled on a critical, never the modifier), runs each part through the target's defenses, and takes the hit points off with `adjust_hp`; a hit whose entry also forces a save ("...or be paralyzed") has the creature that was hit make it afterwards. `withinFiveFeet` left out is read from the grid placement of the two and refused when either is not on the map. `penalty` is a whole number from -20 to 0 added to the roll (a positive one is refused: the caller may make the attack harder, never easier).
  - `resolve_save { attackerId, list, action, targetIds, magical?, faces? }`: each target rolls its own save (Strength and Dexterity saves of a Paralyzed, Stunned, Petrified or Unconscious creature fail without a die), the damage is rolled once for all of them (and not at all when nobody can take any), a saver takes the half rounded down once over the whole roll, a failer takes all and gains the conditions it is not immune to.
  - `resolve_concentration { instanceId, damage, faces? }`: the Constitution save against max(10, half the damage), and a lost one issues `end_concentration`. Refused for a creature that is not concentrating on anything. `damage` is the caller's account of what the creature just took.
  - `roll_condition_save { instanceId, name, faces? }` and `roll_ongoing_damage { instanceId, name, faces? }`: the repeat save of a "save ends" condition, or its ongoing damage, rolled and then settled (`resolve_condition_save` / `settle_ongoing_damage`). Refused unless the turn hooks marked that roll as owed (`due`), as the runner offers a roll only then.
  - **Whose dice.** A roll nobody has a hand for is the server's (`secureDie`), and a person's own roll stays theirs ("players love rolling physical dice"): every command may carry `faces`, the faces a person rolled, and then the server only scores them with the same `DiceRules.score` the prompt uses and never re-rolls. Faces are validated (a d20 with advantage takes two, each face within its die; a wrong shape is a 400). `resolve_attack`: `faces.attack` (the d20 or d20s) and `faces.damage` (one list per rolled damage part, in order, dice by size from the smallest, a critical doubling the dice), where damage faces need the d20 faces because the critical decides how many there are; whichever is left out the server rolls. `resolve_save`: `faces.saves`, one entry per target in `targetIds` order (null: the server rolls that one), and `faces.damage`. The other three take `faces` as a flat list.
  - **What is posted.** After the save (so a lost race re-rolls and only the saved attempt's rolls are posted) each roll goes to `campaign_messages` as the client posts one (`rollMessageRow`), under the roller's name (the attacker for an attack and its damage, the target for its own save), once per batch. A roll the server threw carries `server_rolled: true`; a roll made from supplied faces is posted unstamped with `manual: true` in its metadata. The reply's `effects` end each command with `{ type: "resolved", resolved }` (`ResolvedAction`, `src/rules/fight/fightState.ts`): hit, critical, the d20 and the total, the damage per type before and after defenses, the dying outcome of a player, each target's save and the conditions gained or resisted, all plain numbers a narrator may quote.
  - **What the server reads about a creature, and what it refuses.** The attacker's entry comes from the stat block of the combatant (`monster_id` in `library_monsters` or `monsters`, `npc_id` in `npcs`, `companion_id` in `companions`), loaded only for a batch that resolves something; the entry must carry a structured attack or save (#1017). A target's defenses come from the same place, and its save bonus is the stat block's. Armour class is the combatant's printed one. A **player character** has no stat block, and the server works out what the runner would show for them from the same pure rules (#1201 stage 4, `src/rules/fight/playerSheet.ts`): the armour class is the beast's while in Wild Shape, otherwise `calculateAc` over what they wear (`wornGearByMember`), and a save bonus is the ability modifier from the scores in effect (a form's Strength, Dexterity and Constitution replace theirs) plus the proficiency bonus when proficient. **Nothing is stored:** like the browser, the server reads the character's `party_members` row, the campaign's `party_inventory` and the items those rows name (own `items` of this campaign or global, `library_items` normalised, plus the stat blocks of any Wild Shape form) through `loadPlayerSheets`, only for a batch that resolves an action in a fight with a player in it, once per attempt, every read scoped by `campaign_id`. So a save, a repeat save or a concentration save for a player is rolled by the server (or scored from the faces a person supplied) like any creature's, and an attack on a player is rolled against their real armour class. The browser's own `saveBonusFor` still returns null for a player, so the DM's runner still leaves a player's save to the player. The server refuses (400) only a player whose character row could not be read in this campaign, and a player as the attacker (no stat block, so no action to resolve). Also 400: an action with no structured payload, an unknown attacker, target or action, a target not in the fight, an attacker at 0 hit points, a printed armour class with no number. Nothing is saved or posted for a refused command.
  - **Cover (#1202 story 3c).** When the fight has a map the rules can use, cover counts on the server (PHB 2014 ch. 9 "Cover", which SRD 5.2 repeats): `applyResolvingCommand` gives the shared steps a `coverFor` hook (`ResolutionContext.coverFor`), answered by `coverBetween` over the map's walls and closed doors, with every other creature on the board (`isOnBoard`, the same notion the whole-turn options use: placed, and alive or a player at 0) as a possible screen. The map is read once per attempt (`BatchDeps.loadFightMap`: `loadFightMapInput` then `fightMapOf`, scoped to the campaign) and only when the batch resolves something. **Attack:** the roll is compared with the target's AC plus 2 (half cover) or 5 (three-quarters); a target with total cover is refused (400, naming both creatures) before any die is thrown. The `resolved` summary keeps `targetAc` as the number the roll was compared against and adds `cover` and `coverAc` (the part of `targetAc` that is cover). **Save action:** a target's Dexterity save gets +2 or +5 against the acting creature (also a save a hit forces); other abilities get nothing, and each target's summary carries `coverBonus`, already inside its `total`. App convention: the effect starts at the acting creature, so an area with another origin is not modelled, and a target at total cover is not refused for a save action (an area can reach round a corner) but gets the three-quarters bonus. With no map, or when either creature has no position, no cover is applied (`cover: null`), never a guess. The browser supplies no hook, so the DM's runner is unchanged: the DM adjudicates cover at their own table.

### Turn reducer and action resolution (#1017)

The turn state machine is a pure reducer, `reduceEncounterTurn(state, command, deps)` in `src/rules/encounterTurn.ts`; the store's actions are thin wrappers that dispatch a command, adopt the state and act on the events. Turn boundaries are events (`turn_ended`, `round_started`, `turn_started`), so rules that hang off a turn have one place to go (#1018, condition durations). Randomness is injected (`rollD20`, `rollD6`), and the state is plain JSON, so a test or a server function can drive a turn through the same code.

**Every change to a fight is a command.** `applyFightCommand` (`src/rules/fight/fightCommands.ts`) applies any `FightCommand`: the reducer's commands (turn, HP, conditions, initiative, wild shape, legendary actions, boss mechanics, removing a combatant, limited abilities) and the fight's own, which the reducer has no business knowing: `add_curse`, `remove_curse`, `set_reveal_state`, `add_combatants` (newcomers built by the caller, ids and rolled initiative included, joined through `joinFight` so the turn stays with the acting combatant; one whose `instance_id` is already in the fight is refused), `adopt_stats` (the real numbers `adoptedStatsFor` worked out for a combatant that joined on stand-ins, applied by `applyAdoptedStats`), `fire_event` and `check_events`. Initiative has no command of its own: `set_initiative` takes a number to set it or null to blank it and changes that one field and nothing else, so the lobby's blanking and a roll are the same command. The rolling itself (a physical-dice prompt or an automatic d20) stays in the store; the command carries the value rolled. The store no longer edits the roster, the round, the turn pointer or the fired events directly: its actions work out what to send (rolling a value, picking the next reveal state, building a spawn, computing adopted stats) and `dispatch` a command. The only other writers of that state are `adopt` (the result of a command), `ingestParty` (a player's own row, the server's `sync_party`), `hydrateFromLive` and `reset`. Generated events added from the complication dialog stay a store-only addition to the event list, not a command. Recharge and per-day abilities are tracked per combatant in `action_uses`: using one marks it spent, and a spent recharge rolls its d6 at the start of that combatant's turn (`action_recharged` / `recharge_failed`, shown above its actions).

**Condition durations (#1018).** A condition on a creature is a record, `AppliedCondition` (`src/types/condition.types.ts`), and the same shape is stored in `party_members.conditions`, `companions.conditions` and every combatant in `combatants_live` (migration `20261010180827`, whose check constraints refuse a bare string so a stale tab fails and reloads rather than writing the old shape). The name is the key, one record per name; Exhaustion is the record named `Exhaustion` with a `level`. A record may carry a `source` (the combatant's `instance_id`, the spell or ability, and whether the source is concentrating on it), what `ends` it (the start or end of the bearer's or the source's next turn; a count of rounds ticked on the source's turns; a repeat save at the start or end of the bearer's turns, optionally capped at a count of rounds ticked the same way, #1055), and `ongoing` damage. No end means it lasts until removed. The record stores no display name for its source on purpose: the player projection passes conditions through, and a stored name would name a hidden creature. Labels are derived at render time by `src/rules/conditionLabels.ts` against the combatants the viewer may see.

The turn hooks live in `src/rules/conditionDurations.ts` and run inside the reducer wherever it raises `turn_ended` and `turn_started` (`start_combat`, `next_turn`, the random-initiative reshuffle). "Next turn" means the first turn of the anchor that begins after the condition was applied, so an end-of-turn condition is `armed` when that turn starts and expires only at the end of an armed turn; one applied during its anchor's own turn survives that turn's end. A save or ongoing damage that falls due is not rolled by the reducer: the record is flagged `due` and a `condition_save_due` / `ongoing_damage_due` event is raised, and the DM resolves it with `resolve_condition_save` or `settle_ongoing_damage` (the damage itself goes through the normal typed-damage path first). Because the flag lives on the record, a pending roll survives a reload. A source that drops to 0 HP, ends its concentration (`end_concentration`, which the runner calls when a PC's `party_members.concentration` changes) or leaves the fight ends the conditions it was holding. A duration anchored on a source that no longer takes turns (removed, or a monster at 0 HP, whose turns are skipped) counts on the bearer's turns instead, so it cannot outlive its source forever. Editing a condition the creature already has keeps a roll it still owes and an end-of-turn arming for the same anchor. `prev_turn` runs no hooks: stepping back does not undo an expiry.

In the runner, `RunnerConditionBadges` (shared by the desktop row and the phone card) shows one split badge per condition: the body names it with a muted second line saying what ends it ("save ends · WIS 14", "until the end of Vex's next turn") and whether a roll is owed, and opens `ConditionEditor` (source, spell, concentration, what ends it, ongoing damage); the × removes it. The picker's "Custom…" entry makes a DM-named condition such as "Burning". A combatant that holds conditions on others by concentration gets a "✦ Hold Person" chip whose × ends them. `RunnerDueConditions`, under the top bar, lists what is owed: a repeat save (Roll for a stat-block combatant through `rollConditionSave`, Passed / Failed for anyone, since a player rolls at the table), ongoing damage (rolled and applied through the typed-damage path, then settled), and a concentration check whenever a non-PC holder takes damage (the reducer's `concentration_check_due`; Roll, Kept or Lost), plus a quiet line for each condition that ended and why. Conditions applied by a monster's save action record the actor and the action as their source, and what ends them when the save says (`imposedCondition`, `src/rules/combat/resolveAction.ts`, #1050), so a ghoul's paralysis arrives as save ends without the DM setting it. An attack whose hit forces a save (the ghoul's claw) offers that save as a follow-on step in `RunnerAttackFlow` once the hit's damage is applied, or straight after the hit when the attack deals none: the same `RunnerSaveFlow`, locked to the creature that was hit. The applied line names the end in the badge's words ("Goblin is now Paralyzed (save ends · CON 10)."), read from the record the creature now carries, and a save with no damage of its own says nothing about damage. A PC's concentration lives on `party_members.concentration`, so the server's party ingest (`ingestPartyRow`) ends what it held when that spell drops or changes, wherever that happened. End Combat writes the records back without their `due` flags. Players see the same records through `get_player_encounter_state`, and their labels name only sources the player can see.

Stat-block entries roll from their structure, never their prose. `RunnerActionList` shows each entry's summary ("+5 to hit · reach 5 ft · 1d4+3 piercing"), badges and live availability, with **Attack**, **Force save**, one button per option, **Use** for a limited ability with nothing to roll, and **Restore** to undo a spend. The inline `RunnerResolvePanel` runs `useActionResolution` (`src/composables/encounters/`): pick targets, see advantage or disadvantage and why, roll through `usePromptedRoll` (physical dice still work), override hit, miss, crit or a save, correct the damage, preview it through the target's `defenses`, and apply. Damage for a save is rolled once for every target. The AC an attack is rolled against is `effectiveArmorClass` (`src/rules/fight/targeting.ts`, with `withinFiveFeet`, `parseArmorClass`, `combatantDefenses` and `filterImmuneConditions`; `src/lib/encounters/actionTargeting.ts` keeps only the runner's target list), the same one the runner row shows: a party member's live sheet AC or beast form, not the combatant's stale copy. The pure rules live in `src/rules/combat/` and never roll dice; the steps that sequence them with dice (`rollToHit`, `rollDamageParts`, `applyDamage`, `rollSaves`, `applySaveOutcome`, the concentration and repeat-save rolls) live in `src/rules/fight/resolution/`, which takes its dice, its lookups and its fight through a `ResolutionContext`, so the browser (dice from `usePromptedRoll`, fight from the encounter store) and the server's resolving commands (above) run one orchestration.

### DM Controls

**Top bar:**

- Back to Builder link
- Round counter with Previous Turn / Next Turn buttons
- Encounter name
- Roll Initiative button (pre-combat only) — rolls `d20 + initiativeModifier(combatant)` for every combatant that **doesn't have an initiative yet**; a value already in the list (a player's own roll, a monster the DM typed by hand) is never overwritten, whatever its type. The modifier and any disadvantage come from `initiativeRoll()` (`src/rules/initiative.ts`), the one initiative rule the player sheet and the player's panel use too (#1149): the stat block's 2024 `initiative_bonus` when it declares one, for a monster or an NPC alike (an NPC built from a 2024 monster used to drop it, #1116); otherwise the DEX modifier (a Wild Shape form's for a shaped druid) plus a character's `initiative_extra` (Alert, Jack of All Trades), then the check's conditions (2024 Exhaustion's penalty; disadvantage from Poisoned, Frightened or 2014 Exhaustion). The condition rules follow the table's edition, which the runner hands the store (`setRuleset`) and the turn reducer reads from its state. See party-characters.md "Initiative". The d20 itself goes through `usePromptedRoll`, so a DM on **physical** dice mode gets one manual-entry prompt per combatant (labelled with its name) instead of an auto-roll — the runner registers that roller on the store via `setInitiativeRoller()`; the store falls back to an automatic roll (`rollInitiativeValue`) when none is registered. Rolls are silent (not posted to chat) — the order reaches players through the live encounter state, and posting each monster's roll would leak hidden combatants. Cancelling a prompt stops the run and leaves the remaining combatants blank, so pressing the button again picks up where it left off. Mid-combat spawns keep their automatic roll rather than interrupting the turn with a modal
- Per-combatant roll button (pre-combat only) — a die button next to every initiative input in the combatant list (`RunnerInitiativeField.vue`, shared by the desktop row and the mobile card), calling `store.rollInitiative(instanceId)`. Unlike the top-bar button this is an explicit request, so it **does** replace an existing value (it re-rolls a single monster whose roll you don't like). It disappears once combat starts — the order is locked and a stray re-roll would shuffle the turn everyone is standing in; the initiative input stays editable for a manual correction. `store.rollingInitiative` is the shared busy flag: while a manual-entry prompt is open (a single global slot) the top-bar and every per-combatant button disable together
- Lobby roll status (`RunnerRollStatus`): shows the DM which players have rolled ("Rolled 15") and who is "Waiting for roll". Rolling does not mark the encounter started, so the lobby stays a lobby until combat begins. Ties are marked (higher Dexterity first) so the DM can settle them
- Start Combat button, whenever the encounter is in the lobby (round 0), live or not. Until 30 Oct 2026 it showed only while live, so a DM who ran a fight at the table without going live had no way to start it. With players still unrolled it asks once, naming them, then rolls the blanks and starts, never overwriting a roll
- Dice Roller widget
- Go Live / Live badge (only when a campaign is active)
- Abandon — ends the live state without syncing player HP/conditions (roster-NPC death/reveal already happened live during combat)
- End Combat — syncs HP/conditions/death saves/curses back to `party_members` and returns to the encounter sheet. (Roster-NPC death/reveal is handled live as it happens, not here — see "Live roster-NPC sync" below.)

Phones get one compact row per combatant; see "The runner on a phone".

Per combatant row:

- **Active indicator** — gold border ring on the avatar and blue-tinted row highlight for the current turn
- **Faction stripe** — 3px coloured left border from the faction definition
- **INIT cell** — editable number input; typed values take effect immediately
- **Reveal toggle button** (monsters only, overlaid on portrait) — cycles hidden → unseen → revealed. Auto-triggers monster discovery in `discovered_monsters` when cycled to revealed
- **HP cell** — inline editable with +/- buttons; debounced 500ms so rapid tapping accumulates. Animated damage/heal flash overlays the number. A PC's damage follows `src/rules/dying.ts` (see party-characters.md → Death Saves): the `encounterRun` store applies massive damage, death-save failures at 0 HP and the stable and dead states, and the quick damage panel gets a critical-hit option for a PC at 0 HP
- **Quick HP panel** — expands below the row when the row is selected; shows an amount input with Dmg / Heal / +Temp buttons
- **AC** — read-only display; for a PC the calculated value (`useArmorClass`, snapshotted into the combatant by `buildRunCombatants`, see party-characters.md → Armor Class); uses beast AC when wildshaped
- **CONDITIONS** — badge row, click a badge to remove; "+" button opens a dropdown of available conditions. Exhaustion uses a pip chip with level control. Concentration is shown as an indigo chip (auto-cleared by concentration-breaking conditions). Reaction is a ⚡ chip, toggled per turn, reset automatically at the start of each new round

**"Hidden" condition + player Hide action** (by edition since #973: 2024 marks Hidden only on a DC 15 Stealth success; 2014 marks it and shows the total for the DM to judge, `src/rules/hide.ts`) — the pickable condition list (`CONDITIONS` in `src/rules/conditions.ts`) carries a 16th, non-SRD entry, **Hidden**, for tracking a creature that has taken the Hide action. It's a full shared condition: it appears in the DM's condition picker (`ConditionPicker.vue` / `PlayerCharacterHeader` / `PartyConditionsPanel`) and renders as a chip everywhere the others do. Because Open5e has no such entry, its edition-aware rules text lives in `CONDITION_PATCHES` (both `2014` and `2024`) rather than the generated base arrays. On the player side, the **Combat tab** (`PlayerCombatTab.vue`) has a Hide action: it rolls Dexterity (Stealth) via `promptRoll` (using the shared `skillCheckBonus` in `src/rules/skillCheck.ts`, honouring check-disadvantage/Exhaustion-penalty like the Skills tab) and, on a completed roll, marks the character Hidden; the card doubles as a live "you are Hidden / Reveal" indicator. Making any attack from the Combat tab auto-clears Hidden (5e RAW — attacking reveals you), as does the Reveal button or removing the chip; attacks the DM rolls for that PC from the encounter runner (`RunnerPcAttacks.vue` melee/ranged/thrown) clear it too, via the `roll-attack` resolved-callback path.

**Dual-edition conditions (#556)** — condition text is edition-sensitive: `getCondition(name, ruleset)` (`src/rules/conditions.ts`) resolves the campaign's active ruleset against `src/data/srdConditions2014.ts` / `srdConditions2024.ts`, with `CONDITION_PATCHES` (`src/data/conditionPatches.ts`) applied last as an override/fill-gap layer — the 2024 texts there were verified line-by-line against the official 2024 rules glossary (SRD 5.2, CC-BY-4.0) since Open5e has no structured 2024 condition data yet (upstream open5e-api#793); the patch layer is the regeneration point once that data ships. 2024 Exhaustion is mechanically different from 2014: a flat −2×level penalty on every d20 Test (`getExhaustionD20Penalty`) instead of the 2014 disadvantage-based effects, −5ft×level Speed reduction (`getExhaustionSpeedPenaltyFt`), and death at level 6 in both editions. Both resolvers live in `src/rules/conditions.ts` and are wired through the runner's combatant rows/cards, the condition picker, and the player-facing condition views.

- **Surprised badge** — can be set pre-combat or during round 1; auto-cleared when the combatant ends their first turn. A subtle "✦?" button appears on non-surprised combatants during the setup window

**Turn management:**

`nextTurn()` skips dead monsters (HP = 0) while always including players. Round number increments when the turn wraps back to position 0. `prevTurn()` steps backwards. At the start of each combatant's turn: their reaction is restored and their legendary action pool is refilled (extracted as `refreshTurnStart()` in the store so the round-wrap reshuffle path reuses it).

**Optional combat rules (Turn Timer + Random Initiative):**

Two encounter mechanics live in the built-in optional-rule registry (`src/rules/optionalRules.ts`), toggled per campaign in **Campaign Settings → Rules** like every other `OptionalRuleDef`. Both `dmOnly: false` so they also list in the player Reliquary; both default off.

- **`turn_timer`** — a _configurable_ rule (the first one). The DM sets **seconds per turn** (default 60, clamped 5–600). Config is the general mechanism added here: `campaign_rules` gained a nullable `config jsonb` column (migration `20260724000006`), `OptionalRuleDef.config?: RuleConfigField[]` declares the tunable fields, `CampaignRule.config: RuleConfig | null` holds the stored values, and `resolveRuleConfig(rows, key)` (`useOptionalRules`) merges stored values over registry defaults (dropping any non-numeric stray). `RulesTab.vue` renders a number input per field only while the rule is enabled; both the toggle and config writes persist through the single `useUpsertCampaignRule` mutation hook (config optional — flipping the switch passes the existing `config` through so it never wipes tuned values). `campaign_rules` is in `useCampaignLiveSync`'s `SYNC_TABLES`, so a DM toggling/tuning a rule reaches already-mounted players live. The countdown itself is `TurnTimer.vue` (`src/components/encounters/`) — a purely-visual, self-contained clock taking `:seconds` + `:reset-key` (round + active combatant instance id). It restarts whenever the key changes, flashes amber ≤10s, pulses red at 0, and never force-ends a turn. Rendered in the runner top bar (`EncounterRunner.vue`, gated on `store.round > 0`) and on the player panel (`PlayerEncounterPanel.vue`, gated on `!isInLobby`); both derive `turnTimerSeconds`/`turnResetKey` from the shared `useTurnTimerConfig(round, activeCombatantId)` composable (`src/composables/encounters/useTurnTimerConfig.ts`) — only the round/active-combatant source differs (store vs. liveState). Each side runs its own copy — a sub-second drift is fine for a nudge, so no start-timestamp is synced.
- **`random_initiative`** — a plain boolean. When on, the store re-rolls **every** combatant's initiative and re-sorts at the start of each new round, then hands the turn to the top of the fresh order. Implemented as `store.reshuffleInitiative()` (silent auto rolls through the same `initiativeRoll`, disadvantage keeping the lower of two d20s, for all — deliberately **never** the physical-dice prompt, since it fires once per round; a modal storm each round would be unusable), called from `nextTurn()` on the round-wrap branch when `store.randomizeInitiativeEachRound` is set. The runner keeps that store flag in sync with the campaign rule via a `watch` on `isRuleEffectivelyEnabled(..., "random_initiative")` → `store.setRandomizeInitiativeEachRound()`, so toggling mid-fight takes effect on the next wrap. Live sync is automatic: the reshuffled initiatives ride the existing `combatants_live` push, so players see the new order without extra plumbing. `store.reset()` leaves the flag (and the table's `ruleset`) alone: they are the table's settings, which the runner's watches set once on mount, and the run surface resets the store after the runner may already have mounted, which used to switch the rule off for the fight (#1149).

**Wildshape tracking:**

**Wild Shape follows the character's edition, with no house rules (epic #959, 3 Oct 2026).** `wildShapeRules()` in `src/rules/wildshape.ts` turns edition, druid level, circle and Wisdom into every number the sheet, runner, bestiary and rest dialog read: uses, short-rest recovery, max CR and movement limits, Known Forms, the HP model, temp HP, the Moon AC floor, action type, duration, and which slot features apply. The table it implements is in the epic body. Before it the app had one model, partly invented: a CR cap wider than either edition (CR 1/2 at level 2), two uses at every level, every use back on a short rest, and the beast's HP pool for everyone. That cap was pinned by a test, which is how a misreading of Circle of the Moon's wider cap survived; the test now pins the book's table. The edition is read through `useRuleset()`, which #948 makes per-character (`provideCharacterRuleset`). `wildShapeRulesFor(member, classRows, edition)` is the one place the profile, edition and Wisdom meet, for `useWildshapeDruid` and the runner's Evergreen check alike.

When a character takes a form, the combatant and the party row get a `wildshape` overlay (`WildshapeState`), built by `wildshapeStateFor(beast, rules)`. The two editions differ in hit points:

- **2014:** the overlay carries the beast's HP pool. Damage lands on temp HP, then the beast; at 0 the form ends and the excess carries to the character's own HP.
- **2024:** `beast_hp` and `beast_max_hp` are null. The character keeps their own HP and gains temp HP (druid level; Circle of the Moon three times that), which never stacks (`betterTempHp`). The form ends when they drop to 0 (`ownHpForm` in `HpPools`).

Every damage and healing path builds its pools with `formHpPools(own, form)` and clears a form only on `out.reverted`. Before #959 several cleared it whenever `beast_hp` came back null, which under 2024 would have ended the form on every hit. A form costs `usesCost` uses: 1, or 2 for a 2014 Moon level 10 elemental. A short rest restores every use under 2014 and one under 2024 (`RestDialog`).

**Slot trades go through `exchange_wild_shape`** (migration `20261003103928`): 2014 Combat Wild Shape healing (a slot heals the beast 1d8 per level; the client rolls, the server bounds the amount) and both 2024 Wild Resurgence directions. It is a SECURITY DEFINER like its siblings `convert_sorcery_points` and `cast_character_spell_v4`, because it reuses `spend_spell_slot`, which clients cannot call. It authorizes first with the same coalesced predicate. How many uses a druid has is a client rule (`src/rules/wildshape.ts`); the server checks structure and does the trade atomically. The once-per-long-rest flags (`class_choices.wild_resurgence_slot_taken`, `class_choices.wild_shape_form_replaced`) reset through `class_choice_rest_resets`.

**2024 Known Forms** live in `class_choices.wild_shape_known_forms` (monster ids), managed on the sheet's Wild Shape tab (`PlayerWildShapeKnownForms`): learn freely below the cap, then replace one per long rest. `supabase/checks/content_integrity.sql` checks that every id still resolves. Under 2024 the picker offers known and pinned forms; under 2014 discovered and pinned (`availableWildShapeForms`). The bestiary lists the same set. **Evergreen Wild Shape** (2024, level 20) is `useEvergreenWildShape`, mounted in `EncounterRunner`: a druid with no uses left regains one when their initiative is rolled, once per fight.

The avatar switches to the beast portrait. Reverting clears the overlay and restores the display to the character's own stats.

The DM picks the form via `RunnerPcWildshape` ("Choose Form"). The picker is **teleported to `<body>`** as a `position: fixed` floating popover anchored to the toggle button (`useAnchoredPopover` + `computeAnchoredPosition` in `src/lib/floatingPosition.ts`). This is deliberate: the detail panel's `.detail-panel`/`.panel-shell` ancestors are `overflow: hidden`, so an inline (or `position:absolute`) picker gets clipped and appears to render nothing — the original #503 bug. Teleporting sidesteps all ancestor clipping. The available list is the same discovered/pinned-gated set as the player sheet; when it's empty the popover shows a "📌 Pin a form" affordance listing every _eligible_ beast (CR/speed rules only), and pinning one via `useTogglePinnedForm` unlocks it immediately without leaving the runner. Eligibility (`wildShapeFormCost`: beast-only, the edition's CR cap and movement limits, 2014 Moon elementals for two uses) lives in `src/rules/wildshape.ts` and is shared by the runner, the player character sheet and the player bestiary.

**Who is a druid, and at what level, has one answer too.** `druidProfile()` (same file) reads the `character_classes` rows: a druid is a row whose `capabilities` include `wild_shape` (#934). The capability belongs to the class definition (`system_classes` / `custom_classes.capabilities`, a checkbox in the custom class editor) and the database copies it onto every class row by trigger (`20261102100215`), so a homebrew shapeshifter can Wild Shape and a class merely named "Druid…" cannot, and the sheet, runner and bestiary learn it from the rows they already load, with no second query. Circle of the Moon still reads the subclass name, because a subclass may be free text with no definition; `useWildshapeDruid(memberId, member)` wraps it with the edition's rules. All three surfaces go through it. Before 2 Oct 2026 only the sheet did, and the runner and the bestiary read `member.class` / `member.level` directly: a character who took Druid as a second class was not recognised there at all, and the CR cap came from total level.

**Out of combat the player shapes from their own sheet** (`PlayerWildShapeTab`, mounted by `PlayerCharacterView`; the same view is the DM's party page). Three things about it that were wrong until 2 Oct 2026 and must stay right:

- **"Choose Form" opens the list.** The list used to render whenever the druid was not in a form, so the button only flipped its own label. It is a drawer now (`drawerTransition`), closed until asked for, exactly as in the runner.
- **The beasts come from the player projection (`usePlayerMonstersByIds`, `useWildShapeCandidates`), never the DM's bestiary reads.** A player cannot read the `monsters` table, so a beast the DM made and pinned or revealed was missing from the picker, and a druid put into one from the runner showed no beast stats or actions on their sheet. The projection carries those rows. For a DM the composable reads the base table, in preview mode _and_ on the party page (`auth.isDM`), where the projection would answer as a player with no character.
- **A form costs a use, including a change of form.** The confirm button used to stay enabled while already shaped, so "Change" at 2/2 wrote 3/2. A discovered beast whose stats the DM has not revealed (`stat_block` null in the projection) is listed but disabled: there is no hit point pool to assume.

Pins and discoveries are narrowed to the character on the sheet, because a DM reads every member's.

**The runner knows about a form taken outside it (3 Oct 2026).** A PC combatant's `wildshape` is seeded from `party_members.wildshape_state` when the fight is built (`buildRunCombatants`), and the server's party ingest takes it from the party row like temp HP and conditions (`adoptWildshape`, no write-back). Before, a druid who shaped on their own sheet, before or during a fight, showed the beast on the runner card (which reads the party row) while the store did not know: the first hit landed on the druid's own HP, and the write after it persisted `wildshape_state: null`, so the form vanished from the sheet too.

**One overlay builder and one face.** `wildshapeStateFor()` (`src/rules/wildshape.ts`) builds the overlay for both the runner and the sheet, from the beast with its library art merged (`withLibraryArt`): the monster lists carry only the `library_monsters` row's own `image_url`, so a beast whose picture lives in the art tables shaped into a form with no picture. `formPortrait()` (`src/lib/wildshapePortrait.ts`) is the face every party and combatant portrait draws: the beast's while shaped, including on the party tracker, the dashboard, the player's People page and the battle-map token, which used to keep the druid's. A beast with no art draws the caller's monster placeholder, never the druid's portrait, which made a working wild shape look as if it had not happened. A form's `beast_image_url` is only a copy taken when it was assumed, and it is often null (the local Dire Wolf form held none while the library row had art), so a surface that passed only the form drew the placeholder for a druid in a beast that has a picture (30 Oct 2026). Every surface that draws a combatant's or member's face therefore goes through `useFormPortraits()` (`src/composables/party/useFormPortraits.ts`), which reads the beasts on screen with `useMonstersByIds(..., { withArt: true })` and hands `formPortrait` the live picture; the stored copy is only its fallback. The sheet header and the tracker take the beast's walking speed (`walkingSpeed()` in `src/lib/movement.ts`).

**Temp HP:**

Temp HP absorbs damage first, in beast form as well as normal form — it is a buffer in front of whichever HP pool is active, and Wild Shape does not remove it. Does not stack: a new source only replaces the pool if it is larger. Shown as a sky-blue "+N tmp" badge.

The arithmetic (temp → beast HP → real HP, with overflow on revert) lives in `src/rules/hitPoints.ts` (`applyDamage` / `applyHealing` / `betterTempHp`) and is shared by `encounterRun.adjustHp`, the player character sheet (`PlayerCharacterHeader`) and the DM party tracker (`PartyTrackerRow`), so all three agree. `hitPoints.test.ts` covers the beast-form and overflow cases.

**Where a PC's temp HP comes from during a run:** the party member row is the authority. `EncounterRunView.initStore` seeds `temp_hp` onto the player combatant at init, `EncounterRunner`'s `party_members` realtime subscription ingests later changes via `store.ingestTempHp` (assign-only, no write-back — the DB is the source), and the runner row/card read `displayTempHp` from the live party row exactly as they already do for HP, AC and conditions. Without all three a player's temp HP was invisible to the DM, and the first HP write persisted `temp_hp: 0` over it.

**Concentration:**

Concentration on player characters is tracked via `party_members.concentration`. When a concentration-breaking condition is applied via the runner, concentration is automatically ended. When the Dmg button is used against a concentrating PC, a concentration saving throw is prompted (auto-calculates DC as max(10, damage/2)).

**Boss mechanics panel (`RunnerBossMechanics.vue`):**

Appears above the combatant list when relevant.

- **Surprise panel** (pre-combat only): a toggle strip lets the DM mark creatures as surprised before rolling initiative. Surprised count is shown as a summary.

- **Lair Actions panel** (when lair is enabled and combat started): shows the lair owner's lair action list from their stat block. The panel is violet-highlighted when the action is available (once per round, at initiative 20). Clicking an action marks it fired for that round and posts to campaign chat.

- **Legendary Actions panel**: appears for each legendary creature that is NOT the active combatant and still has actions remaining. Lists all legendary actions from the stat block with cost parsed from the action name ("Costs 2 Actions"). Disabled buttons for actions the creature can't afford. Clicking spends actions and posts to chat.

**Stat block detail panel (`RunnerEntityDetail.vue`):**

Opens to the right when a combatant row is clicked. Width is user-resizable by dragging the left border (mouse and touch, 200–700px). On a phone it is a full-screen layer over everything, bottom nav included.

### The runner on a phone

Below `md` (`useIsMobile`) the runner is its own layout, because the desktop one stacked on a 390px screen showed about one and a half combatants: a header, a toolbar of six unlabelled icons, the Surprise strip and a pinned Events panel each took a slice, and every card was four rows tall. The phone layout gives the screen to the initiative order.

- **Header** (`RunnerPhoneHeader`): back, the encounter name with "Pre-combat" or "Round N", the turn timer and a Live marker; a Tools button whose badge counts unfired events plus traps; and an overflow menu with Go live / Stop live, the Map tab, the manual, and Abandon and End combat last, behind a rule, so neither can be hit by accident.
- **Rows** (`RunnerCombatantCard`): one line each. Initiative (the editable field with its die in the lobby, a plain number once started), portrait with the reveal toggle, the name with one summary line (roll status, surprised, wild shape, conditions, concentration, a spent reaction), and HP with a bar and AC. The row flashes whenever its HP changes, whoever changed it, except when the combatant goes into or out of wild shape, which swaps the pool shown rather than hurting anyone. One sheet serves every row, so `useRunnerCombatant` binds a run of +/- taps to the combatant it was made on and clears the typed amount when the sheet moves to another combatant; a blank HP field left on blur changes nothing. The active row scrolls into view as the turn moves.
- **Combatant sheet** (`RunnerCombatantSheet`): tapping a row opens everything you can do to that creature: HP steppers and max HP, an amount with Damage / Heal / +Temp (the sheet closes once one applies), conditions, initiative, surprise (lobby and round 1) and, for monsters, reveal. "Stat block & actions" opens the full-screen stat block.
- **Turn bar** (`RunnerTurnBar`), pinned above the bottom nav: Roll initiative and Start combat in the lobby; Previous, the active combatant (tap to open their stat block and actions) and Next in combat.
- **Tools sheet** (`RunnerToolsSheet`): Surprise, events and hazards, traps, spawn and the encounter's DM note, which the desktop shows in columns. `RunnerDmTools` takes `layout="stack"` for it.

Lair and legendary actions stay above the list on a phone: they are what the current turn needs.

For each combatant type the panel shows:

- _Monsters_: portrait, type/alignment, AC/HP/Speed/CR stats row, full ability score table (with clickable roll buttons), skills grid, senses/languages/resistances/immunities, full trait sections with inline attack roll and damage roll buttons, spellcasting list, legendary action pip tracker with "Use 1" button
- _NPCs_: portrait, race/occupation/alignment, stat block if defined (same sections as monsters), fallback message if no stat block
- _Players_: portrait, species/class/level, AC/HP/Speed/Prof Bonus, full ability scores with saves, skills grid with proficiency indicators, melee + ranged attacks section, death saves (tracked live with success/failure pips)
- _Companions_: portrait, type, AC/HP/Speed, ability scores if stat block defined, trait sections

**Ammunition (`useAmmoConsumption` + `src/rules/ammunition.ts`):** Firing a ranged weapon depletes the carried ammo — arrows/bolts/bullets/needles/darts/firearm rounds — resolved from the member's inventory (quiver/container → belt → backpack) or, for self-charged weapons (laser rifle, internal-magazine firearms), the weapon's own `charges`. `weaponAmmoTag`/`ammoTagFromName` (pure, unit-tested) classify weapons and stacks — tags/subtype/name tiers, with the imported 5e `"ammunition"` property as the final tier yielding the generic `"any"` tag (matches any recognised ammo stack) so a renamed/homebrew ranged weapon still tracks ammo; `weaponUsesChargesAsAmmo` (charges + `isRangedWeaponItem`) gates the self-charged path so a charged _melee_ weapon's charges are never burned by basic attacks. `useAmmoConsumption` owns selection + the decrement (`consumeOneFromStack` shared with `useThrownWeapon`) and is shared by both the DM runner (`RunnerPcAttacks.vue`) and the player's own combat tab (`PlayerCombatTab.vue`) so the two paths cannot diverge; both consume only after the attack roll actually resolves (a cancelled physical-dice prompt spends nothing — the runner passes an `onResolved` callback through the `roll-attack` emit, relayed via `RunnerPcPanel` and resolved in `RunnerEntityDetail`). Both surfaces disable the Attack button and show a remaining count when a weapon needs ammo it doesn't have.

**Thrown weapons (`useThrownWeapon` + `src/rules/thrownWeapon.ts`):** A weapon with the `thrown` property (javelin, dagger, handaxe, spear, light hammer, trident) shows a **Throw** action alongside its melee **Attack** — on the player combat tab as a second button, on the DM runner as a "Thrown Attacks" section. Throw rolls the same to-hit as melee (STR, or best of STR/DEX for finesse — the shared `src/rules/weaponAttack.ts` math) and then the weapon leaves the hand: `useThrownWeapon.throwWeapon` drops one to the ground as a recoverable `item_drop` in campaign chat (reuses `useCampaignMessages.sendItemDrop` + the existing grab flow — no new routes) and decrements the equipped stack, removing the row when the last one is thrown. `isThrownWeapon` (pure, unit-tested) trusts a vault item's `thrown` property and word-boundary name-matches item-less custom stacks — "Longspear" does _not_ match "spear" (Javelin/Spear/Light Hammer/Trident are also seeded as real weapons in `src/data/provisions.ts`). Throw consumption is gated on the roll resolving on both surfaces (see Ammunition above for the runner's callback path).

**Custom attacks (`src/rules/customAttack.ts`, #568):** Player-defined attack buttons for anything not derived from equipment — companion attacks, save-based features, improvised setups. Stored as `party_members.custom_attacks` JSONB (`CustomAttack[]`: `id`, `name`, `attack_bonus: number | null`, `damage` dice expression, `damage_type`); `attack_bonus: null` marks an auto-hit/save-based attack, so only the Damage button renders. The player's combat tab lists them in `PlayerCustomAttacks.vue` (between equipped weapons and the always-available melee card) with inline add/edit/delete, the same `v-roll-mode`/condition-driven attack-disadvantage handling as weapon attacks, and an `attacked` emit that clears Hidden on a completed to-hit roll. `validateCustomAttack` (name + `parseExpression`-parseable damage) gates saving; vitest-covered in `customAttack.test.ts`. The DM sees the identical list in the runner's `RunnerPcAttacks.vue`, in a "Custom Attacks" section after Class Features, emitting `roll-attack`/`roll-damage` through the same pipeline as the thrown/ranged sections so the two surfaces can't diverge.

**Roll mode bar** (top of detail panel, per combatant):

- Normal / Advantage / Disadvantage — affects all roll buttons in the panel
- Results shown in a transient banner (die result, modifier, crit/fumble highlighting, rolled-and-dropped die for adv/disadv)

**Chat mode bar**: toggles whether rolls are posted to campaign chat — Public (roll result visible to all in chat) / Silent (roll not posted to chat).

**Runner → chat write path**: everything the runner posts goes through `useCampaignMessages` — the pending-broadcast flush in `EncounterRunner` uses `sendSystemMessages` (array form, so a burst is one insert), lair/legendary announcements in `RunnerBossMechanics` and the spell-save call in `RunnerEntityDetail` use `sendSystemMessage`, and the flat-damage roll uses `sendRoll`. Never hand-build a `campaign_messages` insert here: the composable owns the row shape and the optimistic local push, so the DM sees their own runner message immediately rather than waiting for the realtime echo (#722).

**Events, hazards and traps strip (`RunnerDmTools.vue`):**

One strip of chips above the initiative list on a desktop (`layout="strip"`), and the same component in the phone's Combat tools sheet (`layout="stack"`, one line per group at thumb size). It renders nothing when the encounter has no events and no traps, so most fights give the list the whole width. It replaced two fixed 200px columns (EVENTS, TRAPS) down the runner's right edge (30 Oct 2026, the maintainer: "the event block ALWAYS takes a full column in the combat tracker but rarely ever gets invoked").

- Each event is a chip: a ▶ chip with its trigger ("Round 3", "HP ≤ 50%", "On death", "Manual") while it can still fire, for manual and auto-triggered events alike (the button force-fires an auto trigger). A fire-once event that has fired becomes a plain ✓ and its name; a repeatable one keeps its ▶ in a quieter style
- `checkEvents()` is called after every HP change and turn advancement; auto-triggers are evaluated against current state
- Firing an `environment_effect` action (#604) posts its label + description to the same pending-broadcast queue a `broadcast_message` action uses (`store.executeEvent`), and the hazard is then written out in full under the chips: rendered from `store.activeEnvironmentEffects`, the computed over fired events' `environment_effect` actions, so it survives a reload without a field of its own. A hazard only exists through a fired event, which is why the strip's visibility checks events and traps and not hazards
- Each trap is a chip with a type-colour dot, its save DC and damage dice; clicking it opens its detail in the entity panel (the same slot used by combatants), clicking again closes it

**Spawn panel (`RunnerSpawnPanel.vue`):**

Collapsible panel at the bottom of the combatant list. Allows the DM to add monsters or NPCs mid-combat:

- Monster / NPC tabs
- EntityCombobox search across all available monsters and every NPC, stat block or not (the encounter builder's NPC search too)
- Faction selector and count input
- "Add" button: injects the combatant(s) into the live initiative list with automatic initiative roll if combat is already started. Legendary action pools are primed for newly spawned legendary creatures.
- A monster the run has not loaded is read with a plain async call (`loadMonstersByIds`), not a watcher on a query: on a phone the panel lives in the tools sheet, which unmounts when it closes, and a watcher went with it, so a spawn picked and swiped away was silently dropped. A monster that cannot be found says so in a toast.

**Live mode and real-time player sync:**

When the DM clicks "Go Live" (requires an active campaign), the current combat state is written to the `encounter_state` table. Players subscribed via `useEncounterLive` see changes in real time (Supabase Realtime subscription).

State pushed on every change: round number, active combatant index, full `combatants_live` array (including HP, conditions, reveal state, wildshape), fired event IDs.

Auto-discovery: when going live, any monster already in the "revealed" reveal state is automatically added to `discovered_monsters` for all party members.

Player HP sync: the runner does not read or write `party_members` itself (#1201 stage 2c). A command that changes a player combatant makes the server write the character's row after the fight's own save (`player_persist` effects, retried three times and reported in `effectFailures`, which the runner shows as a toast), and a `party_members` ring from the campaign doorbell makes the runner send `sync_party`, which has the server ingest HP, temp HP, conditions, Wild Shape forms, death saves and player-rolled initiative changed outside the runner (e.g. a player updating their own sheet) and answer with the fight. Every ring reaches the runner, the one raised by the server's own write included; because the server reads the row itself in the same request that saves the fight, there are no write-timing guards left. This replaced the browser's debounced writes and the per-member `trackWrite` epoch of `useRunnerPartySync`, which existed because one browser was both writing and reading those rows.

**Companion bench sync, lobby only (#569):** A companion's `combat_ready` flag can flip while the encounter still sits in the lobby (round 0) — the DM benches one from the party-tracker `CompanionCard`, or the owning player toggles their own from the player panel (see Player View below). `EncounterRunner.vue` watches the live `companions` query (kept fresh by `useCampaignLiveSync` — `companions` was already in its table list, so this rides the existing subscription) and reconciles the roster against it: benched → `store.removeCombatant(instanceId)`, un-benched → `store.addCompanionCombatant(comp, factionId)`. Runs `immediate` so a bench toggle made while no one had the runner open is still reconciled the moment it mounts. Once combat starts (round > 0) the roster is locked — a companion already in the fight stays in it regardless of a later bench toggle.

**End / Abandon:**

- **End Combat**: confirms, cancels any pending HP debounce, ends the live state, syncs all player combatants' HP + conditions + curses + death saves back to `party_members`, resets the store, navigates to the encounter sheet. Companion combatants get the same write-back — HP + conditions to `companions` (#569; previously companion combatants were silently dropped at End Combat, so damage taken never persisted). (Roster-NPC death/reveal is handled live during combat — see below — not here.)
- **Abandon**: ends live without syncing player HP; useful when a combat didn't actually happen or was a mistake. Skips the companion write-back too, matching party members.

**Live roster-NPC sync:**

Roster NPCs run as combatants of `type: "monster"` carrying an `npc_id` (never `monster_id`), and their records are written back **the moment it happens, not at conclusion** — mirroring how monster discovery fires on reveal. Driven by a `watch` over the NPC combatants in `EncounterRunner.vue` (`src/lib/encounters/npcEncounterSync.ts`, `buildNpcSyncUpdate` + test), reacting to two events:

- **Revealed** — the DM cycles a token to `reveal_state === "revealed"`. The reveal toggle renders for any `type === "monster"` combatant, so roster NPCs are cyclable hidden → unseen → revealed exactly like monsters — that is how an NPC becomes "seen". On reveal the NPC joins the party's seen list: a _widening_ union on `npcs.player_visible_to` (never narrows an existing partial share) with `player_visible_fields` gaining `name`/`portrait` (`NPC_DEFAULT_REVEAL_FIELDS` in `lib/npcDisplay.ts`, shared with `NpcRevealControl` — note the sync _unions_ the defaults in, where a first reveal only seeds them when the DM has chosen nothing). An NPC left `hidden`/`unseen` is never added.
- **Died** — a token drops to 0 HP. **Death is a world fact**, written `status: "dead"` whether or not the party saw it — but **reveal always requires being seen**: a hidden NPC that dies is recorded dead and _not_ disclosed to players. A seen NPC that dies is both marked dead and revealed (same union, plus the `status` field so its death shows). If a hidden death is later seen (the DM cycles it to "revealed"), the reveal fires then, carrying the `status` field.

The builder (`buildNpcSyncUpdate`) takes the NPC's current `{ seen, died }` state and returns `null` when nothing would change (already dead + already revealed, or a DM pre-reveal), so writes happen only on real transitions; the watcher patches the local `store.availableNpcs` snapshot after each write so re-fires stay no-ops (healing-then-re-killing or a reveal→hide→reveal cycle won't spam writes). Reveal needs a party to reveal to; with none, death is still marked. Monster combatants have no persistent per-instance record and are untouched — this is separate from the monster **bestiary** discovery (`discovered_monsters`, `monster_id` only, fired on reveal-cycle + Go Live).

### Player View

Players read combat through `get_player_encounter_state`, which projects each visible combatant through an **allowlist** of the fields the portal reads (#1017). A field added to `RunCombatant` stays with the DM until it is named there; the old denylist had let a monster's concentration and surprise flags and a disguised NPC's true token art through, and would have let `action_uses` through. A disguise that swaps the portrait also withholds `token_url`. `player_encounter_state.test.sql` holds both.

Players see a live encounter panel in their portal. On mobile it renders as a full-page panel at `/play/encounter`; on tablet+ it lives in the layout sidebar (the same panel, just positioned differently by CSS).

**`PlayerEncounterPanel.vue`:**

- When no encounter is running: empty state with a message
- When live, but pre-combat (round 0): "Gathering Party…" lobby header
- Lobby only, and only if the player owns any: a "Your companions" strip (#569) toggles each companion Joining/Elsewhere before combat starts, writing `companions.combat_ready` directly (optimistic, reverts on failure) — see the runner's bench-sync note above
- When combat starts: round number + active combatant name displayed prominently; "YOUR TURN!" banner pulses when it is the player's turn
- On your-turn transition: screen shake animation + optional audio chime (player preference in settings)

**Combatant list (player-visible only):**

- Hidden monsters (reveal_state = "hidden") are completely invisible
- Unseen monsters (reveal_state = "unseen") appear as a "???" row with a grey placeholder portrait and NPC badge
- Revealed monsters and all players appear normally with name, type badge, initiative, portrait
- Active combatant has a highlighted row

**HP display** — controlled by the campaign-level `health_visibility` setting:

- `strategic`: PCs show exact HP and a colour bar; monsters show a descriptive label (Healthy / Hurt / Wounded / Bloodied / Dead) with a colour bar
- `immersive`: PCs show a colour bar with no numbers; monsters show only the label with no bar (`EncounterCombatantList.vue`)
- `unknown`: no HP information shown

HP bar colour thresholds: >75% green, >50% amber, >25% red, 0 grey.

**Clicking a combatant** opens a lightbox. Every visible row is tappable — a tap must never be a no-op, since enlarging the portrait to read a face is the whole point:

- Player / Companion: party member lightbox (portrait, stats, conditions, etc.)
- NPC the party has already met — i.e. present in the `get_player_visible_npcs` projection (`useSharedNpcs`): `PlayerNpcLightbox` — portrait (if the DM enabled it in NPC visibility settings), relationship badge, status dot, occupation, personal connection note (DM-written per PC), player notes widget, star rating (1–5 relevance)
- Everything else — monsters, and NPCs the party has **not** met: `EncounterCombatantLightbox` — enlarged portrait + name straight off the live combatant, plus a player notes widget keyed on `npc_id`/`monster_id` when one is present

That last fallback matters: an enemy NPC the DM revealed only inside the encounter is not in the player's NPC roster, so there is nothing to look up. The live combatant already carries the name, portrait and focal point the row is drawing, and the DM authorised showing it by setting `reveal_state` — so the lightbox renders from the combatant directly. Never gate the player panel's NPC lookup on the raw `npcs` table (`useNpcs`): RLS there requires the NPC to list this player in `player_visible_to`, which is a different visibility axis than encounter reveal, and it also hands the client DM-only columns and the true identity of disguised NPCs.

## The Play screen (#1125)

One screen runs a fight and, before it, exploring: `/encounters/:id/run` (`src/components/encounters/play/`). It replaces the old runner-plus-map pair; `/encounters/:id/run/map`, `EncounterMapView` and the runner's Battle Map button are gone, with no redirect.

**Scatter in a room (#1125 decision 11).** Under the tray of unplaced combatants, `PlayUnplacedTray` offers **Scatter in <room>** (one room) or a `MenuPopover` of the map's rooms (several, the fight's focus room first), shown only when a non-player is waiting. `usePlayMapState` lists the rooms from `roomBattleCells` with names from `useLocationNames`, and `scatterInRoom(roomId)` seats every unplaced non-player through `moveCombatant`, so a scatter spends no movement and records no undo. The rule is `lib/battlemap/scatter.ts`: largest first, each takes the free spot farthest from every token already on the map and from those scattered before it (the room's middle when the map is empty), ties in reading order; a creature with no room left stays in the tray. It shares half-cell occupancy (`lib/battlemap/occupancy.ts`) with `seedTokenPositions`.

**Layout.** From tablet width up the Play screen is full screen (the app shell steps out of the way; "Encounters" is the way out). Left: the initiative list with the tray of unplaced combatants beneath it. Centre: the map with the toolbelt along its bottom. Right: the turn card on someone's turn, or their sheet (`RunnerEntityDetail`) when another combatant is selected. The bar carries Go live, the turn timer, a **Tools** button and a **View** menu. Tools opens a sheet (`PlayToolsSheet`) holding what used to sit around the runner (surprise, lair and legendary mechanics, events, traps, spawning, the DM's note) so the map has the screen. View toggles As players see it, Grid, Zones, Tokens, Fog, Follow the turn and Legend, with Reset view; the legend is off the map until asked for. On a phone the screen is the phone runner with a **List | Map** switch (`PlayPhoneMap`); the map there is the same `PlayMap`. The Table screen button is always enabled and opens the map's one Table screen (`/locations/:id/table`, see "One Table screen per map" below), which follows this fight while it is live and never builds the runner's store (see "Who writes the live row" below).

**Moving a token.** Click a token, then a square, or drag it (a ghost snaps live); the arrow keys step one square; Shift-click adds a waypoint that bends the path; Shift-drag a box (or select several) to move a group in formation, every member by the leader's offset. Tokens move under any tool. A path is drawn with its cost in feet at the end ("25 ft", then "a Dash" or "past a Dash" against what the turn has already moved, then what made it dear). **Back to start** (turn card) takes the turn's moves back until the turn ends; it is per combatant and stored in the run store (`moveHistory`). **The counter warns and never refuses** (#1125 decision 11, "the DM is never blocked"): a move past the speed or past a Dash still happens.

The rules are in `src/lib/battlemap/movement.ts`, pure and DOM-free, each one cited by book:

- Every square costs 5 ft, a diagonal too (PHB 2014 "Movement and Position", PHB 2024 "Moving").
- Difficult terrain costs 1 extra foot per foot (both PHBs, "Difficult Terrain"): a square is 10 ft. A token is slowed when any square it covers is difficult. The zones are the site plan's `zone` regions with `movement_cost > 1`: a room fight keeps the zones that touch the room, a whole-map fight (no focus room) counts every zone on the map (`terrainZonesOf`, `useEncounterRoom.ts`).
- Squeezing: a creature whose box is cut by a wall that a box one size smaller would clear costs 1 extra foot per foot (both PHBs, "Squeezing into a Smaller Space"). It stacks with difficult terrain, so a squeeze through rubble is 15 ft a square. Medium and smaller never squeeze.
- Dash: the action gives extra movement equal to speed, so a move up to twice the speed is a Dash; the bar on the turn card is two speeds long.

`usePlayTokenMoves` owns selection, waypoints, previews and group plans; `usePlayMapState` owns what the map reads and writes that is not geometry (combatants, the map's memory and sight, darkness, doors, token seeding, rooms entered, `moveTerrain`).

**The turn card** (`PlayTurnCard`, frame 10) reads **1 Move, 2 Act, 3 Next turn** and always shows the active combatant, whatever else is selected. Move: "Moving N of S ft" and the bar, or "Moved N ft · Speed unknown" with no bar when nothing on the board names a speed (it never guesses one; a bar against 0 would read full). Act: Action, Bonus action and Reaction chips (`RunCombatant.action_used`, `bonus_used`, `reactionUsed`, reset at turn start), who the token is next to, the combatant's attacks to roll (a monster's or NPC's stat-block Actions and Bonus Actions through `RunnerActionList`; a character's through `PlayPcAttacks`, which mounts the sheet's own `RunnerPcAttacks`), and the Enlarge/Reduce size select. A character's attack rolls from the card go through the same pipeline as from the full sheet: `useRunnerRolls` (prompted roll, chat post, banner state) and `useRunnerPcAttacks` (features, proficiency bonus, ability modifier) are shared by `RunnerEntityDetail`/`RunnerPcPanel` and the card, so there is one implementation. The card has no roll-mode toggle; it rolls plain and public. Next: Next turn, and a line saying damage lands on whoever is selected.

**Token sizes** (decision 13, `src/lib/battlemap/tokenFootprint.ts`). Every creature takes its size: Tiny shares a square (half-cell positions, up to four per square), Small and Medium one square, Large 2 x 2, Huge 3 x 3, Gargantuan 4 x 4 (PHB 2024 "Creature Size"). A monster's comes from `size`, an NPC's from `npcs.size`, a companion's from `companions.size`, a character's from species/subrace, a wild-shaped druid's from the beast (`WildshapeState.beast_size`), and Enlarge/Reduce sets `RunCombatant.size_override` from the turn card, which beats the others. The footprint is baked at spawn because players cannot read the monster tables; `get_player_encounter_state` carries `size_override`.

**Walls and doors.** Walls are segments between two points in cell units; a grid wall's id is the edge key (`"x,y:N"` / `"x,y:W"`), an angled wall's a uuid, so `location_doors.edge_key` and `encounter_state.door_states` keep their meaning. The live snapshot is `MapLive` version 3 (`src/types/mapLive.types.ts`): walls and doors are listed by id, and sight, light and the squeeze test all work on segments (`walls.ts`, `occlusion.ts`, `doors.ts`). Stored snapshots and `dungeon_maps.layers` were migrated once in SQL; every site re-publishes to carry the new shape. A wall may be `visible: false`: it blocks sight but is not drawn.

**Moving maps.** A moving base image (GIF, animated WebP, WebM, MP4) stays on the DM's device: the file lives in the browser's Origin Private File System keyed by the place id, and only a WebP still goes to R2 as the base image. It plays on the DM's own screens (Edit map, Play, the Table screen window, all the same origin); players, and any device without the file, see the still. `locations.map_motion` records `{kind, file_name, bytes, width, height}` so another device knows to ask for the file once ("Pick the file", warned on a mismatch, never refused). The Play map draws the whole stack, base image beneath Drawing beneath the standing layer, so a picture with an imported invisible Drawing still has walls, light and sight.

**Table tools** (frame 11, decision 12; `play/PlayToolbelt.vue`, `usePlayTableTools.ts`, `useAreaTool.ts`). The toolbelt has seven tiles: Move (V), Measure (M), Area (T), Fog (F), Darkness (K), Ping (P), Draw (D). Doors open with a click and tokens move by dragging under every tool, so a press that starts on a token never reaches the tool; `resolvePointerAction` lets a door win over the tool, then an armed portrait, then the tool.

- **Measure.** Drag from anywhere, or click to keep the line and click again to bend it round a pillar (a waypoint); clicking the square it already ends at, or Esc, lets it go. It measures from the middle of a square, 5 ft a square with diagonals included (`lib/battlemap/measure.ts`, PHB 2024 "Moving"). A kept line is re-sent every 5 s so the channel's 10 s expiry does not drop it. Players see the line while it exists.
- **Area.** Sphere, Cone, Line or Cube plus a size in feet. A sphere or cube follows the pointer and a click sets it down (sphere on an intersection; cube centred so it covers whole squares). A cone or line starts on the edge of the selected token's square (so the caster is not in it) and is aimed by the pointer, or, with nobody selected, from a first click. `lib/battlemap/areaTemplates.ts` covers the shapes per PHB 2024/2014 "Areas of Effect" (a cone's width equals its distance from the origin; a line is 5 ft wide); a square is covered when the area covers at least half of it, which is an app convention, as is a creature being inside when any square it stands on is covered. Setting one down selects the creatures inside, which rings them through the ordinary selection; the slip reads "20 ft · 3 inside" and **Damage all N** takes one typed amount off every selected creature through `encounterRun.adjustHp` (`playArea.ts`). It hits the selection, not the template, so the DM can add or drop someone by clicking tokens first. The saves stay the DM's.
- **Fog.** Room · Brush · Hide. Room reveals the whole traced `space` region under the click (`lib/battlemap/roomFog.ts`, `usePlayMapState.revealRoomAt`). Every stroke is a write to the map's memory (`useMapMemory`), not to the fight, so it outlives the fight and shows on the explore screen too. Reveal all and Hide all replace or empty the memory (`replaceWith`, `forgetAll`). The fog slip also holds the **As players see it** switch (the View menu's switch).
- **Ping, Draw.** A ping is a gilt ripple on every screen with "<name> pinged". Draw is a freehand stroke in the drawer's colour (`senderColor(user id)`, `lib/table/identity.ts`); strokes fade when the turn changes (`PlayMap` calls `clearUnpinned()` when the active combatant changes) unless **Pin drawings** is on, and **Clear drawings** wipes all. Strokes go out at most 10 times a second (`DRAW_THROTTLE_MS`; Broadcast is rate limited) and stop at 500 points (the channel's limit).
- **Everyone sees them.** `PlayTableMarks.vue` draws pings, measure lines and drawings from `useTableChannel` on the Play map (the follower window too), the explore map and the player's map (`PlayerEncounterMapView`, where a long press of half a second pings the spot). Coordinates are battle-map image cells. Players send pings only. The explore map (`ExploreMap`) has Move, Measure, Ping and Draw; fog there is by room, so no Area, Fog or Darkness.

Two topics (#1133 review, `20261103093434`): any member pings on `table:<campaign id>`, and only the DM sends measures, drawings and clears, on `table-dm:<campaign id>`, which every member hears. Realtime authorizes a sender when it joins a topic, never per message, so `useTableChannel` takes only a ping from the shared topic, and a player cannot clear the DM's drawings or draw in the DM's name. Verified against the real local Realtime: the DM and the player fixture both join `table:<campaign id>` as private channels and each hears the other's ping (a node check driving supabase-js, 31 Oct 2026). The browser path (pointer to channel on screen) is covered by component tests only.

## Battle Maps — The Room Bridge

Before #868, opening the battle map required a location with its own uploaded image and an explicit `is_battle_map` toggle — a room with no separately uploaded art simply had no battle map to open. `src/lib/battlemap/roomBridge.ts` (epic #868, frame 13 "When the plan is a battle map") bridges this the other way: a room traced on its site's _published_ Atlas plan is already a legal battle map at combat's own cell scale, with no separate art, no separate calibration, and no toggle to remember.

**Two coordinate spaces, one converter pair.** A room's traced cells (`location_map_regions.cells`) live in the Cartographer's own map-cell space — the same space the site's structure was published into (dungeon-craft.md's "Placed in" section covers the sibling case for placements). The battle map's tokens and fog mask, however, have always lived in a separate _image_-cell space, where cell `(0,0)` is the baked image's own top-left corner. The two spaces are offset by exactly the padding the bake added around the drawing, recorded as `grid_calibration.origin_cell_x/y`. `regionCellToBattleCell()` / `battleCellToRegionCell()` (`roomBridge.ts`) are the only two functions that ever apply that offset — every room outline, zone overlay, token seed and fog-reveal check goes through one of the two, so a mismatch there would silently misplace every token seeded into a room rather than surfacing as an error.

**`resolveBattleSurface()`** decides which map an encounter's battle view actually draws, given the encounter's own location, that location's parent, and the parent's regions. Three outcomes: a location with its own `map_url` **and** `grid_calibration` behaves exactly as it did before #868 — nothing changes for a location that carries a separately uploaded battle image, room or not; an **interior space** (`room` or `grounds` — `isInteriorType()` from `@/lib/locations/tiers`, since #886 moved `grounds` down from the site tier to sit beside `room`) with no map of its own but a calibrated parent site resolves to the _parent's_ plan instead, focused on whichever region has `region_role === "space"` and `space_location_id` equal to its id (its cells converted to battle-cell space); anything else — an uncalibrated site, an interior space with neither — resolves to `null`, meaning there is no surface to draw. The result (`mapLocation`, `focusRoomId`, `focusCells`, `calibration`, together a `BattleSurface`) is the single source of truth the runner's gate and the map view's render both consult, via `useLocationBattleSurface()` / `useEncounterRoom()` (`src/composables/encounters/useEncounterRoom.ts`) — both call the same function with the same inputs, so they cannot disagree about which map is on screen. Every call site that decides "does this location ride its parent's plan" goes through `isInteriorType()` rather than comparing `location_type === "room"` inline, so `grounds` is never silently excluded again.

**`seedTokenPositions()`** places every unpositioned player-type combatant — party members and companions alike, "party tokens" in frame 13 — onto a free cell inside the focus room, row-major and footprint-aware, never overlapping two tokens. It only ever fills combatants that have no position yet, which is what makes it safe to call on every mount while live rather than once: re-seeding after the DM has dragged tokens around is a no-op for the ones already placed.

**The fog is the map's memory, not the fight's (epic #1133).** `public.map_memory` (migration `20261103093432_the_map_remembers.sql`) holds one row per campaign and per place whose map is drawn (the site for a fight in a room, else the place itself): `seen`, the squares as `"x,y;x,y"` in the map picture's grid cells (the encoding `lib/battlemap/fogMask.ts` already used). Members read it; only the DM writes, through the invoker RPC `remember_map_cells(campaign, place, reveal, hide, forget)`, which merges on the server so two DM windows brushing at once cannot overwrite each other. It rings the campaign doorbell (`map_memory` signal) like every live table. `encounter_state.fog_mask` is dropped and `get_player_encounter_state` no longer returns it, so Go live no longer wipes anything and `seedFogMask`, `shouldSeedFog`, `roomsRevealedInCombat` and the end-of-combat "Mark N rooms revealed in combat as explored?" prompt are gone. The client side is `useMapMemory` (`src/composables/locations/useMapMemory.ts`): `remember`, `hide`, `replaceWith`, `forgetAll`; a write shows at once and writes batch while one is in flight. `usePlayMapState` reads it for the surface's map place and only the DM's controlling window (not a follower) writes.

**Sight lifts the fog (epic #1133 decision 1).** `src/lib/battlemap/partySight.ts` is the pure core: `sightScene` (the snapshot's lights, walls and doors at their play state, magical darkness; with no snapshot, daylight with nothing in the way), `sightCells` (every square some party viewer sees: lit, or within darkvision, blindsight or truesight range, with a clear line), `shownCells` (memory plus sight, what a player screen draws), `newlySeen` (seen but not yet remembered), `partyVisibleCombatants` (a phone: the own token always, any other only where the party sees a square of its footprint), `tableTokens` (the Table screen and the DM's preview: every placed player character always, any other token only where the party sees it), `footprintCells` and `imageGrid`. `usePartySight` (`src/composables/encounters/usePartySight.ts`) turns party tokens into viewers with their real senses (`usePartySenses`, `src/composables/party/usePartySenses.ts`: species and subrace darkvision plus the character's senses field, none for a character the player may not read) and returns `{ viewers, sight }`; an `onlyInstanceId` makes a phone look through its own character alone. `useRememberSight` (`src/composables/locations/useRememberSight.ts`) writes `newlySeen` into the memory once a drag has settled (300 ms), in the DM's controlling window only and only when the campaign's Map memory setting is `remembered`; in `strict` nothing is written by sight and the DM's hand reveals are the only memory. A square that is remembered but not seen now is drawn half fogged: `BattleMapFogLayer` takes a `seen` set and puts a flat half fog over the punched squares outside it.

**Two campaign settings (epic #1133 decisions 3 and 4).** `campaigns.map_memory` (`remembered` default, or `strict`) and `campaigns.player_sight` (`shared` default, or `own`), set in Campaign Settings, Details (`DetailsTab.vue`, `SettingChoiceList.vue`, beside Health Visibility). `own` is read only by the player's phone (`PlayerEncounterMapView`), which then looks through its own character alone; the Table screen and the DM's preview always use the whole party.

**Rooms are marked Explored as the party walks into them.** In the DM's controlling window `usePlayMapState` watches where the player tokens stand against the traced rooms (`roomCellIndex`, `roomsUnder`) and asserts `explored: true` through `useAssertLocationState` once per room per session, with the note "entered in a fight". Nothing is asked, and nothing un-explores a room. End combat (`EncounterRunner`) writes each player token's final square into `campaigns.explore_party` for the fight's site (`partyAfterFight`, `src/lib/encounters/exploreAfterFight.ts`; a member who was not in the fight keeps the square they had), so the party stands where the fight left them. The explore screen's "Start it" opens the run with `?live=1`, and the runner goes live on arrival once the live row has been read, then drops the query.

**`useCombatExploration()`** (`src/composables/encounters/useCombatExploration.ts`) owns the battle-map gate. The gate (`resolveBattleMapGate()`, pure and independently tested): a room riding its site's published plan is _already_ a legal battle map, so `is_battle_map` is not consulted at all once `surface.focusRoomId` is set — being the focus of a resolved surface already proves the map is the site's own calibrated plan drawn at cell scale, not tactical art the DM has to separately opt into showing. Since #1125 decision 14, `is_battle_map` gates no play at all: any place whose map has a calibrated grid resolves a surface, and a resolved surface opens, room or not (the same in `usePlayMapState`'s loading state and in `EncounterBattlefieldSetup`). The flag's one remaining job is keeping a battle map out of the Atlas's geography zoom (`lib/locations/mapZoom.ts`). Every other combination (no location linked, no map at all, an uncalibrated map) returns its own reason string rather than a single blanket "can't open."

**`seedTokenPositions()` is the only seeding left.** It places every unpositioned player-type combatant onto a free cell inside the focus room (see above). `usePlayMapState`'s `seedRoomIfNeeded()` re-runs it on every call and on a change in the roster's length, which seats a combatant spawned mid-fight; it is idempotent on its own, so no flag guards it. It reads the live row, never the runner's store: the store does not hear players' moves, so seeding from it in a second window put every moved token back at its seat. Each placement is written through `update_combatant_position`. The fog is not seeded: what the party sees comes from their senses.

**Who writes the live row (#1120, reworked by #1201).** Three kinds of write reach `encounter_state`, and each owns its columns. The fight itself (round, turn, combatants, fired events, going live, ending) is written only by the `encounter-command` function, which the runner and the encounter page send commands to; the browser never writes those columns (no `pushState`, no roster blob, no debounce), so a second runner or a player's token move can no longer be overwritten by a stale copy. Every battle map, the DM's and the players', writes token positions one combatant at a time through `update_combatant_position`, which lets the campaign's DM move any token and a player only their own (`20261030104856`), and works on a row that is not live, since every run is a row; a position is not a command, and the runner's store takes it from the row's next read. The DM's battle map writes its own state (magical darkness) through `scheduleMapPush`, which writes only the columns given and merges a burst, so it never carries a roster; its fog is not on the row at all but in `map_memory` (above). These are the only two writes to `encounter_state` left in `src/` (`pushMap` and `updateCombatantPosition`, both in `useEncounterLive`). A battle map opened in a new window (the runner's ↗, or the Table screen button, which opens `/locations/:id/table`) is a **follower**: its tab has no run in its store, so it draws the row and never builds the runner's store, which keeps a "Back to Runner" from it building the runner properly. A follower that is not live says so in place of the map. Both windows draw the saved row, which the doorbell keeps current: `useEncounterLive(id, { follow: true })` re-reads the row on every `encounter_state` ring, and the runner's transport takes the same reads (`liveRevision`). A followed read is never adopted while the tab has a map or token write of its own pending or in flight; it waits for the write to settle and reads again, so a token drag does not flash back. The runner's own list shows a click at once, while the map, which draws the row, shows it when the server has answered. Leaving a view sends a pending map write rather than dropping it.

**One Table screen per map (epic #1133 decision 6).** `/locations/:id/table` (`views/locations/MapTableView.vue`) is the only Table screen; `/encounters/:id/table` and `EncounterTableView` are gone. It stays open on the TV for the whole session and switches between `components/table/MapTableExplore.vue` (the party walking the map, from `campaigns.explore_party`, with memory plus sight as fog) and `MapTableFight.vue` (ribbon, monsters and whose turn, from the live row) while a fight on this map is live: `MapTableView` compares the campaign's running encounter's map place (`useRunningEncounters`, `useEncounterRoom`) with its own and returns to exploring when the fight ends. Both draw through `components/table/TableScreen.vue`, never write, and use `tableTokens`: every placed player character always shows, monsters and other tokens only where the party sees them. A map the party is not exploring shows its memory and no tokens. The picture of a place's Book Nook (#1142) is a third thing it can show, never during a fight: a fight on the map always wins over `campaigns.table_shows`. See `publishing-tools.md`, "Book Nook".

**`BattleMapRoomFocusLayer.vue`** draws the visual half of a focus room: the whole plan dimmed to a translucent near-black everywhere except the focus room's cells (one SVG path with an even-odd fill rule, so the "holes" are the visible room), the room's own outline traced from its cells' actual boundary edges rather than a bounding box (so an L-shaped room reads as L-shaped, not as its rectangle), and any difficult-terrain zone inside the room outlined in dashed cyan. It is the DM's alone, labelled "Fight here" (`FIGHT_LABEL` in `PlayMap.vue`): the layer is not drawn in **As players see it**, and the Table screen and the phones never dim the rest of the map. The zone outline is a _read_, not an enforcement — frame 13 is explicit that it "does not halve anyone's speed"; the DM still applies that by hand with the existing condition/movement tooling.

**`BattleMapLegend.vue`** is a bar under the map explaining the Party / Hostile / Large / Active-turn token colours — pulled from the actual rendering constants (`DEFAULT_TOKEN_RING_COLOR`, `DEFAULT_FACTIONS`) rather than a second invented palette — plus one row per difficult-terrain zone inside the focus room, named for that zone's own `label`.

**`EncounterBattlefieldSetup.vue`** — the builder's pre-placement panel, used before an encounter ever goes live — resolves readiness through the same `useLocationBattleSurface()` rather than checking the location's own `map_url` / `is_battle_map` directly: a room with no map of its own is "ready" for token placement the moment its site's plan is calibrated, exactly as the runner treats it, so the builder and the runner can never disagree about whether a given room supports placement.

**Token art — cutout over portrait (#917).** A monster or NPC token prefers its `cutout_url` (the figure alone on a transparent background) over its `image_url`/`portrait_url`: the whole figure is drawn scaled to fit the ring ("contain", `src/lib/tokenRenderer.ts`'s `drawToken`), standing over the ring's background, rather than the picture cropped to a circle. `src/lib/battlemap/tokenArt.ts`'s `resolveTokenArt()` is the one place that reads `cutout_url` off either row shape. Precedence in `BattleMapTokenLayer.vue`'s `resolveTokenImage()`: a ready 3D-mini render (`portraitOverrides`, drawn "cover", its own composition) beats the baked `RunCombatant.token_url` (the cutout, "contain", no focal point), which beats `portrait_url` (drawn "cover", honouring `portrait_focal_point`). `token_url` is baked at spawn time exactly like `portrait_url` — in `buildRunCombatants.ts` and `encounterCombatLogic.ts`'s `buildMonsterCombatants`/`buildNpcCombatants` — because it has to travel to players, who have no `monsters`/`npcs` table access; party members and companions have no cutout and leave the field unset. Without a cutout, nothing changes: the token draws exactly as it did before #917.

**Paper doll as token (#975).** A party member whose character has its own paper doll (`art.source === "character"`; a species or template doll never qualifies, as it would replace a player's personal portrait with a generic figure) draws that character's OWN doll figure as its token, in its current outfit, so putting on plate changes the mini. A token figure is a `TokenFigure { url, source }`: `dollTokenFigure(picture, anatomy)` frames the figure inside the picture's sheet, undoes the outfit's drift shift and clamps to the picture's clip so a neighbouring figure never enters, and `drawToken` draws it with `containRect`. `useCombatantDollFigures` builds an instance_id to `TokenFigure` map from the party rows and the worn gear, passed to `BattleMapTokenLayer` as `figures` on both the DM and the player map. Precedence: beast form, then mini override, then own doll, then cutout, then portrait. The layer's render key includes `dollFigureKey(figure)`, so a gear change redraws only that token.

**The stack, bottom to top (#1073).** `BattleMapStack` owns it for both the DM and the player view: the ground image (`map_layer_url`, or the base image), the ground live layer (`stratum="ground"`: water and the open mass), the grid, the standing image (`map_layer_stand_url`), the top live layer (`stratum="top"`: the swaying props, running no loop while the snapshot has none), the darkness veil (`BattleMapVeil`, mounted only when `live.darkness` is `dim` or `dark`: one canvas painting `paintLitVeil` over the image rect, redrawn when its inputs or the host size change. The lit edge breathes (2 Nov 2026, `lib/battlemap/veilBreath.ts`): the grid is computed once and kept as a static veil; while any light can breathe a loop re-lays it each frame and, per light, lifts the veil in the ring between the steady reach and the swollen one (`destination-out`) or lays the ambient veil back inside the steady reach when it fades (`source-over`, skipped for a light standing in another's core), each cut to that light's sight mask (`boostMask`, shared with the live layer) and composed on a scratch canvas at `SCRATCH_SCALE` of screen size, plus a warm halo in the light's colour. The rings that lift, the rings that lay back and the halos are each gathered on a canvas of their own and laid on the veil in one draw apiece, never one per light (a draw onto the screen-sized veil cost about half a millisecond); every one of these canvases only grows, because resizing reallocates. A player's lift is also limited to where they see (`seenLimit`), so the opaque unseen veil never leaks. `illuminationGrid` is never re-run per frame. Reduced motion, a hidden tab or a map without lights runs no loop and shows the still veil. The snapshot's lights carve it by the rules, and a light only reaches what it has a clear line to (walls, closed doors, sluices and solid rock stop it; a light on a wall fitting's edge shines from the face it hangs on, `nudgedOrigins`): bright light clears the veil, a light's dim ring halves it, the brightest source at a point wins and light never adds up, so overlapping dim rings stay dim. The light grid (`illuminationGrid`, four samples per cell over the image's cells) is computed from the snapshot and the cell window only, so a pan that merely translates redraws the same grid at a new offset, and so does a zoom: the window's ratios are snapped before rounding, because the float noise of a zoom once grew the window by a cell every few wheel steps and recomputed the grid each time. `currentMapLive` hands every reader the snapshot unwrapped from Vue's reactivity: read through the query row's proxy, one grid took 720 ms instead of 15; the grid itself does not change as a fire flickers; only the breathing edge above moves. The DM's veil is translucent; a player's is their token's sight, below), then room focus, tokens and fog in the views. The standing image shares the ground's box exactly, so it needs no calibration of its own. It is shown only when the image on screen is the location's Drawing (`BattleSurface.standUrl`, set the same way as `live`) and the site was published after the split; a hand-calibrated base image, or an older drawing, is one image under the grid as before.

**What a player sees in the dark (#1073 story 5).** The DM sees everything with darkness as a translucent veil. The player view passes `viewers` to the stack and the veil paints `paintPlayerVeil` instead, from `src/lib/battlemap/vision.ts`, by the 5e rules (the same in 2014 and 2024): a creature sees bright light normally, dim light lightly obscured (veil 0.45) and darkness not at all (opaque). Darkvision within its range lifts that one step: dim light counts as bright, darkness counts as dim, and in darkness the pictures show in shades of grey only (the veil builds the grey from the stack's own ground and standing images, drawn with a grayscale filter and masked by where darkvision reaches into darkness; it draws without the grey until the images have loaded). The range edge is softened over a third of a cell like a light's, and the grey fades with the light level so a ring's edge does not snap. The viewers are the party's tokens (centre of the footprint), each with its own senses: on the Table screen, the DM's preview and a phone in the default **Shared by the party** sight, every player character looks, and on a phone in **Each their own** only that player's own character does (`usePartySight`, see above). What any viewer sees is also lifted out of the fog (`sightCells`), and a square seen is written to the map's memory in Remembered mode. A character in complete darkness without darkvision sees nothing and reveals nothing; in daylight (a map with no light snapshot) line of sight alone decides. A phone whose character has no token placed sees only what is lit. The ranges come from `characterSenses` (`src/rules/characterSenses.ts`, story 9): for each sense the better of what the species grants and what the character's own Senses field lists, never the sum. Species darkvision is read through `darkvisionFeet` (`src/rules/speciesStats.ts`): the first number before "feet" in a trait whose name contains "darkvision", a subrace's own trait replacing its parent's. The Senses field (`party_members.senses`, free text in the monsters' form: "darkvision 60 ft., blindsight 10 ft.", read by `senseRanges` in `src/lib/senses.ts`) carries everything else a class feature, feat, item or spell grants; the DM and the player edit it on the character, and the engine reads only the number. Blindsight within range perceives a point whatever the light, clear and never grey (it is not sight), and truesight within range sees darkness as clear (and, with Devil's Sight, sees through magical darkness, below); both need the same clear line as everything else, so neither passes a wall. The best sense of the best viewer wins per sample, with the same softened range edge. Tremorsense is parsed and shown but not used by the map: it senses creatures touching the ground, not the surroundings. Tokens obey sight like fog: any token other than the player's own whose cells no viewer sees is not drawn (`partyVisibleCombatants` on a phone, `tableTokens` on the Table screen, where every placed player character is always drawn). The fog (memory plus sight, `shownCells`) is drawn above the veil. Sight needs a clear line (story 6, `occlusion.ts`): a sample is seen only when a line from one of the viewers' centres to it crosses no wall, closed door, sluice or solid rock, so nothing behind them is seen, lit or not, and darkvision does not reach round them; with no token placed there is no line to test. What blocks: walls, closed doors, sluices (a solid gate) and solid rock; not open doors or grates (bars you can see through). Doors stand at the state the DM left them in during the fight (doors in play, below). Tokens behind a wall are hidden the same way. The vision grid is rebuilt only when the light grid or the viewers change, not on a pan.

**Magical darkness (#1073 story 10).** The _darkness_ spell's 15-foot sphere, or a lair's shadow, is darkness no light lifts and darkvision cannot see into (2014 and 2024 alike). It lives in `encounter_state.magical_darkness` (jsonb, `EncounterState.magical_darkness`): a list of `{ id, x, y, radius }`, the centre in battle-map image cells (fractional, the space of the fog and tokens) and the radius in feet. It starts empty on every go-live, the DM writes it through `scheduleMapPush({ magicalDarkness })` (see "Who writes the live row"), and `get_player_encounter_state` returns it, so it reaches players on the existing campaign doorbell with no new subscription. The DM places it with the **Darkness** tool in the toolbar (its own group beside the fog tools, radius 10, 15, 20 or 30 ft, 15 by default): a click inside a sphere removes the topmost one there, a click elsewhere places one centred on the click, no drag (`usePlayMapState.toggleDarknessAt`, `zoneIdAt`). The DM sees each sphere's edge as a dashed ring painted by the DM veil (`paintZoneRings`); a player sees no ring, only what their sight leaves. The rules are in the maths: `illumination.ts` takes the spheres as an input (a point inside one is level 0 whatever the ambient and the lights, even on a daylight map, and a light's line that passes through one is stopped like a wall), and `vision.ts` (`LitScene.zones`, `visionGrid`'s `zones`) lets blindsight within its range perceive a point whatever zones are in the way (walls still stop it), lets truesight and Devil's Sight (`Viewer.devilsSightFeet`) within their range see into and through a sphere clearly, and gives everyone else nothing inside a sphere and nothing behind one (a line that enters or crosses a sphere is blocked, so darkvision does not help). A creature standing inside a sphere sees out of it to lit places beyond: the sphere holding the viewer's own origin does not block its line, though what lies inside a sphere stays unseen and a different sphere on the way still blocks. A light inside a sphere sheds no light beyond it. `seenCombatants` and `canSee` follow the same rules. Devil's Sight is read from the character's Senses text by `devilsSightRange` (`src/lib/senses.ts`, 120 ft when named without a number) and returned by `characterSenses` as `devilsSight`, and `formatSenses` lists it after the other senses on the sheets. The veil mounts when the map is dim or dark or there is at least one sphere, for the DM and the player both, so a sphere on a daylight map is ambient 1 outside and 0 inside.

**Doors in play (#1073, moved to the map by #1134).** Only the DM opens and shuts doors, and the state belongs to the map, not the fight (the maintainer, 3 Nov 2026, reversing #1073's "belongs to the fight"): a door opened in a fight stays open when the party goes back to exploring, and one opened while exploring stays open into the next fight. It lives on `map_memory.door_states` beside what the party has seen (migration `20261103093435`; jsonb, shape held by `private.is_door_state_list`): a list of overrides `{ id, open }` over the drawn state in the snapshot's `doors`, ids being segment ids (`"x,y:N"` / `"x,y:W"` for a grid door, a uuid for an angled one). `useMapDoors` (`src/composables/locations/useMapDoors.ts`) reads it for a campaign and map place and writes one door at a time through the invoker RPC `set_map_door` (DM only; it replaces that door's override and returns the list), optimistic in the cache. A DM's press on a door flips it under any tool, on the Play map (`usePlayMapState.toggleDoorAt`) and on the Explore map (`ExploreMap` emits `door`); a follower window and every player screen only read. `encounter_state.door_states` is gone and `get_player_encounter_state` no longer returns doors: players read `map_memory`, which they may, through the same composable, and the `map_memory` signal rings `map-doors` as well as `map-memory`. `effectiveDoors` lays the overrides over the drawn doors, and everything that asks what blocks reads through `occludersOf(live, doorStates)`, memoised per snapshot and per override array: the DM's veil, the party's sight on every screen, the token footprint walls and a fire's flicker mask. `useMapDoors` keeps the previous array while a re-read says the same thing (`sameDoorStates`), so a ring that changes nothing rebuilds no light grid. The leaf is drawn live as well, so an opened door looks open: each snapshot door carries its leaf art (`leaf`, null when the art has no lasting url, see cartographer.md), the live standing bake leaves those leaves out, and the top live layer paints each at its state in play through `paintDoorLeaf` (`src/cartographer/doorLeaf.ts`), the bake's own painter, before the swaying props. A door whose `leaf` is null stays painted in the bake at its drawn state; toggling it changes light and sight but not the picture. The light baked into the picture is also as drawn: the veil follows an opened door, the baked glow does not.

**Which standing image (#1073).** The swaying props (trees, mushrooms, anything with a `sway`) and every door leaf with art of its own are drawn by the top live layer, so the standing image has to leave them out while that layer runs. The stack therefore shows `BattleSurface.standLiveUrl` (`map_layer_stand_live_url`, the standing half without them; set under the same rule as `standUrl`, and by the player view the same way) only while the top layer is mounted AND has emitted `ready` for the current snapshot (every sprite and leaf image decoded). The top layer mounts when `standLiveUrl` is set and the snapshot has sprites or a door with a leaf, whatever the OS motion setting: under reduced motion it draws one still frame (the props at rest, the leaves at their state) instead of a loop, because a door the DM opens must still show. Until `ready`, or when an image fails to load (`ready` never fires), the stack shows the full `standUrl`, so every prop and door is always on screen and a slow or failed image costs the live drawing, never a gap in the map. A new snapshot resets `ready`. Only a snapshot of the current version (`MAP_LIVE_VERSION`, 3) is read (`currentMapLive`): a version-1 snapshot's bakes hold every leaf, which the live layer would draw a second time, so a site published before doors went live is a plain picture until it is published again.

**The live layer (#1073).** Over the map images sits `BattleMapLiveLayer` (one canvas per stratum, ground and top) that animates what the site's `map_live` snapshot says moves (foam drifting over painted water, glints on open sea; see cartographer.md's "Live snapshot"). It takes the fog layer's geometry props, preloads each overlay image once, and draws each group clipped to its cells with `screen` blending; the frame math is `lib/battlemap/liveLayer.ts`. It runs a `requestAnimationFrame` loop only while its stratum has something to move (a water overlay, a swaying sprite, a flickering or pulsing light), the tab is visible and the OS does not ask for reduced motion; otherwise the ground layer draws nothing, since the baked picture already shows the water, and the top layer draws its one still frame. The snapshot is in the Drawing's image cells, so `resolveBattleSurface` (DM) and the player view pass it whenever the location carries one (`liveFor` in `roomBridge.ts`): over the Drawing's bake, and also over a Picture with no Drawing bake, where an import or an AI-styled painting writes walls, doors, lights and water straight into the Picture's cells (a styled save strips the sprites and door leaves, so only motion and sight remain). It is null only when the place has no snapshot.

**Still no VTT.** Nothing here moves a token for the DM: a token seeded onto a room's cells does not move itself, and a hand-revealed cell does not reveal anywhere else. What the party's senses show, and the room a token walks into being marked Explored, are derived from where the DM put the tokens; nothing fires beyond that. The room bridge is prompts and coordinate translation, not a rules engine — the same discipline the site runner itself commits to elsewhere in #868 ("prompts, not automation"). It makes an already-published Atlas plan usable at combat's cell scale; it does not add anything that fires on its own underneath it.

### The server's view of the map (#1202)

The server rules (reach, cover, sight) need the walls, doors and difficult ground of a fight, and they get them the way the Play screen does, not by a second reading of the map. `fightMapOf` (`src/rules/fight/terrain/battleMap.ts`, pure and edge-importable) calls `resolveBattleSurface` for which map the fight is on (the encounter's own calibrated map, else its interior parent site's), `terrainZonesOf` for the difficult zones that touch the fight (a room fight keeps the zones touching the room, a whole-map fight every zone), and `occludersOf` for walls, closed doors and solid rock, with the door overrides laid on. It returns null when the fight has no calibrated map, or when its `map_live` is of an older version (`currentVersionOf`, the pure half of `currentMapLive`): that site has walls the rules cannot read until it is published again. A calibrated map with no `map_live` at all (a picture with a grid and nothing drawn over it) is a map of open ground, as on the Play screen. `reachTerrainOf` turns the result into the `terrain` that `reachable` takes.

**Where the map ends.** The search refuses any step whose covered cells (a Large's far cells included) lie outside `terrain.bounds`, wherever the mover starts (a creature that old data left off the picture may step back on, never further off). `fightMapOf` builds the bounds in `boundsOf`: a square is on the map when at least half of it is on the picture (`standable`: `floor(n + 0.5)` squares of a run `n` long), so the columns are `0` to `standable(cells_per_image_width) - 1` and the rows, from the picture's shape `GridCalibration.image_height_over_width` (its natural height over its width), `0` to `standable(cells_per_image_width * ratio) - 1`. `gridFromRatio` in `lib/battlemap/imageGrid.ts` rounds up instead, which is right for indexing every cell the picture touches and wrong for standing: on a picture 15.09 squares tall a fleeing goblin stopped on the sixteenth row, below the map (seen live, 16 Nov 2026). The server never loads the picture, so the browser records the ratio: where a calibration is made from a picture of known size (the picture grid, the UVTT import, the calibration helper, a Cartographer publish, the AI styler's save) and, for every other map, by `useHealPictureShape`, which the DM's Play screen and Explore screen mount. It measures the battle-map layer's own picture url (the Drawing's when there is one, else the Picture's), and when the stored ratio is missing or more than 0.5% off writes the corrected calibration through the ordinary `useUpdateLocation`, once per picture per session, never for a player or a follower window, and decided from the place as it is when the measurement lands.

A map nobody has opened since the ratio was introduced has none. Its rows are then only the ones KNOWN to exist, a deliberately conservative fallback: the deepest of the cells the party has seen (`map_memory.seen`, read by `loadFightMapInput` from the same campaign-scoped row as the door states), the walls and doors, the solid cells, the difficult cells and the cells the creatures on the board stand on (added by `reachTerrainOf(map, standing)`; `FightMap.rowsKnown` says which case it is). A creature may be offered less room than the picture has, never a square off it, and the fallback heals the next time the DM opens the map.

`loadFightMapInput` (`supabase/functions/_shared/fightMap.ts`) gathers the inputs with the service-role client: the encounter's `location_id`, that place and (for a room) its parent, the site's `location_map_regions`, and `map_memory.door_states` and `map_memory.seen` of the map place (a room on its parent's plan reads the parent's row). Every read is scoped by `campaign_id` in the query; regions have no campaign column and are read only for a place already read for the campaign.

`movementBudgetFeet` (`src/rules/fight/terrain/movementBudget.ts`) is what a creature may still move: `combatantSpeed` (`lib/encounters/combatantSpeed.ts`) less 2024 Exhaustion, less `movement_used`, never below 0, and 0 under a condition whose text sets Speed to 0 (Grappled, Paralyzed, Petrified, Restrained, Unconscious; Stunned too under 2014, where it "can't move").

Not modelled: standing up from Prone (costs half the speed), 2014 Exhaustion (level 2 halves, level 5 is 0), speed bonuses, and the creature occupying a cell (that is `reach.ts`'s `others`, supplied by the caller).

### Whole-turn options (#1202, story 3b)

`turnOptions` (`src/rules/fight/terrain/options/`, pure and edge-importable) turns the terrain facts into a short list of whole-turn options for the creature whose turn it is, and the read-only `encounter-options` function serves them (`POST { encounterId, instanceId }` returns `{ version, options }`). An option is a legal, described thing to do with the turn: a stable `id` (`attack:<list>:<action>:<targetId>`, `dash:<targetId>`, `move:<targetId>`, `disengage`, `dodge`, `hide`, `flee`; the same input always yields the same ids), a `kind`, the `destination` anchor cell with its `path` and `feet` (null when there is no movement or no map), for an attack its `list`, `action` (the entry's printed name, which is what a resolving command names the action by), `steps` (a Multiattack's), `distanceFeet`, `cover`, `longRange`, `closeCombat`, `hitChance` and `expectedDamage` (null until `withNumbers` fills them, see Monster tactics), the opportunity attacks its path `provokes`, the mover's cover against each living hostile at the destination (`exposure`, where "total" means that enemy has no line), and a one-line plain-English `summary`. An AI DM picks one by id and never produces a coordinate. The list offers and describes; it does not say which is best (that is Monster tactics, below).

The rules, each a named block in the file (app conventions over PHB 2014 ch. 9, which the 2024 SRD 5.2 repeats):

1. **Attack**: one per (usable attack, living hostile) that is possible from at least one square the mover can end on this turn, its own included. The square is chosen by, in order: fewest opportunity attacks; not long range; not close combat; least cover for the target; most cover for the mover (the multiset of exposure ranks compared worst first, `compareExposure`); fewest feet; then top row, leftmost. A target at total cover from every reachable square gets no attack option.
2. **Dash**: one per living hostile that no attack reaches this turn, searched with twice the budget ("extra movement equal to your speed"), ending on the square nearest the target (ties: fewest opportunity attacks, fewest feet). Not offered when the best square is where the creature already stands.
3. **Disengage**: at most one, only when a hostile that could take an opportunity attack (reaction free, not Incapacitated) has the mover in its reach. It ends on the reachable square farthest from the nearest hostile (ties: most cover, fewest feet) and provokes nothing. Not offered when no square is farther than the one it stands on.
4. **Dodge**: always, standing put.
5. **Hide**: at most one, only when some reachable square has total cover against every living hostile; the nearest such square. Only walls, closed doors and rock count: darkness and invisibility are not modelled.
6. **Nothing measurable** (no map, the mover has no place on it, or its speed is unknown): no movement is offered. One attack option per (attack, living hostile) with null destination and facts and a summary that says the distance is not known, plus Dodge. Nothing is guessed.
7. **Nothing at 0 hit points or while Incapacitated** (the condition, and the ones that include it: Unconscious, Paralyzed, Petrified, Stunned, from `concentrationBreaksOn`): an empty list. When the creature's Action is spent (`action_used`) it keeps only Bonus Action attacks (unless `bonus_used`) and a plain `move` toward each hostile no attack reaches: Dash, Disengage, Dodge and Hide are Actions.
8. **Multiattack** is offered as one option per target when every step names another usable entry of the same stat block (the stored structure keeps `{ action, count }`, so steps are tied by name and nothing is parsed from prose) and the first step is an attack; that first attack decides where the creature may stand. A Multiattack with no steps, a step naming nothing, or a first step that is not an attack is left out. Option lists ("one of the following breath weapons") are left out: an option has no entry name a command could name.
9. **Cap**: 12 options (`MAX_TURN_OPTIONS`). Dodge, Disengage, Hide and Flee always stay; attacks, dashes and moves against the nearest targets are kept first.
10. **Flee** (kind `flee`, id `flee`): at most one, a Dash away, offered only with a living hostile, the Action free and a map. It does not avoid opportunity attacks (that is Disengage). Where it ends depends on the map's **ways off** (#1203, the maintainer's words: "a wilderness map or a map's outer gate leave the map allowing your fleeing goblin to despawn"). Nothing new is stored: every **Entrance zone** of the map's place is a way off (where the party walks in is where anyone walks out; all of them count, not only the ones that touch the fight's room, because a goblin flees the room and then the site), and a map whose place is open country (location type `wilds`) can be left over **any edge** (every cell on the border of its bounds; when the picture's height is not recorded the bottom is only a guess and is not an edge). Solid rock and cells off the map are never exits, and a creature uses a way off when any square it fills is one (`fightMapOf` builds `FightMap.exits`; the pure read is `src/lib/battlemap/mapExits.ts`). A sealed dungeon level has none.
    - **A way off is reachable this turn** (twice the budget): it ends ON the nearest one by movement cost (ties: fewest opportunity attacks provoked, then top row, leftmost) and the option is marked `leavesMap: true` with `exitLabel` (the zone's name, null for an unnamed zone and for open country's edge) and `exitKind` (`entrance` or `edge`). Summary: `Flee: dash 35 ft and leave the map through "East gate"` / `... through the entrance` / `... over the edge of the map`.
    - **Ways off exist but none is reachable this turn**: it ends on the reachable square that leaves the shortest walk to the nearest way off, measured along the cheapest whole walk from where it stands (one search with no budget over the same walls, doors and rock, never straight-line distance through a wall): the farthest square of that walk the Dash reaches. Summary: `Flee: dash 60 ft toward "East gate", 25 ft short of it`; `leavesMap` is false. A way off no walk reaches, or a Dash that cannot take one step along the walk, is no way off and the next case applies.
    - **No way off**: it ends on the reachable square farthest from the nearest living hostile (ties: most cover, fewest opportunity attacks provoked, fewest feet, then top row, leftmost), only when some square is farther away than the one it stands on.

    Not offered when the Action is spent, nothing can be measured, or there is no living hostile. Only a flee is ever offered a way off: an attack, dash or move that ends on a gate does not leave, and the DM's own moves are unaffected. The `surrender` kind is never produced here: the tactics gate (below) substitutes it.

The function reads the roster (`encounter_state.combatants_live`), the stat blocks, the party members' sheet `speed` and the map, all scoped to the campaign in the query, and writes nothing (no batch id, no version bump). Only the campaign's DM may call it (`_shared/fightAccess.ts`, shared with `encounter-command`), because the options reveal what monsters can do. A creature's attacks are the Actions and Bonus Actions of its stat block that `actionAvailability` finds available (a spent recharge or a used-up N/day ability is left out); its speed is `combatantSpeed` less conditions and `movement_used`. An enemy's reach for opportunity attacks is the longest melee `reach` among its Actions, else 5 ft. A player character has no stat block, so it gets Dodge and the movement options only (a player picks their own turn), at the sheet's speed and a 5 ft reach.

Not modelled: darkness and invisibility (so no sight beyond walls), standing up from Prone, a player's weapon reach from the sheet, companions' speed (`combatantSpeed` reads none, so a companion gets the unmeasured shape), a Wild Shaped player's beast attacks, legendary and reaction attacks, and (in `turnOptions` itself) any ranking of the options. Cover on resolved actions (above) covers attacks and Dexterity saves from the acting creature only: an area effect with another point of origin, cover against a spell that needs no roll, and cover from anything but walls, closed doors, solid rock and creatures are not modelled.

### Monster tactics (#1203)

How a creature chooses its turn when the app plays it. **All of it is app convention: the books do not say how a monster thinks.** Each line is a small named block in `src/rules/fight/tactics/` (pure, edge-importable) so a maintainer can find and change one. A model that plays the creature gets the gated, numbered option list and may ignore the picker; with no model, the picker is the whole decision.

**The fields** (`MonsterStatBlock.tactics`, all optional; the stat-block write guard passes unknown keys through, so no migration): `role` (`brute`, `skirmisher`, `artillery`, `controller`, `leader`, `lurker`), `targets` (`nearest`, `most_wounded`, `spellcasters_first`, `lowest_armor`), `morale` (`{ breaksAt, then }`, `breaksAt` a share of maximum hit points, 0 never, `then` `flee`, `surrender` or `fight_on`), `cover` (`ignores`, `when_cheap`, `fights_from`) and `note` (the DM's own line, carried through, never interpreted). A filled field beats the derived one, each on its own.

**`tacticalProfile(statBlock, creatureType)`** resolves every field. The creature type lives on the monster row, so it is a separate argument (null for an NPC):

| Rule | Derived as |
| --- | --- |
| Cleverness tier (Intelligence) | 3 or less instinct; 4 to 7 simple; 8 to 11 trained; 12 or more tactical |
| Cover | instinct and simple `ignores`; trained `when_cheap`; tactical `fights_from` |
| Targets | instinct and simple `nearest`, or `most_wounded` with the Pack Tactics trait (a pack goes for the weakest); trained `most_wounded`; tactical `spellcasters_first` |
| Role, checked in this order | every attack ranged-only (and at least one) `artillery`; spellcasting, or a save-based entry it can use at will (no recharge, no uses per day), or nothing but save entries `controller` (a breath weapon on a recharge beside a bite is a weapon, not a role); a Stealth skill `lurker`; walking speed 40 ft or more `skirmisher`; else `brute`. `leader` is never derived |
| Morale | undead, construct, ooze or plant: `{ 0, fight_on }`; so is Intelligence 2 or less, except for a beast or a monstrosity (an animal bolts when hurt); everyone else `{ 0.25, flee }` |
| Offered turns | instinct: attack, dash, move, flee; simple adds dodge; trained adds disengage; tactical adds hide. A lurker of tier simple or higher is also offered hide |

Three of these rules were changed on 16 Nov 2026 after a review of 60 library monsters against their derived profile (controller, the beast and monstrosity exception, Pack Tactics): across the 3,865 library monsters 480 stopped fighting to the death, 575 stopped being called controllers and 94 pack hunters go for the most wounded. The principle (the maintainer: "rules where logical, tactics where one is non-typical"): a pattern is fixed in the rule, and a stored `tactics` value is for the creature that is not typical of its kind.

**Stored morale for the library's fiends, celestials, elementals and fey.** These are the kinds whose nature matters more than their Intelligence, so all 806 in the library were reviewed against their derived morale (16 Nov 2026, by model in batches, from published lore where it exists and the creature's page where it does not) and 279 got a stored `tactics.morale` in migration `20261119121115`: elementals, angels and bound or soldier devils that never break, hags, rakshasas, genies and officer devils that surrender, mephits, imps, quasits, pixies and sprites that flee at half. The maintainer approved the whole list. Who a creature goes for was reviewed in the same pass and nothing changed. Other kinds were not reviewed: a sample of 60 across every kind found their faults in the rules, which were fixed instead. A library row keeps its tactics through a rewrite of its stat block (`library_monsters_keep_tactics`, `library_monster_tactics_kept.test.sql`): the Open5e re-import rebuilds a block from source fields that have no tactics and would otherwise undo the review one creature at a time. To clear a library row's tactics on purpose, write `"tactics": {}`; leaving the key out keeps the old value.

**The gate** (`gateOptions(options, profile, mover)`) drops the kinds the profile is not offered. A creature whose morale has broken (`hp / max_hp <= breaksAt`, `breaksAt > 0`) is narrowed further: `flee` keeps only flee, disengage and dodge (and leaves the list alone when none is there), `surrender` replaces the list with one synthetic `surrender` option (no movement), `fight_on` changes nothing. An empty list stays empty. The gate does not re-search squares for a creature that ignores cover: the options code already chose them.

**A way out comes first (#1203).** Two more rules, both in `wayOut.ts` and `pick.ts`. *RULE way-out-names* (5e by the book) lists the named powers that take a creature out of a fight or out of sight: Etherealness, Plane Shift, Teleport and Dimension Door leave; Invisible Passage, Invisibility and Greater Invisibility hide. Misty Step and the like are left out because 30 feet is not out of the fight. Teleport and Plane Shift count only as spells: a monster's own "Teleport" action is a short hop (a blink dog's is 40 feet, a balor's 120; 30 of the library's 44 say "up to N feet") that leaves it in the fight. `wayOutsOf(statBlock)` finds the rest as an Action or Bonus Action entry of that name, and all of them as a spell named in a spellcasting entry (read through `src/rules/statBlock/spellcastingProse.ts`; only an entry named "Spellcasting" or "Innate Spellcasting" counts, so a coven's "Shared Spellcasting (Coven Only)" is not read, as those spells need all three hags) (the 2024 `- **2/Day Each:** ...` lines and the 2014 `2/day each: plane shift (self only)` lines both read; a slot line such as `4th level (3 slots)` is tallied per level, an app convention because the server casts none of a creature's other spells yet, so its slots are whole). Leaving the fight is listed before hiding, and a power with no limit before a limited one. *RULE escape-first* (app convention): a creature whose morale has broken, and whose `then` is `flee` or `surrender`, uses a way out it can use now before it runs or yields. The gate puts one synthetic `escape` option first (`Etherealness: leaves the fight`, `Invisible Passage: turns Invisible`) and keeps the retreat or the Surrender behind it, so a caller or a note can still choose that. A way out is not usable when its uses are spent (N a day reached, a recharge not back), when the Action or Bonus Action it costs is already used, or, for a hiding one, when the creature is already Invisible; a hag whose Plane Shift is spent and who has nothing else simply yields. A `surrender` creature that is already Invisible does not yield: it got unseen to get away, so it is gated like `flee`. `fight_on` is untouched. Carrying it out is the slot, the limit's spend, then `remove_combatant` (leaves) or `apply_condition` Invisible (hides); the creature does not also move that turn. `turn_taken` carries `escapedWith` (the power's name) and `escapeEffect`, and `leftTheMap` stays only for a flee off the map.

**A creature casts a spell (#1021 row 5b, step A; `src/rules/fight/spells/`, `cast_spell` in `encounter-command/resolve.ts`).** A fight could resolve a breath weapon and not a Fireball, because only a stat block entry carried its attack or save in data. A cast turns the spell into that same kind of entry at cast time, so nothing about resolving is new: `castableBy(statBlock, spell)` finds the creature's Spellcasting entry and the group that lists the spell (its save DC, attack bonus, and the limit it is tallied under: `slots/<level>` for a slot, `spell/<name>` for N a day, none for at will and cantrips; `castLimitOf` is the one rule for those keys and `wayOut.ts` uses it too); `pickSpellRecord` chooses among the records of that name; `spellEntryFor(record, castLevel, caster)` builds a structured attack or save entry with the spell's damage at that slot (through `effectsForCast`, no second scaler); and `resolveAttackOn` or `resolveSaveOn` does the rest, with one damage roll shared by every target of a save and each target saving for itself. *RULE spell-record* (app convention, the maintainer's decision of 18 Nov 2026): a campaign's own spell comes first and is taken at its word (the DM wrote it); among library records the campaign's edition comes first, then a reviewed record, and a library record that is not reviewed is never resolved automatically. *RULE cast-by-hand* (the same decision): a spell the game cannot resolve (no damage in data, a `special` save effect, an automatic spell such as Magic Missile, an unreviewed record) is still cast: the slot and the Action are spent and a `cast` effect says why its outcome is the table's. Everything that can refuse a cast is checked before anything is spent: a creature that does not list the spell, a limit used up, no such spell, no target for a spell that is rolled. An upcast of a slot spell spends the slots of the level it is cast at. A concentration spell ends the caster's earlier concentration first. **The caster holds what it cast (19 Nov 2026).** A concentration spell marks its caster (`start_concentration`, a reducer command only the cast issues; `RunCombatant.concentration`, which the runner already shows), whether or not it left a condition on anyone, so a damage-only one or one every target saved against is held too: the caster owes a concentration save when it is hurt, lets go at 0 hit points, and ends it by casting another. A party member is left alone, since theirs is kept on `party_members`. **Not built:** conditions from spells (no spell record has one in data yet; the `/spell-conditions-pass` skill is the way there), healing and automatic damage, areas placed on the map (the targets are named by whoever sends the command), a creature choosing to cast on its own turn, players casting, and any screen for it. The loader does not filter library records by the sources a campaign has switched on: the creature's own stat block names the spell, and the record only supplies its numbers. A spell whose condition is limited to a kind of creature (`condition_effect.only_kinds`: Hold Person is humanoids, Dominate Beast beasts) needs to know what it is aimed at, and `creatureKindOf` (`spells/creatureKind.ts`) says: a creature backed by a monster row has that row's `monster_type`, a player character is a Humanoid (an app convention: every playable species of the 2014 and 2024 Player's Handbooks is one, and a character sheet stores no creature type), and an NPC or companion with no monster row behind it is not known (its free-text race is never guessed from). `cast_spell` refuses a target of a known wrong kind before anything is spent ("Hold Person works only on a humanoid, and Wolf is a beast."); if any target's kind is not known the cast is spent and reported as the table's to rule, with that reason; otherwise it resolves with `kindsChecked`. A creature choosing or the DM's options list offers such a spell only at hostiles of a known, allowed kind (`spellTargetings` with `kindOf`), and never offers it when no kind lookup is given. A condition can also end when it is harmed (`condition_effect.ends_when_harmed`: `by_casters_side` for "until you or your allies damage it", as in the 2024 Charm Monster, or `by_anyone` for "until it takes any damage"; absent means neither). The cast writes it as `endsWhenHarmed` (`source_side` or `anyone`) on the stat block's save condition and on the applied condition's `source`. `applyDamage` ends it through `remove_condition` once hit points were actually lost: damage that came to nothing, a miss or a hand adjustment of hit points ends nothing. "On the source's side" is the creature that imposed it or one in the same faction (the notion `isHostileTo` uses for friend and foe), read through the context's `factionOf`; a context without it counts only the source itself. Damage with no attacker (a condition's ongoing damage) ends only the `anyone` kind, and removing the condition leaves the caster's concentration on other creatures alone. A condition can also be ended by the bearer's own try (`condition_effect.break_free`: the abilities it may choose between and the skill the text names, if any; Black Tentacles, Entangle and Web). The cast writes it as `breakFree` on the applied condition, with the caster's spell save DC it is checked against (`dc`). The `break_free` command (`resolve.ts`) is the creature's Action: it is refused when the creature bears no such condition, cannot act, has already used its Action this turn, or names an ability the condition does not allow. With none named it uses the allowed ability it has the higher modifier in. It rolls a d20 with the rules' own disadvantage on ability checks (Poisoned, Frightened, and 2014 Exhaustion) and the 2024 Exhaustion penalty, none for Restrained, adds the modifier (a stat block's listed bonus for the named skill replaces modifier plus proficiency), and a total that meets the DC removes the condition. A player character's modifier comes from the sheet the server reads, but its skill proficiencies are not on that sheet, so a check that names a skill is refused for a player with a message that the check is theirs to roll and the Dungeon Master can remove the condition on a success. A condition can also make its bearer run (`condition_effect.must_flee`, SRD 5.1 Fear: "must take the Dash action and move away from you by the safest available route on each of its turns, unless there is nowhere to move"; Turn Undead: "as far away from you as it can"). The cast writes it as `mustFlee` on the applied condition's `source`, because what the bearer flees from is the source creature. *RULE flee-by-spell* (app convention implementing those texts): a creature the game runs, bearing such a condition whose source is still in the fight and above 0 hit points, is gated like a broken creature that flees (its retreats and a try at breaking free), and its flee option runs from that one creature and never by a way off the map; it breaks free of a hold before it runs, by the same steps as a broken creature, and it does not use a way out (escape-first stays tied to broken morale). With nowhere to move it is not forced to anything: it keeps Dodge or Disengage and never attacks or casts. A player character is not gated by it (the server does not take a player's turn; the table enforces it). **Not built:** making the creature drop what it holds, and denying it reactions.

**What the review of #1225 fixed (19 Nov 2026).** Four reviewers read the fight path that reaches every table (the server, the rules, the browser, chat and the release gate). What changed, and where the rule now lives:

- *Turn order.* A creature that dies on its own turn no longer ends the round for everyone after it: `stepTurnIndex` (`rules/turnOrder.ts`) steps from its place in the full order. Removing the acting creature starts its successor's turn properly (`startTurn` in `encounterTurn.ts`, shared with `next_turn`; the leaver's own end-of-turn edge does not run, an app convention). `set_initiative` on a running fight keeps the same creature acting. A dead party member (three failed death saves) and a companion at 0 hit points take no turns (`takesTurnsInFight` in `rules/fight/standing.ts`; `isStanding` still means "can be targeted").
- *Ranged attacks.* PHB 2014 ch. 9 "Ranged Attacks in Close Combat" and "Long Range": disadvantage with a hostile that is not incapacitated within 5 feet of the attacker, and beyond normal range. `attackRollMode` takes these as two facts of their own (`hostileWithinFiveFeetOfAttacker`, `longRange`), separate from "the attacker is within 5 feet of the target" (which decides Prone and the critical hit on a Paralyzed or Unconscious target); `rangedAttackFacts` (`terrain/sight.ts`) works them out and the server's `resolve_attack` and spell attacks pass them. Not modelled: "a hostile that can see you". The browser's own attack flows pass them too (`composables/encounters/rangedFacts.ts`): the DM's attack flow and the AI table's attack by the played character show the cause before the roll ("Disadvantage: a foe is within 5 feet of you", "Disadvantage: long range") and combine it with a hand-set mode by the normal rule. The browser holds no wall data there, so a hostile within 5 feet counts even behind a wall, and a weapon whose item names no range (`weapon_range`) is never long range.
- *Surprise.* PHB 2014 ch. 9: a surprised creature has no turn in round 1 (`losesFirstTurnToSurprise`; the server offers it no options and says why). 2024: disadvantage on the initiative roll (`initiativeRoll`). The 2014 "no reaction until that turn ends" is not enforced.
- *Concentration.* SRD 5.1: an incapacitating condition ends it. `apply_condition` and `set_conditions` now end what a stat-block creature holds (`endHeldConcentration`).
- *Dodge* is lost at Speed 0 as well as when incapacitated (PHB 2014 ch. 9 "Dodge").
- *End of a fight.* Stances and conditions that only mean something inside the fight (Dodging, Disengaged, anything with a turn or round ending, a spell held by someone in the fight) are not written back to the character (`conditionsAfterFight`). A retried End combat or Abandon re-runs the write-back, so a failed write does not leave a character without it.
- *A player's hit points.* The fight remembers what it last read from the character's own row (`RunCombatant.sheet_hp`, `sheet_temp_hp`) and adopts the row only when it differs, so a second device loading the fight before the first write has landed no longer puts back the hit points a hit took. Death saves and conditions still take the row as it is.
- *What the server accepts.* A spell cannot be cast with a slot below its level. Custom monsters (and Wild Shape forms) are read only when they belong to this campaign or one of its Dungeon Masters (`customContentScope`). A roster and every reducer command are checked for shape (`encounter-command/commandShape.ts`): whole numbers, arrays where arrays are read, no duplicate instance ids. `go_live` keeps the fight's first start time and takes only a session of this campaign.
- *The runner on a poor connection.* Unsent batches and failed sends are visible (`RunnerUnsavedNotice`, shown once a send has failed), leaving the page with unsent changes asks first, and a batch that keeps failing is announced once. Every batch is bound to the encounter it was made for, and the one sender of batches is the run store's pump (`stores/encounterRunPump.ts`), not the runner: leaving the runner with changes unsent keeps them retrying, keeps the "leave this site?" prompt up until the queue is empty, and a failed send is still told once. Autopilot stops when the runner is left or the switch goes off, without passing one more turn.
- *Second round (the maintainer: "when you find things that are 'not new regressions' still fix them").* The fight now remembers every value it takes from a character's own row and writes back (death saves, conditions, a Wild Shape form, initiative: `RunCombatant.sheet_*`), so a stale read cannot undo any of them. Under the 2014 rules a surprised creature takes no reaction until its first turn ends (`cannotReactWhileSurprised`), and Exhaustion halves speed from level 2 and stops it at 5 (`movementBudgetFeet`, `speedIsZero`). The options a DM is shown are worked out on the same ingested party as the turn the server takes (`_shared/fightPartyIngest.ts`). Custom items, like custom monsters, are read only within the campaign's Dungeon Masters (`customContentScope`). The applied batch ids kept per fight went from 64 to 256 (the reasoning is on `APPLIED_IDS_KEPT`). A worn, attuned Ring or Cloak of Protection, or Staff of Power, adds to every save, on the sheet, the table's roll card and the server alike (`savingThrowItemBonus`). The browser's own attack flows (the DM's runner and the AI table's played character) apply the two ranged disadvantages and say why before the roll, using the walls of the map on show (`encounterRun.occluders`, set by the map screen; open ground when none is up); a player's weapon takes its range from the item's `weapon_range` (`parseWeaponRange`). One sender of batches, held by the store rather than the runner (`stores/encounterRunPump.ts`): changes keep being retried and the leave-page prompt stays up after the runner is left, and an answer is applied only to the fight it was for.
- *Allies.* `isAllyOf` (`rules/fight/allies.ts`, app convention): own faction, or not hostile and sharing a declared enemy; a Neutral is neither friend nor foe, for the tactics judge and for a spell's friends-in-the-area count.

**Who fights whom (`src/rules/fight/sides.ts`, 19 Nov 2026).** *App convention:* an encounter's factions say whom each attacks (`FactionDef.hostile_to`), and two creatures are opponents when their factions differ and either declares the other, so an Ally fights beside the Players and a Neutral is nobody's foe. The server's turns used to take any different faction for a foe, which had a creature on the Ally side attack the party when the app played its turn; the page already read the factions. There is one rule now, `areHostile` / `isHostileTo`, and the encounter's factions are loaded with the fight (`LoadedFight.factions`, `ResolveEnv.factions`, `TurnOptionsInput.factions`) for the turn options and opportunity attacks. A fight that declares neither of two factions falls to "a different faction is an opponent"; an encounter saved with no factions runs on the defaults, as the runner opens it. One definition each, too, of: within 5 feet (`boxesWithinFiveFeet` in `terrain/sight.ts`), incapacitated (`INCAPACITATING_CONDITIONS` in `rules/conditions.ts`), still standing (`rules/fight/standing.ts`) and the ability modifier (`rules/abilityScore.ts`).

**Autopilot (#1203, carried into #1021 row 5a).** A standing switch in the runner (`grimoire:runner-autopilot`, kept on the device): while it is on, the server plays every creature's turn ("Run this turn for me") and the turn passes on after a short pause, the way the AI table's fights run (`useCreatureTurns`, shared by both). It stops at a player's turn, at anyone the rules cannot play, when a turn could not be run (the reason is on that creature's panel), and when a creature walked out of a player's reach, since that opportunity attack is the table's to settle before the turn moves on. The switch is one shared flag (`useRunnerAutopilot`) drawn in the classic runner's top bar and in the combat tools sheet of the phone and the Play screen.

**A creature chooses to cast (#1021 row 5b, step B, first part).** A creature run by the game only ever weighed attacks. One that lists spells now offers its damage spells too (`castableNow` in `spells/castNow.ts`: every listed spell with a use left and an entry the rules can roll; a slot spell at its own level, or at the lowest higher level that still has a slot), weighs them against its attacks, and casts through `cast_spell` (a `cast` step in `carryOut.ts`; the command itself spends the slot and the Action). Where a cast can go is `terrain/spellTargeting.ts`: a spell with no area is one option per foe in range and in sight; a sphere, cylinder or cube is centred on each foe in turn and catches every foe within its size of that one, and every friend; an emanation, or an area with a range of Self, is centred on the caster and leaves the caster out (app convention). A range the text does not give in feet is taken as any distance. With no map every spell is a single-target cast. The numbers are the attack numbers' own arithmetic (`numbers.ts`): for a save, each target's chance to fail times the full average damage plus its chance to succeed times half, summed; a save bonus that cannot be read is taken as a 50% chance (app convention). A resistance, immunity or vulnerability is weighed only once the fight has shown it (next paragraph). *RULE friends-in-the-fire* (the maintainer's decision): a cast that catches any of its own side is never chosen; no stored tactic says a creature does not care, so none does. *RULE no-wasted-slot* ("it does not waste its top slot on something nearly dead"): a cast that spends a slot or a use is not chosen when something free the creature has this turn (any attack, a cantrip, an at-will spell) is expected to deal at least the hit points its targets have left. *RULE cast* : otherwise the best cast on the target the creature's `targets` rule chose is compared with its best attack by expected damage; the higher wins, and a tie goes to what spends nothing, then to the attack. So a creature told to go for the spellcasters first casts at them too. Spell options have their own ceiling (`MAX_SPELL_OPTIONS`, 12) beside the twelve other options, so a caster's attacks, moves and retreats are never pushed out; those kept are the ones catching no friend, then the most foes, then the nearest. A cast is made from where the creature stands. The DM's list of what a creature could do (`encounter-options`) offers the same casts as the turn itself. The spell records are read once a turn, in two queries, and not at all for a creature that lists no spells. *RULE break-free-first* (app convention, the books do not say how a monster spends its Action when held): a creature that is Restrained or Grappled and is offered a try at breaking free (`break_free` option, one per such condition while its Action is free, at every tier that offers attack) takes it when it has nothing to attack or cast at from where it stands; one that can attack does, except a trained or tactical creature held by Restrained, which breaks free first (attacks against it have advantage and its own have disadvantage); a broken creature that would flee and is held tries to break free before it runs. *RULE flee-by-spell* (app convention, see "A creature casts a spell"): a creature frightened by a spell that makes it run flees that spell's caster instead of choosing a target. A creature with no such condition is offered, and picks, exactly what it did before. **Not built:** choosing by what a spell takes from its target (Silence at the wizard, Hold Person at the one who must close in) and combinations, which wait on spells' conditions being in data; using terrain and traps; moving to get a better cast; cones and lines; a creature that does not mind its own side. **Cones and lines (19 Nov 2026):** a cone or a line starts at the caster and is aimed at each living enemy it can reach, one cast per distinct set of creatures caught (`inAimedArea` in `terrain/spellTargeting.ts`). A cone is as wide at any point as that point is far from the caster (SRD 5.1 "Areas of Effect"); a line is its size long and 5 feet wide, since the record keeps no width and every harmful line in the SRD is 5 feet. Length is counted from the edge of the caster's space, a creature of several squares is caught when any of its squares is, a wall stops both, the caster is never in its own, and friends caught are counted as for any area, so the friends-in-the-fire rule weighs them.

**A creature heals (#1021 row 5b; `spells/healEntry.ts`, `spells/healNeed.ts`, `terrain/healTargeting.ts`, `tactics/healChoice.ts`, `resolveHeal` in `encounter-command/resolve.ts`).** A creature or ally that lists a healing spell casts it by the book. *How healing is known:* the library row's structured `effects` (kind "healing": dice, slot scaling, "spellcasting_ability" modifier), the record `castableNow` reads for damage; `healableNow` (`spells/castNow.ts`) offers each listed spell that has a reviewed record (or the campaign's own), one such healing effect cast on chosen creatures, a casting time of Action or Bonus Action (`casting_time`, or "Special" with `casting_time_custom` "bonus-action": the two spellings the library uses; Prayer of Healing at ten minutes is not a heal a fight casts) and a slot or use left, at its own level or the next slot the creature has. A record with no structured healing is never read from its text (cast and spent, left to the table, the reason in the log as `why`), with one exception built from data: a campaign's own spell has flat columns only (`healing_dice`, `higher_level_healing`), and `withFlatHealing` (`spells/healEntry.ts`, applied by `ownRecord` in `_shared/fightSpells.ts`, the one place a custom row is mapped) turns them into one healing effect for one creature, scaling by slot level when the row has per-level dice; the spellcasting modifier is added only if the spell's own data says so, and no column does, so a DM's "2d6" heals 2d6. A row with no healing dice, a damage spell with a stray healing column, or one that is structured already is left as it is. A Mass Cure Wounds stored as an area ("point") is still left to the table. *The amount* (RULE healing-amount): the record's dice (PHB 2014 Cure Wounds 1d8, Healing Word 1d4; PHB 2024 2d8 and 2d4, each plus the spellcasting ability modifier, the same dice again per slot level above the spell's) rolled once for every target; the modifier is the score of the ability the Spellcasting entry names (`spellcastingModifierOf`), so an entry that names none heals nothing. *Who is healed* (`healTargeting.ts`): someone on the caster's side (`isAllyOf`, the caster itself included) who is hurt, or at 0 hit points and not dead (`healNeedOf`: a character with three failed death saves, and any monster, NPC or companion at 0, is dead and refused); never a foe or a Neutral; in range (Touch is 5 feet) and in line of sight; a spell that restores several creatures (Mass Healing Word, up to its count) is one option at the neediest. RULE healing-undead-constructs: the 2014 texts say "no effect on undead or constructs", the 2024 texts do not. The healing effect carries it as `unaffected` (creature kinds, lower case; an empty list excludes nobody), and a cast on such a creature is spent and reports it unaffected. Only a record without the field falls back on the edition (a shared 2014 record excludes undead and constructs, a 2024 or campaign-own one nobody); a creature whose kind the fight cannot tell is healed. RULE healing-ends: the effect's `ends` names what the heal ends (Heal 2014: Blinded, Deafened and "diseases"; Heal 2024: Blinded, Deafened, Poisoned); an app condition is removed from each affected creature (the result's `ended`), a name the app has no condition for ("diseases") is left to the table, and the DM's line says "The table rules on diseases" (`leftToTable`). Heal's 70 hit points are the flat dice "70" with scaling "10" per slot level above 6th. RULE healing-pool: Mass Heal's effect has `pool: 700`, no dice and no target count; nothing is rolled, and the pool is shared out among the creatures it reaches (any number) the downed first, then the lowest share of their hit points, each to full or to what is left (an APP CONVENTION: the book leaves the division to the caster), with the tactics weighing it as what the targets miss, capped by the pool. RULE healing-full: Power Word Heal (SRD 5.2; the 2014 books hold it outside the SRD, so only the 2024 row exists) has `full: true` and no dice: nothing is rolled, the target regains what it misses, and its `ends` takes off Charmed, Frightened, Paralyzed, Poisoned and Stunned. The tactics weigh it as what the target misses, and the line reads "(all hit points)". Its last sentence, a Prone target standing with its Reaction, is the creature's own choice and stays with the table. *What a heal does:* `adjust_hp` with the rolled total, which is the existing healing rule (`healingOutcome`: hit points capped at the maximum, and a character brought above 0 loses Unconscious and the death saves); the result is a `heal` resolved action (rolled total, and per target what it regained and whether it was brought up). *When a creature heals* (`healChoice.ts`, the maintainer's order; app convention): a heal that reaches someone at 0 hit points comes before any attack or damage spell, then one that reaches someone below half; a scratch is never healed. Among heals, the one reaching the most who are down, then the most below half, then the most hit points restored, then the lower slot. Healing Word is a Bonus Action (the cast uses `bonus_used`, never the Action) and so is no turn of its own: like an ally's class-feature Bonus Action it rides the turn the picker chose, cast first. PHB 2014 ch. 10 and PHB 2024 "Bonus Action" spells: no other spell that turn except a cantrip, so with someone down the turn is chosen without a leveled cast (Cure Wounds and damage spells left out), and with someone only below half the heal is skipped when the chosen turn is a leveled cast. A turn the caller names carries no heal. An ally spends their own slot (`env.slotsSpent`), a monster the tally. Not done: a healing spell whose record is stored as an area, Prayer of Healing (ten minutes), and any record that stores one creature for an "up to six" text (the library rows must carry the right target count).

**A creature gives a boon (#1021; `fight/boons.ts`, `spells/boonEntry.ts`, `resolution/boonRolls.ts`, `terrain/boonTargeting.ts`, `tactics/boonChoice.ts`).** A boon is a spell that adds to its targets' own numbers while it lasts: Bless (PHB 2014 and 2024: up to three creatures, one more per slot level above 1st, a d4 on attack rolls and saving throws, Concentration up to 1 minute, an Action) and Shield of Faith (one creature, +2 AC, Concentration up to 10 minutes, a Bonus Action). *How a boon is known:* the library row's structured `effects` hold a `text` effect carrying `grants` (`SpellGrants`: `attack` and `save` dice, `ac`, `rounds`, `morePerSlot`), so a reader that does not know it (the sheet's effect resolver) shows its words; never the prose. *What a cast does:* `cast_spell` spends the cast like any other (concentration, slot, Action or Bonus Action), refuses no targets, more than the plan reaches at that slot, or a dead one, and puts a condition named after the spell on each target with `grants`, sourced on the caster (`concentration: true` for a concentration spell, so `end_concentration`, a failed concentration check or the caster dropping takes it off everyone) and lasting `rounds`; the log line is the `boon` resolved action ("Cleric casts Bless on Pip and Brug."). A condition is one record per name, so a second Bless replaces the first, which is the book's "Combining Magical Effects"; two different boons add. *What a boon changes* (`resolution/`, shared by the server, the DM's runner and the solo table): an attack roll and every saving throw (a spell's, a concentration check, a repeat save) roll the boon's dice after the d20 for the same creature and add them to the total (`rollBoons`), so a natural 1 still misses and a natural 20 still hits; a dice expression with a leading minus takes away (Bane's shape, kept with its sign since the dice parser drops a term's sign); a boon nobody rolled adds nothing (APP CONVENTION). The target's armour class gains its boons' `ac`, read live. *In the tactics' estimates* (`tactics/numbers.ts`): the mean of a boon's dice is added to the bonus, a fractional bonus read linearly between the whole bonuses either side (APP CONVENTION), and "lowest armour" counts Shield of Faith. *When a creature casts one* (`boonChoice.ts`, APP CONVENTION "a boon is cast early, while the fight is ahead of it"): in rounds 1 and 2, only while the caster holds no concentration, an Action boon only when it reaches at least two creatures (or its whole count), after a heal and before an attack; a Bonus Action boon rides the chosen turn after a Bonus Action heal and before an ally's class-feature Bonus Action, and under the Bonus-Action-spell rule like a heal. Targets are of the caster's side, standing, in range and sight, not already holding it: for an AC boon the friend with the most foes beside them first, for a dice boon those beside a foe first. *A Reaction boon: Shield* (PHB 2014 and 2024: a Reaction when hit, +5 AC until the start of your next turn, against the triggering attack too). The row's boon carries `reaction: "when_hit"` (`reactionBoonFor`; a turn's cast refuses it). `rollToHit` asks the context's `reactToHit` once the rules say "hit", and decides the roll again against the raised AC; the attack's line says "but Shield turns it aside". The server answers for a creature the rules play (`reactsByRules`: a monster, NPC or companion, or an AI ally when a played member is named; never the played character, never a player in a DM's own fight): it must be standing, not Incapacitated or surprised, have its Reaction, list Shield with a slot (the lowest that casts it, upcast as `castSpell` does) or a use, and hold no Shield already; it casts only when the +5 turns this hit into a miss and never against a natural 20 (APP CONVENTION). The DM's runner and the solo table do not answer yet (the DM decides; a hit at the solo table is not shielded). The Magic Missile half of Shield is not built. *A Reaction against a cast: Counterspell* (`counterEntry.ts`, `counterReaction` in `encounter-command/resolve.ts`). The row's text effect carries `counters: { rangeFeet: 60 }`. `castSpell` asks, after everything that can be refused and before anything is spent, whether a creature the rules play that is hostile to the caster, standing, not Incapacitated or surprised, with its Reaction, a Counterspell slot or use, within the range and seeing the caster (a map's walls; no positions, no counter) answers it; the nearest one does, ties by initiative. APP CONVENTION: only a leveled spell, never a cantrip. PHB 2014: a slot no lower than the spell stops it outright (the lowest such slot), else a 3rd-level slot and a spellcasting check against DC 10 + the spell's level; the caster's slot or use, Action and deed are spent either way. PHB 2024: the lowest slot of 3rd level or higher, and the caster's Constitution save against the counterer's spell save DC; on a failure the Action is wasted but the slot is not spent (nor written to an ally's sheet). A stopped spell starts no concentration and ends none the caster held, and resolves nothing; the counterer's Reaction, slot and deed are spent whether or not it stops. The line is the `countered` resolved action. A counter whose roll the block cannot make (no spellcasting ability for the check, no save DC, no Constitution save bonus to read) does not counter. Not built: a counter of a counter, and the player's own Counterspell. Not built yet: a boon imposed through a save (Bane), other boon spells (Aid, Heroism, Barkskin, Haste), and the player's own attack and save buttons (the Combat tab's attack buttons and the DM runner's PC roll buttons do not read boons; the chip on the creature names it, so the table adds the d4). *A death saving throw is a saving throw* (PHB "Bless"): `deathSaveRollOutcome` takes the boons' `bonus` from every caller, the natural 1 and 20 still read on the d20 alone. The server rolls an AI-played ally's boon die after the d20 and posts it ("8 + 2 (Bless)"); the solo table rolls the played character's with the app's die (`deathSaveBoonBonus`), since the player gave the d20 only; the player's own sheet asks the player for each boon's die as it asked for the d20. *A person's faces answer only what they were asked for*: a supplied d20 or damage roll, never a boon's die, on the server (`makeDice`) and at the solo table, so a Blessed creature's d4 is never read off its d20.

**A creature knows only what the fight has shown (#1021 row 5b; `tactics/shownDefenses.ts`).** The maintainer's rule (18 Nov 2026): "the resistances also matter for melee attacks and an enemy can't know the player is resistant to something unless he learns that through events or combat, they can't check their sheet". Choosing used to ignore defenses altogether; it now weighs exactly what has been seen, for blades and spells alike. When damage lands and a defense changes it (`applyDamage`), the reducer command `show_defense` writes it on the creature that took the blow: `RunCombatant.shown_defenses`, by damage type, `resistant`, `immune` or `vulnerable`. Damage a defense did not change teaches nothing, and neither does a hand adjustment of hit points, which has no type. *App convention:* it is knowledge of the whole fight, not of one side: a blow shrugged off in the open is seen by everyone there. The expected damage of an attack or a cast multiplies each part by 0, 0.5 or 2 for what is shown for that target and that type, and by 1 otherwise (`shownDefenseMultiplier`); the choosing reads nothing else, and a test fails if it ever reads the target's real defenses. *RULE weapon-lessons* (5e by the book): fire is fire, whatever threw it, so every type but a weapon's is one lesson. A weapon's damage (bludgeoning, piercing, slashing) is remembered with what the blow carried (`slashing`, `slashing:magical`), because a defense can be "from nonmagical attacks": what held against a magic blow holds against a plain one too, and what glanced off a plain blow says nothing of a magic one. A cast's damage is weighed as magical. Both the server and the browser's resolution record it (the browser's `apply` switches gained the case; the AI table's attack forwards it). The field stays the DM's: it is not in the players' projection. **Not built:** what a recorded character learned before the fight (in its memory, from talk or an earlier fight) counting as known when a fight starts; showing a player what their party has learned of a foe; a creature's lore about a kind (everyone knows fire does not burn a fire elemental).

**A caster knows what a spell is for (#1021 row 5b, the clever layer; `tactics/shownThreat.ts`, `tactics/conditionWorth.ts`).** The maintainer's rules: "intelligent monsters might actively hunt mages, archers", "certain spells serve certain goals", and a creature knows only what it has been shown. The fight now records what each creature DOES, through the `show_deed` command (written where each fact is known, like `show_defense`): `RunCombatant.shown_deeds` holds the damage it has dealt after defenses, its turns started, the spells it has been seen to cast and its attacks by delivery. A condition spell used to have 0 expected damage, so it was offered and never chosen; it now has `expectedWorth`, in hit points: the chance each target fails its save, times `conditionWorth` = the target's damage per turn (what the fight has seen, else the mover's own best damage, "until it has seen otherwise a creature takes its foe to be about as dangerous as itself") times the share of its turn the condition takes away (Paralyzed 1, Restrained 0.5 or 0.75 for a brawler, Blinded 0.5 or 0.75 for an archer or caster, a spell that stops casting 1 or 0.75 for a caster and 0 for anyone else; the whole table is `CONDITION_SHARES`) times the turns it is expected to last, never more than `ASSUMED_ROUNDS` (3). A repeat save lasts a geometric series from the target's fail chance, and the worth never reads a stat block, which a test holds. *RULE condition-worth:* only a trained or tactical creature counts the worth, except one with no attack and no damage spell, which casts its best condition spell rather than nothing. *RULE spell-for-its-target:* such a creature weighs a single-target condition spell on every foe in range and takes the highest, which sends Hold Person to the brawler and a casting-stopper to the caster. *RULE hunt-casters-and-archers:* `spellcasters_first` goes for a foe seen to cast (or holding a spell), then one seen to shoot, then the most wounded. *RULE no-wasted-slot* uses the same value, so a clever creature does not Hold a foe its dagger can finish. All the numbers are app conventions and the knobs a tuning pass will move. **Not built:** combinations across turns (Hold, then the greatsword on the held foe), terrain and traps, a creature's lore about a kind, the worth of a condition to the caster's own side (Invisibility on an ally), and offering a spell that only stops casting (Silence has no damage and no named condition, so it is still not automatable).

**The numbers** (`withNumbers(options, ctx)`) fill `hitChance` and `expectedDamage` on attack options. Book rules: a natural 1 misses and a natural 20 hits whatever the numbers say (PHB 2014 ch. 9 "Rolling 1 or 20"); advantage `1 - (1 - p)^2`, disadvantage `p^2`; long range and an enemy within 5 ft of a ranged attacker each give disadvantage (ch. 9 "Ranged Attacks"), combined with the existing `attackRollMode` (conditions, Prone, Invisible), so sources cancel rather than stack; cover adds to the armor class (ch. 9 "Cover"); a critical rolls the dice twice (ch. 9 "Critical Hits"), so expected damage is `hit x (dice + flat) + P(natural 20) x dice`. App convention: a Multiattack sums its steps each times its count, and its hit chance is the mean over its swings; a melee-or-ranged attack is thrown (so ranged rules apply) when the target is beyond its reach; the 2024 exhaustion penalty lowers the roll. Null when the target's armor class is unknown (`armorClassOf`), a step names nothing the mover has, or (damage only) a damage part cannot be read. Nothing is rounded inside; the picker's sentence rounds for display.

**The picker** (`pickTurn(options, profile, ctx)` returns `{ optionId, reason }`, null only for an empty list), in order: a broken creature retreats (flee, else disengage, else dodge) or yields; otherwise, among attack options, the target is chosen by `profile.targets` among the targets that have an attack option (nearest, most wounded by share of hit points, a concentrating target else most wounded, lowest armor with unknown last; ties by order in the fight), and then that target's highest `expectedDamage` (unknown lowest; with none known a Multiattack first, then list order). A trained or tactical creature skips an option that provokes when another against the same target does not; a creature that fights from cover prefers, among options within 20% of the best expected damage, the best `exposure`. With no attack, every role closes on the target its rule chooses (the least distance left), then Dodges, then takes the first option. An attack option already covers every square the creature could strike or shoot from, so no attack means no such square is in reach, and a ranged creature that Dodged then would stand still all fight. The `reason` is one plain sentence ("Attacks Fresco, the nearest enemy, with Greatclub: 65% to hit for about 9 damage.").

Not modelled: damage resistance, immunity and vulnerability (the numbers are damage as printed), automatic critical hits on Paralyzed or Unconscious targets, riders that need a saving throw, a `leader`'s effect on its allies (the role only changes what a lurker is offered), `note` (read only by the check described under "The server plays a turn"), and any group tactics (focus fire, flanking). Tiers above "simple" differ only in what is offered and how targets and cover are weighed, never in rules of play.

**Does a model pick better? The evaluation set (#1203 story 3).** `scripts/tactics-eval/` holds a labelled set of about 40 invented fights (`scenarios.ts`, builders in `fixtures.ts`) and a script that runs three pickers over it: the rules-only `pickTurn`, a Jev Choice over the gated options and a Jev Score per option, highest wins (`supabase/functions/_shared/tacticsJudge.ts`: `choiceRequest`, `scoreRequest`, `pickFromChoice`, `pickFromScores`; pure, the call injected, null when unjudged, nothing wired into an edge function). Each scenario is a creature (every cleverness tier, every derived role, an authored `leader`, notes) in a small fight on a grid (walls, difficult ground, cover, allies, concentration, morale), with labels a Dungeon Master would give: `good` turns, `bad` turns, one line why. The labels are written from the situation and the creature before any picker runs on it; option ids come from listing the options once (`run.ts --options`), and `scenarios.test.ts` holds every label to a turn that exists after the gate. The set is made up, because the requests carry its text to a third party. Rerun it with `npx tsx --tsconfig tsconfig.node.json scripts/tactics-eval/run.ts --label <name>` (`--dry` is rules only and sends nothing; the key `JEV_API_KEY` is read from `.env.local`, this checkout's or the main one, and never printed). It prints good, neither, bad and unanswered per picker, a table by tag, every scenario where the pickers disagree with the labels' `why`, and the tokens the API reports, and writes the full result to `--out` (default the session scratchpad), not into the repo. A wording change in `tacticsJudge.ts` bumps `TACTICS_WORDING`, so a result file says which wording it measured. The judge is given every living enemy's hit points, which a real creature might not know; what a creature can see is not modelled here either. What the comparison showed: a judge that picks the turn (Choice or Score) mostly follows where an option sits in the list (handed the same turns in reverse order, Choice fell from 31 to 14 good picks of 40 and Score from 33 to 28), so neither is a safe general picker; the one place a model helped and held in both orders is reading a DM's note, which rules cannot. So the design that stands is the note veto: only a creature with a note is asked, one yes or no per turn ("does this turn go against the note?", `noteRequest`, `optionsAllowedByNote`, a threshold of 0.5), and `pickTurn` still decides over the turns the note leaves. A creature with no note never calls the model. Rerun both orders with `run.ts --label <name> --note-only --thresholds 0.5,0.7` and again with `--reverse` (20 noted scenarios, 20 requests a run); the files record the chance per turn, and `--reverse` without `--note-only` repeats the Choice and Score comparison.

**Temper (#1021).** `temper.ts` beside the profile reads what can be done to a creature without a weapon: whether words reach it (`words`, `handling` for animal wits or no language, `none` for constructs, oozes, plants and the mindless dead), whether it can be frightened or charmed (the stat block's condition immunities), and whether it ever yields (the profile's morale). The AI table's narrator reads it for each foe and the fight refuses rulings that break it; see agent-runtime.md.

### The server plays a turn (#1203)

`encounter-command` accepts one more command: `{ type: "take_turn", instanceId, optionId? }`, sent alone in its batch. The server builds the creature's options (`assembleTurnOptions` in `supabase/functions/_shared/turnOptionsFor.ts`, the same assembly `encounter-options` serves, so the two cannot disagree), narrows them with `gateOptions` by `tacticalProfile(statBlock, monster_type)` (an NPC or companion has no creature type: null), puts numbers on them with `withNumbers` (a target's armor class is `knownArmorClass`: a player's from the sheet, null when it cannot be read, which leaves its numbers out), and then either picks with `pickTurn` (no `optionId`, `picked: "rules"`) or takes the one named (`picked: "caller"`). The id must be one of the *gated* options computed at that moment; anything else is a 400 "That option is not on offer." that lists nothing. With no `optionId` the server will not pick for a creature whose Action is already spent (`action_used`): a move is then the only turn on offer, and picking it walked an ogre away from the target it had just attacked and into an opportunity attack, so it is a 400 ("<name> has already used its Action this turn; name an option to move it."). A caller may still name an option.

**Carrying it out** is `stepsFor(option, attacks)` (`src/rules/fight/tactics/carryOut.ts`, pure), applied in order inside the attempt that may be saved, so a refusal at any step writes nothing:

1. **Move.** The token's `position` is set to the option's destination and `record_move` adds the option's feet to `movement_used`. A position is not a command (the Play screen writes it through `update_combatant_position`, and the server's own saves keep the row's), so the saved fight takes it from the attempt's state. `record_move` is issued whoever's turn it is, because the options' own movement budget reads `movement_used` the same way.
2. **Attack.** Each swing is a `resolve_attack` against the option's target from the new position (cover and distance come from the map, as for any resolved attack). A Multiattack makes each step `count` times in printed order, each its own resolved attack with its own rolls; a swing is skipped once the target is at 0 hit points, and the swings left are not redirected. A limited or recharge entry is then spent with `use_action` (`actionUseKey`, `actionLimit`), as the runner does, so the same ability is not offered again; only the chosen entry is spent, not the entries a Multiattack names.
3. **Slot.** `set_action_used` for Dash, Flee, Disengage, Dodge, Hide and an attack from Actions; `set_bonus_used` for an attack from Bonus Actions. Move and Surrender use neither. Surrender changes no state.
4. **Leave.** A flee whose option has `leavesMap` ends with `remove_combatant` for the mover, after its move and its Action (the active turn index shifts as for any removal). The `turn_taken` effect then carries `leftTheMap: true` and the `reason` names the way out: "Falls back: at 1 of 7 hit points it breaks and flees, leaving the map through "East gate"." / "... over the edge of the map." A creature that got away is simply gone from this fight: it is **not counted as slain**, no defeat and no loot is recorded for it, and nothing of the kind is touched.

The reply's `effects` begin with `{ type: "turn_taken", turn: { instanceId, optionId, kind, summary, reason, picked } }`, then the resolved effects. It is refused (400) when the creature is not in the fight, is at 0 hit points (a party member the AI plays is not refused while dying: see below), is Incapacitated (it has no options), or has no stat block (a player character the server cannot read, or one Wild Shaped; a player takes their own turn). It need not be the active creature's turn: the DM may run a creature out of turn, as the runner allows, and `take_turn` never advances the turn.

**Allies (#1021).** A party member the AI plays takes its turn through the same pipeline, seen through a stat block made from their own sheet: `allyStatBlock` (`src/rules/fight/allies/statBlock.ts`) holds the six scores, the armour class the runner shows (`playerArmorClass`), the sheet's speed and, as Actions, the attacks `pcAttackRowsOf` lists for what they hold (melee, ranged and thrown weapons, Unarmed Strike, custom attacks with a to-hit bonus; never the Improvised Weapon row), each rolled by `attackEntryOf` (ability modifier plus proficiency to hit). `take_turn` puts that block on the env (`StatBlockSources.allies`, keyed by `party_member_id`) for the mover only, so reach, the swing and opportunity attacks read the one block; the sheet row (`PlayerSheetRow`) therefore also reads `speed`, `level` and `custom_attacks`. **Spells (#1021).** The block also carries a Spellcasting entry built from the sheet (`allySpellcastingEntries`, `src/rules/fight/allies/spells.ts`), written as the prose `parseSpellcasting` reads so `castableNow`, the spell options and `cast_spell` cast an ally's spells exactly as a monster's: one entry per source (a class, or innate) and pair of numbers, so a multiclass caster's spells each use their own class's save DC and attack bonus, worked out by the sheet's rules (`computeSpellcastingByClass`, `grantSaveDc`, `grantAttackBonus`; PHB 2014 "Spellcasting": 8 + proficiency + ability modifier, and proficiency + ability modifier). What is ready: a prepared caster's prepared and always-prepared spells, a known-spells caster's known ones, every cantrip (at will), and an innate spell, at will or with a daily limit. A leveled spell is limited by the sheet's unspent slots at its level, and a higher level's slot casts it when its own are gone (the monster pipeline's upcast rule). The line's slot count is the sheet's unspent slots plus the casts the fight already tallied on the combatant (`slots/<level>` in `action_uses`), because a cast written to the sheet is also in the tally and would otherwise count twice; a rest the sheet took meanwhile gives the slots back. `loadPlayerSheets` reads the ally's `character_spells` (named by id from `library_spells` or the campaign DMs' `spells`), `character_classes` and the class and subclass definitions they are pinned to (`PlayerSheets.casting`, `NO_CASTING` when nothing is read); custom definitions are scoped like custom monsters plus the shared book rows. After a cast, `allySlotSpend` marks the first unspent slot of the level used, `env.slotsSpent` collects the sheet's whole slot list and `runBatch` writes it after the fight is saved (`deps.writeSpellSlots`, absolute, once per member, a failure goes to `effectFailures` as `ally_spell_slots`). **Innate spells with a daily limit** are a "N/day each" line, N being the grant's `uses_remaining` (null reads as none, as the Spells tab reads it) plus the casts the fight tallied under `spell/<name>`, the slot convention again; they are offered while N is above 0. A cast from such a line writes the grant's `uses_remaining` minus one (`allyInnateSpend`, `env.innateSpent`, written after the save through `deps.writeInnateUses`, absolute, once per grant, the member checked against the campaign; a failure is `ally_innate_uses`). `take_turn` pays a cast where the block lists it (`castableBy`): a slot line spends a slot, a per-day line a use, and an at-will or cantrip line nothing (an at-will innate spell of 3rd level no longer takes a 3rd-level slot). **Pact Magic** slots (`pool: "pact"` on the sheet's `spell_slots`) count with the Spellcasting slots at their level, since either kind casts either kind of spell (PHB 2014 "Multiclassing: Pact Magic"); the cast spends the pool of the spell's own class first (`slotPoolFor`: a Warlock, or a custom class with short-rest slots, spends Pact Magic; anyone else Spellcasting) and the other pool when that one has none at the level. A Wild Shaped ally casts nothing (the form's block). Concentration is the pipeline's own. Healing spells (Cure Wounds, Healing Word) are cast like a monster's (see "A creature heals" above); Boons (Bless, Shield of Faith) are cast like a monster's too (see "A creature gives a boon" above); not offered yet: other non-damage spells, a spell whose name has a comma, bracket or colon (the prose cannot carry it), and a negative spell attack bonus (the prose reads `+N` only). **Class features (#1021).** An ally fights like their class, read from the sheet's class rows (`character_classes`, book classes only; a homebrew class sharing a name is not read) and the sheet's own feature catalogue (`src/rules/fight/allies/features.ts`). **Extra Attack** (PHB 2014 and 2024: Barbarian, Monk, Paladin and Ranger at 5th level, Fighter at 5th, 11th and 20th for two, three and four attacks; it does not add between classes): `allyStatBlock` adds one Multiattack entry per set of swings the Attack action can make (`swingSets`), named `Extra Attack (<weapon>)`, so the tactics, the options and `take_turn` read it as a monster's Multiattack. A ranged or thrown attack is offered as one weapon only when one stack (or the weapon's charges) holds that many pieces, and each swing uses its own. **A mixed set** (each attack of the Attack action may use a different weapon): where the best weapon of a kind (melee, or ranged and thrown) cannot make every swing (one javelin, one dagger), the swings it cannot make are the next best weapon's, one more entry `Extra Attack (A + B)`; only weapons of one kind mix, so the whole set is made from one square at one target, and the weapon of the shortest reach or range leads (it says where the creature may stand). The best is told by an average hit against armour class 12 times the chance to hit it, an ordering and not a rule; a set that cannot be filled to two swings is not offered, and a melee set never needs one (melee and bare hands have no end). A turn that swings a melee weapon and throws a dagger at someone out of reach is not offered: the option has one target and the creature does not walk between swings. The options' cut to twelve now keeps a Multiattack before a single swing among equally near attacks, so a creature with many weapons keeps its sets. **Sneak Attack** (PHB 2014 and 2024 Rogue: once per turn, a finesse or ranged weapon hit): the dice are the catalogue's `scaling` at the Rogue's level and the attacks it rides are the catalogue rider's `applies_to` read through `ridersFor` over the sheet's own attack shape, so Unarmed Strike and a longsword never carry it. `resolve_attack` adds the dice to the hit (doubled on a critical like any die) when the roll has advantage, or another enemy of the target within 5 feet of it that is not incapacitated stands there and the attacker has no disadvantage (`attackRollMode`, the roll's own rule, worked out before the roll because the damage is rolled with it). The turn's one use is tallied after a hit that carried it, so a miss keeps it. "Once per turn" is any creature's turn (PHB 2014 and 2024), so the key names the fight's current turn, `sneak_attack/<round>:<whose turn>` (`sneakUseKey`): a Rogue who used it on their own turn has another use for an opportunity attack in a foe's turn, which the strike's estimate weighs too. A Wild Shaped member has none of these features. **More Extra Attack** (`attacksPerAttackAction` reads the class rows and `class_choices`): a Bard of the College of Valor (PHB 2014 and 2024) or of Swords (Xanathar's, 2014 only; the 2024 book has no Swords) attacks twice from 6th Bard level, read from the class row's `subclass_name`; a Warlock of 5th level with the Thirsting Blade invocation and the Pact of the Blade (`pact_boon` in 2014, `eldritch_invocations` where 2024 makes it an invocation) attacks twice with the pact weapon, which the sheet does not record (checked 20 Nov 2026: no field, `class_choices` key or browser storage names the pact weapon, only `pact_boon` and `eldritch_invocations`), so every held melee weapon stands for it (an APP CONVENTION until the sheet can say which weapon is bound; a bow and bare hands keep one attack). Sources do not add. **Sneak Attack in the tactics** (`withNumbers`, `sneakDiceOf`): when the turn's use is unspent and the attack rides Sneak Attack, a swing with advantage, or at normal with an enemy of the target beside it (`enemyBesideTarget`, the one rule `resolve_attack` also uses), adds the dice to its expected damage once per option (a Multiattack counts the dice for the first eligible swing that hits, not each), so a dagger beats a longsword for a Rogue when it applies. **Limited uses** (Second Wind, Action Surge, Rage, a Monk's Ki or Focus): one mechanism. `featureUse` (`allies/features.ts`) reads the pool from the sheet's catalogue row (`usesMaxAt` over the class level, so the edition's table) and what is left from the sheet's `class_resources` (`PlayerSheetRow.class_resources`, read by `loadPlayerSheets`; no stored entry reads full, as on the sheet), and `featureSpend` pays through the sheet's own `payCost`. `take_turn` keeps the paid object on `env.resourcesSpent` (and in the in-memory sheet, so a second turn of the request sees it), and `runBatch` writes it after the fight is saved (`deps.writeClassResources`, the whole object, absolute, once per member; a failure is `effectFailures` as `ally_class_resources`). **The Bonus Action** is a modifier on the turn the picker chose, because one `take_turn` plays one option: `chooseBonusAction` (`tactics/bonusAction.ts`) picks, in order, Second Wind below half the hit points, Rage before the first melee Strength attack, Flurry of Blows after an Unarmed Strike turn while Ki is left, else the Martial Arts bonus strike, and `carryOut`'s `feature` step runs it before or after the turn's own steps. A turn the caller named gets none, and the reply's `reason` says what the Bonus Action was. **Second Wind** (PHB 2014 and 2024): 1d10 + Fighter level, rolled by the server and posted, healing through `adjust_hp`. **Action Surge** (PHB 2014 and 2024, Fighter 2nd level): one more Multiattack entry per set of swings, `Action Surge (<weapon>)` (mixed sets too: `Action Surge (A + B)`), of twice the Attack action's swings, on the block only while a use is left and only when the set swings more than the plain Attack action does, so the tactics weigh it by expected damage like any attack; the sheet is charged when that entry was the turn. **A cast with the extra action** (PHB 2014 only: the 2024 Action Surge is "one additional action, except the Magic action", so a 2024 surge is never a cast): `take_turn` adds composite options (`tactics/surgeCast.ts`) for the best three safe damage casts, each followed by the best extra action the mover still has after it (the first cast's slot or use is tallied on a copy of the mover before the options are assembled again): another safe cast, or an Attack action from the square it stands on (never a walk, never the Action Surge entry itself); the composite's numbers are both actions' together, and the picker weighs it like any cast, so it is taken whenever its second action adds damage. The steps are the cast, a `surge` step that charges the sheet, and the second action. The Bonus-Action-spell rule holds: a composite with a leveled spell in either action is a leveled cast to `healChoice` (a Bonus Action heal does not ride it, and with someone down it is left out of the choice). The `encounter-options` list does not show the composites (it lists single actions and no numbers); a caller cannot name one. **Rage** (PHB 2014 and 2024): a `Raging` condition lasting ten rounds (so it leaves with the fight), the sheet's Rage Damage added to a Strength melee weapon hit (a 2024 rider also rides Unarmed Strike) as a flat amount a critical does not double, and resistance to bludgeoning, piercing and slashing through the damage defenses of every resolution. A rage the player already started on the sheet (`class_choices.rage_active`, `rageStartedOnSheet`) makes the ally Raging at the start of its turn for the full minute (the sheet keeps no time left) and spends no further use. While raging an ally's block lists no spell, and starting a Rage ends the concentration it holds (`end_concentration`; PHB 2014 and 2024 "Rage"). **A Rage ends early** (`allies/rage.ts`, `allies/rageUpkeep.ts`): the server judges every Rage it started for an ally (a Raging condition sourced on its own bearer with the spell "Rage"; one a DM typed on by hand, or a human-played Barbarian's, is the table's) after every command, on the fight as the command found it and left it, and at `next_turn` for the creature whose turn is ending. PHB 2014: knocked unconscious (the Unconscious condition, or 0 hit points) ends it; at the end of the Barbarian's turn it goes out unless an attack was rolled (`shown_deeds` melee or ranged, hit or miss) or damage taken (hit points or temporary hit points lowered) since the end of its last turn, tallied as `rage/kept` in `action_uses` and cleared at each turn's end. PHB 2024: the condition is a `turn` end on the bearer (until the end of its next turn; started on its own turn it survives that turn's end, is armed when its next turn starts); Incapacitated or 0 hit points ends it; an attack roll on the armed turn extends it (the condition is taken off and put on again, since the reducer keeps an applied condition armed over an armed one), and so does the Bonus Action when the chosen turn makes no attack (`rage_extend` in `chooseBonusAction`, no use spent). A Rage that began in the fight is remembered (`rage/started`), so a sheet whose `rage_active` toggle is still on does not start it again after it ended. Not modelled: 2024's "force an enemy to make a saving throw" (no weapon or feature of an ally's block forces one), the 10-minute cap of a 2024 Rage (a fight never reaches a hundred rounds), 2014's "attacked a hostile creature" (any attack rolled counts). The browser applies the same upkeep to a command before the server answers (`applyWithRageUpkeep`, in `fightSync.ts` and the run store), so the DM's screen does not keep a Rage the server ends. The Bonus Action is checked in one place, `chooseBonusAction`. **Martial Arts and Flurry of Blows**: a Monk's Unarmed Strike rolls the sheet's Martial Arts die with the better of Strength and Dexterity (`unarmedDamageBase`). **Monk weapons** (`isMonkWeapon`, `monkTraining`): PHB 2014 "Martial Arts" gives a Monk Dexterity and the Martial Arts die with monk weapons (shortswords and simple melee weapons without the two-handed or heavy property), PHB 2024 with Simple melee weapons and Martial melee weapons that have Light; a weapon's category is its `subtype` ("Simple Melee Weapons"), and a weapon with none is not one the app can call a monk weapon, except a shortsword by name (2014). The benefits hold only "while unarmed or wielding only monk weapons, with no armor and no shield" (`monkTraining`: no body armor, no shield, every weapon held a monk weapon): then each held melee weapon, and a thrown one, is struck with the better of Strength and Dexterity, and the Martial Arts die stands in for the weapon's own die only when it is greater. Otherwise a Monk's Unarmed Strike is the flat 1 + Strength like anyone's. After the Attack action (an attack from the Actions list, any weapon: PHB 2014 and 2024 "Flurry of Blows" asks nothing of the weapon) the Bonus Action is Flurry of Blows (two unarmed strikes, 1 Ki or Focus Point from 2nd level) or, with no point to spend and Martial Arts holding (every attack such a Monk makes is an Unarmed Strike or a monk weapon), one Martial Arts strike. **Divine Smite** (Paladin 2nd level): `resolve_attack` adds the sheet catalogue rider's radiant dice on a melee weapon hit (2d8, +1d8 per slot level above 1st, +1d8 against a fiend or undead, doubled on a critical) and spends the lowest unspent slot through the same write as a cast (`ally slots`); at most once a turn (`smite/<turns>` in `action_uses`), which is the ally's tactic to save slots and not a rule of the book (2014 allows a smite on every hit); in 2024, where the smite is a spell cast as a Bonus Action after the hit, it also needs and uses the Bonus Action. **Paladin's Smite** (PHB 2024, 2nd level): the free cast once per Long Rest is a 1st-level Divine Smite (2d8) that spends the sheet's `paladins_smite` use (the catalogue's `oncePerLongRest`, written through the class-resource path) and no slot; while the use is left it is the cast taken first (an APP CONVENTION: it costs no slot), then the lowest slot as before; a 2014 member has no such row. **Improved Divine Smite** (PHB 2014, 11th level) and **Radiant Strikes** (PHB 2024, 11th level): every melee weapon hit adds 1d8 radiant (2024: an Unarmed Strike too), with no slot, no use and no once-a-turn limit, doubled on a critical (`improvedSmiteFor`, the 2014 catalogue row's die for both editions, as the 2024 catalogue has no Radiant Strikes row). **Not built yet:** Pact Magic slots for a smite as a separate choice (the smite takes the lowest slot of either pool), the Warlock's pact weapon is not told apart from other held melee weapons (the sheet records no weapon as bound), a melee swing and a throw at different targets in one Attack action (an option has one target), and a 2024 Barbarian's Rage extended by forcing a save. **Ammunition and thrown weapons.** A ranged attack uses up a piece of ammunition and a throw leaves the hand (PHB 2014 "Ammunition", "Thrown"), the way the browser's runner does it (`useAmmoConsumption`, `useThrownWeapon`), worked out in `allies/gear.ts`: the stack is the first with the weapon's ammunition kind, a quiver (container) before the belt before the backpack; a charged stack or a self-charged weapon loses a charge; the last unit takes the row away. `allyStatBlock` leaves out a ranged attack with no ammunition or charges left, and a throw with no weapon in the stack, so the ally is not offered them (the browser disables the same buttons). After the swing in `take_turn`, `allyAttackSpend` says what it used up, `env.spent` collects it, and `runBatch` writes it after the fight is saved: a thrown weapon is first put on the ground as the chat's thrown-weapon drop (`deps.dropThrown`, an `item_drop` with `thrown: true`), and only when that posted is the stack written (`deps.writeGear`, absolute numbers so a retry lands once). A miss costs the same as a hit. Two attacks in one request see the stack the first left (`settleSpend`). A failed write is reported in `effectFailures` and never undoes the fight. An ally never flees off the map and never yields (`allyProfile`): the temper rules are for foes, so its morale never breaks and Flee is not on offer. **A Wild Shaped ally fights as the form:** `allyStatBlock` returns the beast's block (its speed, Claws and other actions, bonus actions, traits, senses and defenses; the form's AC from `beast_ac`), with Strength, Dexterity and Constitution from the beast and Intelligence, Wisdom and Charisma from the character (PHB 2014 and 2024 "Wild Shape"). Spellcasting, legendary and lair actions are not carried into a form, and a form's attacks use nothing up. The form's hit points are the fight's own pools (`RunCombatant.wildshape`), not read by a turn. `loadPlayerSheets` already read each form's whole `stat_block` (`PlayerSheets.beasts`, typed `FormStatBlock`), scoped to the library or this campaign's own and its DM's monsters. A form whose block was not read is refused, as before. An ally at 0 hit points who is dying takes a **death saving throw** as its turn: the server's d20 goes through `deathSaveRollOutcome` (10 or more succeeds, below 10 fails, a natural 1 is two failures, a natural 20 stands them up at 1 hit point and clears Unconscious), the tally, conditions and hit points are written on the combatant, and the reply's `turn_taken` has `kind: "death_save"` and `deathSave: { d20, label, status }` (`dying`, `stable`, `dead` or `up`); the roll is posted to the campaign log like any roll the server throws (stamped server-rolled), and the end of the fight writes the tally and conditions to the sheet. A stable or dead one has no turn (400). `encounter-options` lists an ally's options the same way (their sheet's block, no Flee; `allyProfile` and `ALLY_NEVER_OFFERED` in `src/rules/fight/allies/profile.ts`), reading the sheets through `_shared/fightPlayerSheets.ts`. **Opportunity attacks.** Only the played character's Reaction is the player's own. `take_turn` takes an optional `playedMemberId` (the table sends the person's character: `useFightCommands.takeTurn(instanceId, playedMemberId)`); with it, every other party member with a sheet strikes a foe leaving their reach by the rules (`strikeOnLeaving`), and the played one is still reported as `provoked_player`. Without it every player who may strike is reported, as before.


**The DM's note is checked, and only the note (#1203 story 4).** No model picks a monster's turn: the labelled comparison showed a Jev Choice following list position, so the rules-only picker stays the picker. The one place a model helps is reading a creature's free-text `note`. When the server is picking (no `optionId`), the creature's `tactics.note` is not blank and there are at least two turns, the server asks Jev one narrow yes or no per turn ("does taking this turn go against the note?", `noteRequest` in `tacticsJudge.ts`), drops the turns whose probability is 0.5 or more (`optionsAllowedByNote`), and `pickTurn` chooses among the rest. Everything else is exactly the rules-only pick: no note, a turn the caller named, campaign AI off, no platform `typesafe` key (the same `rerankKey` rule as campaign search), the fight at its cap, a call that failed or timed out (6 seconds), an answer with a hole in it, or a note that would rule out every turn. A failure is never an error to the caller.

- **Once per request.** `runBatch` keeps the answers for the request: an attempt that reruns because the fight changed under it reuses the answer when the creature and the set of option ids are the same, and asks again only when they differ.
- **The cap** is 60 note judgments a fight (`MAX_NOTE_JUDGMENTS_PER_FIGHT`): a fight of ten rounds with three noted creatures asks 30, so normal play stays under it and a client looping on `take_turn` stops. The count is the DM's `ai_credit_ledger` rows of operation `tactics_note_judgment` written since the fight went live (`encounter_state.started_at`), or in the last hour for a fight that has not gone live yet (the row has no creation time), plus the request's own earlier asks. The ledger carries no encounter id, so a DM running two fights in different campaigns at once is counted across both: it over-counts, never under.
- **Nothing is charged to the user.** One cost row per real call (a call that answered), written after the fight is saved like the rolls, through `recordFreeGeneration` at delta 0 under `tactics_note_judgment`, model `jev-latest`, input tokens only. `ai_generation_credit_costs` has no row for the operation yet (it needs a migration, kept out of this story), so the admin cost breakdown does not list it; the ledger row is there regardless.
- **The reply says so.** `picked` is `"rules_with_note"` only when a real answer ruled at least one turn out; `ruledOutByNote` then lists each ruled-out turn (`optionId`, `summary`) so a DM can see why a creature held still, and `reason` begins "Its note ruled out N other turns, so:" and keeps the picker's own sentence. An answer that rules nothing out, or every turn, leaves `picked` as `"rules"`.

Four cases from the comparison the note check cannot handle, so a note should not lean on them: it cannot make the picker Hide (the rules choose among what is left, and Hide is never what they choose); it can rule out a guard's only good attack and leave Dodge; it cannot tell who is touching something (adjacency facts are given, not a picture of the room); and one case flipped with the order of the options, so a note that sits near the line is not reliable. `encounter-options` only lists options and never asks.

### The DM's side: "Run this turn for me" and "How it fights" (#1203 story 4)

**The button.** `RunnerRunForMe.vue` sits above the action list of a monster or NPC in the runner's detail panel (`RunnerMonsterPanel`, `RunnerNpcPanel`) and in the Play screen's turn card (`PlayTurnCard`, section "2 · Act"). It is offered for a creature that is not on the party's side and has Actions; a companion fights for the party and is not offered it. One press sends `take_turn` with no `optionId`, so the server picks: `useFightCommands().takeTurn(instanceId)` goes through `lifecycle` (the queue is drained first, the command goes alone, the answer is folded in and the live row re-read, which is what moves the token on the DM's map) and returns `{ turn, outcomes }` from the reply's `turn_taken` and `resolved` effects. `turn` is null for a batch the server had already applied. The runner provides it to the panels as `RUNNER_TAKE_TURN` (`createRunnerTakeTurn` in `runnerResolve.ts`), which also holds the last result, the last refusal and the pending flag per `instance_id`, so a result survives the panel closing and the turn moving on, and a second press while one is out does nothing. A panel mounted outside the runner finds no provider and draws no button.

What the DM reads under the button, in print and never as a toast: the turn's `summary`, its `reason`, the turns the note ruled out, "It left the map and is out of the fight." for a creature that fled by a way off, and one line per roll (`describeResolvedAction` in `src/lib/encounters/resolvedLine.ts`, the client's own reading of a resolved summary; the server's chat lines are separate). When the creature moved over a map with nothing the rules can read (no wall, door, solid cell or difficult cell: `TurnTaken.bareMap`, set in `takeTurn.ts`), a line says "Nothing is drawn on this map, so it crossed it as open ground", because a picture of tables and walls is an empty floor to the rules until it is traced or zoned and a DM would otherwise read the walk as a choice. A refusal shows the server's sentence in place. Two refusals are never sent: the button is greyed with its reason for a creature at 0 hit points and for one whose Action is spent this turn. The button never ends the turn; the DM presses Next turn. There is no standing autopilot: the app plays a turn only when asked, each time.

**The fields.** `StatBlockTacticsFields.vue` is the "How it fights" section of the shared `StatBlockEditor`, so the monster form and the NPC form both have it (the monster form passes its creature type, which decides the default morale; an NPC passes none). Role, Goes for, Cover and When it is losing are selects whose first option is "Automatic: <what the stat block alone gives>", computed with `tacticalProfile` on the block without its authored tactics, so it follows the form as Intelligence or the actions change. Morale is offered as presets (fights to the death, flees or surrenders at a quarter or at half); a stored value that matches none is shown as its own option and kept. "Its note" is one line, 200 characters at most in the form (the server caps nothing). Nothing empty is stored: Automatic deletes the key, an empty note deletes `note`, and the last key gone deletes `tactics`. A library monster's section is read-only with the rest of its form. The NPC editor rebuilds its stat block from named fields on the way in and on the way out (`toStatBlockDraft`, `buildStatBlock`), so `tactics` is named in both; before that an NPC edit dropped it. The fields take the authored tactics as a model (`v-model:tactics`) and the stat block only to read, so a form whose draft is not a whole stat block can use them: the companion form has the section for a companion that fights (not for a pet), deriving "Automatic" from the block as it would be saved, and it names `tactics` in its draft, in what it takes from a monster and in what it saves; before that, saving any change to a companion's stat block dropped its tactics. **On a sheet nobody edits** (the monster's and the NPC's, desktop and phone), `StatBlockTacticsSummary` reads the whole profile out in a "How it fights" box after the actions (the host draws the box, a `TraitList`; the NPC sheets fetch the summary only when the Combat tab is shown, so the tactics rules are not a cost of every NPC page): one sentence each for role, target, cover and morale (`tacticsSentences`; the wording is shared with the fields in `tacticsWords.ts`), then the note. It shows the resolved profile, authored and derived alike, because that is what the turn is chosen by.

**Players never receive it.** `tactics` can hold a plot secret ("turns on the party at the altar"). The one place a player reads a campaign monster's stat block is `get_player_visible_monsters`, once its stats are revealed or as a pinned Wild Shape form, and `20261119121049` makes it return `stat_block - 'tactics'` (`monster_stat_reveal.test.sql`). `monsters_select` lets only the DM side read the table, and `get_player_visible_npcs` returns no stat block at all.

Not in this story: the opportunity attacks a path provokes (the enemies do not react), the effect of Dodge and Hide (the Action is used and no condition is applied), picking by a model (the note check above only rules turns out), ending the turn, legendary and lair actions, spells.

## Key Capabilities / USPs

1. **Unified initiative tracker and stat block browser in one panel.** Clicking any combatant instantly opens their full stat block in a resizable side panel without navigating away. Every ability score, save, skill, and action has a roll button. The DM never needs to look up a second window.

2. **Faction system with automatic colour coding.** Every combatant has a faction with a hex colour. The left border stripe gives a consistent visual grouping across the list. Custom factions support any alignment (e.g. "Town Guard", "Cultists of X", "Mind-Controlled Party Member").

3. **Three-level monster reveal system.** Hidden / Unseen / Revealed is per-combatant and controls what players see. Unseen gives players a "something is there" slot without naming the creature. Cycling to Revealed auto-discovers the monster in the player bestiary.

4. **Pre-scripted encounter events.** The event system handles common "boss phase" patterns without any mid-session fiddling. A phase-2 wave spawn (On Death → Spawn 4 Skeletons) or a timed reinforcement (Round 3 → Spawn Archers) is defined once at build time and fires automatically. Manual events serve as bookmarked DM prompts.

5. **Full boss fight support.** Lair actions appear at initiative 20 with one click per round. Legendary action pools reset automatically at turn start and are tracked with pip indicators in both the combatant list and the detail panel. Action costs parsed from stat block names.

6. **Wildshape overlay.** Beast form HP is tracked independently without touching real character stats. Overflow damage carries through to real HP on revert. The combatant portrait and AC switch to beast form display automatically.

7. **Live player sync via Supabase Realtime.** Players see the initiative order, active turn, HP bars, conditions, and turn indicators on their own device in real time. HP changes in the runner are debounced and written to `party_members`; changes made externally are pushed back in. No separate "sync" button needed.

8. **Bidirectional HP persistence.** Ending combat is a one-click operation that writes HP, conditions, curses, and death saves to all party members (and, as of #569, companion HP + conditions) atomically. Nothing is lost if the DM closes the tab mid-combat — hydration from `encounter_state` restores the full live state on reload.

9. **Mid-combat spawn** — monsters or stat-block NPCs can be injected into the live initiative order at any time, with automatic initiative rolls and legendary action pool priming.

10. **Difficulty calculator integrated into the builder.** The DMG XP budget calculation (with count multiplier, party size adjustment, ally offset, and trap XP) runs live as the DM adds combatants. Visual threshold bars and an enemy breakdown table make it immediately clear whether a planned encounter is worth balancing differently.

11. **Re-import clobber protection (#560).** Re-syncing monsters from Open5e into the shared `library_monsters` table only refreshes fields Open5e actually supplies — name, type/size, source metadata, `stat_block`. DM-authored notes, portrait, description, habitat, and lair link are never touched by a re-run. Full field breakdown in [`docs/library-reimport.md`](../../docs/library-reimport.md).

12. **Party-aware AI encounter suggester (#337), now retrieval-backed (#595).** One concept prompt plus a difficulty tier returns a themed encounter — name, environment, tactics, twist, and a combatant list resolved directly against the DM's own Bestiary, preferring their homebrew monsters by name over same-named library monsters. The party summary and candidate monster block that ground the suggestion are built server-side from the campaign's own data, never trusted from the client — the candidate block is normally populated by semantic (embedding) retrieval over the DM's homebrew and the shared library, falling back to a compact index of the DM's own monsters whenever retrieval is unavailable.

### `EncounterEvent` (JSONB, inside `Encounter.events`)

```ts
type EventTrigger =
  | { type: "round_start"; round: number }
  | { type: "combatant_hp_pct"; combatant_def_id: string; pct: number }
  | { type: "combatant_dies"; combatant_def_id: string }
  | { type: "manual" };

interface SpawnDef {
  monster_id: string; // bestiary monster, or (kind: "npc") the NPC to bring in
  kind?: "monster" | "npc"; // absent = "monster" (#604) — every pre-#604 row has no kind field
  count: number;
  faction_id: string;
  custom_name?: string;
}

type EventAction =
  | { type: "spawn_combatants"; spawns: SpawnDef[] }
  | { type: "broadcast_message"; message: string }
  // #604 — a hazard/terrain change that stays in play once fired; no mechanical payload
  | { type: "environment_effect"; label: string; description: string };

interface EncounterEvent {

  trigger: EventTrigger;
  actions: EventAction[];
```

### `RunCombatant` (ephemeral, inside `EncounterState.combatants_live`)

The live in-memory (and Supabase-persisted) combatant object during a run.

Key fields beyond the definition: `instance_id` (format: `p-{memberId}`, `m-{defId}-{i}`, `n-{defId}-{i}`, `c-{compId}`, `spawn-{monsterId}-{ts}-{i}`), `initiative`, `hp`, `max_hp`, `ac`, `conditions` (`AppliedCondition[]`, #1018), `curses[]`, `death_saves`, `reveal_state` (`"hidden" | "unseen" | "revealed"`), `wildshape?: WildshapeState`, `temp_hp?`, `concentration?`, `surprised?`, `legendary_action_cap?`, `legendary_actions_remaining?`, `reactionUsed?`.

### `RevealState`

- `revealed` — player sees name, portrait, conditions; triggers auto-discovery

### Difficulty system

The `calculateDifficulty()` utility in `encounter.types.ts` implements the full DMG XP budget. Exports `CR_XP` (CR → XP map), `XP_THRESHOLDS` (level 1–20 × Easy/Medium/Hard/Deadly), `crToXp()`, `monsterMultiplier()`, `calculateDifficulty()`. Labels: Trivial / Easy / Medium / Hard / Deadly / Legendary (Legendary = > 2× deadly threshold).
