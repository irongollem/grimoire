# Publishing & Output Tools

## Overview

These are DM-only tools for creating physical and printed campaign materials. They appear in the desktop navigation under a "Publishing" or "Tools" group and are not available in the player portal. The tools share a common design: they produce output that can be printed on A4 paper, exported as PNG/PDF, or uploaded to a VTT. None require external software. Book Nook is the exception to the print theme: it makes a living picture for a place that plays on screens (see its section).

---

## Scriptorium (Document Publisher)

Route: `/scriptorium`, `/scriptorium/new`, `/scriptorium/:id`

A "Canva for D&D" document publisher, and since #1176 one surface: the DM writes on the page that prints, a themed, editable Tiptap sheet laid out live by Paged.js, with a panel beside it that describes whatever is selected. The picture editor, the Illuminator, lives inside it (see "Illuminator inside the book"). The design is the canvas *Scriptorium One Surface* (<https://claude.ai/artifact/7Ss5qL1d5Jt1GVwecmRNnd>, frames 01 to 16); frame 16 lists every control that existed before it and where it lives now, and nothing on it may be lost. The module is `src/scriptorium/` (`README.md` there names the folders).

### Books, chapters and handouts (#1115 story 13)

The design is the canvas *Scriptorium Chapters* (<https://claude.ai/artifact/9dbv3njiLcf9dkZVee93BY>, frames 01 to 12); the decisions are in the body of epic #1115 under "Story 13".

- **A document is a book of chapters, and there is no other shape.** `scriptorium_documents` is the book (title, `kind`, look, page settings, sharing, furniture); the text lives in `scriptorium_chapters` (`position`, `content` as a Tiptap JSON *object* in jsonb, `title`, `word_count`). A handout is a book with one chapter. Migrations `20261029222021` (the model) and `20261029222335` (every old document moved into one chapter; nothing lost: an unreadable body became plain paragraphs). A chapter is named by its first top-level heading (`chapterTitle`, `src/scriptorium/lib/chapterTitle.ts`), written by the client so the chapter list never loads a body. The book's `word_count` is a trigger's (`private.touch_book_from_chapters`): never write it. That trigger is also how a chapter rings live sync: the book's own trigger rings when the book is shared, so a private draft rings nothing.
- **Kind.** `kind` is `book` or `handout`. A handout is set in one of four themes (`letter`, `notice`, `journal`, `plain`; these are looks, and a handout may also lay one of the twelve shared papers over its theme, see "Paper" below; `src/scriptorium/lib/looks.ts` is the one registry of looks, their classes, CSS and a paper's defaults: A5, one column, no page numbers). The list has **New handout** (the paper picker, one click creates and opens it) and **New book** (the template gallery, which creates the book and emits `created`).
- **Editor** (`ScriptoriumBookEditor.vue` shell, `ScriptoriumChapterEditor.vue` per chapter, `ScriptoriumBookHeader.vue`, `ScriptoriumBookSettings.vue`). It holds one chapter; the chapter list (`chapters/ChapterRail.vue`) adds at the end, moves (drag or menu) and deletes (useConfirm; the last chapter cannot go). With one chapter there is no list, only "+ Add chapter" in the footer; a handout never offers it, being one chapter on one paper. A handout says "handout", never "book", in its settings, header and delete confirm. Everything autosaves (`useAutosave`): a chapter through `useSaveChapter`, which patches the caches instead of refetching (an invalidation re-downloaded the whole book on every save), and the settings through `useBookSettings`. There is no Save button. The app's sidebar and bars step aside while a book is open (`editorFocus`). The open chapter is in the address (`?chapter=`), so a reload or a shared link lands on the same chapter.
- **One surface, Focus and Read as spreads (#1176, Scriptorium One Surface):** there is no Write | Split | Inspect switch. The page you write on is the real page: the book is laid out whenever it is open, by `ScriptoriumPreviewPane.vue`, which outside Read as spreads is an off-screen layout host (`.preview-offscreen`: `visibility: hidden` in a zero-height clip, never `display: none`, so Paged.js still measures real layout; its furniture is non-interactive, furniture is edited on the editor's pages) that reports each layout's `ChapterFlow` for the editor to draw. **Focus** (a header toggle, stored under `grimoire:scriptorium:focus`) hides the chapter list for calm writing. **Read as spreads** (a header button, formerly Inspect) shows the same laid-out pages full screen as spreads, lamplit with the campaign theme's dark twin, with notes; Escape and Close return to the page, and so does a note's "Edit this part" (`editBlock` in the shell). Reading is a visit and is never remembered. While the book's first layout runs the chapter list shows a quiet footer ("Numbering the rest of the book", with the chapter being laid out) and a dash for chapters with no page numbers yet; the focused chapter lays out first, and the engine yields to the browser (`yieldToBrowser`, idle time with a 250 ms timeout) before every later chapter so typing stays responsive. The export passes no scheduler. A document with nothing written yet lays out to no pages, so Read as spreads draws a bare sheet in its look instead of an empty stage. Notes (`scriptorium_notes`, `inspect/`) are the author's own, pinned to a block so they follow their text when pages move, never shared or printed.
- **The panel beside the page (#1176 story 2).** A ~20rem panel to the right of the page (`panel/ScriptoriumPanel.vue`, wired in `ScriptoriumChapterEditor.vue`), never over it, always describes the current selection, or the page when nothing is selected. What is selected is one answer, `useScriptoriumSelection` (`deriveSelection` is the pure rule: furniture the DM last pressed on the page, a footer the DM clicked, then a selected image, entry, cover, contents or keepable box in the text, then a cursor in a cover or a box, then the page). Sections: **Page** (the book page and where it falls in its chapter, the paper with a Book settings link, what is on this page, Add to this page), **Footer** (see "Footers are on the page"), **Contents** (nothing to set; it says the page is made from the headings), **Block** (a box or table: the book's look as a link to Book settings, Keep on one page, Across both columns; `panel/BlockPanelSection.vue`), **Picture** (an image in the text and art on the page are one section: **Layer** Behind the text / In front / In the text, then the options for that layer; moving between the text and the page is `useEditorPictures`, which carries `original`, `illuminate` and `bakedFor` across by key and turns width between px and % of the page), **Decoration** (watercolour, watermark, artist credit), **Cover** (applied as typed, one undo step per change) and **Linked entry**. Edits go to the node the selection names, by position (`lib/panel/nodeAttrs.ts`). From 87.5rem the panel is always there; below it, it opens when something is selected, shrinks the page rather than covering it, and closes on its close button or when the DM clicks back into the text (selecting the same thing again reopens it). Focus hides it. The two-column warning's "Place it on the page instead" asks for placement by a `sc-place-on-page` DOM event (`detail.pos`) that the chapter editor answers. **Edit picture** (and the quick edits in the section) work for a picture and for art on the page alike, and only for a picture in the DM's own library (`isBucketUrl("assetImages", original)`, `usePictureEditing.canEditPicture`); anything else says "Only pictures in your library can be edited".
- **The left rail and the book kit (#1176 story 4, frame 13).** The rail beside the page has two tabs, **Chapters** and **Book kit** (`ScriptoriumBookEditor.vue`); a one-chapter book or a handout has the kit alone. `components/kit/BookKit.vue` holds three things: every block the book can be written in (eleven featured tiles named by `kit` in `lib/blockRegistry.ts`, the rest under "More blocks", including the four class tables), the campaign's entries (a search over NPCs, own monsters, spells, items, quests, places, deities, species, factions and subclasses, `useKitCampaignEntries`, `lib/kit/campaignEntries.ts`) and **Art** (Browse pictures, a Web address that must be http or https, and this session's picks, `KitArtSection.vue`). A kit item is one value (`lib/kit/kitItem.ts`) placed by one function (`lib/kit/placeKitItem.ts`), so click and drag give the same content: clicked, it lands at the cursor; dragged, a gold drop line names where ("Drop: Read-aloud") and it lands between top-level blocks, never inside a box (`tiptap/kitDrop.ts`). The toolbar's **From the campaign** opens the kit tab and focuses its search through the Scriptorium UI store. **"/" on an empty line** opens the same blocks as a menu (`tiptap/slashMenu.ts`, `@tiptap/suggestion`, the list in `components/kit/SlashMenuList.vue` carries `data-slip`); the "/" line is taken out and the block put in its place, and a slash in running text is only a slash. A Column Break is offered only in a two-column book (`lib/kit/twoColumn.ts`), and Attribution only inside a pull quote. The block registry no longer holds page furniture: the panel's "Add to this page" covers watercolour, watermark and artist credit.
- **Toolbar** (`ScriptoriumEditorToolbar.vue`): Bold, Italic, Heading, List, **Read-aloud**, **Sidebar**, **Stat block** (the registry's Monster Stat Block), **Table**, **Drop cap**, **Wide**, **From the campaign**, **More** (strikethrough, inline code, numbered list, callout, code block, page break), Cover, Undo, Redo. A read-aloud or a sidebar is the book's own descriptive and note block; nothing about them lives in a floating inspector.
- **Drop cap and Keep on one page are attributes, not markup.** `dropCap` is a flag on a paragraph (`tiptap/dropCap.ts`, class `sc-drop-cap`, drawn with `::first-letter` in `theme-base.css` and finished by each look, so the editor, the preview and the PDF set the same letter; the text is never changed). `keepTogether` is a flag on a read-aloud, sidebar, pull quote, wide block, blockquote or table (`tiptap/blockKeep.ts`, rendered as `data-keep`, which `theme-base.css` turns into `break-inside: avoid` and which beats the layout's own "a very long box may break" call). It is set from the panel's Block section, which also wraps a box in the wide block or takes it out (Across both columns).
- **Zoom (#1176 story 7, frame 07).** A control in the header (`ZoomControl.vue`): minus, the level (**Fit** or a percentage) and plus. The steps are 50, 75, 100, 125, 150 and 200 percent (`lib/zoom.ts`); **Fit width** (Mod+0) fills the space up to 200 percent and **Actual size** (Mod+1) is 100, which is the printed size. It is a transform on the sheet (`ScriptoriumChapterEditor.vue`), never CSS `zoom`, for the reason given under "The preview scales with a transform", and a new zoom keeps the spot the writer was looking at where it is on screen: the caret when it is in view, else the middle of the pane (`zoomAnchorPoint` / `zoomScrollDelta`). It used to scroll to the caret, which sent a DM reading page 12 with the caret still on the cover back to the cover. The choice is remembered per browser (`scriptoriumZoom`, `grimoire:scriptorium:zoom`). There are no spreads while writing: two live pages of one document would need a second layout, against "the PDF is the page"; Read as spreads is the place for facing pages.
- **Layout per chapter** (`src/scriptorium/lib/bookLayout/`). Every chapter opens on a right-hand page (a blank page is inserted after a chapter that would end on one), so a change in one chapter can never move another chapter's pages: the engine lays out only the chapter that changed, then one post-pass writes labels, footers, the contents page and furniture over all pages in book order. Measured on the 533-page Sothery book (29 Oct 2026): a full layout 9.2 s, one 33-page chapter re-laid out in 0.7 s, a footer or page-number change 5 ms. The preview (`useBookPreview`) and the PDF export use the same engine, so the preview is what prints. Paged.js's processed page rules are global, so the engine keeps only the newest run's styles (reasoning in the engine's header). A chapter whose prepared HTML is empty is never handed to Paged.js (it would paginate the whole app). Furniture pinned to a page names its chapter and the page within it (`{type:"page", chapterId, page}`).
- **What prints and what players read.** `src/scriptorium/lib/layoutContent.ts` is the one place a chapter's JSON becomes layout HTML: a DM-only `secretBlock` ("Only you see this", now offered in the Scriptorium) never previews or prints; a handout's preview and print drop the Deep half of a lens pair, a book prints both readings. Players never read chapter rows: `public.get_player_handout(doc, chapter?)` (definer, holders and the campaign's DMs only) returns the chapter list and one chapter with `private.strip_secret_nodes` applied, so a handout may now hold lens pairs (the refusal trigger of `20261027080700` is gone). Sharing, a quest's give-handout and a notice board's take read the whole book through `private.book_body`, which strips the same way (`20261030072503`): an NPC embedded in a secret block or a Deep half is revealed to nobody. Reordering chapters is one call, `reorder_scriptorium_chapters(book, ids)` (invoker; it refuses an order that does not name every chapter exactly once), so a drag touches the book and rings its players once. A book keeps at least one chapter: `private.keep_one_chapter` refuses the delete that would empty it, after locking the book so two tabs deleting at once cannot both pass. When the chapter a phone reader has open disappears, `ScriptoriumReader` returns to the contents.
- **Give to players** (`HandoutShareDialog.vue`) is one screen: **Hand it over** (tick who gets it, see what that reveals) or **Pin it on a board** (pick a board, the line on the front; the pin's style follows the paper, `noticePinStyleForPaper`, and taking the notice gives the whole party the handout as the board already does). `HandoutAudienceLine.vue` under a handout's header says who holds it and what linked entry is still hidden.
- **Carried with the book:** the World Bundle and the campaign backup move chapters with their book through one module, `src/scriptorium/lib/bookTransfer.ts` (new ids, `document_id` and furniture `chapterId` remapped; a file from before chapters imports as one chapter). The demo catalogue copies chapters (tier 2) and not notes. `npm run scriptorium:book` writes one chapter per manuscript file and keeps chapter ids stable on re-import (by position), so notes survive.

### Document Types

Documents are tagged with a type that drives the colour-coded badge in the list view: Custom, Spell, Monster, Item, Class, Subclass, Species (race), Background, Adventure, NPC Sheet, Location, Quest. See `ScriptoriumDocType` in `src/scriptorium/types.ts`.

### Editor and custom nodes

`createScriptoriumExtensions()` (`src/scriptorium/lib/scriptoriumExtensions.ts`) builds the Tiptap extension stack on top of `StarterKit` and the table extensions. Beyond the standard formatting (bold, italic, strikethrough, inline code, H1 to H3, lists, blockquotes, code blocks), the galley has book-specific custom nodes, each its own module under `src/scriptorium/tiptap/` (`lensPair` and `secretBlock` stay in `src/lib/tiptap/`, shared with the rich text editor):

- `coverPage`: front cover, inside cover, part divider, back cover blocks; its words are typed on the cover and the rest is edited in the panel beside the page (`panel/CoverPanelSection.vue`), live, with no Apply (see "Covers, the contents page and linked entries are drawn as they print")
- `tocBlock`: a table of contents that Paged.js fills with real page numbers at render time (`src/scriptorium/lib/pagedToc.ts`)
- `descriptiveBlock`: read-aloud boxed text
- `noteBlock`: a callout/note box
- `quoteBlock` and `attribution`: a pull quote and its attribution line
- `wideBlock`: a block that spans both columns
- `columnBreak`: forces a new column
- `pageBreak`: forces a new page (this replaced the old horizontal-rule convention; see `documentContent.ts`'s import-boundary normalization for legacy documents)
- `divider`: the fine rule with a small ornament that closes a chapter's title block (style Flourish, Rule or Stars, chosen in `panel/DividerPanelSection.vue`). It is `div.sc-divider`, never an `<hr>`: an `hr` is a legacy page break in print and StarterKit's horizontalRule owns the tag. The ornament is a CSS mask over the look's accent (`--sc-divider-color`, default `--sc-accent`) in `theme-base.css`, so it recolours with every look and paper and prints
- `skipCounting` / `resetCounting`: structural page-numbering controls
- `SpacerVertical` / `SpacerHorizontal`: layout spacers
- `ScriptoriumImage`: the image node, with layout modes (size presets, align, float-left/float-right with text wrap, gutter-bleed in wrap mode), its options (size S/M/L/XL, align, wrap, gutter bleed, keep with its text) are in the panel's Picture section when the image is selected. It has no free-placement mode: the Picture section's **Layer** control (Behind the text, In front, In the text) moves the picture between the text and the page: Behind or In front turns it into art furniture (see Page furniture). An old pasted `data-layout-mode="absolute"` image parses as inline; the import boundary (`documentContent.ts`) lifts one into art furniture
- `dropCap`, `blockKeep`: attribute extensions (see "Drop cap and Keep on one page")
- `slashMenu`, `kitDrop`: the "/" menu and the drop line (see "The left rail and the book kit")
- `pageFlow`, `furnitureUnderlay`: draw the laid-out page's gaps, columns, footers and the picture layer behind the text on the editor's sheet
- `BlockId`: a stable per-block id used for click-to-edit (a note in Read as spreads jumps to its block), surviving Paged.js's pagination
- `entityEmbed` (`src/scriptorium/tiptap/entityEmbed.ts`): a live-linked NPC/monster/spell/item/location/quest/deity/species/faction/subclass block (see Linked entity embeds, below)

Every block above is inserted from the book kit or with "/" (`lib/blockRegistry.ts` is the one list, grouped Text, Cover Pages, Layout, Callouts, Templates, Structural); a live-linked entry is dragged or clicked in from the kit's campaign search (see "The left rail and the book kit"). The Insert Block modal (`BlockPickerPanel.vue`) and the Insert Asset panel (`AssetInsertPanel.vue`) are gone.

### The editor's page is the real page (#1175)

The sheet the DM writes on is the page that prints, line for line, on every paper and page size.

- **One geometry.** `src/scriptorium/lib/pageGeometry.ts` holds the `@page` margins, the print slack and the column gap; `pagedPreviewCss.ts` builds `@page` from it, and the chapter editor puts it on the sheet as `--sc-*` custom properties (page width and height, margins, fitted content height, column width and gap). Type is stated once for both sides in `theme-base.css` (`.pagedjs_page, .phb-editor .ProseMirror`: 16px / 1.5; the papers override both). The editor also undoes Tiptap's `font-variant-ligatures: none` and `white-space: break-spaces`, which made the sheet break lines a word early in the book's fonts. The sheet is scaled to the pane with a transform (never CSS `zoom`, which re-lays text out); anything measured on it uses `offsetWithin` (`pageFlow.ts`), never `getBoundingClientRect`.
- **Pages and columns come from the preview.** After each layout the preview measures the open chapter (`src/scriptorium/lib/pageFlow/measureFlow.ts`) into a `ChapterFlow` (`pageFlow/types.ts`): where each page starts, and in two columns where the second column of each page's last column row starts, each as a block id plus a count of "layout text" characters (text not under `contenteditable="false"`, `pageFlow/layoutText.ts`, counted the same way on both sides). The editor's `PageFlow` extension (`src/scriptorium/tiptap/pageFlow.ts`) draws a page gap there (a widget that fills the rest of the page, its bottom margin, the gap between sheets and the next top margin) and a forced column break. A two-column chapter is a real multicol editor (`phb-two-col sc-flow-columns` on the root): a block widget with `column-span: all` inside a paragraph is a full-width spanner in Chrome, and a `break-before: column` one forces the column mid-paragraph; the rows above a spanner the browser balances itself, identically on both sides. A column's start is "right after the last column-1 content", not "the first column-2 content": the browser can push a float into the next column ahead of text still filling this one.
- **What the preparation reshaped.** `pagedPrepare.ts` reshapes some blocks before layout; the flow names them (`layoutClasses`: `sc-table--span`, `sc-flow-float-end`) and the editor gives the same blocks the same classes (`scriptorium-page-flow.css`). The contents page and covers span both columns in the editor as on the page.
- **Markers take no room.** Page and column breaks, spacers, the wide-block outline and the numbering pills are drawn with outlines, zero-height lines and labels out of the flow (`scriptorium-editor.css`), so they never move text the page does not move.
- **Ctrl+Enter breaks the page** (Cmd+Enter on a Mac, where Ctrl+Enter also works; `PageBreakKeys` and `breakPageHere` in `tiptap/pageBreak.ts`): what follows the caret starts the next page and the caret goes with it. A break always sits between top-level blocks: the caret's place is first widened to the edge of whatever it is at the edge of (the start of a box's first paragraph is the start of the box, which then moves whole), and anything still around it is split there, so a box broken in its middle becomes two whole boxes and a numbered list carries on counting (`start`). At the end of a block the next page opens on a new empty paragraph. It declines in code and in a table, where the key keeps its usual meaning.
- **A page that opens on a whole box names the box.** `measureFlow.ts` widens a page or column start at the very beginning of a box's first paragraph to the box itself (unless the box is a continuation fragment, `data-split-from`), so the editor draws the gap before the box. Naming the inner paragraph drew the gap between the box's frame and its first line, leaving an empty frame at the foot of the page before.
- **Until the first layout lands** the sheet is one continuous page with the real measure (a two-column chapter is written in a one-column strip where column 1 sits); page gaps and columns then appear as the layout reports them. The editor's scroll container keeps CSS scroll anchoring (`overflow-anchor: auto`), so gaps inserted above the line being written do not move it.
- **Known limits**: a linked entry's lore column that print splits across pages shows whole in the editor, so that page's height differs (the gap fill absorbs it). A wrapped picture the DM has set not to keep with its text (see "When print moves a picture") and that the printer pushes into the next column stays beside its paragraph in the editor, which cannot reorder markup.
- **When print moves a picture** (#1176 story 11): a wrapped picture sits before its paragraph, and when it does not fit at the foot of a column the printer pushes it on and leaves the text where it was, which the editor cannot draw. `measureFlow.ts` reports every wrapped picture drawn in a later column or page than the first line of the paragraph after it (`ChapterFlow.pushedFloats`; a picture already grouped with its paragraph is never reported). When a flow arrives, PageFlow's `appendTransaction` (`keepPushedPictures`) sets `keepWithText: true` on each pushed picture the DM has not chosen for, outside the undo history, and `groupWrappedImages` then groups it with its paragraph (and a heading right before it) whatever the paragraph's length, so the pair moves to the next column whole, as in a word processor, and the editor shows what prints. `keepWithText` has three values: unset (the default), `true`, and `false`, which the DM sets by unticking **Keep with its text** in the panel's Picture section to let the printer move the picture on alone. There used to be a margin note asking the DM to choose; the maintainer found it baffling (11 Nov 2026), so the sensible choice is now made for them.

### Covers, the contents page and linked entries are drawn as they print (#1176 stories 5 and 6)

Frames 05 and 06. These three were placeholders in the editor (a card saying a cover was there); they are now the printed page, edited in place, so there is no second picture of the book to compare with.

- **Covers** (`CoverPageView.vue`, markup from `lib/coverMarkup.ts`, the same function `tiptap/coverPage.ts` renders for the page). The words are typed on the cover: its fields are marked while editing and a typed word does not redraw the cover (`drawingKey`), so the caret stays. The attrs are `title`, `subtitle`, `partNumber`, `blurb1` to `blurb3`, `tagline` and `productUrl`, plus `backgroundImage`, `titlePlace` (`top`, `middle`, `bottom`) and `shade` (`none`, `dusk`, `parchment`). `shade` replaced the old `titleScrim` toggle; migration `20261111031621` rewrote every stored cover, and the Markdown import still reads `scrim: false` as `none`. The panel's Cover section keeps the art (upload, browse the library), where the title sits, the shade under the title (with art on a front cover), and which cover it is (Front, Inside, Part, Back).
- **The contents page** (`ContentsView.vue`) shows the contents HTML the layout wrote, with the page numbers where headings landed, and a quiet note that it is made from the headings. It is selected for the panel (nothing to set) and never edited as text. Before the first layout, or in a read-only view, it is the placeholder it always was; the phone reader draws its own tappable list.
- **Linked entries** keep their node view (`EntityEmbedView.vue`) and take the printer's fit for each entry by block id from `usePrintedBook` (`PRINTED_BOOK_KEY`; the book editor provides it, `useBookPreview` writes it after each layout through `recordPrintedBook`, `lib/entryFit.ts` reads the per-entry result of `pagedEntryFit.ts`). So a column or wide entry, its art height and its band sit as printed. Every option still lives in the panel's Linked entry section.
- **The one remaining difference**: a linked entry's lore column that print splits across pages shows whole in the editor.

### Footers are on the page (#1176 story 6, frame 10)

Each page of the open chapter draws the footer the print made, in its bottom margin (`ChapterFlow.footers`, drawn by the `PageFlow` extension from the same `buildFooter` element the preview and the PDF use, `lib/pagedFooters.ts`). Clicking one selects it for the panel (`pageFlow` storage `footer`; a click in the text, any key or Escape clears it). The panel's **Footer** section (`panel/FooterPanelSection.vue`) holds the book's choices and three choices that are about that page only:

- The running title on right pages (`footer_title`: chapter, book or custom, with `footer_text` for custom; a left page always carries the book's title, `lib/footerTitle.ts`), and the numbers (show them, where the count starts). These are the same settings as Book settings.
- **Footer style** (`footer_style`: plain or ribbon, the choice sits beside the running title here and in Book settings). The ribbon sets the running title on a tan banner with a swallow-tailed inner end, flush to the page's edge (`sc-footer-style--ribbon` on the look's element, CSS on `.sc-footer-text` in `theme-base.css`, no markup change, so the editor's footers, the preview and the PDF share it). The page number stays where the look puts it; the banner's colours are the look's `--sc-ribbon-bg|edge|ink` tokens. It is 22px tall inside the 32px footer, so it fits A4, A5 and Letter alike. Ink-friendly keeps it. Drawn on the *Scriptorium Supplement Pages* canvas, frame 03.
- **No footer on this page**, **Don't count this page** and **Start the count again here**. They are stored as the page-numbering markers `skipCounting` (with `keepFooter` for "Don't count", so the page keeps its running title) and `resetCounting` at the page's first block (`lib/pageMarkers.ts`), the same stored form print has always honoured, and the DM never sees them as chips. A footer prints only on numbered pages and on a skipped page that keeps its footer (`pageHasFooter`, `lib/pageNumbering.ts`). There is no footer toolbar (italic, alignment) because print has no per-footer style.

`offsetWithin` (`pageFlow.ts`) reads nested elements from their drawn position, because split blocks broke a sum of `offsetTop`.

### Lens pair (#1115)

A passage read at two levels: **Bright** (a child's reading) and **Deep** (an adult's), set side by side. `src/lib/tiptap/lensPair.ts` holds three nodes: `lensPair` (attr `variant`: `boxed` default, `light`) with content exactly `lensBright lensDeep`, so neither half can be deleted alone. Each half takes `block+`. The labels come from `renderHTML` outside the content hole (`.sc-lens-label`, non-editable), so they are never document text; the sun and moon glyphs are CSS masks. `insertLensPair()` (Mod-Alt-L) refuses inside a pair. Insert it from the block picker (Callouts) or the entity editor's toolbar. The galley's Boxed / Light toggle and "Lens pair" strip are `LensPairView.vue`, editor-only, never in `renderHTML`. An empty half shows a placeholder in the galley (`p.is-empty`).

- **Book styling** is `.sc-lens` in `theme-base.css` from the `--sc-lens-*` tokens in both theme files: gilt rule above, dusk-plum rule below, cream and dusk grounds. Inside `.sc-wide` the halves go side by side with a hairline between. `.sc-lens--light` drops grounds, rules and label text and leads each half with its glyph. `.ink-friendly` zeroes the grounds, makes the rules near-black and dashes the Deep separator. An empty half (or a wholly empty pair) is hidden under `.phb-page` (preview and PDF) with `:has()`; the galley keeps it.
- **Entity text** uses the same markup styled from the app's tones in `src/assets/lens-pair.css` (Bright amber, Deep arcane; Deep's label reads "Deep · DM only").
- **Audience:** `renderStoredDoc(content, { audience })` (`viewerRender.ts`) shows a DM both halves and a player only the Bright half's blocks, unwrapped, no box or label. The default is `player`. `RichTextViewer` passes `dm` only when the signed-in user's role is DM (`useLensAudience` in `secretDisclosures.ts`, fed by the layout's `isDm`), never merely because a layout provides the disclosure context: `DefaultLayout` provides it to every role. **The server withholds the Deep half** exactly where it withholds `secretBlock`: `private.strip_secret_nodes` replaces a pair with its Bright half's blocks and drops a stray `lensDeep` (`20261027012548`), so every projection that calls `private.withhold_secret_blocks` (locations, items, puzzles, notes, factions) sends a player Bright only. The client view is presentation, not the protection.
- **Where the editor offers it:** `RichTextEditor` shows the toolbar button only when `allowSecrets` (a field the server strips) or `allowLensPairs` (a field players never read, such as an NPC's lore in `NpcLoreTab.vue`) is set. A quest beat's rumour and reveal text (`allow-secrets` in `QuestBeatFields`) offer it, since `get_player_visible_quest_beats` strips them like the other projections (a quest's `summary` stays plain text and does not). The node is registered in every editor, so text holding a pair is never lost by opening it elsewhere, but only a `creatable` one (`lensPairExtensions({ creatable })`: those two props in `RichTextEditor`, always in the Scriptorium) makes one. Elsewhere `insertLensPair()` and Mod-Alt-L do nothing and a pasted or dropped pair arrives as its Bright half alone; text selected inside a Deep half and pasted is kept as text, since that is the DM sharing the line on purpose.
- **In a handout:** since #1115 story 13 a player reads a handout through `get_player_handout`, which strips the Deep half like every other projection, so a handout may hold a pair and its players read the Bright half. (Until then players read the row directly and `20261027080700` refused to share a document holding a pair.) A handout's own preview and print drop the Deep half too; a book prints both readings.

### Markdown import directives

`markdownToScriptoriumContent(markdown, options?)` (`src/scriptorium/lib/markdownImport.ts`) reads `::: name [args]` containers (flat, not nested; an unknown name passes its content through). Besides `read-aloud`, `note` and `quote`:

- `::: lens [light] [wide]`: a paragraph that opens with a bold run-in label (`**Bright.**`, `**Bright:**`, `**Bright lens:**`, any case; same for Deep) starts that half and the label is stripped; text before any label is Bright. `light` sets the variant; `wide` wraps the pair in a `wideBlock`.
- `::: wide`: wraps its blocks in a `wideBlock`.
- `::: art`: `key: value` lines (`slug`, `size` = full|half|column|wide|opener, `lane`, `existing`, `alt`, `caption`, `brief`). `options.resolveArt(slot)` returning `{ src }` emits the image (half = `50%`, otherwise `100%`; wide and opener inside a `wideBlock`) and an italic caption paragraph; otherwise a `noteBlock` "Art to come: caption" with "Brief: ..." (or "Source: existing") on a second line. `ArtSlot` is exported.
- `::: statblock` (`name:`) and `::: embed` (`type:`, `name:`): `options.resolveEmbed({ type, name })` returning `{ id }` emits an `entityEmbed` (statblock is `monster`); otherwise a note "Stat block: name (not yet in the campaign)".

The module does no I/O: the caller looks art and entities up and passes the answers in.

### Linked entity embeds (#915 story 3)

Two paths put an `entityEmbed` node into a document: the **book kit's campaign search** (`BookKit.vue`, NPCs, own monsters, spells, items, quests, places, deities, species, factions and subclasses, dragged onto the page or clicked in at the cursor) and **Send to Scriptorium** on an entity's own detail page (`NpcDetail.vue`, `MonsterDetail.vue`, `SpellDetail.vue`, `ItemDetail.vue`, `QuestOverviewLifecycle.vue`), which creates a whole new document whose content is a single `entityEmbed` node (the entity's formatted body already opens with its name) (`buildEntityEmbedDocumentContent`, `src/scriptorium/lib/entityEmbeds.ts`). Either way the node stores only `{ entityType, entityId }`, never a copy of the entity's fields, so the document always shows CURRENT data and never goes stale when the source entity is edited.

Resolution is split across three pieces:

- `collectEntityRefs(json)` / `resolveEntityEmbeds(html, lookup)` (`src/scriptorium/lib/entityEmbeds.ts`) are pure: the first walks a Tiptap JSON document for the unique `{type, id}` refs it holds, the second replaces each placeholder `div[data-type="entity-embed"]` in a rendered HTML string with the entity's current, sanitized body HTML (or a "no longer available" marker), in place, so `data-block-id` and every other attribute on the block survive.
- `useEntityEmbedData(refs, { theme })` (`src/scriptorium/composables/useEntityEmbedData.ts`) fetches every referenced entity UNSCOPED by id (`useQueries`, batched per type, sharing query keys with `useNpc`/`useResolvedMonster`/`useSpell`/`useItem`/`useLocation`/`useQuest` so the cache is shared), resolves the secondary joins the formatters want (an NPC's location name, a quest's giver/location names and objectives, an item's granted spells) in a second dependent pass, and formats each into body HTML via `formatEntityEmbedBodyHtml` (`scriptoriumImport.ts`'s single dispatch point over the same formatter objects `formatNpcForScriptorium` etc. already use).
- `EntityEmbedView.vue` is the node's Vue node view (`VueNodeViewRenderer`): it renders the live, sanitized content inline in the galley, with a small toolbar (editable mode only) that keeps only **Open** (routes to the entity's own page) and **Detach…** (confirms via `useConfirm`, then replaces the node with its current content as ordinary editable nodes; the entity stops updating the document from that point on). Every other option (size, art, lore, band, new page, what sharing reveals) is chosen in the panel's Linked entry section (`panel/EmbedPanelSection.vue`). The panel asks the entry to open or detach by a DOM event on its element (`sc-embed-open`, `sc-embed-detach`, `lib/panel/embedSignals.ts`), because the view knows what it shows and holds the router.
- **Open and Detach (#1176).** **Open** shows a monster's or spell's sheet over the book (`MonsterDetailModal` / `SpellDetailModal`) and an NPC in the app's NPC peek (`useOpenNpc`), so the book stays where it was (the monster and spell routes are children of their lists, which put the bestiary behind the sheet); other kinds go to their own page. **Detach** turns the entry into ordinary editable text that looks exactly as it did: the schema keeps the entry's `sc-` classes through `tiptap/detachedEntry.ts` (`ClassedBlock` and `ClassedLine` for classed divs, `ScClass` on paragraphs and headings, `ClassedSpan` for spans, each parsed span unique so two side by side never merge, and `EntryArt` for the bare entry picture), only ever `sc-` classes and the `data-band-position` / `data-label` / `data-art-kind` attributes, so pasted HTML brings no styling of its own. An entry that started its own page gets a real page break before it (or before the level-two heading right above it, `detachedEntryBreakAt`), so no page moves. The range replaced is the document's node, never the node view's `props.node`, whose reactive copy reports a leaf's size as 2 and once deleted the next entry with it. A detached entry is the DM's own text from then on: it no longer follows the creature, and a player reading a handout sees it as written, whatever the creature's reveal state.

The preview pane and PDF export stay HTML-string based (Paged.js paginates a string, not live components), so the editor resolves embeds itself, per chapter: `useBookChapterHtml` takes the open chapter's HTML from the live editor and every other chapter's from `chapterLayoutHtml` (memoised on its `updated_at`), each through `resolveEntityEmbeds(html, lookup)` where `lookup` comes from `useEntityEmbedData` over the refs of every chapter. HTML is built **on demand only**, inside the debounced render, never per keystroke or per embed's data landing: on the 533-page Sothery book the eager version cost ~100 ms per keystroke and per embed landing, about 160 landings on open, which froze scrolling for ~18 s of the first 30 (#1115). Keep it lazy: anything that re-reads the book as HTML belongs inside the render.

`ScriptoriumDocumentView.vue` is the read-only counterpart: it mounts a non-editable `Editor` with `createScriptoriumExtensions()` through `<EditorContent>`, which is enough for `entityEmbed`'s own node view to resolve itself live (no manual `resolveEntityEmbeds` pass needed): `VueNodeViewRenderer` only activates once `editor.contentComponent` is set, which happens on `<EditorContent>` mount regardless of `editable`. It replaced the generic `RichTextViewer` for a quest beat's attached handout in `QuestRunContainedTool.vue`, whose schema had no idea what a `coverPage`, `noteBlock` or `entityEmbed` node was, silently dropping a handout's cover, read-aloud boxes and linked entities at the table.

A chapter's `content` is a jsonb Tiptap document (#1115 story 13), so there is no stored string to parse and no "could not be read" state any more. `src/scriptorium/lib/documentContent.ts` keeps the import boundary only: **`normalizeImportedDocument(row, chapterId)`** is where content still arrives from outside this app's editor (an old World Bundle or backup, through `bookTransfer.ts`): a Tiptap object, a JSON string or raw HTML becomes a chapter's JSON, and legacy decorations are lifted into `page_furniture` pinned to that chapter.

The `watercolor`, `watermark`, and `artistCredit` Tiptap nodes were deleted in story 2 — they existed only so old content parsed, and the import-boundary normalization now lifts those legacy shapes into `page_furniture` before the schema ever sees them, so nothing needs to keep parsing them. New decorations have only ever been page furniture (see below), never content nodes.

### Monster/NPC entry layout (#915 story 6 round 2)

A monster embeds as a Monster Manual-style ENTRY, not just a framed stat block: a document heading (so it enters the table of contents and Read as spreads' note pins find it by block id — `pagedToc.ts`), the framed block, and the creature's art and lore. `scriptoriumImport.ts`'s `monsterFormatter` wraps all of it in `.sc-statblock-entry`, a `column-span: all` unit laid out as its own CSS grid (`theme-base.css`'s "Linked entity ENTRY layout" section) — deliberately not a manual `.sc-column-break` (round 1's approach), which Paged.js's multicol polyfill didn't honour reliably and could spill a tall stat block's art onto an otherwise empty next page.

- **Size** (`estimateStatBlockSize()`) is decided from the stat block's own TEXT length (tags stripped), not entry count — measured theme-agnostic, since the two themes print materially the same words at very different HTML verbosity. `WIDE_STATBLOCK_CHAR_THRESHOLD` (1,350) is calibrated against the Sugarwell booklet's six creatures; see the constant's own doc comment for the measured numbers.
- **Column size**: a two-cell grid — stat block left, art then lore right, both cells the width of the page's own two-column measure.
- **Wide size**: the stat block band (its own internal two-column flow) then the art floated at the start of the lore, which wraps beside and under it; `bandPosition: "bottom"` puts art and lore above the band instead. The art takes what the page leaves under the band, never more than 16rem. Two grid layouts before it failed on the Sugarwell booklet (#917).
- **Fitting an entry to its page is measured, not predicted (#915 story 6, round 3).** A Paged.js handler (`src/scriptorium/lib/pagedEntryFit.ts`, registered by both renderers) preloads every entry's art, then on each page, before Paged.js looks for overflow, takes any entry whose margin box runs past the page bottom, drops its bottom margin, and binary-searches the tallest art that still ends it on the page (floor 96px). One that cannot fit even then gets `sc-statblock-entry--split` (`break-inside: auto`, `pagedPreviewCss.ts`). Before the art, a *column* entry that starts its page and still overflows is set wide, on the page and in the parsed source Paged.js clones continuations from (#1115): a column entry is a two-cell grid, a grid does not break across pages, and the stat block's tail was painted into an off-page column, the embed wrapper's box landed there too, Paged.js broke before the whole entry, found itself where the page began, logged "Unable to layout item" and printed none of the tail (the Candy Archer's Bonus Actions and four other Sothery creatures). The column-or-wide choice comes from a character count (`estimateStatBlockSize`), which cannot see typography; the page can. A column entry lower on a page is left to move whole to the next one and is measured again at its top. It replaced a band-height formula that typography changes had pushed 19 to 41px short, which lost the Caramel Crusher's lore: Paged.js resumes after an unbreakable block that fits no page, so the rest of the entry was silently dropped. Two traps it handles: the page content box is itself a multicol, so an entry fitted to its border box whose bottom margin overflowed was laid out in an off-page column and the page printed empty; and `beforeParsed` receives the HTML string, so the preload runs in `afterParsed`.
- **Duplicate name**: when the entity has no lore (or `showLore: false`), the entry heading gets `sc-statblock-entry-heading--no-lore` (visually hidden, `theme-base.css`) rather than being removed — it still needs to be there for the TOC/reader list. With lore, both the heading and the frame's own name show, matching a real Monster Manual entry.
- **Codex entries (#1115 story 7).** A deity, faction, species or subclass embed prints the way a 5e book sets one (`scriptoriumImport.ts`): a `.sc-codex-entry` with a small `h3` name (never an `h1`, which a two-column book reads as a chapter title), an italic line (a deity's titles, a faction's kind and alignment, "Cleric Subclass"), bold-label property lines, the text, then a species' traits and subraces or a subclass's always-prepared spell table and its features as "Level N: Name", in numeric level order. The picture (deity portrait, species image, faction emblem; a subclass has none) floats right like a treasure entry's and can be hidden per node; there is no cutout choice. Unlike `.sc-item-entry` the wrapper may break across pages, since a species runs for several. The book's class content is its subclasses, which is why the class embed is a `custom_subclasses` row: `useEntityEmbedData` reads its features (`class_features` by id, `useFeaturesByIds`'s key) and spell names in a second pass, and renders nothing until both are in rather than a subclass without its features. Rich text that holds a lens pair prints as the pair (`tiptapJsonToHtml`), not as both readings run together.
- **Overrides** (`size`, `showArt`, `art`, `showLore`, `bandPosition`, all `entityEmbed` attrs edited in the panel's Linked entry section) are applied post-hoc by one function, `applyEmbedNodeOptions()` (`entityEmbeds.ts`), swapping classes/attributes on the already-injected HTML: the formatter always emits a size-"auto" default shape, and per-node attrs never change what's cached in the shared entity lookup. `resolveEntityEmbeds()` calls it for the paged preview and the PDF (options read from `data-*`), and `EntityEmbedView.vue` calls it for the editor, the phone reader and quest handouts (options read from the node's attrs). Before #917 that view ignored every option, so art or lore hidden in the book still showed on a phone.
- **Art: picture and cutout (#917).** A monster has two images: `image_url`, the picture, and `cutout_url`, the creature alone on a transparent background. The formatter emits both (`entityArtFiguresHtml`, `src/scriptorium/lib/entityArt.ts`, each tagged `data-art-kind`) and the `art` attr keeps one: `auto` (default) prefers the cutout and falls back to the picture, `cutout`/`picture` force one and fall back to the other. A cutout prints unframed and larger; a picture gets a thin printed frame. A DM's `library_monster_art` override reaches the book too: `useEntityEmbedData` merges the art layers per field (`withLibraryArt`) before formatting a library monster. Nothing here is monster-specific, so NPC portraits can follow.
- **Theme.** `EntityEmbedView.vue` formats in the document's theme via `SCRIPTORIUM_THEME_KEY` (`scriptoriumTheme.ts`), provided by the editor and by `ScriptoriumDocumentView`; it used to format every embed in the 2024 layout, including in Classic documents on a phone.
- A monster's `description` may be Tiptap JSON or plain text (both shapes exist in real data) — `richTextOrPlain()` (`scriptoriumImport.ts`) handles either, escaping plain text, and treats a genuinely empty Tiptap doc as "no lore" rather than falling back to dumping the raw JSON string.

### Long-box and long-table breaking (#915 story 6 round 2)

Every box (`.sc-note`, `.sc-descriptive`), stat block/entry, and table defaults to `break-inside: avoid` in the authoritative paged stylesheet (`pagedPreviewCss.ts`) — right for something short (it reads better jumping whole to the next page than splitting) but wrong for something long, which instead stranded the page before it part-blank. `classifyLongBoxes()` (`src/scriptorium/lib/pagedBoxes.ts`) marks a `.sc-note`/`.sc-descriptive` past `LONG_BOX_CHAR_THRESHOLD` (700 characters of text) `sc-box--long`; `promoteTableHeaders()` (`pagedTables.ts`) does the same for a generic table past `LONG_TABLE_ROW_THRESHOLD` (6 rows) with `sc-table--long`. Both run in the one pre-layout pass, `preparePagedBody()` (`pagedPrepare.ts`), so the live preview and the exported PDF paginate identically. A stat block/entry is deliberately excluded from this carve-out — its own size decision is what keeps it inside a page, not a break-relaxation. A table row itself never splits (`tr { break-inside: avoid }`, unconditional); a repeated `<thead>` only repeats across a PAGE break, never across a COLUMN break within one page. Chrome's *print* layout does repeat it at a column break, which its screen layout (the one Paged.js measures) does not, so the exported document sets `thead { display: table-row-group }` (`printResetCss`): Paged.js has already copied the header into each page's piece of the table (#1115). A table wider than its column (its longest words plus cell padding, four columns of prose in half a page) is set across the page with the heading that introduces it: a Paged.js handler (`pagedTableFit.ts`) measures a row, because a table broken across two columns reports both as its own width, and marks the table `sc-table--span`, in the parsed source too (`pagedSource.ts`). Words are never broken to make a table fit.

### Page furniture

Watercolour splatters, watermarks, and artist credits are not part of the Tiptap content stream: they live in a sibling `page_furniture` jsonb column (`PageFurnitureItem[]`, see `src/scriptorium/types.ts`), anchored to a page or a block and positioned as a percentage of the page box so they survive page-size changes. There is no content-node form of these three kinds any more (see above) — `documentContent.ts`'s import-boundary normalization is the only place that still lifts a decoration out of a document's content, for the pre-story-2 shapes it exists to convert. Dragging one on the live book updates its `x`/`y`/`width` directly; the panel's Decoration section (`panel/DecorationPanelSection.vue`) edits variant, tint, opacity, text, rotation, artist, corner, width, layer (`under/over` the text), place and stays, or removes it.

**A picture placed on the page is art furniture (#1175)**, the one way to put a picture anywhere on a page, in front of or behind the text. The **Layer** control in the panel's Picture section (Behind the text or In front; it needs the laid-out pages, which are always there now) turns the selected image into an `art` item at the same place and width, anchored to the block it sat in or beside, so it travels with that text to whatever page it lands on, and selects it. Behind the text, art is muted with `mix-blend-mode: multiply` at the panel's **Strength** (`props.opacity`, default `DEFAULT_UNDER_ART_OPACITY` = 40, chosen by looking at a dark portrait behind a paragraph on every paper). The editor draws the chapter's furniture on its own pages (`EditorFurnitureLayer.vue`, page math in `furniture/editorPages.ts`) with the same `buildFurnitureElement` as the preview: in front of the text in an overlay, behind it in a widget inside the ProseMirror root (`FurnitureUnderlay`, z-index -1 in an isolated root, so it paints over the paper and under the text). Items are dragged and resized there with the preview's `useFurnitureEditing`; a selected item is drawn in front with its outline so a picture behind the text can still be moved. The phone reader cannot place anything on a page, so `get_player_handout` returns `chapter.art` (`20261110230437`): block-anchored art whose block survives `private.strip_secret_nodes` (a picture placed from a secret block or a Deep half is withheld with it), as `{blockId, src}` only, and the reader shows each one at full width after its block (`placedArtInFlow.ts`).

**A picture that follows its paragraph keeps its place beside it (#1176).** For a block-anchored item, `y` is the offset of the picture's top from the top of its anchor block, in percent of the page height (negative when the picture starts above the paragraph); `x` stays a percent of the page width. Page-anchored and corner-pinned items are unchanged: their `x` and `y` are still page coordinates. So when text is written and the paragraph moves to the next page, the picture goes with it and stays where it was beside it, instead of keeping a place on the page the paragraph left. The math is one pure module, `furniture/anchorOffset.ts`: the preview and print pass (`renderFurniture`) and the editor layer both measure the block's top on its page (rect ratios in the preview, offsets in the editor, never an assumed scale), add `y`, and hold the picture inside the page (top between 0 and 100 minus its own height; an image that has not loaded is placed again when it does). Each drawn element carries `data-anchor-top` (the block's top, percent of the page) so a drag converts the drawn top back to an offset without knowing about blocks. Place on page, drag, and re-anchoring all write offsets; snapping into a corner still pins to the page and writes page coordinates.

Selecting a picture that follows a paragraph draws the **anchor mark** in the page's left margin, level with the paragraph's top, with a hairline to the picture. Drag the mark onto another paragraph to anchor the picture there; it stays exactly where it is drawn (the offset is recomputed for the new paragraph). It is a pointer gesture only; there is no keyboard route, and the panel's **Stays** row ("With its paragraph" and "On page N") remains the other way to change an anchor. When a new layout carries a picture to another page with its paragraph, the chapter editor's footer says so for a few seconds ("The picture moved to page 3 with its paragraph."), and says nothing when the DM changed the anchor themselves. A page anchor whose page no longer exists (the chapter got shorter) is drawn on the chapter's last page in the editor, the preview and print, and the editor notes it beside the picture ("Page 5 is gone; this waits on the last page.").


**Corner-pinned art.** A picture or watercolour may carry `corner` (`top-left`, `top-right`, `bottom-left`, `bottom-right`; `FurnitureCorner`). Then `x`/`y` are insets from that corner's two paper edges, in % of the page (0/0 = flush, full bleed), and `buildFurnitureElement` places it with `right`/`bottom` for the right/bottom corners, so widening it grows it away from the corner. Dragging snaps an item flush into a corner when its box is within `SNAP_PCT` (2.5% of the page, about 5 mm on A4) of it on both axes, shown by a dashed outline and `sc-furniture--snapped`; pulled further away it is free again. A cornered item is resized from the inner corner, so the pinned one never moves. Snapping, or choosing a corner in the panel's **Place** row, also pins a block-anchored item to the page it is drawn on (the anchor becomes `{type: "page"}`, read from the page element's `data-chapter-id` / `data-chapter-page`); **Stays** in the panel flips between "With its paragraph" (the first block on that page) and "On page N", converting `y` each way so the picture stays exactly where it is drawn (a page coordinate when it stays on its page, an offset from the paragraph when it follows one: `lib/panel/anchorChange.ts`), both found from the DOM by `furniturePlacement`, and is disabled when nothing is laid out. Watermarks and artist credits ignore `corner`. The column is jsonb and book export/import copies items whole, so there is no migration.

### Themes and page sizes

Three book looks and four handout papers (`letter`, `notice`, `journal`, `plain`): see `src/scriptorium/lib/looks.ts` (the only theme-to-class mapping) and `src/scriptorium/styles/theme-*.css`. The book looks are **Grimoire** (`grimoire`, the house look and the default for every new book, a template or an AI draft), the 2024 book (`onednd2024`, teal/navy, current PHB styling) and the 2014 book (`phb2014`, brown/gold). An existing book keeps its look; the Look select in Book settings offers Grimoire first (#1176).

A book or a handout has its own **Paper** (`paper_tone`: null is the look's own, or one of the twelve ids in `src/scriptorium/papers/papers.ts`: the painting tool's ten stock papers plus the maintainer's two handmade scans, `grey` and `warm-grey`, which keep the light lift they had as book papers so a book on them looks the same; Book settings, with the page panel naming it on the Paper line). It is the same module and the same picker (`papers/PaperPicker.vue`, used by Book settings and by the painting's New sheet) as the painting's, so a paper is chosen and drawn one way. The ids are also the SQL check on `scriptorium_documents.paper_tone` (`20261112200559`); `papers.test.ts` reads the migration and fails if the two lists differ, and `white` became `hot-press`. `bookSurfaceClasses` in `looks.ts` is the one function every renderer (editor, preview, reader, document view, PDF) calls for the classes on its `.sc-theme` element (`sc-paper`, the ribbon), and `bookSurfaceStyle` is its pair, the inline custom properties (`--sc-paper-image`, `--sc-paper-veil`, `--sc-paper-size`, `--sc-page-bg`) that the one `.sc-paper` rule in `theme-base.css` paints from: papers are served from the art CDN, which a stylesheet cannot name, so the URL is set per element. The rule's selectors carry `:not(.ink-friendly)` and outrank every look's own page background (the handouts' `--sc-paper-bg` gradients included); `looks.test.ts` compares the specificity per painted element. The tile is drawn in millimetres (1024 px of surface x `surfaceScale` is about 86.7 mm x scale, the size it has on a painted full page) so a paper's features are as large on a page, in the preview and in the PDF as in a painting. Each paper has a `veil`, a white wash laid over it on a page only (never on a painting), the smallest that keeps its darkest patches (5th-percentile luminance) at WCAG 4.5:1 behind the palest `--sc-ink` of any look; `papers.test.ts` decodes every surface and checks it against every `theme-*.css` ink, so a darker paper or a paler look fails it. The PDF is built client side, and `inlineSameOriginAssets` also inlines URLs on the art CDN (including inside the body's `style` attribute, as unquoted `url(data:...)`), so the PDF carries the paper. Ink-friendly prints plain white without the class or the style. A player reading a shared book or handout sees its paper: `get_player_handout` returns `paper_tone`. The two scans live at `public/assets/papers/` like the others, with grains made by `scripts/paintbox/scanGrains.ts`.

**Page dressing (#1181).** A book or handout can carry hand-painted marks on every page: a darker stain low on the page, a wash along the outer edge (the top, for a handout) and flourishes in the four corners. `scriptorium_documents.page_dressing` holds only the choices, `{v:1, seed, stain, wash, corners}` with each part `{on, strength 0..1}`; null is none, and anything malformed reads as none (`parseDressing`). Where the marks fall is never stored: `dressPage(dressing, pageNumber, kind, {aspect, handout})` in `src/scriptorium/dressing/dressing.ts` works it out from the seed and the page's physical number in the whole book (covers and blank pages count, odd is a right-hand page), each part on its own random stream, so the same page gets the same marks in the editor, the paged preview, the PDF and the player's reader, and ticking one part never moves another. A cover (any variant) or a blank page is bare, and ink-friendly prints none (`activeDressing`). Every renderer builds its marks through `buildDressingLayer` (`dressing/dressingLayer.ts`): `renderFurniture` for the preview and the PDF (behind "under" furniture), `EditorFurnitureLayer` into the editor underlay (page numbers from the layout through `BOOK_DRESSING_KEY`), and `usePageDressing` for the reader and a standing document view, where the surface is one page. A mark is a box filled with `--sc-ink` and cut by a mask, so the picture is `mask-image`: WebP for the painted marks, a potrace SVG for the flourish, built by `scripts/paintbox/markAssets.ts` into `public/assets/paintbox/marks/`. The mask pictures are named once in `dressingCss()`, never on each mark, because the PDF inlines every URL as data and a per-mark URL would repeat it on every page. Book settings has a Page dressing block (`dressing/DressingSettings.vue`) with Shuffle for a new seed. `get_player_handout` returns `page_dressing` (`20261112205025`).

Grimoire is rag paper (`#f3ead6`) set in Cinzel for titles and rubrics and Alegreya for reading, with ink `#2b2019`, oxblood `#6e1f1a` for rubrics and gilt `#c9962e` for hairlines and the small eight-point star only, never for small text. It is ruled and never filled, so it prints well at home. A chapter title sits over a double gilt hairline, and each chapter opens with a red bookmark ribbon hanging from the top edge of the page with a gilt star on it (`preparePagedBody` marks each chapter's first `h1` with `sc-chapter-opener`; the class means nothing to the other looks). Page numbers are centred between two small gilt stars. A read-aloud box is a torn paper slip with an oxblood edge on the left, a sidebar sits between two gilt hairlines, a pull quote has a gilt rule on its left, and tables are ruled with an oxblood rule under the header. The drop cap (`p.sc-drop-cap::first-letter`: an oxblood square, a gilt inset frame, a cream capital) is the toolbar's **Drop cap**; the other looks draw their own.

The Grimoire stat block is ruled with a gilt hairline above and below, a vitals row (AC, HP with the dice under it, Speed with Initiative under it), six ability coins and the CR on an oxblood ribbon at the top right. A look never changes an entity's words, only their setting: the formatter (`scriptoriumImport.ts`) writes Grimoire's stat block with the 2024 wording (a monster carries no edition of its own, so the formatter only knows the theme, and every look but `phb2014` gets the 2024 text), and only the markup differs. The ability table's two "Mod" and "Save" column heads have no place on a coin, so the coin shows the modifier and draws "Save" from a `data-label` in CSS. The CR ribbon is decoration (`aria-hidden`); the Challenge line still prints the CR. A "(Recharge 5-6)" in an action's name is wrapped in `.sc-recharge` for the gilt-outlined tag. Page size options are unchanged: A4, A5, Letter. An ink-friendly toggle strips backgrounds and decorations before printing/exporting.

### Preview and PDF export

The preview pane lays the real Paged.js pagination out live behind the page you write on, and shows it as spreads in Read as spreads (fitted to the screen). The **PDF** button downloads a real PDF (#565): `useScriptoriumPdf` (`src/scriptorium/composables/useScriptoriumPdf.ts`) takes the already laid-out pages and posts them to the `render-pdf` edge function, which prints them through Cloudflare Browser Run's REST `/pdf` and returns the PDF. There is no print dialog and no hidden iframe any more; the result is a true vector PDF with selectable text and embedded TrueType.

The live preview and the export both lay pages out in the app's own document, and Paged.js puts each render's page rules in `document.head`. Each one asks its own `Previewer` which `<style>` elements are its (`src/scriptorium/lib/pagedStyles.ts`) rather than diffing the head: an export spans the render-pdf round trip, the preview keeps re-rendering while the DM types, and a diff used to copy the preview's rules into the PDF and then delete them from under the preview. The file is handed over by `downloadBlob` (`src/lib/downloadBlob.ts`), which every download in the app shares, and which revokes the blob's URL a minute later rather than right after the click, which Safari would abort.

- **The document must be self-contained.** Cloudflare's browser cannot reach the app's origin. Pictures already go in as `data:` URLs (`compactPrintImages`), and `inlineSameOriginAssets()` (`src/scriptorium/lib/inlineSameOriginAssets.ts`) turns every remaining root-relative `url(/…)` and `src="/…"` (the self-hosted fonts, the parchment page background) into a `data:` URI; one it cannot load fails the export rather than printing in Georgia or without parchment. A picture the canvas cannot read keeps its https CDN URL, which the renderer can fetch. The Sugarwell booklet sends about 14 MB of HTML; the cap is 40 MB (`PDF_HTML_MAX_BYTES`, Cloudflare's own limit is 50 MB). Accepting is not printing, though: a bigger book is split into parts (`planPdfChunks`, `src/scriptorium/lib/pdfChunks.ts`) of at most 16 MB and 150 pages each, printed one request at a time and merged in the browser. Those limits are measured, not derived (27 Oct 2026, the 478-page Sothery draft): a 319-page, 31 MB part failed at Cloudflare with 503 "Service unavailable" (code 7010) after 35 s, while 160 pages at 13.5 MB and 40 pages at 17.5 MB printed in under 15 s. Raise them only against a new measurement.
- **The printer must lay out the page Paged.js measured (#1115).** render-pdf's Chrome lays every page out again from the exported HTML, and anything that comes out taller than it was fitted falls into the page's off-page column and is not printed. Four rules keep the two layouts the same, each found by a page that lost text in the Sothery draft: the book states its own baseline (`.sc-theme` line height 1.5 and its own `h4`-`h6`, `theme-base.css`) instead of inheriting Tailwind's preflight, which the exported document does not carry; Vellum's heading fonts stop at `.sc-theme` (`vellum.css`), so the preview no longer sets the book in Alegreya while the PDF prints Cinzel; the export embeds Paged.js's processed copy of the paged CSS and never `buildPagedPreviewCss`'s raw text, because Paged.js takes `break-after`/`break-before` out of the stylesheet and applies them itself, and the raw text gave Chrome native breaks the pagination never saw; and each page is fitted `PRINT_SLACK_PX` (6px) short and printed full (`PAGE_CONTENT_SELECTOR` in `printResetCss`), for the sub-pixel differences of another machine's Chrome. `@media print` cannot carry that last one: Paged.js applies print rules on screen. To check an export without Cloudflare, capture the HTML posted to render-pdf, then lay it out in local Chrome in screen and in print media: every element should sit in the same place in both, and none outside its page.
- **Every export is read back, and a page that printed differently is named (#1176).** Once the PDF is handed over, `useScriptoriumPdf` reads it with pdf.js (`pdfjs-dist`, loaded only then, `src/scriptorium/lib/pdfPageTexts.ts`) and `src/scriptorium/lib/printCheck.ts` compares it page by page with what the laid-out pages said. The text of a laid-out page is only what it shows (a line Paged.js left past the page edge is not held against the printer); footers, page numbers and furniture are known and never count. Texts are compared as letters and digits only, with ligatures split, so hyphenation, spacing and line breaks cannot be a mismatch. A page passes when its first and last four words are somewhere on the printed page and the amount of text on it is within about one percent (at least ten letters) of what was laid out; order is not compared, because pdf.js reads boxes and floats in the order Chrome painted them. The PDF must also have the same number of pages. A page that fails is named with a reason: "starts with different words", "ends with different words", "has text the page did not", "is missing text the page had", "page missing" or "extra page". The export dialog stays open after the file is downloaded and says "All 28 pages printed as laid out." or lists each "Page 14 printed differently" with a **Show me** button (it emits `showPage` with the chapter and the page in it, and the book editor brings that page into view). The check never blocks or delays the download, and if pdf.js cannot read the file the dialog says so quietly and claims nothing.
- **A print test runs in CI (#1176).** `npm run scriptorium:print-check` (`scripts/scriptorium/print-check.ts`) lays a fixture book out through the real layout engine and the real print document (`src/scriptorium/lib/printDocument.ts`, shared with the export) in a bare Vite page, prints it with Chrome's own PDF printing, reads it back and runs the same check, exiting non-zero on any page that printed differently. The fixture (`printCheckFixture.ts`) holds two-column text, a stat block, read-aloud boxes, tables, a wrapped picture and page and column breaks. It needs no Supabase and no secrets; the release workflow runs it in the performance job right after Chromium is installed. To see a page it names, set `PRINT_CHECK_PDF=<file>` to keep the PDF and `PRINT_CHECK_VERBOSE=1` for the texts; `PRINT_CHECK_CHANNEL=chrome` prints with an installed Chrome when Playwright's own build is not downloaded. The test page loads the book's stylesheets and fonts as the app does: laying out under bare defaults and printing under the theme reads as a hundred false mismatches.
- **The preview scales with a transform, never CSS `zoom` (#1115).** The preview paginates at scale 1, then `ScriptoriumPreviewPane.vue` scales the laid-out pages (Read as spreads fits a spread to the screen) with `transform: scale()`, which draws them as laid out. CSS `zoom` lays the text out again at the new size, and in the full Sothery draft 18 paragraphs that ended within a pixel of a page bottom showed in the off-page column at Fit. A transform does not change layout size, so a box around the scaled pages takes the scaled size (`scaledBoxSize`, `useScriptoriumZoom.ts`, which now holds nothing else) and the scroll area matches what is drawn. Measure layout at scale 1.
- **Server side** (`supabase/functions/render-pdf/`, decisions in `_shared/pdfRender.ts`): caller from the verified JWT, body validated before the per-user `pdf_render` rate limit (30 an hour, `_shared/rate-limit.ts`), then Cloudflare. It needs two secrets, `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_BROWSER_RUN_TOKEN` (an API token with Browser Rendering: Edit), set with `supabase secrets set` in production; locally they sit in `.env.local` beside the R2 keys, served with `supabase functions serve --env-file .env.local` (no `VITE_` prefix, so Vite never ships them to the client); without them it answers 503 "PDF export is not set up on this server yet." On Workers Free Cloudflare allows one `/pdf` request every 10 seconds account-wide and 10 browser-minutes a day; its 429 becomes "The PDF printer is busy" (or the daily-limit sentence).

**PDF with campaign data.** For a document with a `campaign_id`, an `OverflowMenu` beside the PDF button opens `ScriptoriumExportDialog.vue`. It hosts the shared bundle picker (`BundleEntityPicker.vue`, state in `useBundleSelection`), the same one the World Bundle tab uses, scoped to the document's own campaign (not necessarily the active one). `bundlePreselection()` (`src/scriptorium/lib/bundlePreselection.ts`) ticks the entities the book links (`collectEntityRefs`) plus the document itself; the picker drops any id it does not offer (a linked shared-library monster is not campaign data). On export the dialog calls `buildBundle` and passes the result to `exportPdf({ ..., bundle })`, which embeds it in the PDF. The World Bundle tab's old "Attach to PDF…" upload step is gone; the tab still imports PDFs that carry data.

**Pictures go in at print size (27 Sep 2026).** Chrome's print pipeline passes a JPEG into the PDF untouched but re-encodes any other image losslessly, at full source resolution: the Sugarwell booklet's WebP art exported at 3 to 4 MB a picture and about 600 ppi, and the file came to 55 MB. Before the pages are copied into the iframe, `compactPrintImages()` (`src/scriptorium/lib/printImages.ts`) redraws each laid-out picture at 300 ppi of its printed size: opaque ones as JPEG, anything with transparency as a smaller PNG so frameless art still sits on the page. A picture it cannot read back (no CORS, failed load) keeps its source. The same booklet now exports at 6 MB. It relies on the asset CDN sending `access-control-allow-origin: *`, which it does.

Both renderers call one function for the pre-layout pass, `preparePagedBody()` (`src/scriptorium/lib/pagedPrepare.ts`), which runs in this order: `stripTrailingEmptyParagraphs`, `expandTocPlaceholder` (`pagedToc.ts`, needs `pageSize` for its column count), `promoteTableHeaders` (`pagedTables.ts`, also classifies a long generic table `sc-table--long`), `classifyLongBoxes` (`pagedBoxes.ts`, classifies a long `.sc-note`/`.sc-descriptive` `sc-box--long`), `groupWrappedImages` (`pagedFloats.ts`, see below), then the two-column wrapper. It used to be two hand-kept chains, one per renderer, and a step added to one and not the other was a bug (#915 story 6 round 2 found the live preview missing `promoteTableHeaders` entirely and passing no `pageSize`); a new step goes in `preparePagedBody` and nowhere else.

**Wrapped images keep their caption text (27 Sep 2026).** A wrapped image (`wrapLeft`/`wrapRight`) is a float placed before its paragraph. When the float does not fit what is left of a column, the browser moves it to the next column and leaves the text where it was, so a portrait lands beside the wrong entry (Rosie in the Sugarwell booklet's Appendix C). `groupWrappedImages()` wraps a heading directly before the float, the float, and the paragraph after it in `.sc-float-group` (`break-inside: avoid` in `pagedPreviewCss.ts`, `display: flow-root` in `theme-base.css` so the next heading starts below the picture), but only when that paragraph is caption-length, under `FLOAT_GROUP_CHAR_THRESHOLD` (360 characters). A longer section keeps flowing freely: grouped, it moves on whole and blanks the space it missed, which pushed Masters' Lane onto a new page when tried.

A cover page (`coverPage.ts`) forces `break-before: page` on itself (`pagedPreviewCss.ts`) rather than relying on its own full height to push the next thing onto a new page — two consecutive covers (front then inside) share the same named page ("sc-cover"), and a shared page name does not by itself force a break between them, which round 1 left the inside cover sharing page 1 with the front cover, clipped invisible under the page box's own `overflow: hidden`. A cover's own art image carries `sc-cover-art`, opting it out of the generic `.pagedjs_page_content img { max-height; object-fit: contain }` cap that otherwise exists to stop an oversized inline image overflowing its page — applied to a full-bleed cover photo, that cap silently shrank it to ~72% of the sheet.

### Templates

New books start from a template, never a blank page (`src/scriptorium/data/templates/`; a template's markdown is split into chapters at its top-level headings, `chapters.ts`): Blank Book, Adventure Module, Monster Compendium, Spell Compendium, Subclass Supplement, One-Page Dungeon, or an imported Markdown file, all starting on the Grimoire look. Each template seeds `doc_type`, initial Tiptap content, and starting settings (theme, page size, tags); every field stays editable afterward.

### Campaign scope (#915)

`scriptorium_documents.campaign_id` is nullable; null means the document is account-wide, set means it belongs to one campaign the DM owns (RLS requires `private.is_campaign_dm(campaign_id)` on insert and update; deleting a campaign sets its documents' `campaign_id` back to null rather than deleting them). A new document defaults to the active campaign; the Book settings panel's Campaign select (`ScriptoriumBookSettings.vue`) offers the active campaign or "All my campaigns", and additionally shows the document's own campaign as a third option when it differs from the active one, so saving cannot silently rescope it.

`documentScopeOf` / `isDocumentUsableIn` (`src/scriptorium/lib/documentScope.ts`) classify a document as `campaign` / `general` / `other_campaign` relative to the active campaign, mirroring `itemScopeOf` for the Vault minus the "library" tier (every Scriptorium document is the DM's own). The document list's Scope filter (`scriptoriumFilterScope` in `useScriptoriumUiStore`) uses the same four options as the Vault (Usable here / This campaign / General / Other campaigns), defaulting to Usable here. The quest beat handout picker (`QuestBeatAttachmentsPanel.vue`) narrows to documents usable in the quest's own campaign; a beat already carrying a handout id resolves it unscoped through `useScriptoriumDocument`, since a resolver of a stored id must never re-filter by scope.

### Document list

`ScriptoriumDocumentList.vue` renders a card grid (1 to 4 columns depending on width) with a colour-coded type bar, word count, and the Published badge. Filters are type, scope, and free-text search over title/tags, all held in `useScriptoriumUiStore` (`scriptoriumSearch`, `scriptoriumFilterType`, `scriptoriumFilterScope`, `scriptoriumHasActiveFilters`, `resetScriptoriumFilters`) so leaving and returning to the list does not drop them (#723). The bar is the shared `ListFilterBar` + `ListSearchInput` + `ListFilterSelect`; the doc-type filter is a select rather than a segmented group because the ten types do not fit as joined segments without clipping at md widths, the same call the Bestiary makes for its 14 creature types.

### Phone reading view (#915 story 7)

Scriptorium is the one Publishing tool that is not `desktopOnly` in `src/lib/nav.ts` — Card Forge, the Mint, and Character Sheet stay hidden below `md` because they are A4/letter-bound output tools with nothing to do on a phone, but a Scriptorium document is worth *reading* on one even though writing still isn't practical there. `ScriptoriumEditorView.vue` branches on `useBelow("md")`: `/scriptorium/new` shows a short "writing needs more room" `EmptyState` with a way back to the list, and `/scriptorium/:id` shows `ScriptoriumReader.vue` instead of the book editor. Both routes carry `meta.fullscreenMobile` (`src/router/routes.ts`) so the reader owns the whole phone screen — no app top bar or bottom nav — the same contract the NPC/monster sheets and quest surfaces use. `ScriptoriumView.vue` and `ScriptoriumDocumentList.vue`'s "New Document" affordances are hidden below `md` (`useAbove("md")`) for the same reason; a card still opens `/scriptorium/:id` normally, which is what puts it into the reader.

`ScriptoriumReader.vue` reuses `ScriptoriumDocumentView.vue` (the same read-only renderer the quest-runner handout uses) rather than building a second renderer, via a new `layout="reader"` prop that only adds a modifier class — every phone-specific override lives in `ScriptoriumReader`'s own scoped `:deep()` styles, never in the shared theme CSS (`src/scriptorium/styles/theme-*.css`), which #915's page-shape work was editing concurrently. It turns page/column breaks into a quiet divider or nothing, floats a cover page into a fixed-height hero/closing card (the print-only `pagedPreviewCss.ts` is what normally gives `.sc-cover` its height, which the reader has none of), drops every image's float/wrap layout to a full-width block capped to `60vh` (and shows art placed on a page after the block it was placed from, see Page furniture), and wraps tables in a horizontally-scrollable frame (`@tiptap/extension-table` already renders a `.tableWrapper` div around every table, so no extra markup was needed for that one).

Since #1115 story 13 the reader's contents list is the book's chapters (frame 07): a book with several chapters opens on that list and loads one chapter at a time, with the next and previous chapter at the end; a book of one chapter shows it directly. The player's handout page reads the same way through `get_player_handout`.

### Publishing and storage

The `is_published` flag is a DM-only status badge (green, in the list) for tracking done versus draft. It changes no access. Sharing with players is a separate act, described under Handouts below. Documents are owner-only for writes: `scriptorium_documents` RLS is scoped to `user_id`, and the row also carries a `demo_source` marker (set only by the demo-campaign copy machinery, never by the client) that exempts demo copies from the document quota.

### Handouts (#970)

A campaign's document can be given to players: `scriptorium_documents.player_visible_to` holds party member ids, written only through the `share_handout` RPC. A player reads nothing of the documents table itself: `scriptorium_documents_select` admits the author, the campaign's DMs and the DM library, never a holder, because a placed picture's untreated original (`page_furniture[].props.original`) sits on the row and row security cannot hide a column (`20261111070730`). The player's handout list comes from `get_player_handouts(campaign, party member)` (definer: that character's player or a DM of the campaign; the list columns only, `usePlayerHandouts`), and one handout from `get_player_handout`. Moving a document out of its campaign withdraws the share (DB trigger); an account-wide document cannot be shared.

- **One flow, three entrances.** `HandoutShareDialog.vue` is the picker (skipped when the caller already chose) plus a confirmation built from the RPC's dry run: who receives it, what it reveals ("Ser Vallis: name (seen as The Almoner)", "The Bounty: the quest starts"), and what players will not see and why. Wording lives in `src/scriptorium/lib/handoutShareSummary.ts`. `HandoutShareControl.vue` mounts it for the desktop metadata toolbar (built on `AudienceRevealControl`; a change opens the confirmation, nothing is written until Confirm) and for the phone reader's "Give to players" button (`ScriptoriumEditorView.vue`, reader `#actions` slot).
- **Reveals.** Each linked entry decides its own reveal (its `reveal` attr, set in the panel's Linked entry section); sharing applies them to every recipient, idempotently. A deity or faction is shared with the recipients the way a place is (`player_visible_to`, `20261029011624`), unless its reveal is off; a species, subclass or spell is rules text the campaign's players can already read, and an item shows once the party holds it, so sharing reveals none of those. Unsharing ("Take it back from everyone?", via `useConfirm`) removes the handout and never un-reveals anything.
- **No campaign, or another one.** The toolbar control is disabled with a hint; with no campaign it offers to move the document into the active campaign through the ordinary save. The audience is the active campaign's party, so a document from another campaign must be opened under its own.
- **Pending-reveal banner.** `HandoutPendingBanner.vue` runs the dry run against the current recipients, debounced after each save (`usePendingHandoutReveals`), and shows "N linked entries are hidden from players. Reveal" when something would change (a newly linked NPC, say). Autosave never reveals; the button opens the same confirmation.
- **No email.** A handout is given at the table; players see it arrive in their journal (unread dot, live). Email is for planning between sessions only, see [notifications.md](notifications.md).
- **List.** Cards show a "Shared" badge with the recipient count beside Published.
- **Unsaved edits are saved first.** `share_handout` reads the stored body, so the editor saves pending edits before the confirmation opens (`saveBeforeShare`); a reveal toggled on an embed a moment ago is the one that applies.
- **What a holder can read.** The player read fetches only `ReadableScriptoriumDocument`'s columns (no tags, AI provenance or owner id), but the select policy is row-level: a holder querying the API directly can read every column of a handout. Treat a shared document's tags as visible to its players.

### Draft with AI (#910)

**Entry point:** a **Draft with AI** button in the Scriptorium template gallery (`TemplateGallery.vue`) and the Scriptorium view (`ScriptoriumView.vue`), both setting `ui.scriptoriumDraftOpen`. `ScriptoriumDraftDialog.vue` is mounted globally in `AiGeneratorPanels.vue`, so a draft started in the background can be reopened from the AI badge on any page (state in `src/ai/useScriptoriumDraft.ts`).

**The DM picks** a kind (`handout`, `faction_dossier`, `session_recap`), a subject (an NPC, location, faction or session note; `KIND_SUBJECTS` fixes which kinds take which subjects), an audience (`players` or `dm`) and a steer.

**Server path only:** `supabase/functions/draft-scriptorium-document/index.ts`, pure helpers in `supabase/functions/_shared/scriptoriumDraft.ts`. Order: auth, account gate, request validation (unknown values are rejected, never defaulted), campaign and `ai_enabled` check, **DM-role gate via `isCampaignDm`**, prompt rows (`scriptorium_draft` plus the edition's `ruleset_context_<ruleset>`), rate limit, `reserveCredits`, fetch, model, parse, `recordGeneration` (refund on failure). Ledger reason `scriptorium_draft`, 2 credits because the output is a multi-page document. A faction dossier reads the faction's places and other factions from `world_links` on both ends, worded from the faction's side with the catalogue (`factionLinkWord`: `forward` when the faction is the link's `from`, `reverse` when it is the `to`), so "controls Dock Ward" and "seen as a rival by The Ledger" both appear; a players draft keeps only ties whose far end is shared.

**Every read is filtered by `campaign_id`.** A subject id from the client is only ever looked up inside the campaign, so it cannot name another campaign's row. The context blocks cover the subject and what hangs off it (a faction's members and locations, an NPC's relations, a session's other notes).

**The audience rule decides what the model may see.** For `players` a block carries only what the players could already see in the app: an NPC's name, race, occupation and appearance, a location's description only when shared, notes and related entities only when shared with at least one player. A `dm` draft gets everything the row holds. This is enforced in the builders, in one tested place, not inline in the handler.

**Output is a whitelist, not trusted HTML.** The model returns `{ title, html }`; `sanitizeDraftHtml` keeps only `ALLOWED_TAGS` with every attribute stripped (comments removed), and no title or empty HTML is a failed draft. The client converts it with `htmlToScriptoriumJson` and creates a book of one chapter (`useCreateScriptoriumBook`; a `handout` draft is `kind: "handout"` on the Plain page paper, the others are books; quota-gated through `useGenerationGate("scriptorium_documents")`) carrying `ai_provenance`, then navigates to `/scriptorium/:id`.

### Quota

Document creation is quota-gated (`scriptorium_documents` in `check_quota`/`check_all_quotas`); hitting the limit triggers `PaywallModal`.

## Card Forge (Card Printer)

Route: `/forge`

A card-layout and print tool that generates physical trading cards for NPCs, monsters, items, and spells, plus Interlude activity cards and items-only loot decks. Cards match standard card game proportions and are designed to be cut out and used at the table.

### Card Sizes

Two formats, selectable at the top of the view:

| Format | Dimensions  | Grid on A4 | Cards per sheet |
| ------ | ----------- | ---------- | --------------- |
| MTG    | 63 × 88 mm  | 3 × 3      | 9               |
| Tarot  | 70 × 120 mm | 2 × 2      | 4               |

### Entity Sources

Four source tabs, each with a searchable, scrollable list and per-source selection count badge:

- **NPCs** — searchable by name, occupation, race
- **Monsters** — searchable by name, type, habitat; subtitle shows size/type/CR
- **Items** — searchable by name, item type, rarity; subtitle shows rarity/type/subtype
- **Spells** — searchable by name, school, class list; subtitle shows level/school

Selections from all four sources aggregate into a single combined `selectedSubjects` list — you can mix entity types freely.

**Select All / None** buttons operate on the current filtered list. Tab count badges show how many cards are selected per source.

### Card Anatomy (per card type)

Every card has a **front** and a **back** component. Front and back are separate sheets when printing.

**NPC / Monster front:**

- Title bar with name + CR or level badge
- Art area (portrait image with focal-point cropping, or glyph placeholder)
- Type line (race · occupation for NPC; size · type for monster)
- Stats strip: HP / AC / Speed
- Ability score grid: STR/DEX/CON/INT/WIS/CHA with modifier
- Footer: entity tags + kind label

**NPC / Monster back:**

- Full stat block rows (skills, saves, resistances, senses, languages, challenge)
- Abilities & Actions section (special abilities and actions, truncated to fit)
- Flavor footer: a monster's lore (`description`), else its habitat; an NPC's personality, else backstory. Never a monster's `notes`: those are the DM's private notes, and a printed card goes to the table (cards printed them until 4 Nov 2026)

**Item front:**

- Title bar with name + rarity badge
- Art area (item image with focal-point cropping, or glyph placeholder)
- Type line (rarity · type · subtype)
- Stats strip: DMG / AC / Charges
- Info grid: weight, value, attunement, tags
- Footer

**Spell front:**

- Title bar with name + level badge
- Art area
- Type line (school · casting time)
- Stats: Range / Duration / Components
- Description text (truncated to fit)
- Footer: class tags

**Back cards** for items and spells show extended description, property list, and flavor text.

**Tarot variants** of all four types use the taller 70 × 120 mm format with adjusted layouts for the larger card body.

Frame color is driven by entity type: each card uses a CSS `--fc` custom property that tints the card border/header.

### Print Layout

- Prints front sheets followed by back sheets
- **Duplex alignment**: back sheets have columns reversed per row so that when the paper is flipped on the long (left) edge, each back aligns with its front
- Cards are padded with empty placeholders to fill the grid
- 1 mm bleed on each side (cards are printed 2 mm oversize and sit with `-1mm` margin so color fully covers cut lines)
- Print CSS is injected into `<head>` at print-time to guarantee `@page { size: A4 portrait; margin: 0; }` is honored by all browsers including Safari
- App chrome (sidebar, header) is hidden during print via `@media print` rules

### Card Library (Saved Collections)

- Named card collections can be saved to and loaded from `localStorage` (key: `cardforge_library`)
- Each collection stores the list of `{ kind, id }` pairs and a creation timestamp
- Load dialog shows all saved collections with card count and date; loading a collection restores full selection state and switches to the tab with the most cards
- Collections can be deleted individually

### Preview

Live card preview grid on screen (screen-sized rendering, separate from print size). Scrollable preview area shows all selected cards as front faces; clicking a card turns it over.

### Save one card as an image (#1141)

Under each preview card, **Save front** / **Save back** (whichever face is showing) downloads that face as a PNG at its print size, 63×88 mm (744×1041 px) or 70×120 mm (827×1419 px) at 300 dpi, with transparent rounded corners and no bleed. For posting a card, sending it to a player or dropping it into a VTT; nothing is generated, so no credits. Named after the entity, `Ashen_Warden_card_front.png`, like The Mint's tokens. Hidden in a loot deck for a non-item, which has no front to draw.

`useCardImageExport` (`src/composables/cardforge/`) renders the preview card's own DOM; sizes and names live in `src/lib/cardforge/cardImage.ts`. Four decisions that look like oversights:

- **modern-screenshot, not html2canvas.** html2canvas repaints the DOM itself and cannot draw the card designs (`color-mix`, `clip-path`, `mask-image` icons, `filter`; it throws on the first `color-mix`). modern-screenshot serialises the card into an SVG `foreignObject`, so the browser draws it as on screen, and inlines only the font families the card uses and every image it shows. It is lazy-loaded on the first save. Art comes from the CDN, which sends `Access-Control-Allow-Origin: *`, so inlining it never taints the canvas.
- **The PNG is stamped 300 dpi by hand.** The library records 96 dpi × scale (357 dpi at the 3.72× a 200 px card needs), which would print "at actual size" as a 53 mm card. The composable sets `context.dpi` after `createContext`.
- **A `clip-path` on the render's root.** Inside a `foreignObject`, a rounded card's `overflow: hidden` does not clip a transformed child, so the focal-cropped portrait filled the corners square. `inset(0 round <the card's radius>)` clips everything.
- **Clamped text is cut by hand in the saved copy.** A back clamps its flavor footer and its last ability entry with `-webkit-line-clamp`; inside a `foreignObject` Chrome still clamps the lines but draws no "…", so saved cards ended mid-word ("(a single white feather", 8 Nov 2026). `src/lib/cardforge/lineClamp.ts` measures, on an unclamped copy laid out beside each clamped box, how much text fits with a "…", and writes that into the clone being drawn (`onCloneNode`). The live card is never changed.

### Paint portrait for entities with no art (#910)

A card or token whose entity has no picture can have one painted from where it is being made. `PaintPortraitButton.vue` is presentation only (label, cost badge, error); the caller owns the logic. `src/ai/useMissingPortrait.ts` does the work for five kinds (`npc`, `party`, `monster`, `item`, `spell`): it generates the entity's own portrait with the **same image kind and bucket the entity's detail editor uses** (`KIND_CONFIG`: for example `npc_portrait` in `npc-portraits`), then saves the URL onto the entity through its own update mutation, with a centred focal point. So the card, the token and the detail page all gain the picture at once, the Gallery files it under the right tab, and provenance is recorded per stored image like any other (#935). Text-only generation, so the likeness gate (reference images only) does not apply, as in `EntityImageBlock`. Entity facts come from `src/ai/entityImageContext.ts`, kept in step with the editors' `aiContext` so a portrait painted here describes the same entity.

One paint runs at a time across every surface (`paintingId` is module state): a second would spend credits while the first renders. A failed paint is a message on the card, not a thrown error.

Card Forge: `useCardPortraitPainter` (`src/composables/cardforge/`) wraps four painters and decides eligibility (`hasNoArt`): an NPC without a portrait, a monster without art that is not shared, an item or spell without art whose id is a uuid. **Library (shared) monsters, spells and items are read-only, so only the DM's own rows offer it**; their ids are slugs, the DM's are uuids. Shown in `CardForgePreviewGrid.vue`; The Mint's tokens tab (`TokenForgeView.vue`) uses `useMissingPortrait` directly for NPC, party member and monster tokens, one painter per kind sharing the one-at-a-time lock.

## Illuminator inside the book (picture editing in the Scriptorium)

No route of its own: `/illuminate`, `IlluminatorView`, `useScriptoriumIlluminator` and the sidebar entry are gone (#1176 story 9). The Illuminator is the Scriptorium's picture editor (`src/scriptorium/illuminator/`), and it works on a picture where the picture sits: in the text or placed on the page. The design is frames 11 and 12 of the canvas. Colour, vignette, texture, depth of field, the painted mask and the edges are client-side canvas processing at full resolution; only the AI actions (below) call a server.

### Where it lives

- **Quick edits in the panel** (`panel/PictureEditSection.vue`, a section of the picture's panel): Edges (Torn paper, Torn (classic), Faded, Straight, with the sides and sliders for the style), Colour (a preset, Warmth, Contrast), Vignette, a **More tools** button that opens the workbench, and **Reset to the original picture** for a treated one (it asks first only when an AI result would be dropped). Each choice reads the recipe, changes one step and writes it back to the image node or the art item (`lib/panel/pictureTreatment.ts`, `illuminator/lib/recipeEdits.ts`), so the panel and the workbench always show the same thing.
- **The workbench** (`illuminator/components/IlluminatorWorkbench.vue`, state in `illuminator/useIlluminateWorkbench.ts`): a full-screen layer over the book with a tool rail of icon tiles in two columns (`IlluminateToolRail.vue`, `AppButton size="tile-icon"`), each tool named in its tooltip with its key in the tile's top-right corner: **Paint** (Brush, Smudge, Eraser, Pick colour, then the foreground colour over the background colour, with swap and reset) above **Picture** (Crop, Edges, Grade, Vignette, Texture, Wash, Focus; Text greyed under LATER; the picture tool panels are `Illuminate*Panel.vue`). The keys are one table, `illuminator/toolKeys.ts`, that both the bindings and the rail read: B, S, E, I, C, R (Edges, "ragged"), G, V, T, W, F, plus X swap and D reset the colours and P toggles Compare. The workbench opens on the tool used last on this device (`grimoire:illuminate:tool`), the Brush the first time; the panel's Crop button still opens on Crop. The rail fits a small laptop without scrolling, and so does the one-row options bar, whose Flow and Smoothing fold into a More menu on a narrow stage. The stage is in the middle and the tool's controls on the right. A picture tool shows `IlluminateStage`; a paint tool swaps it for the painting canvas (see Painting below). The old grading tool is called Grade (its panel still reads "Colour grading"), so "colour" in the rail means paint colour. **Done, back to page N** writes the recipe to the picture and returns to the same page; **Cancel** drops the session. The painted mask and a texture exist as stored pictures only after Done or when picked (a texture uploads as soon as it is picked), so a recipe handed back points only at stored pictures. The mask uploads as WebP, as does "Add to my pictures", because the `asset-images` bucket refuses PNG.
- **Before and after** (`IlluminateStage.vue`): the split slider shows only when **Compare** (top right of the stage, or P) is on, it is off at every opening, and unavailable while the crop box or the focus point is being placed; hold O to see the original. The page shows a quick preview of an edit (`usePicturePreviews`, DOM only) while the real bake runs once edits pause (`usePictureBakes`); `usePictureEditing` mounts both and opens the workbench.
- **Save as a new picture** (workbench header, `components/IlluminateExportMenu.vue`): Download as WebP (every plan), Download as PNG (Pro; Free sees it greyed out with "PNG downloads come with Pro", maintainer 12 Nov 2026), Copy to the clipboard (every plan: browsers only take a PNG there, and a paste is not a file export), or Add to my pictures. The picture in the book stays as it is.
- **Crop** (#1176 story 9c, `illuminator/lib/crop.ts`, box geometry in `cropBox.ts`, `IlluminateCropBox.vue` / `IlluminateCropPanel.vue`): a `crop` step `{x, y, w, h}` in fractions of the base image, run right after `ai` and before every other step; a crop that keeps everything is dropped. Bake, page preview, print and Save as all draw through `drawBase`, so the cropped size is what bakes and prints; the other steps run on the cropped canvas. Shapes: Free, 1:1, 4:3, 3:2, 16:9, and Page for art on the page. The panel's **Crop** button opens the workbench on that tool. Leaving Crop with a changed shape restarts the painting (the erasing and any paint layers were drawn on the old shape) and says so. Export lays a cropped picture out at its cropped shape before Paged.js runs (`fitCroppedPictures`, `fitCroppedArt` in `lib/printImages.ts`), so a PDF exported before the new bake lands cannot stretch it.
- **Paper: Printed into the paper | On top** (its own panel section, shown for every picture, not only editable ones): `blend: "paper" | "top"` on the image node (`data-blend`) and `props.blend` on art, drawn by one rule in `theme-base.css` (`mix-blend-mode: multiply`) in the editor, preview and print alike, and kept in the players' copy. Defaults in `lib/furniture/blend.ts`: art behind the text is printed into the paper (it always was), everything else sits on top. Converting between the text and the page carries a chosen blend (`pictureConversion.ts`).
- **Which pictures can be edited**: any picture served from Grimoire's storage (`isEditablePicture`: `parsePublicUrl(url) !== null`, either URL shape, any bucket; the original is only ever read), never a picture from an outside web address (it would taint the canvas). **Cleanup deletes only what the Illuminator made** (`illuminator/lib/ownedPictures.ts`): an `asset-images` file directly under the author's own id whose name starts `ill-` (bakes, masks, textures, AI results), and never an `original`. Every Scriptorium delete path goes through it: `removedFurnitureUrls` + `useBookSettings`, the `usePictureBakes` discard, and a chapter's own cleanup (`lib/chapterImages.ts`, called through `composables/chapterImageCleanup.ts` when a chapter is saved or deleted), which the Scriptorium uses instead of the shared rich-text cleanup in `useImageUpload.ts`: that one still deletes every asset-images picture a field drops, which is right for a field's own uploads and wrong for a book whose pictures may be anyone's. A plain picture the DM placed and never edited is not deleted when it leaves the book; it may be in use elsewhere. The sweep checks candidates against the server (`scriptorium_pictures_in_use`) in batches of 500 URLs.
- **The paper wash** (`wash` step, `illuminator/lib/paperWash.ts`): the homebrew-supplement look, a painting that runs to every edge with the text on a brushed paper wash painted over it. Where the brush went the picture is erased, so the page's paper shows through on the page and in print, and faint light and dark brush streaks are drawn into the erased area so it shows brushwork; the edge is ragged dry-brush sweeps. It is painted by the paint engine with copies of the stock brushes tuned for the wash (a body of hard-round strokes, edge sweeps of dry-brush, flat bristle and round wash whose pressure runs out along each stroke, soft streaks on their own layers), at the picture's shape with its long side at most `REFERENCE_LONG` (2048) and then scaled, so a 4096 bake costs about what a 2048 one does. The live preview passes `draft` and paints at 768; the last three washes are kept, so a change to any other step repaints no wash. The step is `{ from: left|right|top|bottom, reach 0.15 to 0.9, brush (fine to broad), dry (wet to dry), seed }`, and it is drawn after `edges` and before the DM's own erasing (`mask`), which goes on top. It is deterministic from its own seed (no `Math.random`) and sized as fractions of the picture, so the preview, the Worker bake and the print redraw draw the same wash; "Paint it again" changes only the seed. The panel's Paper wash block and the Illuminator's Wash tool are one component (`IlluminateWashPanel.vue`) over the same edits (`illuminator/lib/washEdits.ts`). Like every step it is opaque JSON to the server.
- **Both tears.** Edge style `classic` is the layered fade the old Illuminator had, now called "Torn (classic)"; `paper` is "Torn paper" (irregular outline, fibres, a lift shadow, `tornPaper.ts`). Neither replaced the other.
- **Manual link**: the workbench header links the in-app manual page "Illuminator: Image Effects" (`publishing-illuminator.md`, id `illuminator-image-effects`); the page stays so that link keeps working and the Scriptorium page points to it.

### Painting (#1181)

The Paint tools paint on the picture inside the workbench (`illuminator/paint/`). The engine keeps each layer as lazily allocated tiles of straight RGBA and lays a stroke as dabs of a brush preset, so a stroke touches and uploads only the tiles it changed; the session (`paint/session/`) decides which layer a stroke lands on, keeps one undo history across every layer, and the compositor draws paper, picture and layers to the stage. The picture is the bottom layer and is never painted on: a Brush or Smudge stroke on it makes a new paint layer above it, and the Eraser on it paints the picture's mask.

- **Tools.** Brush, Smudge, Eraser and Pick colour. Each painting tool remembers its own brush, and the options bar's size, opacity and flow replace the brush's own while set. The right panel stacks Brushes, Layers and Colour as sections, any number open at once, the open set kept per device (`paint/usePaintSections.ts`, `grimoire:illuminate:paint-sections`); a click on a colour swatch opens Colour on that swatch. There are also two full-panel views, Brush settings (from the options bar) and Pen (from the status line, which also shows the pressure and tilt the pen last reported). The pressure curve is kept per device in `localStorage` and never fails painting if storage is blocked. Only a pen reports pressure: a mouse, trackpad or finger paints at full pressure, so a stroke never thins or fades by itself (the maintainer read that as a bug, 12 Nov 2026); Fade is a control a brush chooses on purpose.
- **Saving a painting.** The recipe's `paint` step is `{ type, width, height, paper, layers }` and runs last in `STEP_ORDER`, over every other treatment. Its width and height are the picture's document size, the picture at bake size, and `paper` is the stock paper id (so brushes catch that paper's grain). Each layer is stored as 1024 px chunks, one WebP per chunk named `{user}/ill-paint-{id}.webp` (`illuminator/lib/paintChunks.ts` for the chunk geometry, `paint/paintLayerIO.ts` to encode and decode, `paint/paintSave.ts` to save and load). Done uploads only the chunks a layer touched since it was loaded, four at a time, and reuses the rest by URL. Chunks that were replaced or removed, and every chunk of a deleted layer, are marked for sweep only after every upload has succeeded, so a failed save loses nothing. If the picture's size no longer matches the saved painting on load, the painting is dropped and a toast says so. A crop change that would remove paint asks first (Change the crop? Keep painting, or change it anyway). Layers, blend, opacity, visibility and alpha lock are saved; user brushes and recents live in the session only.
- **The sweep.** Chunks are `ill-` files, so they follow the cleanup rule above (the Illuminator's own files only, never an `original`). The sweep asks `scriptorium_pictures_in_use` which marked URLs any chapter or page still refers to, 500 URLs per call because a painting holds many chunks and the server refuses more.
- **Blank sheet.** Add to this page has a Blank sheet button next to Picture (`panel/NewSheetDialog.vue`, helpers in `lib/panel/newSheet.ts` and `lib/panel/newSheetUpload.ts`). It offers four sizes (Full page cut to the book's page shape, Half page, Square, Wide), each capped at `MAX_BAKE_EDGE` on its long edge, and the twelve stock papers (`papers/papers.ts`, `papers/PaperPicker.vue`). The paper surface is tiled to the size at the paper's `surfaceScale` (larger for papers with big features, so the repeat does not show), encoded as WebP and stored as `{user}/sheet-{id}.webp`. That original is deliberately not an `ill-` file, so cleanup never treats it as the Illuminator's own. The picture is added to the page with a recipe holding one empty `paint` step that carries the paper, and the Illuminator opens on it with the Brush armed (the workbench opens on the new item itself, not on the selection). Cancel straight after starting removes the empty sheet and its file; Done keeps it.
- **Paint on this page.** Next to Blank sheet in Add to this page, one click and no dialog (`composables/usePagePainting.ts`, maths in `lib/panel/pagePainting.ts`). It stores a fully transparent WebP at the page's full size (Blank sheet's "Full page" size, capped at `MAX_BAKE_EDGE`) as `{user}/sheet-{id}.webp`, adds it as art with `fill: "page"` (every edge, cropped like cover), behind the text (`z: "under"`), `blend: "paper"` (printed into the paper), `opacity: 100` (art behind the text is otherwise muted to 40) and `painting: 1`, which names it "Painting" in the page panel's list. Its recipe is one empty `paint` step on the book's paper (`paper_tone`); with none, the stock paper whose mean colour is closest to the look's page colour (`LOOK_PAGE_COLOURS`), else no paper. The DM can bring it in front with the picture's Layer control. The Illuminator opens on it with the Brush armed and lays the paper under the painting as a display backdrop only (`Compositor.setPaper(surface, scale)`); the bake (`applySteps`) never draws it, so the page and its paper show through wherever nothing is painted, on screen and in print. It counts toward the free plan's one canvas (`paint_canvases`, checked before anything is stored, with the same upgrade prompt); Cancel straight after starting removes the empty painting and its file, as for a blank sheet.
- **Flatten.** The Layers tab can flatten the painting into the picture. The workbench stores the flat picture as `{user}/ill-flat-{id}.webp` and `usePictureEditing` writes it through `flattenPatch` (`lib/panel/pictureTreatment.ts`): it becomes both `src` and `original`, and the recipe and `bakedFor` are cleared. It is the `original`, so the sweep never offers it while the picture keeps it, while the old bake, chunks and mask become sweepable. A flattened picture holds no paint step, so this frees the canvas slot. In the text it is one editor step, so Ctrl+Z can bring the old recipe back, which is why the confirm does not promise it cannot be undone.
- **The canvas limit.** Painting canvases are a quota resource, `paint_canvases` in `check_quota` and `check_all_quotas`: Free keeps 1, Pro is unlimited. There is no table behind it. `private.count_paint_canvases` counts `paint` steps in chapter content and in page furniture, excluding demo copies. The client enforces it before a new canvas is made (starting a blank sheet, or the first paint layer on a picture), with the upgrade prompt (`PaywallModal`, message in `illuminator/lib/paintQuota.ts`). Nothing ever deletes a painting to fit the limit.
- **The Eraser on the picture replaces the old brush.** The mask is painted at the picture's bake size (the cropped picture, long edge capped at `MAX_BAKE_EDGE`), so it is full resolution rather than the 900 px preview. Done uploads it as `{user}/ill-mask-{id}.webp` (white with the mask's alpha) exactly as before and an untouched saved mask is reused, not uploaded again. The mask step's meaning is unchanged: an alpha picture, drawn with `destination-out`, stretched to the canvas. Alt with the Eraser restores what was erased. The compositor cuts the mask out of the picture live, so the picture under the paint is the recipe rendered without its mask step and is redrawn when another tool changes the recipe.
- **Shortcuts.** Every tool's key (above), X swap and D reset the colours, P Compare, `[` and `]` size down and up, Mod+Z undo, Shift+Mod+Z or Mod+Y redo (the paint history, while a paint tool is armed). **Show original is hold O**, since B is the Brush.
- **iPad and Pencil** (`paint/render/touchGestures.ts`, a pure state machine; `PaintStage.vue` adapts pointer events to it). Once a pen has been seen on the device (`grimoire:paint:pen-seen`), a single finger pans and only the pen paints; before that one finger paints, so a touch-only device still works. Two fingers pinch and pan; a two-finger tap undoes and a three-finger tap redoes (all fingers up within 300 ms, none moved more than 10 px, and a pinch is never a tap). While the pen is down every touch is ignored, so a resting palm draws nothing. A finger stroke starts only after 4 px or 120 ms, so a second finger landing at once cancels it instead of leaving a dot. The page's own pinch zoom is stopped on the stage. Where the browser gives the Pencil's angle as altitude and azimuth (Safari), tilt is derived from them.

### Pictures keep their edits as a recipe (#1176 story 9)

A treated picture is not a flattened file. The book holds the recipe, and the baked image is a cache made from it. An image node (and an art item on the page) carries four things: `src`, the picture shown; `original`, the untouched picture; `illuminate`, a versioned list of steps (`ai`, `crop`, `grade`, `dof`, `vignette`, `texture`, `edges`, `wash` and `mask`); and `bakedFor`, a hash of the steps `src` was baked from (`src/scriptorium/illuminator/lib/treatment.ts`). Steps always run in one fixed order, the texture under the vignette and the mask last, whatever order they are listed in, and `edges` has two styles: `classic` (the layered fade above) and `paper` (a torn sheet with a fibre band and a lift shadow, `tornPaper.ts`). A torn edge is seeded and measured along each side's own 0 to 1 coordinate, so the small preview and the full-size bake tear the same way, and the picture keeps its box with the shadow inside a margin. The texture and mask are stored pictures a step points at, not things held in memory.

Print renders the recipe: `compactPrintImages` redraws any picture that carries `data-original` and `data-illuminate` from its original, so a PDF never shows a stale or missing bake. Readers that run no editor (players, the phone reader) see the bake. When the editor opens a book, `usePictureBakes` finds pictures whose recipe hash is not `bakedFor`, bakes them at full resolution in a Web Worker, stores each under a new key (`{userId}/ill-{hash}-{random}.webp`, because stored files never change), and writes `src` and `bakedFor` back outside undo history. Players never receive `original` or `illuminate`, since a cut-out or masked secret would show through the original. Cleanup reads every address a picture holds (`src`, `original` and the pictures its recipe uses) when it compares two saves, so the first bake never deletes the original, a replaced bake goes at once, and an original goes only when nothing refers to it; art on the page gets the same check when the book's settings save.

### Ask the Illuminator (AI picture actions, #1176 story 10, frame 12)

`illuminator/components/IlluminateAskSection.vue` in the workbench's right column, under the tool: **Cut out the figure**, **Turn into an ink sketch**, **Paint as a watercolour**, **Extend to the page edge** (toward the edge the DM picks) and **Match this book's look**. Each carries the app's sparkle (`IconGenerate`) and a cost badge (`useIlluminatePictureCost`: the `illuminate_picture` price on OpenAI, then the size multiplier), and the whole section is absent when AI is off for the campaign (`campaign.isAiEnabled`). The edge function is `supabase/functions/illuminate-picture` (cloned from `generate-nook-part`): OpenAI only, on platform keys; the client sends PNG bytes and the server never fetches a client URL; no client-written prompt text reaches the model, since the look is a name from a fixed list and its descriptors live on the server (`_shared/scriptoriumLookStyles.ts`). Its refusals are one tested function (`refusalFor.ts`): not the campaign's DM, AI off, and, for the three restyles that may show a real person, a likeness notice not yet acknowledged (the client pre-flights the same check). It is priced as its own type (`illuminate_picture`, migration `20261111034827`) and logged as `illuminate_<action>`. Deploying the function is a separate step from pushing the client.

- **The result is the recipe's base image, not a filter.** An `ai` step (`{type: "ai", action, output}`, `treatment.ts`) points at the stored result; `baseImageUrl` makes that the picture later steps start from, and `applySteps` skips the step itself. The original is untouched, a second action builds on the first (the action is recorded as a chain, "cutout+ink"), and bake, page preview and print all draw from the same base. **Use the original picture** asks first, because the result cost credits.
- **Labelled AI-made.** The bake of an AI picture re-embeds the provenance mark that the canvas re-encode dropped (`illuminator/lib/bakeUpload.ts`, `edited: true`), so the players' copy is marked too. The AI chip sits beside the reader (`HandoutAiLabels.vue`) and in the panel for the author, and is never drawn on the paper. Known gap, not new: the PDF re-encodes pictures and drops embedded XMP for every AI picture.
- `context/compliance/ai-act.md` lists the function and the generator type.

### Describe it (a picture painted from words, #1176)

The picture panel's third source, beside **Upload a file** and the library, offered only for a book of the active campaign with AI on. It is the notes' scene painter (`notes/ChroniclerGenerateDialog.vue`: same words, `@` mentions that paint an NPC from their portrait, same credit check and likeness notice) with the book's six shapes (`lib/describeShapes.ts`): **Full page** (the book's own page shape), **Tall**, **Square**, **Landscape**, **Wide banner** and **Narrow column**. The model paints only three oblongs, so each shape is painted at the nearest one and cut to its proportions by a centred `crop` step in the recipe; the generated file stays untouched, so its AI mark and provenance stay true, and the cost shown is for the oblong actually painted.

It paints in the background (`composables/useDescribedPictures.ts`). The picture carries `pendingJob` and `pendingShape` (image attrs saved as `data-pending-job` / `data-pending-shape`, art props) while it paints; the job is waited for, then the file becomes `src`, the crop becomes the recipe (`bakedFor` empty, so it bakes) and the marks go. The picture is found again by its block id (or the art's id), never by position, so writing above it is safe. A reload mid-paint resumes from the saved mark; a failed job clears the mark and toasts. A local (BYOK) job lives in memory and is reported lost after a reload. The marks are editor state: print ignores them, and the server's player strip should drop them too (it removes only `original`, `illuminate` and `bakedFor` today).

### Export

- Preview renders at up to 900 px on the longest side (for performance)
- A bake and a download process at full source resolution
- **Reset all to defaults** in the workbench resets every tool; **Reset to the original picture** in the panel drops the whole recipe

## Book Nook (A Place's Picture That Breathes)

Route: `/book-nook` (the list) and `/book-nook/:id` (the studio). Desktop-only in the sidebar, under Publish beside the Cartographer. Epic [#1142](https://github.com/irongollem/grimoire/issues/1142); the design is the canvas [Book Nook](https://claude.ai/artifact/Nq31S9bKY3hkymDWgwTdLN) (frames 01 to 10, plus 02a, 05b, 06b, 09b, 09c), approved 5 Nov 2026. Read the frame before changing a surface.

A **nook** is one painting cut into layers and moved a little by code: the **room** (the picture, painted empty), **cut-outs** (each thing that moves, at a depth) and **touches** (code effects: glow, steam, smoke, dust, embers, rain, snow, fireflies, falling leaves, shadows). Every motion repeats exactly in one loop. It follows the Cartographer's pattern: the Cartographer makes a map that a place binds, Book Nook makes a nook that a place shows. A nook is its own campaign record, and a place shows at most one nook while a nook is shown at one place or none.

### Data

Migration `20261105124218_book_nook.sql` holds all of it.

- **`book_nooks`**: `campaign_id`, `title`, `scene` jsonb (the engine's `Scene`; the client is the only writer, and a scene it cannot read renders as its still), `still_url` (the composed first frame, what lists, cards and reduce motion show) and `rev`. `rev` is bumped on every save so a stale tab's save can be refused and a player's cached bitmaps know to reload. Any DM of the campaign may make and edit one (`private.is_campaign_dm`, co-DMs included, as with Cartographer maps); a player has no read on the table. Insert, update and delete ring the campaign doorbell, and the table is copied with the demo campaign (`private.demo_campaign_tables`).
- **`locations.book_nook_id`**: the nook a place shows, `on delete set null`, with a partial unique index so the one-to-one rule is the database's, not the UI's. It joins `private.enforce_same_campaign_refs` (a nook from another campaign cannot be shown), and `get_player_visible_locations` appends it as the last column of the `setof locations` row.
- **`get_player_book_nook(p_location_id)`**: how a player reads a nook, a definer because players have no read on `book_nooks`. It joins through `get_player_visible_locations`, so a place the player may not see answers no rows and the two can never disagree. Its refusal test is `supabase/tests/book_nook.test.sql`.
- **`library_nook_parts`**: the stock shelf. `kind` is `cutout` or `frame`, `group_key` is fire, cloth, creatures, air or frames, and `preset` is what the shelf sets when a part is placed (a hold and a named motion, or a frame's shape). Signed-in read, admin write. The art lives on R2 under `location-images/srd/nooks/`, with its own storage policies in the same migration. A nook that uses a stock part copies the image URL into its own scene, so nothing in `book_nooks` points at this table by id. Its source is the `grimoire-book-nook` content source, titled "Grimoire Book Nook".
- **`campaigns.table_shows`** (`map` or `picture`, default `map`): the Table screen's **On the table** switch. It sits on the campaign row beside the party's position instead of travelling as a moment, so a TV that joins late shows what the room is showing.

Files are WebP under `location-images/{userId}/nooks/{nook id}/`. Saving a nook that a place shows writes its still to that place's `image_url`.

### The engine (`src/lib/bookNook/`)

`scene.ts` (the types and validation), `render.ts` (the canvas drawing), `presets.ts` (named motions), `edit.ts` (every studio operation as a pure function of the scene), `framing.ts` (the window checks), `shadows.ts`, `particles.ts`, `tilt.ts`, `moods.ts`, plus the stage and depth geometry. It was moved here from `scripts/promo/scenes`, and **the promo filmer imports it** (`scripts/promo/scenes/reel.ts`: `ReelScene` extends `Scene`); how the promo pipeline films, sounds and captions is unchanged.

### The studio (`/book-nook/:id`)

Full screen, layers on the left (`StudioLayers`), the stage in the middle, the selected thing on the right (`StudioInspector`). The sidebar and bars step aside while it is open.

- **Front and Side.** Front is the picture itself, where a thing is placed and pinned. Side is a toy theatre seen from the edge, where depth is set by dragging cards along a line marked Far, Picture and Near (0.2 to 1.6). Depth is never typed, and a thing that stands on another shares its depth.
- **Layers and the inspector.** A cut-out's inspector offers a hold (Stands, Hangs, Floats), a named motion (Flame, Cloth, Hanging, Wagging, Floating, Wandering, or None) with one **Strength** and one **Pace**, throws-light and casts-a-shadow toggles, and "Lies on a side wall". The engine's numbers sit behind **Exact**; a hand-tuned motion reads "Custom". Hanging and Wagging are both the engine's sway, told apart by size and speed (a slow small swing, or a quick wide one); Wagging swings about the pin, which the maker drags to where the part joins, a tail's root (8 Nov 2026, from the prison-cell Reel's dog). Touches have their own panel (amount: a little, some, lots; a glow follows a flame).
- **Shadows belong to the light, not the viewer.** A cast shadow lies on the surface it falls on, at that surface's depth. Near a flame it falls away from the light and wavers with the flicker. It never lengthens because the viewer moved (frame 05b).
- **Picture-wide settings.** The **loop** (with Play and Pause), **breathing** (Still, Gentle, Deep), a **mood** and the **frame**.
- **Frames.** The studio's TV and Phone previews draw the frame in that screen's shape, so the DM sees it as soon as it is picked; the Atlas preview does not, as the Atlas shows the picture inside its pane (`useNookImages` loads both shapes, outside `ready`). Until 7 Nov 2026 nothing but a player's full screen ever drew one, so a DM picked a frame and never saw it, and the TV showed none although frame 09c gives the wide shape to the TV. A frame that fails to load is left out and the nook still plays. A frame is fitted to a screen of another shape in five slices along the long side: its two ends and its centre keep their painted shape and two plain bands stretch (`frameSlices`), so a window's cross or an ornament at the centre is never stretched; a frame whose preset says `fit: "cover"` (stone) is instead scaled evenly to cover the screen and cropped at the sides (`frameCover`). **Your own frame** (the maintainer, 7 Nov 2026): *Upload your own…* in the Frame picker takes a wide shape (TV and website), a tall one (phones) or both, refuses a picture whose middle is not at least 70% see-through (`hasOpening`), and stores it at `location-images/{userId}/nooks/frames/` rather than in one nook's folder, because a DM's frames are listed under **Yours** in every nook of the campaign and `nookFiles` must never delete one with the first nook that used it.
- **Show on.** One picture, a window per screen: TV, Table and Atlas are 16:9, the phone is tall and draggable. The studio checks every window at the camera's furthest reach and refuses a dark edge, and it flags a cut-out whose own edge floats inside a window (`StudioFramingNotice`; "Breathe gentler" is the offered fix).
- **Autosave** (`useNookDraft` over `useAutosave`; no Save button). The status line is the feedback and **Done** returns to where the studio was opened from. If another tab saved the nook meanwhile (`rev` moved), the draft goes **stale**: autosave pauses ("Saved elsewhere") and **Reload** takes the other tab's copy, so two tabs never overwrite each other.
- **Creating a nook opens it** (*New nook*, and *Bring it to life* on a place, through `useStartNook`): a Sanctioned Exception in CLAUDE.md. Deleting still returns to the list.

### Getting art in: four ways, free first

The add-a-cut-out dialog (`AddCutoutDialog`, opened by "Add a cut-out") offers, in this order:

| Way | What it does | Price |
| --- | --- | --- |
| **Stock shelf** | Parts painted for Grimoire, with their motion preset. | Free |
| **Upload** | A PNG or WebP with a transparent background. An alpha check runs first; a flat picture is offered **Remove background** rather than refused. | Free (Remove background is one picture) |
| **Lift** | Paint over a thing in the room (a brush; Alt or Eraser takes paint away), optionally say what it is: it is cut out and the gap behind it is painted in so the room is whole when the thing moves. | Two pictures |
| **Paint** | A new part painted to match the room (the room picture travels with the request so the part matches its light), on a transparent background. | One picture |

`supabase/functions/generate-nook-part` does the model calls (`paint`, `lift`, `fill`): OpenAI only (transparent backgrounds and edit masks), **platform keys only** (a campaign's own key is never read), and the room picture is read from the nook row server-side and checked with `isSafeStorageUrl`, never fetched from a client URL. Every call is priced as one `entity_cutout` picture at 1024x1024, so **a call costs what a picture from that model costs today**: Paint 1, Remove background 1, Lift 2 (a lift then a fill, run by `liftFlow`). Wording lives in `addCutout/costLabels.ts`. Painting the room (*New nook*, **Paint with AI**) is one call to the place picture generator, priced as one `entity_image`; starting from an Atlas location's picture or an upload costs nothing. The edge function returns bytes and uploads nothing; the client uploads.

**Lift is a brush, not a box** (maintainer, 6 Nov 2026: "I get a rectangle marquee? shouldn't I just get a brush"). The picture zooms and pans with the shared canvas controls (`canvasControls/wheel`, `useCanvasHand`), and the brush size is in screen pixels, so zooming in makes the same brush finer. The painted mask's bounds become the crop; the model sees the untouched crop plus the DM's words ("the music box, not the table", sent as their own sentence in the lift prompt, at most 300 characters). The model draws the edge, and `clipToBrush` then drops whatever it kept outside the painted area (dilated by `brushSlack`, so a stroke that falls short does not cut the thing); the fill mask comes from the clipped part, so what was left out stays in the room.

**AI off.** A campaign with AI off is offered none of the model calls: *New nook* has no Paint with AI, and *Add a cut-out* shows only the shelf and Upload (no Lift, Paint or Remove background), as every Generate button elsewhere is hidden rather than disabled. Every model call carries `IconGenerate` and nothing else does: a touch is code, so its row is drawn with `IconWind`.

**Words on screen.** The UI calls a place an *Atlas location* ("From the Atlas", "Show in the Atlas…"), because DMs reach it through the Atlas and the word "place" alone named nothing they had seen (maintainer, 5 Nov 2026).

### Where a nook plays

- **Atlas Overview.** `AtlasPlacePicture` plays the nook quietly under a paper label, with **Edit picture** (into the studio), **Table screen**, and for a place with only a picture **Bring it to life**.
- **Players.** `PlaceNookPicture` in the place view, read through `get_player_book_nook`; tapping it opens full screen (`BookNookFullscreen`). On a phone the picture is a window you tilt. It has no button of its own: the tap that opens full screen asks for motion permission (iPhone), Android asks nothing, and a refusal leaves the picture breathing. Tilt is smoothed, eases back to centre and is bounded by the framing check; the pointer does the same on desktop and the website, and the TV breathes. An optional **frame** (a tall and a wide shape) covers the screen's edge wherever the picture is the whole screen (a player's full screen and the Table screen, never a picture inside a page) and **never moves**: the room shifts behind it and the shadow inside its opening moves with the room.
- **The Table screen** (`/locations/:id/table`, `MapTableView`, `MapTablePicture`). It shows the picture when the place has a nook and either there is no map to play on, or the DM sets **On the table** to Picture (a switch on the explore bar, kept in `campaigns.table_shows`). Two rules: **a fight always shows the map**, whatever the switch says, and a nook is never drawn under a map; and **nothing is chosen until the map's reads have answered** (`useLocationBattleSurface` settled), so a TV never flashes the picture while a map loads. Picture and map crossfade. Sound stays the place's own ambience.
- **Sound** (story 15, decision 13). A nook has no sound of its own: it is drawn live on a canvas (never a video, so there is no track to embed), and its sound is the ambience of the place that shows it. The studio's **Sound** row (`StudioSoundRow`, `useNookPlaceSound`) edits that place's `audio_theme`, the same field as the place's Details form, autosaving through `useAutosave`; the edit is saved on the place it was typed for even if the nook moves meanwhile. A blank field shows what the place inherits (`resolveInheritedTheme`), and Play plays it through `useAmbiencePlayback`, owned by the place the theme comes from, exactly as the Atlas pane's Play does. Play is hidden when no ambient scene answers the theme, and the row says so. Nothing plays when the studio opens, and a nook shown at no place has no Sound row. Full screen has no Play: it is the player's view, and players have no soundboard (the table's sound comes from the DM's device).

### Performance rules

One canvas per nook on screen (`BookNookPlayer`). At most **30 fps**, device pixel ratio at most **1.5**, plays only while visible (`useVisibleLoop`: on screen and the tab visible), **reduce motion shows the still**, and a frame has a **4 ms** budget. The still also shows until the images are in. Studio decoding goes through `useNookImages`.

### Stock shelf

The first shelf is 32 cut-outs plus frames (four manuscript styles; four windows and walls, a plain wooden window, a four-pane window, stone and stone with prison bars, were briefed on 7 Nov 2026 in the painter's `window` lane), defined in `scripts/book-nook-stock.data.ts` and painted by the maintainer's painter queue (briefs queued 5 Nov 2026, 39 images, output in `~/Desktop/art-955/scenes/`). `npm run nook:stock` turns each painted PNG into a WebP (alpha kept, longest side 1536 px), puts it on R2 at `location-images/srd/nooks/<id>.webp` and upserts its `library_nook_parts` row; parts with no file are listed as still to paint and the shelf ships with what is painted. `-- --check` reports only. The production run (`-- --production --yes-production`) is the maintainer's.

### DM View

Route: `/rules`

A five-tab rules reference and management screen for the DM. Includes a built-in dice roller.

All three searchable tabs keep their query in `useRulesUiStore` — `compendiumSearch`, `manualSearch`, `customRulesSearch` (+ `*HasActiveFilters` / `reset*Filters`) — so switching tabs or leaving the Reliquary does not wipe it, and all three render the same `ListFilterBar` + `ListSearchInput` chrome with a Clear button (#723). In the two sidebar tabs the search sits in the bar's `above` slot so Clear falls beneath it rather than fighting the 16rem column for width.

**Tabs:**

**DM Screen**
Quick-reference panel with common combat tables, conditions, and other at-a-glance information used during play.

**Compendium**
Read-only SRD/Open5e rules browser. Search and browse standard D&D 5e rules content, scoped to the active campaign's ruleset via `useRuleset()`.

**Dual-edition sync (#555, closes #142)** — the `sync-srd-rules` Edge Function was rewritten from the old v1 `/v1/sections/` (2014-only) endpoint to Open5e v2 `/v2/rulesets/` + `/v2/rules/`, synced for both editions. `library_rules` holds 268 rows for 2014 (41 sections + 227 rules) and 67 for 2024 (11 + 56). A ruleset becomes a top-level (parent) row; rules nest under it via `parent_slug`. Cleanup on each sync run is scoped by a provenance marker (`provenance->>endpoint`) so it only ever removes rows this sync previously wrote itself — legacy v1 and abandoned-v2 identities are cleaned this way, and user-authored custom rules are never touched. Deployed on a weekly cron (`supabase functions deploy sync-srd-rules`); admin/service-role manual invocation unchanged (`supabase functions invoke sync-srd-rules`).

**Custom Rules**
DM-authored rules, tables, and house rule documents. Each rule has:

- Title, category, tags
- Rich text content body (Tiptap editor)
- **Player visible flag** — when checked, the rule appears in the player Reliquary portal

Custom rules support an optional **Tracker** bolt-on:

- Two tracker types: **Level** (named states, e.g. Chilled → Frozen → Hypothermic) and **Points** (numeric pool, e.g. 0–20 Sanity)
- Min/Max values, plus an optional Starting value (`TrackerDef.start`, `src/types/rule.types.ts`) for trackers that don't start at their floor, e.g. the demo campaign's Lucidity (0–10, every character starts at 8). Absent, a character with no saved state reads at `min`, same as before this field existed. Every reader of an unset tracker value (the player character sheet, DM tracker buttons, the dashboard rule-tracker widget, and the delta-apply math) goes through the one pure helper `trackerInitialValue()` (`src/lib/rules/trackerValue.ts`), which also clamps a saved `start` into [min, max]
- **Levels** (Level type): each level has a numeric or ability-code value, a name, a color badge, and a list of mechanical effects:
  - Note (label shown on player sheet)
  - Speed penalty (numeric)
  - Disadvantage on ability checks (optional scope: specific abilities or all)
  - Disadvantage on saving throws (optional scope)
  - Exhaustion level (1–6)
  - Saving throw (ability, base DC, optional +tracker value)
- **DM Buttons**: named buttons with a delta value (e.g. "Add Corruption +1", "Cleanse −1") shown in the DM's party panel

**DM Manual**
A set of built-in markdown reference pages loaded from `src/manual/`. Current pages:

- Item Tags Overview
- Item Containers
- Item Ranged Ammo
- Workshop: Crafting Ingredients
- Workshop: Cooking / Food
- Encounters: Monster Discovery

**Licences** (`src/components/rules/LicensesTab.vue`, reachable at `/rules?tab=licenses`)

Per-source attribution for every body of shared content in the database, and the licence texts those licences oblige us to publish. Shipped for #567 as a pre-launch legal gate.

The shape to understand before touching it: most of what we host is **not** WotC SRD. Of ~3,540 shared monsters only ~660 are SRD; the rest is Kobold Press (OGL 1.0a, except the Black Flag Reference Document which is **ORC**) and EN Publishing (OGL 1.0a). Calling any of it "SRD" in the UI is a licence problem, not a wording nitpick.

- **`content_sources`** (migration `20260729000002`) is the catalogue: one row per `source_document_key` with `title`, `publisher`, `license_keys`, `copyright_notice`, `product_url`, `is_redistributable`, `is_metadata_curated`. Attribution is a join, not 3,500 copies of a copyright line that can drift.
- **`get_content_licenses()`** — `SECURITY INVOKER`, no args. Returns one row per source that actually has content, with per-kind tallies (monsters/spells/items/species/rules/classes) joined to the catalogue. The join is `LEFT` on purpose: an uncatalogued source surfaces as "Uncatalogued source" rather than disappearing from the page whose job is proving nothing is unattributed.
- **`src/data/ogl.ts`** — the OGL 1.0a text, verbatim, machine-extracted from the Open Gaming Foundation's canonical copy. Section 10 requires we ship it. **Never reword or regenerate it.** Sections 1–14 render as-is; section 15 is rebuilt at render time from the `copyright_notice` of every OGL source present, because section 6 requires the chain to name each work we actually copy.
- **`src/data/licenses.ts` / `src/lib/library/contentLicenses.ts`** — licence descriptors and the pure grouping/§15-chain helpers (unit-tested).
- **`is_metadata_curated`** — rows where upstream metadata is wrong or absent and we maintain them by hand. `scripts/seed-content-sources.ts` skips them. This is what stops a re-seed silently reverting Black Flag's licence from ORC to Open5e's incorrect CC-BY tag.
- **Audio** (`get_audio_licenses()`, migration `20260729000003`, `AudioLicenseCard.vue`) — the tab also covers the soundboard's shipped catalogue: 802 sounds, of which **82 are CC-BY and legally require credit**. Grouped by `(license, source)` rather than modelled into `content_sources`, because audio attribution is per-sound and each `sound_library` row already stores a ready-to-display credit line. `attributions` is **null, never `[]`**, for CC0 groups — no credit required is a different state from credits gone missing, and the card says so in words. Per-sound credit still travels onto the DM's board via `SoundCard.vue`; this is the consolidated notice.

A library row's `source` and `source_document_key` are the Open5e v2 document key (`ccdx`, `bfrd`, `deepm`, `deepmx`, `wz`, `open5e`, `tdcs`), equal to its `content_sources.key`; there is no alias layer between key generations (#1124). A5E (`a5e`, `menagerie`) is frozen with its old keys and no importer touches an `a5e` gamesystem document until #934.

### AI house rule generator (#910)

The Reliquary's Custom Rules tab has a **Generate** action (`RulesView.vue`, `ui.customRuleGeneratorOpen`) opening `CustomRuleGeneratorPanel.vue` (state in `src/ai/useCustomRuleGeneration.ts`). Constraints: category and an "Allow a tracker" toggle. `generate-entity-text` with `generator: "custom_rule"`, ledger reason `custom_rule_generation`.

`normalizeCustomRule` (`src/lib/rules/customRuleAi.ts`) turns the answer into a `rules` row. The category must be in `RULE_CATEGORIES`; no title or no effect text means no rule. The body is assembled as a Tiptap document: summary, then Trigger, Effect and Exceptions as headed sections.

**Tracker validation is strict, and a failing tracker costs only the tracker.** `normalizeTracker` returns null on any structural fault (min not below max, a start outside the range, an unknown type, a level outside the range or out of order, an effect of an unknown type or missing its value, exhaustion outside 1-6, a save without a valid ability and DC, buttons or triggers it cannot read), so a half-valid tracker never reaches the player sheet, and the rule text still lands without it. With the toggle off the tracker is always null.

**Writes:** `createRule` with `is_player_visible: false` (a generated rule is never published to players unprompted), the tracker, and `ai_provenance`. Then it navigates to `/rules/:id`.

## Key Capabilities / USPs

- **All output is print-ready without external software.** Card Forge, The Mint and character sheets print through the browser's print dialog; a Scriptorium book downloads as a real PDF made by the `render-pdf` edge function (Cloudflare Browser Run), so it no longer depends on the reader's browser or print settings (#565).
- **Duplex alignment is automatic** — Card Forge and The Mint both reverse columns on back sheets so double-sided printing works correctly on any printer with long-edge flip.
- **Card Forge aggregates across all entity types** — a single print run can mix NPCs, monsters, items, and spells. Most similar tools require one entity type per export.
- **Card Library persists named collections** — the DM can save a boss encounter's card set and reload it next session without re-selecting.
- **Scriptorium produces genuinely styled output** — not raw HTML. The preview matches the chosen PHB theme (teal/navy 2024 or classic 2014) with two-column layout, ornamental headers, and proper page dimensions.
- **Scriptorium pictures have professional layout controls** — in the text (size presets, float left/right with text wrap, gutter bleed) or placed on the page behind or in front of the text, pinned to a corner or kept with a paragraph; comparable to desktop DTP software.
- **Token focal-point awareness** — portrait images in tokens use the same focal-point metadata set on the entity, so the face stays centered in the circle even for off-center portraits.
- **Book Nook turns one painting into a living picture**: cut into a room, cut-outs and touches, moved a little by shared engine code that the promo filmer also uses, and shown at a place, on players' phones and on the Table screen.
- **The Illuminator edits pictures inside the book, as a recipe over the original.** Edges, colour, vignette, texture, depth of field and a painted mask are composited in Canvas 2D at full resolution in the browser; the book keeps the settings, never a flattened file, and print draws from the recipe. Optional AI actions are the only part that calls a server.
- **Custom Rules with Trackers integrate into the live session** — a rule like "Corruption" can define named levels, mechanical effects, and DM control buttons that appear directly in the party tracker during play.
