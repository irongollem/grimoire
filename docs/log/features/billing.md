- [x] **Anti-abuse: new-account credit velocity guard** (irongollem/grimoire#467) — caps how fast a _young_ account can burn purchased credits (buy → burn → chargeback / friendly fraud), at the same server chokepoint as suspension (`reserve_credits()`). **Shipped OFF by default** — thresholds must be tuned against real post-launch usage or they'd throttle legit power users (the issue's explicit deferral reason), so this ships the _mechanism_ ready to flip on. `abuse_guard_config` singleton: `enabled` (master), `enforce` (block vs **log-only**), `young_account_days` (7), `window_hours` (24), `max_purchased_spend_window` (2600). - [x] **Checkout idempotency: collapse accidental double-submits onto one Checkout Session** — belt-and-suspenders hardening of the two checkout edge functions. A double-click / impatient re-click / client retry on _Buy_ or _Subscribe_ previously spun up two distinct Stripe Checkout Sessions (no double _charge_ — the user completes only one — but two live sessions and two `purchase_consents` audit rows per intent). Both `stripe-create-credit-checkout` and `stripe-create-checkout` now pass a Stripe **`idempotencyKey`** to `checkout.sessions.create`, scoped `{user}:{product}:{30s-bucket}` (`credit:…:{packId}` / `sub:…:{interval}`), so duplicate submissions within the window return the _same_ session Stripe caches for 24h rather than minting a new one. Distinct purchases never collide (different pack/interval → different key) and a deliberate repeat buy lands in a later bucket; a double-click straddling a bucket boundary degrades to prior behaviour (one extra abandoned session, still no double charge). Complements the existing `already_subscribed` 409 guard (which only fires once the first checkout's webhook lands) and the DB-level ledger idempotency indexes on the fulfillment side. Server-only — no client, API-contract, or schema change.
