# Features — Encounters & Combat

Shipped features in the **Encounters & Combat** area, newest first. Part of the Grimoire feature log — see the [log index](../index.md).

- [x] Thrown weapons — Melee + Throw, and the weapon lands on the ground. A weapon with the `thrown` property (javelin, dagger, handaxe, spear, light hammer, trident) now offers two attacks: the normal melee **Attack** and a new **Throw**. Throwing rolls the same to-hit (STR, or best of STR/DEX for finesse — the shared `src/lib/weaponAttack.ts` math, so both surfaces agree) and then the physical weapon leaves the hand: one is dropped to the ground as a recoverable `item_drop` in campaign chat (reusing the existing `useCampaignMessages.sendItemDrop` + `grab_item_drop` flow — **no new routes, RPCs, or tables**) and the equipped stack shrinks by one; throwing the last one removes it from the loadout. Works identically whether the **player** clicks it on their own combat tab or the **DM** clicks it in the encounter runner's new "Thrown Attacks" section (thrown weapons appeared nowhere on the runner before). Detection is `isThrownWeapon` (`src/lib/thrownWeapon.ts`, 7 tests): it trusts a vault item's `thrown` property and name-matches item-less custom stacks — which mattered because **Javelin/Spear/Light Hammer/Trident didn't exist as items at all**; they're now proper SRD weapons in `src/data/provisions.ts` (so freshly-seeded libraries roll real 1d6/STR javelins instead of an improvised 1d4; existing libraries pick them up on the next item-library seed). Daggers and handaxes were already thrown vault weapons, so they get Throw automatically. Shared throw behaviour lives in `useThrownWeapon` so the two surfaces can't diverge. Built on top of the earlier fix where firing a ranged weapon from the player's own combat tab finally consumes ammunition (shared `useAmmoConsumption`/`src/lib/ammunition.ts`), which the DM runner already did. (`src/lib/thrownWeapon.ts` + test, `src/composables/useThrownWeapon.ts`, `src/components/player/PlayerCombatTab.vue`, `src/components/encounters/RunnerPcAttacks.vue`, `src/data/provisions.ts`)

- [x] Per-combatant initiative roll button in the runner — a die button beside every initiative input while the encounter is still being prepped, so the DM can roll (or re-roll) one creature instead of only the whole table. Extracted as `RunnerInitiativeField.vue` rather than pasted into both list layouts: the desktop grid row and the mobile card now share one input + button implementation. It calls `store.rollInitiative(instanceId)`, which — unlike the top-bar "Roll Initiative" — deliberately **replaces** an existing value, since re-rolling a result you don't like is its whole purpose. It honours physical-dice mode through the same injected `InitiativeRoller` as the bulk roll, and shares `store.rollingInitiative` so the top bar and every row button disable together while a manual-entry prompt is open (that prompt is a single global slot). The button disappears once combat starts — the order is locked at that point and a stray re-roll would shuffle the turn everyone is standing in; the input stays editable for a manual correction. The INIT column widened 3.5rem → 4.75rem in the row grid **and** the list header, which duplicate the grid template and have to move together (noted in the feature doc). (`src/components/encounters/RunnerInitiativeField.vue`, `RunnerCombatantRow.vue`, `RunnerCombatantCard.vue`, `RunnerCombatantList.vue`, `src/stores/encounterRun.ts`)

- [x] **DM: edit a combatant's current/max HP on the fly in the encounter runner** (irongollem/grimoire#505) — the runner only let the DM nudge current HP (±1 / typed) and Dmg/Heal/+Temp; there was no way to change **max** HP, so a monster that spawned with the wrong HP (e.g. the 2-HP `parseInt` bug from #503, fixed in `100054b2`) couldn't be corrected without deleting and re-adding it, and damage clamped to that wrong max. Made the `/ max` denominator in each combatant row an editable input (`RunnerCombatantRow.vue`) wired to a new `setMaxHp(instanceId, value)` store action: it edits the beast overlay when wildshaped and the real max otherwise, floors to ≥1, and keeps a combatant that was at full HP full at the new max (bumping a 2/2 monster to 11 gives 11/11, not 2/11). Player combatants persist `current_hp`+`max_hp` via the existing `persistPlayer` path so the portal stays in sync; monster edits ride the live combatant push. Re-runs `checkEvents()` so HP-percent triggers re-evaluate against the new max.
