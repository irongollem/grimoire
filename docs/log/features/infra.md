# Features — Infrastructure

Shipped features in the **Infrastructure** area, newest first. Part of the Grimoire feature log — see the [log index](../index.md).

- [x] **MCP server — traverse your campaign from your own AI (read-only v1)** — a DM can connect their own AI client (Claude Desktop / claude.ai / Claude Code) and look up campaign content by conversation ("give me details on that NPC", "what's the goblin boss's stat block") instead of clicking through pages. Implemented as a thin OAuth 2.1 _resource server_ edge function (`supabase/functions/mcp/`) speaking minimal MCP JSON-RPC (`initialize`/`tools/list`/`tools/call`) over Streamable HTTP; it validates the Supabase-issued OAuth JWT and runs every query through an RLS-scoped client, so existing RLS enforces tenancy — no `mcp_tokens` table, no manual user filtering. Auth uses Supabase's native **OAuth 2.1 Server** (beta) as the authorization server with Dynamic Client Registration, so claude.ai self-registers when the DM pastes the connector URL — no tokens to copy. A transport-agnostic read-only tool layer (`_shared/mcp/{registry,tools}.ts`) exposes `list_campaigns`, `search`, `get`, `list`, and `campaign_overview` across ~15 DM-facing entity types via a single `ENTITY_REGISTRY` (adding a type = one line); heavy JSONB columns are kept out of search/list, returned in full only by `get`. New `/oauth/consent` page (`OAuthConsentView.vue`) renders the approve/deny screen via `supabase.auth.oauth.*`; a **AI Connections** tab in Campaign Settings (`AiConnectionTab.vue`) shows the connector URL + setup steps and lists/revokes connected apps. Read-only by design (no create/generate via MCP → zero credit spend, smallest security surface); generation stays in-app. Config in `config.toml`: `[functions.mcp] verify_jwt=false` + `[auth.oauth_server]` enabled with DCR.

- [x] **MCP server — create & update content from your own AI (write v2)** — extends the read-only MCP server with `create` and `update` tools so a DM can author content by conversation ("add a quest called …", "set that NPC's alignment to …") and get the created/updated record back. Registry-driven like the read tools: each `EntityDef` gains an optional `create` block declaring its writable fields (type/required/enum), driving one generic `create` and one generic `update` tool whose descriptions auto-list the per-type fields (`describeCreatableFields()`), so adding a field is one registry line. Creatable set = the nine narrative campaign entities (quest, note, npc, faction, location, encounter, deity, pantheon, puzzle); the SRD library + party_member stay read-only. Security: every write forces `user_id = auth.uid()` (never a client value), whitelists declared fields (rejecting `id`/`user_id`/timestamps and typos), validates enums/uuids/numbers/arrays, and leans on existing RLS for tenancy — no `SECURITY DEFINER` surface added. **Free-tier limits are respected automatically**: writes go through the same RLS-scoped client as the app, so the DB `enforce_quota` triggers apply; the MCP just translates the raw `quota_exceeded` into a clean "Free-tier limit reached (N) … upgrade to Pro" message via `check_quota`. Validation logic is unit-tested (`_shared/mcp/tools.test.ts`). Same single 76 kB edge function (`supabase functions deploy mcp`).

- [x] **MCP server — entity images as inline image blocks (`get_image`)** — `get` only returned storage URLs, which a consuming agent's sandbox usually can't fetch (allowlist + binary web-fetch limits), so portraits/maps were effectively invisible over MCP. New `get_image` tool fetches the object server-side and returns it through the MCP channel as a real **image content block** (base64 + mime), with the URL kept as a text block for clients that prefer linking. Registry-driven like the rest: each `EntityDef` gains an optional `imageFields` map (`which` selector → `*_url` column, first = default), so the eleven art-bearing types are covered by one generic tool whose description auto-lists the per-type images (`describeImageFields()`) — npc (portrait/disguise), location (image/map), item (image/mundane), monster/spell/trap/puzzle (image), faction/pantheon (emblem), deity/party_member (portrait). The transport gained an `McpContentResult` passthrough so a tool can emit pre-built content (the image block) instead of JSON text. Security: the row is read under the caller's JWT (RLS-gated, same as `get`), and an **SSRF guard** only inline-fetches objects under this project's own `…/storage/v1/object/` prefix — any external URL is returned as a link, never proxied. Pure `resolveImageColumn` + registry image invariants unit-tested (25/25). (A `data_uri`/`both` format with a `max_width` thumbnail option was briefly added and then **removed**: even the 400px variant dumped a large base64 blob into the conversation and needed manual decode/render gymnastics — not worth it for normal use. The inline image block is the keeper; revisit a deliberate inline path only if a real chat-widget/CSP embedding need appears.) Ships in the same edge function (`supabase functions deploy mcp`). _From the hosted-MCP handoff testing; items #1 (quest enum search) and #2 (write-tool auth) from the same notes were already resolved in the create/update v2 work above._

- [x] **In-app reporter: Bug vs Feature request** — players were filing feature requests through the bug-only reporter (and being told to "feel free"), which muddied triage. The reporter now opens a **type picker** (Bug / Feature request) with per-type fields — bug: where / what you were doing / expected / actual; feature: what you'd like + what problem it solves, with location optional — and dynamic header, icon, and copy (`BugReportModal.vue`, new `IconLightbulb`). The `create-bug-report` edge function branches the issue title (`[App Bug Report]` vs `[Feature Request]`), body sections, maintainer-banner wording, and labels (`bug` vs `enhancement`), and stays back-compatible with older clients (missing `kind` defaults to bug). Clearer triage for us, clearer form for them.
