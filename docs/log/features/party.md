# Features — Party & Characters

Shipped features in the **Party & Characters** area, newest first. Part of the Grimoire feature log — see the [log index](../index.md).


- [x] **Campaign content gating — species & classes** (#566) — DMs can now block species and system classes from character creation, and mark custom classes/subclasses as campaign-exclusive. New `campaignContentGating.ts` library (11 tests) exposes `useCampaignSpecies()` / `useCampaignSystemClasses()` / `useCampaignCustomClasses()` / `useCampaignCustomSubclasses()`, each returning `{ data (gated), all (ungated), isLoading }`. Closed leaks in `CharacterCreateBasicsStep.vue` (species picker), `CharacterCreateClassStep.vue` (class/subclass), `LevelUpWizard.vue` (prevent multiclass into disabled classes), `PlayerAppearanceSection.vue` (shapeshifter disguise), and `PartyMemberForm.vue` (removed 27 lines of duplicate inline logic). Grandfathering: existing characters who selected content before it was disabled still render and level correctly. (`src/lib/campaignContentGating.ts`, `src/lib/campaignContentGating.test.ts`, `src/composables/useSpecies.ts`, `src/composables/useCustomClasses.ts`, `src/composables/useCustomSubclasses.ts`, plus 5 component fixes)


- [x] **Natural armor with Dex + correct armor/formula interplay** — two gaps in the AC-formula system closed. `"natural:<N>"` only covered fixed shells (Tortle 17); Dex-based natural armor (Lizardfolk, Sorcerer Draconic Resilience 13 + Dex) wasn't representable — `computeAc` and the character editor now support `"natural:<N>+dex"`. And no formula interacted with worn armor at all: a barbarian/monk/mage-armor character kept their unarmored formula while wearing body armor (RAW: those calculations only function unarmored), and natural armor never yielded to better worn armor (RAW: use natural armor only when worn armor would leave a *lower* AC). The rules now live in one tested pure function, `resolveBaseAc(formula, storedAc, parsedArmor, dex)` in `src/lib/armorAc.ts`: `"armor"` derives from equipped armor; `"unarmored:*"`/`"mage_armor"` are replaced by armor-derived AC while body armor is equipped; `"natural:*"` takes the higher of shell vs. worn armor; manual/null `ac` is never overridden; shields stack on top in every case. `useShieldAcBonus` delegates to it — and is now wrapped in `createSharedComposable`, so N combatant/tracker rows share one set of inventory-scanning computeds instead of each row re-scanning the full inventory+catalog on every change (its dead `bonusFor`/`baseAcFor` exports were dropped too). (`src/lib/armorAc.ts`, `src/lib/armorAc.test.ts`, `src/composables/useShieldAc.ts`, `src/types/party.types.ts`, `src/components/play/CharacterEditTabs.vue`)

- [x] **Player-managed companions** (#569) — players can now create, edit and manage their own companions instead of everything routing through the DM. On `/play/party` the player gets an "Add companion" affordance opening the same `CompanionForm` side-sheet the DM uses, with the owner locked to their own character; the companion lightbox grows owner-gated management: HP damage/heal steppers, condition add/remove, a `combat_ready` "With the party / Elsewhere" toggle, Edit and Delete (confirm-guarded). Two security-relevant changes rode along: the form's NPC-source picker now uses the player-safe `useSharedNpcs()` projection for non-DMs (the raw `npcs` query leaks DM-only columns and disguised identities), and the `companions` RLS was reworked (migration `20260725000002`) — insert now requires membership of the target campaign, update/delete allow the creator, the campaign DM (`private.is_campaign_dm`), **or** the player whose character owns the companion (`private.my_party_member_id`), which is also what lets End Combat sync companion HP back and lets a player manage DM-created companions assigned to them. Companion cards show an "Elsewhere" badge when benched. Encounter auto-join + bench flow is logged under Encounters. (`PlayerPartyView.vue`, `PlayerPartyCompanionCard.vue`, `PlayerPartyCompanionLightbox.vue`, `CompanionForm.vue`, `useCompanions.ts`, migration `20260725000002`)

- [x] **Derived Armor Class from equipped armor + Dex — kills the shield double-count** (#571) — player AC was a hand-typed integer with only the shield added live at display, so a DM copying Beyond's final AC (which already includes the shield) into the `ac` field got it added a second time (a firbolg druid showing 17 instead of 15; two of three party shield-wearers were mis-stored the same way). Added a new `ac_formula: "armor"` mode that **live-derives** base AC from the body armor in the paper doll — exactly like the shield already worked, so swapping plate for leather updates every sheet/tracker instantly with no re-save. `src/lib/armorAc.ts` (11 tests) parses the SRD `armor_class` strings the compendium stores (`"18"` → fixed, `"11 + Dex modifier"` → +full Dex, `"14 + Dex modifier (max 2)"` → +capped Dex, cap read from the string; penalties never clamped) and resolves the equipped armor per member; `useShieldAc` grew `baseAcFor`/`acFor`/`armorFor` and the 7 canonical AC displays (player header, party tracker, lightbox, party card, runner panel + combatant, sheet export) route through one `acFor(member)` that keeps the `beast_ac ?? …` Wild-Shape precedence. **Hybrid by design**: 75+ magic/compendium armor rows have a null `armor_class` and magic bonuses (+1 plate, Ring of Protection, Defense style) aren't structured anywhere, so the stored `ac` remains the manual override/fallback and every existing null-formula character is byte-for-byte unchanged. The character editor gains an "Equipped armor" AC option with a live "11 + DEX (+2)" breakdown preview. Typecheck clean, 18 lib tests green.
