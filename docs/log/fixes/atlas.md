# Fixes — Atlas & Locations

Resolved bugs in the **Atlas & Locations** area, newest first. Part of the Grimoire fix log — see the [log index](../index.md).

- [x] Player-visibility payload leak — locations (#507 part 5, security; the highest-value narrative leak). Two player SELECT policies on `locations` both shipped the FULL row through the client's `select *` (`useSharedLocations`/`useLocation`): (a) `locations_player_select` (player_visible_to-gated) returned `description` even when `is_description_shared=false`, DM `notes`, `map_url` regardless of `is_map_shared`, and **every** `map_pins` entry including `visible_to_players=false` — secret child-location names, ids, and map coordinates (a hidden dungeon readable from devtools); (b) `locations_shared_map_campaign_member_select` handed **any** campaign member the whole row as soon as `is_map_shared=true` (the battle-map read path) with no player_visible_to gate at all, leaking a shared battle map's DM notes + secret pins to every member. Fixed in `20260711000013_player_visible_locations_projection.sql`: new `get_player_visible_locations(p_campaign_id, p_location_id)` SECURITY DEFINER projection nulls `notes`, nulls `description` unless `is_description_shared`, nulls `map_url` unless `is_map_shared`, and filters `map_pins` to `visible_to_players=true`. The single-id mode additionally allows a shared map (`is_map_shared`) the player isn't explicitly in `player_visible_to` for, so live-encounter battle-map VTT reads keep working; the list mode is player_visible_to only. Both leaky player policies are dropped (base table owner-only). Client: `useSharedLocations` (list) routes through the RPC (base-table read kept only for DM-preview, which the DM owns); new `usePlayerVisibleLocation` (single) replaces `useLocation` in `PlayerEncounterMapView` + `PlayerEncounterPanel`; `PlayerPartyView` switched `useAllLocations`→`useSharedLocations` for its id→name map. Verified by impersonation in a rolled-back tx: a player in `visible_to` gets `description`/`notes` null, `map_url` present only when shared, and 16 of 28 pins (12 secret filtered) on one map / 1 of 4 on another; a member not in `visible_to` gets a shared map via single-id (battle map) but not in the list, and a non-shared map not at all; direct base-table read returns 0 rows. `get_player_visible_locations` has `search_path=public`, `anon` EXECUTE revoked, so only the intentional `authenticated_security_definer` advisor class applies; `vue-tsc -b` ok. Applied to remote. (`supabase/migrations/20260711000013_player_visible_locations_projection.sql`, `src/composables/useLocations.ts`, `src/views/play/PlayerEncounterMapView.vue`, `src/components/player/PlayerEncounterPanel.vue`, `src/views/play/PlayerPartyView.vue`)

- [x] Security: store_items INSERT policy let a campaign player write rows pointing at another user's location — found by `/security-review` of the store-items PR. The `store_items_insert` policy only checked `auth.uid() = user_id`, never location ownership, and campaign members can read every location UUID in the campaign. Harmless on its own, but the global `(location_id, item_id)` unique constraint added in `20260612000001` weaponized it: a player could insert an (own user_id, victim location_id, item_id) row — invisible to the DM (whose reads filter `user_id = auth.uid()`) but occupying the global key — to (a) block the DM from stocking that item (their plain `.insert()` hits a duplicate-key error) and (b) run an existence oracle over the DM's store contents via `ignoreDuplicates` upsert + read-back, leaking even `visible=false`/non-shared rows. Fixed in migration `20260612000003` by tightening the INSERT WITH CHECK to also require `exists (select 1 from locations l where l.id = location_id and l.user_id = auth.uid())`. Verified zero existing rows violated ownership (rejects nothing legitimate) and confirmed an attacker insert against another user's location now returns RLS error 42501. (`supabase/migrations/20260612000003_store_items_insert_location_ownership.sql`)

- [x] Codebase-wide sweep for the store-items bug classes (N requests per click, refetch storms, duplicate-insert risks) — parallel-agent audit after the quick-fill incident, verified by hand before fixing. Fixed: crafting consumed ingredients with one DELETE per row and inserted outputs with one INSERT per row → now a single `.in()` delete + one batch insert (`src/composables/useCrafting.ts`); adding an equipment bundle (e.g. Explorer's Pack) inserted each sub-item sequentially in both the inventory panel and character creation → new `useAddInventoryItems` bulk mutation, one POST for all sub-items (`src/composables/usePartyInventory.ts`, `useInventoryMutations.ts`, `useCharacterCreationForm.ts`); soundboard page/sound drag-reorder updated every row's sort_order → callers now diff against current order and skip unchanged rows (`useSoundboardPages.ts`, `useSounds.ts`, `SoundboardPageTabs.vue`, `SoundboardView.vue`); campaign chat invalidated its query once per incoming message during bursts → 250ms trailing debounce matching useCampaignLiveSync (`useCampaignChat.ts`). Migration `20260612000002`: merged one existing duplicate NPC-inventory stack, added partial unique index `npc_inventory (npc_id, item_id) where item_id is not null` and `character_classes (party_member_id, class_name)` unique constraint; `useNpcInventory.addItem` now merges quantity into the existing stack on conflict. Known-but-deferred (bounded small N, need RPCs for column-to-column updates): innate-spell uses reset on rest (`useCharacterSpells.ts` ~5-15 PATCHes), level-up spell adds (1-3 POSTs), quest trigger firing on calendar advance, preset-location import parent linking.

- [x] Store inventory quick-fill appeared dead and produced 777 duplicate rows (500 on `store_items` GET) — three compounding causes. (1) Quick-fill fired one POST per picked item (the count input's `max="20"` doesn't stop typed values, so "99" → 99 concurrent INSERTs), jamming the connection pool until statements hit the statement timeout, so the panel's GET 500'd and kept showing "No items yet". (2) Each retry click re-inserted everything because the duplicate-exclusion set came from the failing query (empty), and the DB had no uniqueness guard — one location ended up with 777 rows for 144 distinct items. (3) The RLS policies added for shared store visibility referenced other RLS-protected tables (`store_items` → `locations`; `items` → `store_items` → `locations`), stacking ~37 subplans into every store query plan (~75ms planning, per-row execution for players). Fixed by: deduping prod data; migration `20260612000001` adding a `(location_id, item_id)` unique constraint and replacing both player-visibility policies with flat `security definer` helpers (`can_see_shared_store`, `item_in_visible_shared_store`); a bulk `useAddStoreItems` upsert (single request, `ignoreDuplicates` on the new constraint); clamping the fill count to 1–20 in code; and a disabled "Filling…" button state while the mutation is pending. (`src/composables/useStoreItems.ts`, `src/components/locations/StoreInventory.vue`)

- [x] Player portal atlas showed all shared locations instead of only those visible to the current player — after migration `20260413000003` set all null `player_visible_to` to `{}`, the `.not("player_visible_to", "is", null)` filter returned every location; also the locations RLS still used a blanket `is_campaign_member()` policy instead of the per-player scoping added for notes/quests; fixed by updating `useSharedLocations` to filter by `linkedPartyMemberId` (or non-empty array for DM preview) and adding `locations_player_select` RLS policy (`src/composables/useLocations.ts`, `supabase/migrations/20260413000012_locations_player_visibility_rls.sql`)

- [x] Location map pin placement overlay clicks didn't register — two causes: (1) `setPointerCapture` on every pointerdown redirected the resulting `click` event to `mapFrame` instead of the placement overlay per the Pointer Events spec, so `onPlacePin` never fired; (2) hovered pins at `z-20` rendered on top of the overlay (also `z-20`) since they appear later in the DOM, so clicks over existing pips hit the pin handler instead; fixed by bailing out of `setPointerCapture` early when `placingChildId` is set, and raising the overlay to `z-30` (`src/components/locations/LocationMap.vue`)

- [x] Wares don't render for players — `items` table had no campaign-member RLS policy, so the `items(*)` join in `fetchStoreItems` returned nothing for players even though `store_items` RLS was correct; added `items_campaign_member_select` policy allowing campaign members to read items that appear as visible wares in a shared location (irongollem/grimoire#69)

- [x] Atlas map location dots: nearby collapsed dots rendered above the expanded pill (z-index), pill centered on cursor instead of growing from the dot (pinStyle anchor), and names truncated at 128px regardless of available space; fixed by promoting hovered pin to z-20, anchoring the expanded pill at the dot position (grows right/left from pin), and widening name truncation to max-w-48 (irongollem/grimoire#56)

- [x] Saving an existing location wipes it from the list — `buildPayload()` included `campaign_id: null`, overwriting the row's campaign_id on every update; locations query filters by campaign_id so the row became invisible. Fixed by removing `campaign_id` from the update payload.

- [x] Atlas "Travel to" pin button expanded the location detail but never scrolled it into view (irongollem/grimoire#75) — root cause: `onPinGo` called `toggle()` but did nothing after; fixed by replacing with `goToLocation()` which expands the target and all shared ancestors, awaits `nextTick`, then calls `scrollIntoView`; also added `visibleTree` computed so children are hidden when their parent is collapsed (collapsing a parent cleans up the list), and a "Close all" button to fold everything at once

- [x] Location map pins go over the sticky PageHeader when scrolling — PageHeader sticky z-index raised from z-10 to z-20

- [x] Location map pin hover popup unreachable (gap between dot and popup drops hover state) — replaced separate popup with inline pill design; dot expands into pill containing token + name + action buttons, all inside one element with no gap

- [x] Location map image stretches to fill editor width even for small maps — inner container uses w-fit so it hugs image natural size; max-w-full prevents overflow

- [x] Pin color doesn't update when a child location's type is changed — getChildType() does live lookup in children prop, falling back to stored type

- [x] Players saw **broken images on location-map pins** (irongollem/grimoire#502) — each pin carries a denormalised `child_image_url` snapshot in the parent's `map_pins` JSONB. The DM's editor silently re-hydrates that snapshot from live child data before rendering, but the player view rendered the stored value verbatim; when a child's image is later replaced its old storage file is deleted, so the stale URL 404s. Fixed by re-hydrating pins from live shared child locations on the player side (`PlayerLocationDetailPanel` gains a `sharedChildren` map from `useSharedLocations`; shared children resolve their current image, unshared ones keep the snapshot per design). Belt-and-suspenders: `LocationMap` now hides any pin `<img>` that fails to load, falling back to the child's initial letter — killing the broken-image glyph regardless of cause.
