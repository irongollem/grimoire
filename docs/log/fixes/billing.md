# Fixes — Billing

Resolved bugs in the **Billing** area, newest first. Part of the Grimoire fix log — see the [log index](../index.md).

- [x] Reserve-before-generate credit hardening (irongollem/grimoire#463) — investigation showed the ticket's core ask had already shipped in the pre-launch security remediation (`20260621000007_credit_reservation.sql` + `_shared/credits.ts`): every generator (npc, location, trap, entity-image, chronicle-text/image, music, downtime, style-map, forge-mini, poll-meshy-jobs) follows reserve → generate → release-on-failure / release-and-record-on-success via the `reserve_credits`/`release_credits` RPCs, with pending negative ledger rows holding the balance atomically (advisory-locked, counted in `sum(delta)` so concurrent reservations can't all pass, excluded from the analytics view). Later migrations (`20260628000005`, `20260711000003`) integrated the holds with the velocity guard and clawback clamps. The ticket's "reconcile if actual differs from estimate" is realized as release-full-hold + record-actual-spend — equivalent and simpler. One residual gap remained: a hard kill of the Edge isolate (wall-clock timeout, platform crash) bypasses the try/catch release paths and leaks the pending hold, permanently reducing the user's balance. Fixed with `20260720000007_release_stale_credit_holds.sql` — a pg_cron sweep (every 15 min, mirroring the stale-image-jobs cron) deleting `pending = true` rows older than 2 hours, comfortably past the longest legitimate hold (the Meshy sculpt pipeline's 30-min-per-phase staleness window); a late `release_credits()` on swept ids is a safe no-op since it only deletes still-pending rows.

- [x] Credit-ledger money-path fixes surfaced by the payment audit (irongollem/grimoire#493), in migration `20260710000002_credit_ledger_refund_reset_fixes.sql` + `supabase/functions/stripe-webhook/index.ts`. (1) **Partial-refund over-clawback:** `charge.refunded` fires on partial refunds too, but `clawback_pack_credits` reversed the pack's FULL grant regardless of amount, so a €2 goodwill refund on a €13/1000-credit pack wiped all 1000 credits. Now PROPORTIONAL — reverses `round(credits * amount_refunded / amount)` — with the webhook threading `charge.amount_refunded`/`charge.amount` (and disputes passing equal amounts → fraction 1.0). Proportional is a POLICY DEFAULT chosen absent a product decision; the RPC documents the one-line switch to "only on full refund". (2) **Subscription period-reset race:** `topUpSubscriptionCredits` read `ai_credit_buckets.subscription_balance` (which INCLUDES pending reservation rows) and wrote `delta = allowance - current` without the per-user advisory lock, racing reserve/release_credits — a held generation `-h` committed during a reset then released on failure left `allowance + h` free credits. Moved into a locked `reset_subscription_credits(uuid, text, date)` SECURITY DEFINER RPC that takes `pg_advisory_xact_lock` and computes `current` EXCLUDING pending rows, preserving per-period idempotency (unique index + 23505). (3) **Clawback clamp included pending:** the `least(credits, purchased_balance)` clamp read a balance including pending holds → transient under-clawback; now clamps against the settled purchased balance (`where not pending`). New RPCs are service_role-only (revoked from public/anon/authenticated); the new clawback amount params default to null so the existing 3-arg admin-refund caller (always a full refund) is unchanged.

- [x] Lyria music generation credits not showing up and pricing misconfigured — three root causes: (1) `logUsage()` was being called for the structuring step (text expansion) with a missing `imageUsage` field, logging `UNKNOWN` generation type instead of the actual music generation; fixed by removing the log call for the internal structuring step and only logging the final Lyria generation step; (2) `lyria-3-clip-preview` was priced at \$0.05 instead of \$0.04, and `lyria-3-pro-preview` was missing entirely; both entries seeded with fallback provider `'gemini'` instead of `'google'` so the join with campaign provider settings never matched; fixed by updating prices to correct amounts (\$0.04 and \$0.08) and setting provider to `'google'` so `ai_generation_costs` view correctly computes real dollar costs for Lyria generations (`src/lib/aiMusic.ts`, `supabase/migrations/20260604000001_fix_lyria_pricing.sql`).

- [x] AI Usage Stats listed admin credit grants as "(UNKNOWN) · (unknown)" zero-cost generations — the `ai_generation_costs` view selected every `ai_credit_ledger` row with no filter, so credit _additions_ (admin_grant, and future purchases/refunds/refreshes — all `delta > 0`, no model/provider) were counted as generations in both the settings panel and the admin Credits tab. Fixed by filtering the view to `where l.delta <= 0` (a generation always deducts credits or is free for BYOK; only credit additions are positive), so the breakdown shows real models only and still surfaces any genuine generation that's missing a model. Migration `20260607000002_ai_generation_costs_exclude_credit_grants.sql`.

- [x] Tester/admin app invites never granted their plan — every redeemed tester invite landed the user on `free` (0/3 in prod: fabio, Ali, Ilyas all stuck free). Root cause: `SignupView` called `consume_app_invite(token)` immediately after `signUp()`, but with email confirmation enabled there is no session yet, so `auth.uid()` was null and the function's `update user_subscriptions … where user_id = auth.uid()` matched zero rows while still bumping `use_count` — the grant silently no-op'd every time. Fixed by carrying the invite token through signup metadata (`auth.signUp` → `options.data.invite_token`) and applying the granted plan server-side in the `on_auth_user_created_subscription` trigger (`create_free_subscription`), which fires on the `auth.users` insert with the real `new.id` and needs no session: it reads `raw_user_meta_data->>'invite_token'`, consumes the invite, and provisions the subscription at the granted plan (tester for tester/admin invites), upserting and never downgrading an existing tester/pro. Removed the broken post-signup `consume_app_invite` client call. Backfilled the 3 affected testers to `tester`. Migration `20260608000001_apply_invite_plan_on_signup.sql`.
