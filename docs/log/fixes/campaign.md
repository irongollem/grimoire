# Fixes — Campaign

Resolved bugs in the **Campaign** area, newest first. Part of the Grimoire fix log — see the [log index](../index.md).

- [x] Live campaign state could get permanently stranded on stale data after a realtime gap — a player (or DM) had to manually reload to see changes that arrived while their socket was down. `useCampaignLiveSync` subscribes every connected client to `postgres_changes` and refreshes TanStack queries by invalidating on each event, but those projection queries are `staleTime: Infinity`, so they *only* ever refetch when an event fires. Realtime was therefore the sole source of truth: any event delivered during a socket drop, a network blip, or a mobile browser freezing a backgrounded tab's socket was lost forever, leaving the client stale until a full page reload. The symptom surfaced as "assigning an item to a player needs a refresh," but it was general to every synced entity, not item-specific — the happy-path item-assign flow (`party_inventory` INSERT → invalidate `party-inventory` + `items`) was already wired correctly and verified end-to-end (table in the `supabase_realtime` publication, RLS via `private.is_campaign_member` lets any member read the row, `get_player_visible_items` returns any item with a `party_inventory` row in the player's campaign). The gap was purely resilience to a *missed* event. Fixed by making realtime a notification layer over the DB rather than the only state: extracted the table→query-key bindings into a single `SYNC_TABLES` source of truth (looped into the channel bindings and reused to build `RECONCILE_KEYS`), and added a throttled `reconcile()` that re-invalidates every synced key — re-deriving state from the DB — on the three "we may have missed events" signals: realtime **re-subscribe** (rejoin after a drop; the initial `SUBSCRIBED` is skipped since first-load queries fetch on their own), window **`online`**, and tab **`visibilitychange → visible`**. `invalidateQueries` only refetches *active* observers, so the cost is bounded to whatever's on screen; a 2s throttle collapses the burst when a wake trips all three at once. Listeners are torn down on campaign switch and unmount via a shared `teardown()`. Happy-path behaviour is unchanged (same coalesced per-event invalidation, same `party_inventory` INSERT → `items` and `campaigns` UPDATE special cases). (`src/composables/useCampaignLiveSync.ts`)

- [x] Player journal — filter state, quest-log badge over-count, dead Encounter option (#529, the 3 remaining items; closes it). (1) **Filter state was a local ref** violating the Filter State Pattern — moved `filterCategory` into `useUiStore` (`journalFilterCategory` + `journalHasActiveFilters` + `resetJournalFilters`), wired via `storeToRefs`, and added a **Clear** button in the toolbar (visible only when a filter is active, on the mine/party tabs). (2) **Quest Log badge over-counted** — the badge used `playerQuests.length`, but the list renders only Active/Rumors/Completed/Failed groups, so a shared `undiscovered` quest inflated the badge past the visible rows; the count now filters to `QUEST_LOG_STATUSES` (the exact statuses that render). (3) **Dead "Encounter" context option** — the journal ref-type picker offered "Encounter" but `useEncounters` is owner-only by RLS, so the list was always empty for players; removed the option, its `case`, and the `useEncounters` call. `vue-tsc -b` ok. (`src/stores/ui.ts`, `src/views/play/PlayerJournalView.vue`)

- [x] Timeline CHRONICLE session bars over-extended and overflowed the strip as sessions accumulated. Bar width was the raw duration mapped 1:1 through the axis pixels-per-year scale with an 8px floor and **no ceiling** (`CalendarTimeline.vue`), and the same expression was duplicated in three places (stacking math, bar `width` style, and the 36px inline-vs-above label threshold). At high zoom one in-game day is ~96px, so the horizontal right-push stacking (each bar shoved to butt against the previous one's right edge) accumulated full-day bar widths until the run spilled past the right edge and labels collided (e.g. "Session 9" overrunning TODAY). Fixed by sqrt-compressing the width: `sessionBarWidth(rawPx) = min(160, 8 + 4.5·√rawPx)` — a sublinear curve that squashes short and long sessions into a tight 8–160px band (longer still reads wider, just compressed) so the strip packs at any zoom (a 5-day session at 1WK went 480px→107px, a 30-day off-screen 2880px→160px cap). Width is now computed once in `positionedSessionEvents` and carried on the event as `barWidth`, used by stacking, the bar style, and both label thresholds (removing the 3-way duplication that let them drift). (`src/components/calendar/CalendarTimeline.vue`)

- [x] Player journal: clicking an `@location` link jumped to the Atlas list instead of opening the location, and getting back to the journal entry was inconvenient (irongollem/grimoire#442) — `EntityMentionChip.navigate()` hard-routed every player-portal entity chip to a list page (`/play/atlas` for locations). Fixed by opening locations in a quick-view dialog over the current page instead: added `playerLocationDialogId` state + `openPlayerLocationDialog`/`closePlayerLocationDialog` to `useUiStore`; the chip now sets that store state for `location` chips in `/play/*` (other entity types unchanged). New `PlayerLocationDialog.vue` (mounted once in `PlayerLayout`) resolves the location from `useSharedLocations`, reuses `PlayerLocationDetailPanel` + `PlayerPartyNpcLightbox`, marks it read, lets pin clicks swap to shared children, and offers a "View in Atlas →" escape hatch. Works from any rich text in the portal (journal, quests, etc.).

- [x] Timeline year labels stacked on top of each other at large zoom levels or on narrow screens — step between year ticks was hardcoded (1/2/5) regardless of available pixels. Step is now computed from `pixelsPerYear` so labels maintain at least 40px spacing. Month labels at 1yr zoom are also suppressed when per-month width is below 50px. (#407)

- [x] Player calendar feed (`ical-feed` edge function) rejected unauthenticated calendar clients with 401 — Google Calendar / Apple Calendar / Outlook subscribe to an ICS URL and can't attach a Supabase JWT, so the gateway was blocking every request before it reached our code. Per-function `verify_jwt = false` was declared in `supabase/functions/ical-feed/config.toml` but the Supabase CLI doesn't read per-function configs — it reads the root `supabase/config.toml`, which didn't exist. Fixed by creating the root config with `[functions.ical-feed] verify_jwt = false` (and the same for `api-key-vault`, which has the same browser-from-anywhere access model). The function itself is already safe: it enforces access via a random per-campaign `ical_token` in the URL path and only returns CONFIRMED sessions — never draft scheduling or DM-only notes. Stale per-function `config.toml` files removed so the pattern doesn't mislead future contributors. Redeploy with `supabase functions deploy ical-feed api-key-vault` for the flag to take effect on the hosted project (`supabase/config.toml`)
