# Fixes — Collaboration

Resolved bugs in the **Collaboration** area, newest first. Part of the Grimoire fix log — see the [log index](../index.md).

- [x] Players kept reaching for refresh because realtime was mostly used as an invalidation signal and only the DM channel could recover after a missed-event gap (#579). Every client subscription now uses one `createRealtimeChannel()` lifecycle for subscribe status, throttled `online`/rejoin/long-background recovery, stale-callback protection, and teardown. The campaign registry dispatches all 25 shared table types through typed world/player/system reducers: complete base-table payloads update already-loaded exact caches directly, while joins, RLS-dependent lists, and redacted `SECURITY DEFINER` projections use explicit targeted invalidation because a raw row cannot safely reproduce their shape. Encounter state, party HP/temp HP/conditions/initiative, chat, party inventory, presence, player-removal detection, and short-lived AI row waiters all follow the same channel architecture; HTTP reads are limited to initial load, genuine gap recovery, or those deliberately derived query shapes. Campaign switches can no longer apply an old channel or in-flight response, routine tab focus no longer polls chat or encounter state, and runner ingestion no longer echoes received HP/condition rows back to Postgres. Chat has one subscription, fetches the newest 100 messages, opens at the latest message, and loads older 100-message pages on upward scroll while preserving the reader's viewport. Reducer and lifecycle coverage verifies direct cache moves/deletes, projection invalidation, heal throttling/detach, and late-callback guards. (`src/lib/realtimeChannel.ts`, `src/lib/realtimeHeal.ts`, `src/lib/realtimeCache.ts`, `src/lib/campaignRealtimeWorld.ts`, `src/lib/campaignRealtimePlayer.ts`, `src/lib/campaignRealtimeSystems.ts`, `src/composables/useCampaignLiveSync.ts`, `src/composables/useCampaignMessages.ts`, `src/composables/useCampaignPresence.ts`, `src/composables/usePlayerRemovalGuard.ts`, `src/components/chat/ChatPanelContent.vue`, `src/components/chat/CampaignChatPanel.vue`)

- [x] The live-sync self-heal reconciled on **every** alt-tab — `reconcile()` ran unconditionally on each visibilitychange-to-visible (throttled only by a flat 2s window), bursting invalidations for all ~21 reconcile keys and a dozen-plus simultaneous refetches of unchanged campaign data on routine tab switches, even when the realtime socket never dropped. Now gated: the channel status callback records `sawDrop` on `CHANNEL_ERROR`/`TIMED_OUT`/`CLOSED`, the hidden timestamp is tracked, and becoming visible reconciles only when a drop was actually seen **or** the tab was hidden ≥ 5 minutes (missed-event safety net); coming back `online` still reconciles unconditionally, and genuine drop-then-rejoin behaviour is unchanged. (`src/composables/useCampaignLiveSync.ts`)

- [x] Player not ejected when removed from a campaign mid-session + membership live-sync never fired (#535, closes it). Two problems: (1) `campaign_members` was **not in the `supabase_realtime` publication at all** (`in_realtime_pub=false`), so the `campaign_members` handler added to `useCampaignLiveSync` in the prior batch never fired — display-name renames and add/remove silently didn't propagate despite the handler existing. (2) No eject: a player the DM removed mid-session kept a dead session whose queries returned empty under RLS, showing blank content instead of redirecting out. Fixed in `20260711000018_realtime_campaign_members.sql` — `alter table campaign_members replica identity full` (so a DELETE payload carries the old row's `user_id`/`campaign_id`, not just the PK) + add it to `supabase_realtime`. Client: new `usePlayerRemovalGuard` (mounted in `PlayerLayout` only — the DM layout must never eject when it removes a player, that's someone else's row) subscribes to `campaign_members` DELETE for the active campaign and, when `payload.old.user_id === auth.user.id`, shows a sticky "You have been removed from {campaign} by the DM" toast, clears the active campaign + localStorage, `refreshMembership()` (re-derives role from any remaining membership — earliest-joined, or none), and routes to `play`/`dashboard`/`login` accordingly. Verified `campaign_members` now shows `replica_identity=full` + `in_pub=true`; `vue-tsc -b` ok. Applied to remote. (`supabase/migrations/20260711000018_realtime_campaign_members.sql`, `src/composables/usePlayerRemovalGuard.ts`, `src/layouts/PlayerLayout.vue`)

- [x] Invite `use_count` burned on no-op re-joins (#536). `join_campaign_via_invite` did an `insert … on conflict (campaign_id, user_id) do nothing` then an **unconditional** `update campaign_invites set use_count = use_count + 1`, and `JoinCampaignView` calls `attemptJoin()` on every mount for an authenticated user — so an existing member re-opening a capped invite link (or a page remount) decremented remaining uses without adding anyone, prematurely exhausting `max_uses`. Fixed in `20260711000017_invite_use_count_only_on_insert.sql`: `get diagnostics … = row_count` after the insert, and the `use_count` increment now runs only when a row was actually created (`row_count > 0`). Rest of the body (owner-can't-join-as-player guard, display-name derivation, SECURITY DEFINER + `search_path=public`) unchanged. Verified the `on conflict do nothing → row_count` mechanic (1 on fresh insert, 0 on re-insert) in a rolled-back tx; advisor shows only the pre-existing intentional `authenticated_security_definer` class on the function. Applied to remote. (`supabase/migrations/20260711000017_invite_use_count_only_on_insert.sql`)

- [x] Player with role in one campaign, DM role in another, couldn't access player portal (irongollem/grimoire#173) — root cause was `loadMembership(userId, campaignId?)` didn't have the active campaign ID passed in on app boot and after token refresh/login, so role would fall back to the oldest campaign membership instead of the player's previously-selected campaign. Fixed by: (1) making `loadMembership(userId, campaignId?)` accept an optional campaign ID — if set, fetches that specific membership; without it falls back to oldest-first behaviour (used during initial login when `activeCampaignId` is not yet set); (2) threading the parameter through `refreshMembership(campaignId?)`; (3) calling `refreshMembership(campaign.id)` in `switchToCampaign()` to reload the correct membership when the active campaign changes; (4) passing `campaignId` to `refreshMembership()` in `JoinCampaignView` after a successful join; (5) reading `localStorage.getItem("grimoire_active_campaign")` in `initialize()`, `onAuthStateChange` callback, and `signIn()`, then passing it to `loadMembership()` so role is scoped to the active campaign immediately on app boot and after token refresh/login, not just when navigating to switch campaigns (`src/stores/auth.ts`, `src/stores/campaign.ts`, `src/views/auth/JoinCampaignView.vue`)

- [x] in the settings to assign a character to a player I only see ids so I have no idea which character or player is which — same fix: display_name now populated from email at DB level

- [x] New player lands on DM dashboard after first login and campaign appears blank until refresh (irongollem/grimoire#8, irongollem/grimoire#10) — `signIn()` relied on `onAuthStateChange` (setTimeout-deferred) to load membership, so the router guard saw role=null and didn't redirect to `/play`; fixed by eagerly loading membership from the `signInWithPassword` response before navigating.
