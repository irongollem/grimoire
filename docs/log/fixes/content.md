# Fixes — Content & Import

Resolved bugs in the **Content & Import** area, newest first. Part of the Grimoire fix log — see the [log index](../index.md).

- [x] Artificer licensing hardening — the app shipped Tasha's-derived infusion effect text app-wide (`src/data/artificerInfusions.ts` in the public repo + client bundle) and mislabeled the 17 system Artificer `class_features` rows as `source: 'srd-5.1'`, but the Artificer is deliberately excluded from every SRD (5.1 and 5.2.1 — same brand-protection bucket as Aasimar, which is why Open5e/our `srd_species` only carry the 9 licensed 2024 species). The class chassis (hit die, saves, slot tables, option names, level gates) is uncopyrightable mechanics and stays shipped for everyone; the expressive effect text is now campaign-supplied content: new `class_option_texts` table (member-read/member-write RLS via `private.is_campaign_member`, live-synced, generic over `class_name`/`choice_key` for future non-SRD `text_pick` options), inline `RichTextEditor` in `PlayerArtificerInfusions` so members transcribe text from their own sourcebooks, `artificerInfusions.ts` slimmed to a names+`min_level` mechanics index with a do-not-restore warning, and provenance relabeled to `grimoire-system` (migration `20260725000003`). Existing campaigns were grandfathered by seeding the previous descriptions directly into their `class_option_texts` rows via service SQL — deliberately NOT via a committed migration, so the text no longer exists anywhere in the repo.

- [x] Players saw empty species / backgrounds / custom-class / custom-subclass / abilities lists during character creation and in the player Reliquary's Codex tab, even after the DM had authored them — the RLS SELECT policies on all five tables restricted reads to `auth.uid() = user_id`, i.e. only the DM. Players sign in as separate auth users, so the CharacterCreateWizard's pickers and Codex lists rendered "No species in the campaign yet". Fixed by widening the SELECT policies to `auth.uid() = user_id OR public.is_dm_of_my_campaigns(user_id)` — where the helper checks the current user shares a campaign with the row's owner-DM. `class_features` keeps its existing `user_id IS NULL` (system-seeded) branch alongside the new one. INSERT / UPDATE / DELETE stay owner-only; only read access widens, and only to users who share a campaign with the DM. `system_classes` didn't need the change since it's already open to all authenticated users (`supabase/migrations/20260414000007_player_character_options_rls.sql`)

- [x] SRD item import creating duplicates on re-run (Supabase 1000-row cap causing dedup check to miss items beyond row 1000)

- [x] SRD re-import idempotency: several client-side Open5e import paths silently clobbered DM/admin data on re-run instead of only refreshing upstream content (irongollem/grimoire#560). **Monster import** (`useImportSrdMonsters`) did `.update(m)` with the full mapped object — since the mapper always sets `notes`/`image_url`/`habitat`/`tags` to empty defaults (Open5e has none of that data), re-running wiped any DM-uploaded art, notes, habitat, and tags every time, contradicting its own doc comment. **Spell import** (`useImportSrdSpells`) always upserted `mechanics_reviewed: false` from the mapper, silently resetting an admin's manual mechanics review (and re-overwriting the reviewed content) on every re-run — exactly the risk called out for upstream fixes like open5e-api#964. **Class/subclass import** (`useImportOpen5eClasses`/`useImportOpen5eSubclasses`) overwrote the *entire* row on update with the importer's hardcoded defaults (`primary_ability`, proficiencies, spell-slot tables, `caster_type`, `steps`, `resources`, `granted_spells`, `hp_per_level`, …) — all fields Open5e's API has no data for and that a DM fills in by hand after the initial import — so re-importing silently discarded that manual configuration. **Species import** (`SpeciesOpen5ePanel.vue`) had the same shape of bug: `upsertRace` reused one payload object with `notes`/`image_url`/`focal_point`/`subraces`/`is_shapeshifter`/`avg_height`/`avg_weight`/`granted_spells` hardcoded to empty for both insert and update. Fixed all four by splitting "upstream content" (refreshed on every run) from "never-imported / DM-owned" fields (set once at creation, preserved on update): `monsterImportUpdateFields` (`src/lib/open5eMonsterImport.ts`), `planSrdSpellImport` (`src/lib/open5eSpellImport.ts`, also excludes already-`mechanics_reviewed` rows from the upsert batch entirely), `classImportUpdateFields`/`subclassImportUpdateFields` (`src/lib/open5eClassImport.ts`), and `buildImportedFields`/`buildCreateOnlyDefaults` (`SpeciesOpen5ePanel.vue`). Items (`useImportSrdItems`) and feats (`useImportSrdFeatures`) already had this split correctly. Documented the full per-entity re-import contract in `docs/srd-reimport.md`. Unit-tested in `open5eMonsterImport.test.ts`, `open5eSpellImport.test.ts`, `open5eClassImport.test.ts`.

- [x] SRD art orphaned by the v2 identity transition — the #553 data refresh reseeded srd_spells/srd_monsters under new ids but srd_monster_art/srd_spell_art still referenced the old ones (222+52 rows), and the monster art backfill had patched the doomed legacy rows, leaving every SRD monster without art. Caught by the post-epic 8-angle review; fixed by migration `20260722000004` (deterministic `'srd_' || srd_id` remap + denormalized art restore), verified live: 0 orphans, 220 monsters + 111 spells re-arted. Same review wave also fixed: seed reads unpaginated past PostgREST's 1000-row cap (incomplete mechanics_reviewed protection), SRD item re-import never backfilling `mastery`, the background review banner never clearing via its own "Review background" path, half-made background ASI choices silently persisting as zero bonus, the background editor surfacing raw CHECK-constraint errors, `weapon_masteries` keyed on item names instead of ids, a write-only `class_choices` key, and an initiative tie-break inconsistent with the roll modifier. Structural follow-ups tracked in irongollem/grimoire#562.
