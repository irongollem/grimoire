# Fixes — Database & Security

Resolved bugs in the **Database & Security** area, newest first. Part of the Grimoire fix log — see the [log index](../index.md).

- [x] Two legacy permissive base-table RLS UPDATE policies (#491) were left open after their exploits were closed only at the RPC layer, giving campaign members direct PostgREST write paths that bypassed the hardened `SECURITY DEFINER` claim/VTT RPCs (intra-campaign, requires membership, but real economy/state tampering). **(1) `campaign_messages_claim`** — `FOR UPDATE USING (type IN (item_drop, currency_drop, vendor_offer, player_offer, loot_chest) AND is_campaign_member(campaign_id))` with **no `WITH CHECK`**. The loot economy was rebuilt as atomic row-locked RPCs (`claim_item_drop`, `grab_item_drop`, `claim_currency_drop`, `claim_vendor_offer`, `claim_loot_chest_atom` — `20260621000006`/`20260629000002`) that bypass RLS, yet the policy still let any member `PATCH campaign_messages.metadata` to reset `quantity_remaining` or overwrite `claimed_by_user_id`/`paid_by_user_id` and steal loot/currency/vendor purchases. Investigation of `src/` found the four loot types are all claimed via `.rpc()`, but `claimPlayerOffer()` (`useCampaignMessages.ts:514`) still writes `metadata` **directly** for `type='player_offer'` (no atomic RPC exists for it) — so the policy was narrowed to `player_offer` only (with a matching `WITH CHECK`, which the original lacked) rather than dropped, keeping that legitimate write working while closing the four RPC-backed types. A future atomic `player_offer` RPC would let the policy be dropped entirely. **(2) `encounter_state_member_update`** — `FOR UPDATE USING/WITH CHECK is_campaign_member(campaign_id)`, granting every member unrestricted UPDATE of the whole `encounter_state` row (move/delete any token, zero any HP, rewrite initiative), bypassing `update_combatant_position` (`SECURITY DEFINER`, `20260512000003`) which limits a player to their own token. No legitimate member direct-write exists — DM writes (`goLive`/`pushState`/`endLive`, stop-other-encounter) are covered by `encounter_state_dm_all` and players go exclusively through the RPC — so the policy was dropped. Migration `20260710000001_tighten_claim_vtt_rls_policies.sql` (references `private.is_campaign_member` per the `20260629000002` relocation). NOTE: must be applied manually via `supabase db push`, then `get_advisors({ type: "security" })` re-run. (`supabase/migrations/20260710000001_tighten_claim_vtt_rls_policies.sql`)

- [x] MCP `search` tool threw on quests and silently dropped them from every result set — `operator does not exist: quest_status_enum ~~* unknown`. The generic search builder in `supabase/functions/_shared/mcp/tools.ts` turns each entry of an entity's `searchFields` into an `.ilike` (`~~*`) predicate OR'd together, but the quest registry entry listed `status` among its `searchFields`, and `quests.status` is typed `quest_status_enum` — Postgres has no `ILIKE` for enum operands, so the whole quest branch errored and quests vanished from both type-scoped (`types: ["quest"]`) and unscoped all-type sweeps, making existing quests look missing. Fixed by dropping `status` from quest's `searchFields` (kept in `extraListColumns` so it still shows in result rows — status is an exact-value filter, not a fuzzy text field). Audited the rest of the registry: the only two enum columns in the whole schema are `quests.status` and `locations.location_type`, and neither now appears in any `searchFields` (`npc.status` looked similar but is a `text` column, so it was already safe). NOTE: lives in an edge function — requires `supabase functions deploy` to take effect. (`supabase/functions/_shared/mcp/registry.ts`)

- [x] `grab_item_drop` (stacked-loot grab, #126) skipped authorization — unlike its sibling `claim_item_drop`, the `SECURITY DEFINER` RPC never checked campaign membership and trusted a client-supplied `p_claimer_user_id`, so any authenticated user could drain item stacks in **any** campaign by message id and stamp the claim with an arbitrary user. Found while auditing the 63 Supabase security advisories (the other 31 flagged SECURITY DEFINER functions all had correct internal `auth.uid()`/membership/admin gates — linter noise). Fixed by adding the `private.is_campaign_member(v_campaign_id)` gate and recording `auth.uid()` as the claimer instead of the spoofable parameter (migration `20260629000002`). Same migration did the advisor cleanup: relocated the 8 RLS-helper predicates (`is_app_admin`, `is_campaign_dm`, `is_campaign_member`, `is_dm_of_my_campaigns`, `is_faction_pc_member`, `can_see_shared_store`, `item_in_visible_shared_store`, `owns_crafting_recipe`) out of the API-exposed `public` schema into a non-exposed `private` schema (PostgREST only exposes `public` + `graphql_public`, so the functions are no longer REST-callable while RLS still resolves them — `authenticated` keeps `USAGE`+`EXECUTE`). The repoint of all 98 public + 6 `storage.objects` policies and 12 dependent functions was done **mechanically** via `pg_get_functiondef`/`pg_policies` + `regexp_replace` (zero hand-transcription) and dry-run-verified end-to-end in a rolled-back transaction before applying. Also dropped `anon` `EXECUTE` (via the `PUBLIC` grant) on 18 login-only RPCs — re-granted explicitly to `authenticated`+`service_role` — kept anon on `validate_app_invite`/`get_srd_*_sources`; added an admin-read policy to `rate_limit_events` (RLS-on-no-policy); and locked the `enforce_byok_pro_only` trigger function off the RPC surface (`20260629000003`). Advisor count 63 → 26, all remaining warnings being intentional `authenticated` RPCs.

- [x] Pre-launch security review (9-agent parallel audit) — fixed the real, exploitable findings. **(1) Player→DM privilege escalation:** `campaign_members_update_own` had a `USING` clause but no `WITH CHECK`, so a player could `update({role:'dm'})` on their own row and every server-side `is_campaign_dm()` check trusted it — closed with a `BEFORE UPDATE` trigger (`guard_campaign_member_self_update`) that forbids non-DMs changing role/campaign/party assignment (migration `20260621000001`). **(2) Canonical SRD-art poisoning:** `srd_monster_art`/`srd_spell_art`/`srd_art_defaults` INSERT/UPDATE gated only on ownership, so any user could set `is_canonical=true` (served to everyone + baked into `srd_*.image_url` by the admin sync RPC). Added `WITH CHECK (is_canonical=false OR is_app_admin())`, made `srd_art_defaults` admin-write-only, and added an `is_user_app_admin()` author guard to both sync RPCs (`20260621000002`). **(3) AI cost-drain:** all 8 generators checked the balance with a non-atomic read then deducted with `allow_negative=true` (never refused), so concurrent requests from a ~1-credit user all ran paid provider calls. Added a PENDING `reserve_credits()`/`release_credits()` hold (atomic advisory-locked gate, excluded from the `ai_generation_costs` view) — generators reserve before the paid call and release on success/failure (`20260621000007` + all `generate-*`/`style-map`). **(4) Loot claim-stealing:** `claimVendorOffer`/`claimCurrencyDrop`/`claimItemDrop` did the "already claimed?" check client-side then a plain UPDATE, so a player could overwrite another's claim or race it. Converted to row-locked `SECURITY DEFINER` RPCs that re-check under `FOR UPDATE` and stamp the claimer from `auth.uid()` (`20260621000006`, `useCampaignMessages.ts`, `CampaignChat.vue`). **(5) Stored XSS in chat (the audit missed this — a regression test caught it):** `marked.parseInline` does NOT escape raw HTML (it passes `<img onerror>` through), so chat was a live stored-XSS sink hitting every participant. Wired DOMPurify via `src/lib/sanitizeHtml.ts` + `renderTiptap.ts`, routed the chat + 4 Tiptap `v-html` sinks (player crafting, encounter runner ×2, trap modal) and 3 hand-rolled markdown renderers through it, pinned with `chatMarkdown.test.ts`. **Hardening:** `tile-packs` bucket + `app_settings` writes scoped/admin-gated (`20260621000003`); 52 owner UPDATE policies given mirrored `WITH CHECK` (`20260621000004`); bug-report fields fenced against GitHub markdown/@mention injection; `sync-srd-rules` constant-time key compare + generic errors; Stripe checkout/portal + freesound moved to the origin-allowlisted shared CORS helper; duplicate-subscription checkout guard; `imageJob` dynamic-write target allowlist; LoginView open-redirect guard; model-authored image-subject length caps + `style-map` source-image size bound. Per-user rate limiting (deferred to #466) now also done — `rate_limit_events` + advisory-locked `check_rate_limit()` RPC gating every AI generator (30/60s) and the bug reporter (15/day), hourly pg_cron purge (`20260621000008`). NOTE: all the edge-function code changes (reservation, rate limiting, CORS, bug-report, sync-srd) require `supabase functions deploy` to take effect; the migrations are already applied.

- [x] Security: players could read every campaign location and unmask disguised NPCs (whole-codebase RLS/authz audit). (1) The `locations` "Campaign members can read campaign locations" SELECT policy was a bare `is_campaign_member(campaign_id)` with no `player_visible_to` gate; because RLS policies are OR'd it overrode the properly-gated shared-map policy, so any player could `select * from locations` and read every secret dungeon, DM note, and unshared map in the campaign. Replaced with a `player_visible_to`-gated `locations_player_select` mirroring the npcs pattern (DMs keep full access via "Users can read own locations"). (2) The `npcs` row gate was correct but the player read path did `select *`, shipping DM-only columns (backstory, personality, notes, stat_block, alignment, linked_monster_id) the player UI never renders, and — critically — a disguised NPC's REAL `name`/`portrait_url` even when `is_revealed = false`, so a player could unmask hidden NPCs via devtools. Added a `security definer` projection function `get_player_visible_npcs(p_campaign_id, p_location_ids)` that strips the DM-only columns, swaps the disguise identity into name/portrait (so even consumers not using the client display helper, e.g. journal @-mention chips, never see the real one), and honours `player_visible_fields`; rewired `useSharedNpcs`/`useSharedNpcsByLocations` to call it instead of `select *`. Verified the projection as a real player (DM columns null) and the disguise swap (concealed NPC "Heartwin Blackraven" projects to cover name "The Duke"). Migration `20260613000001`. (`src/composables/useNpcs.ts`)

- [x] Mutation-safety sweep (audit follow-up): bulk reorder/restore helpers (`reorderNotes`, `reorderEntries`, `restoreInnateUses`, `usePopulateAllSettingHeroes`) used `await Promise.all(... supabase.update())` — the query builder resolves to `{ error }` rather than throwing, so a failed row left the data partially scrambled while the mutation reported success; now they collect results and throw on the first `.error`. `PartyMemberForm` Save/Remove had no in-flight guard (double-click → duplicate party_members row, no DB constraint); added a `saving` ref gating both handlers and buttons. (`src/composables/useNotes.ts`, `usePlayerJournal.ts`, `useCharacterSpells.ts`, `useHallOfHeroes.ts`, `src/components/party/PartyMemberForm.vue`)

- [x] Edge-function hygiene batch (irongollem/grimoire#495) — of the five low-severity audit items, three were already fixed on `main` (wildcard CORS on the 6 generators, provider-error text reflected to clients, and the `notify_marketing_rebuild` EXECUTE revoke). Fixed the remaining two. (1) **Frozen accounts could still run BYOK generations**: `reserveCredits` short-circuits on `cost <= 0` *before* the `reserve_credits` RPC that holds the suspension/velocity gate, so a frozen Pro account on its own keys bypassed the freeze. Added a shared `supabase/functions/_shared/suspension.ts` (`isAccountSuspended` + `suspendedResponse`, gated on `user_subscriptions.suspended_at`) called before any provider work in all 8 generators. (2) **`campaign.ai_enabled` was only enforced by `generate-entity-image`** — the DM "disable AI for this campaign" toggle is now honored by the other 7 (npc, location, chronicle-text, chronicle-image, music, style-map, trap). `deno check` green on all 8.
