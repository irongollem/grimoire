# Fixes — Database & Security

Resolved bugs in the **Database & Security** area, newest first. Part of the Grimoire fix log — see the [log index](../index.md).

- [x] **`20260730000010` could never apply to a fresh database — it dropped columns before the policies that depend on them** — Postgres tracks an RLS policy referencing a column as a dependency of it, so `alter table srd_monster_art drop column is_canonical` failed with "cannot drop column ... because other objects depend on it" while `srd_monster_art_canonical_select` / `_insert` / `_update` still existed; the migration dropped them a dozen lines *later*. Same inversion again in section 5 for `srd_art_defaults.contributed_by`. This never showed up against the production database because the migration had not reached it — the `spell-database` CI job boots a throwaway Postgres and replays every migration from scratch, and had been red on this since #584, which in turn blocked `production-release` and stranded migrations `…006`–`…011` (production sat at `…005`). Fixed by moving both policy-drop blocks above their column drops and recreating the policies after. Verified with a real `supabase db reset` — full replay, then `supabase test db` (84 pgTAP tests) and the spell-concurrency script.

- [x] **`db:pull` regenerated a seed that could not be loaded** — its `-x` exclusion list had not kept up with the reference tables migrations now populate themselves (`system_classes`, `metamagic_options`, `class_ritual_policies`, `class_spellcasting_policies`, `class_choice_rest_resets`, `disposable_email_domains`, `content_sources`), so a pulled `supabase/seed.sql` re-inserted rows the migrations had already written and `supabase db reset` died on a duplicate-key violation. Added the seven tables to the exclusion list. Only bites local development — `supabase/seed.sql` is gitignored (tester data), so CI never seeds.

- [x] Canonical SRD art was owned by whichever account uploaded it, and the three FKs disagreed about what that meant (#584) — `srd_spell_art.user_id` was `ON DELETE CASCADE` with all 96 of its rows canonical, so **deleting that account would have silently destroyed all 96 canonical spell-art rows**; `srd_monster_art.user_id` and `srd_art_defaults.contributed_by` were `NO ACTION`, blocking account deletion outright. Found by the #580 integrity pass and split out because it needed a model decision, not a one-line FK change: CASCADE everywhere destroys art shared by every user, SET NULL everywhere needs columns that the per-user override lookup may depend on. Fixed the way CLAUDE.md already prescribes ("Never store canonical art under a user UUID — if that account changes, every canonical URL in the DB breaks"), finishing a move the `srd/` storage prefix and `is_canonical` flag had started: canonical rows now live in dedicated `srd_monster_art_canonical` / `srd_spell_art_canonical` tables keyed solely on `srd_id` with **no `user_id` column at all**, admin-only writes via `private.is_app_admin()`, readable by any signed-in user. `srd_monster_art` / `srd_spell_art` keep only personal per-DM overrides, so `is_canonical` is gone and their CASCADE FK is finally correct — deleting an account now removes only that account's own private rows. `srd_art_defaults` turned out never to have had an override story at all (its unique key is `(content_type, srd_slug)` with no `user_id` component, so every row was already global and `contributed_by` was pure broken provenance) so it was dropped rather than split. All 1,072 canonical rows move under `do`-block assertions that compare before/after counts **self-referentially** rather than against hardcoded numbers, so they stay correct if counts drift before this applies. The user-art-trumps-canonical precedence was preserved and made testable: the previously-inline `{...canonical, ...own}` merge is now exported `mergeSrdMonsterArtLayers` / `mergeSrdSpellArtLayers`, same rule verbatim, with 10 tests. Both sync RPCs were recreated to read the new tables **before** `public.is_user_app_admin(uuid)` is dropped — ordering that matters, because Postgres does not dependency-track function calls inside PL/pgSQL bodies, so a premature drop would have succeeded silently and failed at runtime; verified no policy, view, or client caller referenced it. Added the two matching dangling-reference checks to `supabase/checks/content_integrity.sql`, which that file explicitly requires for any new text-id reference to shared content. (`supabase/migrations/20260730000010_unown_canonical_srd_art.sql`, `src/composables/useSrdMonsterArt.ts`, `useSrdSpellArt.ts`, `useSrdArtDefaults.ts`, `src/components/admin/SrdArtRepairPanel.vue`)

- [x] 11 player-authored notes had been invisible in the app since companion/party-member notes moved to the generic `entity_notes` table (#587) — `companion_player_notes` and `party_member_player_notes` stopped being read by any code, but their rows were never migrated, so a note a player wrote simply vanished from the UI while still sitting in the database. Found by the #580 dead-surface sweep, which flagged both tables as unreferenced but **not** empty — which is exactly why they weren't dropped in that pass. Backfilled into `entity_notes` as private notes (`is_private = true`, `shared_with_dm = false`): verified against the two tables' original migrations that every one of their RLS policies gated on `auth.uid() = user_id` with no sharing mechanism at all, so private is the faithful mapping rather than an invented one. `entity_type` literals (`companion`, `party_member`) were read off the actual `PlayerNotesWidget` mount sites rather than guessed, `campaign_id` derived by joining `companions`/`party_members`, and the old `updated_at` reused for `created_at` as the best available signal. Guarded with `where not exists` rather than `on conflict` because `entity_notes` has no unique constraint on `(user_id, entity_type, entity_id)` — checked, only the pkey. Of 11 rows: 3 migrated, 6 were blank, and 2 were **not** duplicates — that player had re-typed a note from scratch once the old widget went dark, so old and new text differed in substance. Those 2 were checked with the owner and confirmed leftover test data, so they're discarded deliberately rather than silently: had the text mattered it would have needed merging first, since the widget renders one private note per entity and a second would never have surfaced. Both tables then dropped. (`supabase/migrations/20260730000006_backfill_player_notes_into_entity_notes.sql`)

- [x] `party_inventory_dm_all` was a permissive RLS policy that permitted nothing its own siblings didn't (#586, partial) — dropped. The proof is in the helper definitions rather than in the data: `private.is_campaign_dm(cid)` is `private.is_campaign_member(cid)` plus `and role = 'dm'`, so the DM predicate implies the member predicate unconditionally. `party_inventory_dm_all` is `FOR ALL` with both `USING` and `WITH CHECK` set to `is_campaign_dm(campaign_id)`, while `party_inventory_member_{select,insert,update,delete}` cover the same four actions with `is_campaign_member(campaign_id)` — so per action (accounting for an UPDATE policy with no `WITH CHECK` reusing its `USING` clause) the member policy already permits a superset. Dropping it removes 4 of the advisor's 45 overlapping `(table, action)` pairs and changes no permission; a DM keeps full access by being a campaign member. **Both approaches #586 originally proposed were investigated and rejected**, recorded in the migration so they aren't re-tried: (1) adding `TO authenticated` to the ~90 overlapping policies is cosmetic — it moves the advisor 270 → 45 but buys an authenticated user nothing, while several affected policies are deliberately anon-reachable (`plans_public_read`, the canonical-art reads, `pro_waitlist_insert`, invite validation), so a blanket change risks silently breaking anonymous paths for a linter win; (2) merging each overlapping pair into one OR'd policy is close to a wash, since Postgres already combines permissive policies with OR and short-circuits — the saving is per-policy machinery, not predicate evaluation — and it would cost the `*_dm_*` / `*_member_*` legibility on the app's most security-sensitive tables, where a mistake is a privilege bug. The genuinely valuable subset is dropping strict-subset policies, and a mechanical per-action sweep found exactly this one. (`supabase/migrations/20260730000007_drop_redundant_party_inventory_dm_policy.sql`)

- [x] Schema consolidation audit (#580) across 267 migrations / 118 tables — found and fixed drift in four areas, and disproved two of the issue's own assumptions. **(1) Unindexed FKs.** 9 FK columns had no supporting index, every one of them an RLS predicate column or a parent-delete lookup (`abuse_guard_trips.user_id`, `class_option_texts.user_id`, `downtime_grants.granted_by`, `encounter_state_player_updates.campaign_id`/`.encounter_id`, `npc_sets.user_id`, `soundboard_broadcast.sound_id`/`.user_id`, `spell_change_windows.source_class_id`). A catalog query independently reproduced the advisor's list exactly, and a second query confirmed that afterwards **every** `campaign_id`/`user_id`/`owner_user_id`/`party_member_id` column on an RLS-enabled table has a leading index — not just the FK ones. **(2) RLS initplan.** 20 policies across 10 tables called bare `auth.uid()`, re-executing it per candidate row; rewrapped as `(select auth.uid())` with predicates otherwise byte-identical. All 9 `private.*` RLS helpers were already `STABLE`, and no policy applies a function to a filtered column (the admin ones are JWT-only and already `(select …)`-wrapped), so those two scope items were verified clean rather than changed. **(3) `REPLICA IDENTITY FULL` was pure cost.** 25 realtime tables carried it to get `old` records in payloads — but per Supabase's docs, *"when RLS is enabled and replica identity is set to full on a table, the `old` record contains only the primary key(s)"*. RLS is on for all 25 and all 25 have a PK, so `FULL` was writing a full old-row image to the WAL on every UPDATE/DELETE for a payload identical to `DEFAULT`. Reverted all 25. **(4) Account deletion was broken.** 60 FKs to `auth.users` already `CASCADE`, but 16 were created with the implicit `NO ACTION` default, so deleting an account failed outright with an FK violation; aligned them (`campaign_messages.recipient_user_id` cascades rather than SET NULL on purpose — a whisper with a null recipient becomes a campaign-wide message, so nulling it would *widen* who can read it). Also dropped the dead `party_member_levels` view (superseded by client-side `totalLevel()`), and documented the deliberately-kept tables in the migration so the next audit doesn't re-litigate them. **Two findings inverted the issue's expectations:** the 114 "unused index" advisor hits are a false positive here — stats span 7½ months and 16.1M scans, but the largest table holding a zero-scan index has 2,015 rows and all 166 total 2.68 MB, so the planner prefers a seq scan regardless and `idx_scan = 0` says nothing about scale; dropping them would have undone item (1). And the realtime publication had **zero** speculative members to remove — all 32 published tables have a live subscriber. The drift ran the other way: `campaign_rules` (in `SYNC_TABLES`) and `image_generation_jobs` (subscribed by `waitForRow`) were never published, so their channels could never fire and image jobs completed only via the 4-second poll fallback; both added. Performance advisor 414 → 391 findings (`unindexed_foreign_keys` 9→0, `auth_rls_initplan` 20→0); security advisor unchanged, its 64 findings all pre-existing. Substantial findings split to #584 (canonical SRD art owned by a user account), #585 (campaign-scoped homebrew blocks campaign delete), #586 (270 `multiple_permissive_policies`), #587 (11 orphaned player notes needing backfill), #588 (N+1 write loops), #589 (unwired surface). (`supabase/migrations/20260730000005_schema_audit_indexes_rls_replica_identity.sql`)

- [x] Three realtime handlers had never worked, because they read non-primary-key fields off `payload.old` — which RLS strips. Found while auditing the realtime publication for #580. Supabase reduces a DELETE's `old` record to the primary key whenever RLS is enabled, and separately *"Delete events are not filterable"*, so a `filter: campaign_id=eq.X` is ignored for DELETEs entirely and every subscriber receives every delete with an id and nothing else. **(1) `usePlayerRemovalGuard.ts`** read `payload.old.user_id` on `campaign_members` (PK is `id`), so `removedUserId` was always `undefined` and the guard returned early every time — a player the DM removed mid-session was never ejected in realtime, and only left when the reconnect/visibility-return HTTP re-check happened to fire. Now any `campaign_members` delete triggers the same authoritative `confirmStillMember()` read the delivery-gap path already used, and the misleading filter is gone. **(2) `useEncounterLive.ts`** (`useRunningEncounters`) read `payload.old.encounter_id`, which is `UNIQUE` but not the PK, so a deleted `encounter_state` row was never pruned from any connected client's live list; now matches on `id`, which is also inherently safe against the unfiltered cross-campaign deletes the docs describe. **(3) `campaignRealtimeSystems.ts`** read `old.source_table`/`old.source_id` for the `minis` case — unknowable on delete (and `minis` never had `REPLICA IDENTITY FULL` at all, so this one was broken from the start); it now invalidates the whole `["minis","for"]` projection prefix rather than leaving a stale one behind. Same file's `campaign_members` case gated its `my-memberships`/`campaigns`/`my-characters` fan-out on `old.user_id`, so removals never invalidated; it now invalidates blind on delete. The generic `applyRealtimeRow` reducer was already correct — it keys on `change.old.id` and only consults `matches()` for non-deletes. Added three regression tests using a realistic PK-only delete payload, since the existing test helper had been handing the reducer a full old row. (`src/composables/usePlayerRemovalGuard.ts`, `src/composables/useEncounterLive.ts`, `src/lib/campaignRealtimeSystems.ts`)

- [x] Two legacy permissive base-table RLS UPDATE policies (#491) were left open after their exploits were closed only at the RPC layer, giving campaign members direct PostgREST write paths that bypassed the hardened `SECURITY DEFINER` claim/VTT RPCs (intra-campaign, requires membership, but real economy/state tampering). **(1) `campaign_messages_claim`** — `FOR UPDATE USING (type IN (item_drop, currency_drop, vendor_offer, player_offer, loot_chest) AND is_campaign_member(campaign_id))` with **no `WITH CHECK`**. The loot economy was rebuilt as atomic row-locked RPCs (`claim_item_drop`, `grab_item_drop`, `claim_currency_drop`, `claim_vendor_offer`, `claim_loot_chest_atom` — `20260621000006`/`20260629000002`) that bypass RLS, yet the policy still let any member `PATCH campaign_messages.metadata` to reset `quantity_remaining` or overwrite `claimed_by_user_id`/`paid_by_user_id` and steal loot/currency/vendor purchases. Investigation of `src/` found the four loot types are all claimed via `.rpc()`, but `claimPlayerOffer()` (`useCampaignMessages.ts:514`) still writes `metadata` **directly** for `type='player_offer'` (no atomic RPC exists for it) — so the policy was narrowed to `player_offer` only (with a matching `WITH CHECK`, which the original lacked) rather than dropped, keeping that legitimate write working while closing the four RPC-backed types. A future atomic `player_offer` RPC would let the policy be dropped entirely. **(2) `encounter_state_member_update`** — `FOR UPDATE USING/WITH CHECK is_campaign_member(campaign_id)`, granting every member unrestricted UPDATE of the whole `encounter_state` row (move/delete any token, zero any HP, rewrite initiative), bypassing `update_combatant_position` (`SECURITY DEFINER`, `20260512000003`) which limits a player to their own token. No legitimate member direct-write exists — DM writes (`goLive`/`pushState`/`endLive`, stop-other-encounter) are covered by `encounter_state_dm_all` and players go exclusively through the RPC — so the policy was dropped. Migration `20260710000001_tighten_claim_vtt_rls_policies.sql` (references `private.is_campaign_member` per the `20260629000002` relocation). NOTE: must be applied manually via `supabase db push`, then `get_advisors({ type: "security" })` re-run. (`supabase/migrations/20260710000001_tighten_claim_vtt_rls_policies.sql`)

- [x] MCP `search` tool threw on quests and silently dropped them from every result set — `operator does not exist: quest_status_enum ~~* unknown`. The generic search builder in `supabase/functions/_shared/mcp/tools.ts` turns each entry of an entity's `searchFields` into an `.ilike` (`~~*`) predicate OR'd together, but the quest registry entry listed `status` among its `searchFields`, and `quests.status` is typed `quest_status_enum` — Postgres has no `ILIKE` for enum operands, so the whole quest branch errored and quests vanished from both type-scoped (`types: ["quest"]`) and unscoped all-type sweeps, making existing quests look missing. Fixed by dropping `status` from quest's `searchFields` (kept in `extraListColumns` so it still shows in result rows — status is an exact-value filter, not a fuzzy text field). Audited the rest of the registry: the only two enum columns in the whole schema are `quests.status` and `locations.location_type`, and neither now appears in any `searchFields` (`npc.status` looked similar but is a `text` column, so it was already safe). NOTE: lives in an edge function — requires `supabase functions deploy` to take effect. (`supabase/functions/_shared/mcp/registry.ts`)

- [x] Pre-launch security review (9-agent parallel audit) — fixed the real, exploitable findings. **(1) Player→DM privilege escalation:** `campaign_members_update_own` had a `USING` clause but no `WITH CHECK`, so a player could `update({role:'dm'})` on their own row and every server-side `is_campaign_dm()` check trusted it — closed with a `BEFORE UPDATE` trigger (`guard_campaign_member_self_update`) that forbids non-DMs changing role/campaign/party assignment (migration `20260621000001`). **(2) Canonical SRD-art poisoning:** `srd_monster_art`/`srd_spell_art`/`srd_art_defaults` INSERT/UPDATE gated only on ownership, so any user could set `is_canonical=true` (served to everyone + baked into `srd_*.image_url` by the admin sync RPC).
