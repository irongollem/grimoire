# Fixes — Encounters & Combat

Resolved bugs in the **Encounters & Combat** area, newest first. Part of the Grimoire fix log — see the [log index](../index.md).

- [x] Pre-push review batch on the ammo/thrown/Hidden work — five correctness holes closed before the feature ever shipped. **(1) Any charged weapon was treated as ammo-dependent**: both `weaponAmmoInfo` (player tab) and the runner's `isSelfCharged` gated on `charges !== null`, so a charged *melee* weapon (staff whose charges power a daily ability) burned a charge per basic attack and eventually disabled the Attack button with "No ammunition available". New `weaponUsesChargesAsAmmo(item)` (charges + actually ranged) gates both sides. **(2) Ammo detection was pure name-matching**: the tag/subtype tiers of `weaponAmmoTag` never fire for imported items (tags always `[]`, subtype generic), so a renamed/homebrew bow silently got infinite ammo. The classifier now consults the imported 5e `"ammunition"` property as a final tier, returning a new `"any"` tag that matches any recognised ammo stack; `isRangedWeaponItem` also reads the `subtype` "Ranged" category. **(3) Item-less thrown false positives**: `isThrownWeapon`'s name fallback substring-matched ("Longspear".includes("spear")), giving non-thrown customs a working Throw button that could lose the weapon — now word-boundary matched, with tests. **(4) DM-runner consumption ignored cancelled rolls**: `fireRangedAttack`/`fireThrownAttack` consumed ammo / dropped the weapon immediately after `emit("roll-attack")` while the handler discarded the roll result, so cancelling a physical-dice prompt still spent resources (the player tab already gated on the roll resolving). The `roll-attack` emit contract grew an optional `onResolved(rolled)` callback (relayed through `RunnerPcPanel`, resolved in `RunnerEntityDetail` from `performCheck`'s null-on-cancel), and consumption now runs only on `rolled === true`. **(5) Hidden survived DM-rolled attacks**: only the player tab's own `rollAttackWith` cleared the Hidden condition; attacks rolled from the runner left the PC Hidden (and its advantage effects) indefinitely — the same resolved-callback path now clears Hidden for melee/ranged/thrown runner attacks, mirroring `PlayerCombatTab.clearHidden`. The duplicated decrement-or-remove stack logic also collapsed into a shared `consumeOneFromStack`. (`src/lib/ammunition.ts`, `src/lib/thrownWeapon.ts`, + tests, `src/composables/useAmmoConsumption.ts`, `src/composables/useThrownWeapon.ts`, `src/components/player/PlayerCombatTab.vue`, `src/components/encounters/RunnerPcAttacks.vue`, `RunnerPcPanel.vue`, `RunnerEntityDetail.vue`)

- [x] Concentration was force-ended by damage that temp HP fully absorbed — `quickDamage` in `useRunnerCombatant` computed the "dropped to 0 HP" check as naive `hpBefore − amount` off the display HP, ignoring the temp-HP/beast-form absorption that `store.adjustHp` (via `applyDamage`) actually applies: a concentrating PC with temp 10 / HP 5 taking 8 damage kept all 5 real HP yet lost their spell. The check now routes the same `applyDamage` pools math from `src/lib/hitPoints.ts` and only ends concentration when *real* HP reaches 0; the concentration-*save* prompt still fires on absorbed damage (damage taken is damage taken — SAC). The player/DM `displayTempHp` rule (players read the live party row, others the combatant) was also de-duplicated into a shared tested helper in `hitPoints.ts` used by both `useRunnerCombatant` and `EncounterCombatantList`. (`src/lib/hitPoints.ts`, `src/lib/hitPoints.test.ts`, `src/composables/useRunnerCombatant.ts`, `src/components/player/EncounterCombatantList.vue`)

- [x] Player encounter panel: two review fixes on the new optional-rules/lightbox work. **(1) NPC lightbox race**: tapping an already-met NPC combatant before the `useSharedNpcs` query resolved fell through to the bare `EncounterCombatantLightbox` (no relationship/status/rating/connection note) because the lookup happened once at click time — the tapped combatant is now stored raw and the lightbox choice *derived*, so the rich `PlayerNpcLightbox` appears the moment the data arrives. **(2) Rule toggles never reached mounted players**: `campaign_rules` (turn timer, random initiative) was missing from `useCampaignLiveSync`'s `SYNC_TABLES`, so a DM enabling the turn timer mid-session was invisible to players until reload (60s staleTime, no focus refetch) — added, per the standing convention that every multi-participant campaign table joins live sync. The turn-timer wiring duplicated between `EncounterRunner` and `PlayerEncounterPanel` also collapsed into a shared `useTurnTimerConfig(round, activeCombatantId)` composable. (`src/components/player/PlayerEncounterPanel.vue`, `src/components/encounters/EncounterRunner.vue`, `src/composables/useTurnTimerConfig.ts`, `src/composables/useCampaignLiveSync.ts`)

- [x] A player firing a ranged weapon from their own character sheet never depleted their ammunition — a shortbow attack rolled fine but the 20-arrow quiver stayed at 20 forever. Ammo-consumption logic existed only on the DM side (`RunnerPcAttacks.vue`): the player-facing combat tab (`PlayerCombatTab.vue`) rolled the attack through `rollAttackWith` and stopped, never touching inventory. Rather than copy the runner's ~110 lines of ammo handling (which would silently diverge), the shared parts were extracted: `src/lib/ammunition.ts` (`weaponAmmoTag`/`ammoTagFromName`, pure classifiers with 14 unit tests) and `useAmmoConsumption` (a composable owning ammo-stack selection — quiver/container → belt → backpack — plus the charge/quantity decrement and self-charged-weapon path). The runner was refactored onto both (its local copies deleted), and the player tab now consumes ammo after a **successful** roll only (a cancelled dice prompt spends nothing — `rollAttackWith` now returns whether it rolled), with the Attack button disabled and a remaining-count / "no ammo" indicator shown when a weapon needs ammo it lacks, mirroring the runner. Self-charged weapons (laser rifle, internal-magazine firearms) decrement the weapon's own `charges`. (`src/lib/ammunition.ts`, `src/lib/ammunition.test.ts`, `src/composables/useAmmoConsumption.ts`, `src/components/player/PlayerCombatTab.vue`, `src/components/encounters/RunnerPcAttacks.vue`)

- [x] A PC's temporary HP was invisible during an encounter and got silently wiped — and Wild Shape disagreed with itself about whether temp HP exists at all. **(1) Never seeded**: `EncounterRunView.initStore` built player combatants from the party row without copying `temp_hp`, so a character who walked into the fight with Aid/Inspiring Leader temp HP showed none in the runner. Worse, `adjustHp` persists `temp_hp: c.temp_hp ?? 0` on every player HP change, so the DM's first Dmg click wrote **0** back over the player's real temp HP. **(2) Never synced**: the runner's `party_members` realtime subscription ingested `current_hp` and `current_initiative` only, so temp HP a player granted themselves mid-fight never reached the DM. Added `store.ingestTempHp` (assign-only, no write-back — the DB row is the authority, so there is no echo to guard) and a `displayTempHp` in `useRunnerCombatant` that reads the live party row for players, exactly as `displayHp`/`displayAc`/`displayConditions` already did; the runner row, mobile card, PC detail panel and the player-facing combatant list all render it. **(3) Wild Shape inconsistency**: the store absorbed temp HP before beast HP (correct — temp HP is a buffer in front of whichever pool is active and Wild Shape doesn't remove it), while the player sheet did the opposite: it hid the badge and the Tmp button while wildshaped and sent damage straight to beast HP, so the same hit resolved differently depending on who clicked it. Root cause was three hand-rolled copies of the arithmetic, so it's now one tested module — `src/lib/hitPoints.ts` (`applyDamage`/`applyHealing`/`betterTempHp`, 15 tests covering absorption, beast-form overflow and the tracker's negative floor) — used by `encounterRun.adjustHp`, `PlayerCharacterHeader` and `PartyTrackerRow`. Two more bugs fell out of the consolidation: the party tracker ignored beast form entirely (a wildshaped druid took damage on their *real* HP there, and its HP readout showed real HP, so it now reads and damages the beast pool with a "(Brown Bear)" hint), and the player sheet skipped the concentration save when temp HP fully absorbed a hit (damage taken is damage taken — SAC). Temp HP no longer stacks on the player sheet either (`betterTempHp`), matching the runner; the × button still clears it outright. (`src/lib/hitPoints.ts`, `src/lib/hitPoints.test.ts`, `src/stores/encounterRun.ts`, `src/views/encounters/EncounterRunView.vue`, `src/components/encounters/EncounterRunner.vue`, `src/composables/useRunnerCombatant.ts`, `RunnerCombatantRow.vue`, `RunnerCombatantCard.vue`, `RunnerPcPanel.vue`, `src/components/player/EncounterCombatantList.vue`, `src/components/player/PlayerCharacterHeader.vue`, `src/views/play/PlayerCharacterView.vue`, `src/components/party/PartyTrackerRow.vue`)

- [x] The encounter runner's "Roll Initiative" ignored physical-dice mode and clobbered initiatives that were already in — two bugs in one button. **(1) Physical mode not respected**: `rollAllInitiatives()` rolled `Math.floor(Math.random() * 20) + 1` inline in the store, the one initiative roll in the app that never went through `usePromptedRoll` — a DM with dice mode set to **physical** got auto-rolls with no manual-entry prompt, while their players (whose `rollMyInitiative` does use `promptRoll`) were correctly prompted. Fixed by giving the store an injectable `InitiativeRoller` (registered by `EncounterRunner` via `setInitiativeRoller()`, mirroring the existing `setPersistHandler` seam so the store stays UI-free): rolls now resolve through `promptRoll`, one prompt per combatant labelled with its name, silent so hidden monsters don't leak into campaign chat. Cancelling stops the run and leaves the rest blank — pressing the button again resumes. `startCombat()` is async for the same reason and still starts combat if the DM cancels (blank initiatives sort last and can be typed in). **(2) Overwrote existing rolls**: the skip guard was `c.type === "player" && c.initiative !== null`, so only *players* were protected — any monster or NPC the DM had already rolled or typed by hand was silently re-rolled on the next press. The guard is now type-agnostic (`c.initiative !== null`): the button only ever fills blanks. Mid-combat spawns keep the automatic roll (via the extracted `autoRollInitiative()`) rather than interrupting a live turn with a modal. The busy state moved onto the store as `rollingInitiative` when the per-combatant roll button landed, so every roll control disables together while a prompt is open. (`src/stores/encounterRun.ts`, `src/components/encounters/EncounterRunner.vue`)

- [x] `initiative_bonus` had three contradictory semantics (#526 item 4 of 7). The field was set = DEX mod (creation form), displayed as DEX mod ignoring the field (header), exported as `initiative_bonus + dexMod` (PDF renderer), and rolled as DEX mod only (encounter panel) — so a DEX-16 character showed INIT +3 on the sheet but +6 on the PDF, and a custom Alert bonus was ignored in the header + roll. Per the owner's call, `initiative_bonus` is now consistently the **extra on top of the DEX modifier** (feat/special bonuses like Alert; proficiency does not add in standard 5e), and the DEX mod is added wherever initiative is shown/rolled: creation seeds `0` (not dexMod), the header shows `dexMod + initiative_bonus`, the encounter roll adds the member's `initiative_bonus`, and the renderer (already `initiative_bonus + dexMod`) is now correct rather than double-counting. Both editable inputs relabeled from "= DEX mod" to "extra on top of DEX (e.g. Alert +5)". Data migration `20260711000022` converts existing rows `new_extra = old_total − dexMod` (using `floor()` on numeric, not integer division) so every character's effective initiative is unchanged — verified against live data: of 9 rows, 8 auto-seeded ones became `0` and 1 genuine custom (dexMod+3) became `3`. `vue-tsc -b` ok. Applied to remote.
