# Fixes — Images & Art

Resolved bugs in the **Images & Art** area, newest first. Part of the Grimoire fix log — see the [log index](../index.md).

- [x] `FocalImage`'s `loading="lazy"` was silently defeated, so every image on a page downloaded immediately whether or not it was ever scrolled to. When no manual focal point is stored (locations have no focal-point column at all, so `LocationCard` always hits this path) the component runs smartcrop, which pulls the image through a second `new Image()` — and that ran from a `{ immediate: true }` watcher at mount, for every instance on the page. A campaign with a few hundred locations therefore fetched a few hundred images before the first row scrolled past. Gated the whole resolve pass behind an `IntersectionObserver` on the root element (`rootMargin: 200px`, matching `useInfiniteScroll`), exempting `print` mode — Card Forge renders into an off-screen container that never intersects and needs focal points resolved to lay the card out. Also pointed the smartcrop probe at the *same* variant width the `<img>` renders instead of a hard-coded `_w400`, so it reuses the display fetch from cache rather than pulling a second, differently-sized copy. (`src/components/common/FocalImage.vue`)

- [x] `LocationCard` requested the 400 px image variant for a 56 px avatar slot, and `LocationList` rendered a card for every location in the campaign at once — the only entity list without `useInfiniteScroll`. Dropped the card to `render-width="200"` (the smallest variant, still 3× the display size) and paged the list like every other entity list. (`src/components/locations/LocationCard.vue`, `src/components/locations/LocationList.vue`)

- [x] A vision icon (`darkvision.svg`) looked fuzzy at any scale — it had been re-saved by Affinity Designer's SVG export as an embedded low-res PNG (`<image>` + base64, `serif.com` namespace) instead of curves, so it was a scaled-up bitmap, not a vector. Regenerated as a true potrace vector, with the cluttered star sparkles removed via connected-components (drop the small holes, keep the moon). For future Affinity edits: SVG export → More… → Rasterise: Nothing. (`public/assets/vision/darkvision.svg`)

- [x] Manual portrait/image uploads from 16 entity forms (NPCs, monsters, spells, items, factions, pantheons, deities, party members, companions, character wizards, etc.) silently routed to the `asset-images` bucket instead of their per-entity bucket — root cause was `ImageUpload.vue` declaring `bucket = "asset-images"` as the default prop value, so any call site that forgot the `:bucket` attribute fell into the asset-images catch-all. The Art Library category for those entities looked nearly empty as a result. Fixed by making `bucket` a required prop (TypeScript now fails any future call site that forgets it) and wiring each form to the correct bucket: monster-images, spell-images, item-images, faction-images, npc-portraits for character/companion/PC portraits, plus two new buckets (`pantheon-emblems`, `loot-images`) for use cases that weren't a clean fit for any existing one. (`src/components/common/ImageUpload.vue` + 16 call sites + `supabase/migrations/20260511000001_pantheon_loot_buckets.sql`)

- [x] `backfillVariants()` could create recursive `_w200_w200.webp` (and worse) variant chains when called with a URL that was already a variant — FocalImage's `onError` passed `props.src` to the backfill regardless of whether `props.src` was the original or a variant, and `variantPath()` then tacked another `_w<n>` suffix on. A historical migration script triggered this once and produced ~930 garbage files in `npc-portraits` alone. Fixed defensively in `backfillVariants` with an early-return guard `/_w\d+(?=[._])/` that refuses to run if the input looks like a variant. Also tightened ArtPickerModal's variant-detection regex to catch `_w<width>` chains regardless of file extension, plus added a thumbnail `@error` fallback so missing webp variants degrade to the original instead of breaking. (`src/lib/storage.ts`, `src/components/common/ArtPickerModal.vue`)

- [x] ArtPickerModal returned an empty list for almost every bucket even though images were uploaded — Supabase storage `list()` requires a SELECT policy on `storage.objects` to return rows, and 8 image buckets (npc-portraits, asset-images, spell-images, puzzle-images, item-images, monster-images, trap-images, location-images) were created with insert/update/delete policies but no select. Authenticated users could `getPublicUrl()` (which doesn't hit the API) but could not enumerate their own files. Added per-bucket SELECT policies scoped to `(storage.foldername(name))[1] = auth.uid()::text`. (`supabase/migrations/20260510000001_storage_select_policies.sql`)

- [x] Mobile photo upload on items (and all image upload zones) did nothing after selecting a photo on iOS — three root causes: (1) `class="hidden"` (display:none) on the file input caused iOS WebKit to drop `@change` events unreliably — fixed with `class="sr-only"` and replacing programmatic `.click()` calls with native `<label :for>` connections; (2) `canvas.toBlob("image/webp")` silently returns a PNG blob on Safari < 16.1 instead of null — fixed with a JPEG fallback that checks `blob.type !== "image/webp"`; (3) 3 MB bucket limit was too tight for high-detail digital art at 1920px — raised to 5 MB. Silent failures were also masking the error; `uploadError` is now surfaced to the user (`src/components/common/ImageUpload.vue`, `src/components/party/CompanionForm.vue`, `src/lib/mediaConvert.ts`, `src/lib/storage.ts`).

- [x] Entity deletions left orphaned images in Supabase Storage — delete functions for NPCs, monsters, items, spells, party members, companions, Hall of Heroes, traps, puzzles, and dungeon features only removed the DB row; fixed by changing each `deleteX(id)` to accept the full entity, then calling `removeStorageImages('asset-images', ...imageFields)` after the DB delete; added standalone `removeStorageImages` utility to `useImageUpload.ts`; also removed duplicate manual image-removal code that had existed in `MonsterDetail.vue` and `SpellDetail.vue`; SRD/external URLs are silently skipped (no `/object/public/asset-images/` marker match)

- [x] `FocalImage` focal point ignored in overflow-clipped containers — when `max-h-*` was applied without an explicit height, `h-full` on the inner elements resolved to `auto`, so `object-fit: cover` + `object-position` had no effect and the image showed its natural top; fixed in `FocalImage.vue` by detecting the clipped case (`renderedH > containerH + 2`) and switching to `translateY` positioning so the focal point is always centred in the visible strip

- [x] deleting a spell or monster doesn't return to list, and orphaned images left in storage — navigate first (before mutateAsync) to avoid TanStack refetch-404 race; image URLs deleted from asset-images bucket on entity delete
