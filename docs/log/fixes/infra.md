# Fixes — Infrastructure

Resolved bugs in the **Infrastructure** area, newest first. Part of the Grimoire fix log — see the [log index](../index.md).

- [x] Egress/performance audit — the initial JS payload was **4.9 MB across 59 preloaded chunks on every page load**, and a large share of it was code nothing on the page could reach. Three independent causes. **(1) Vite 8 deprecated the function form of `manualChunks` and never consults it for virtual modules**, so Vite's `__vitePreload` helper (`\0vite/preload-helper.js`, needed by the entry and by every chunk containing a dynamic import) was folded into whichever feature chunk claimed it first — it landed in `model-viewer`, making the entry statically import **1 MB of Simulacrum-only 3D code** to reach a ~1 kB function. Migrated `build.rollupOptions.output.manualChunks` → `build.rolldownOptions.output.codeSplitting.groups` (rolldown-native, does see virtual modules) and pinned the helper to its own chunk. **(2)** `useCharacterSheetPdf` imported `jspdf` + `html2canvas` at module scope; made both `await import()` inside `exportPdf`. **(3)** Babel's shared runtime helpers were co-located by rolldown inside the `pdf` chunk, so `vendor` imported `_typeof` back out of it and dragged all ~590 kB of PDF code into the entry graph — pinned `@babel/runtime` to `vendor` so the edge only points the other way. Net: **4.9 MB → 3.3 MB initial JS (−33%)**, with `model-viewer` and `pdf` now genuinely async-only. (`vite.config.ts`, `src/composables/useCharacterSheetPdf.ts`)

- [x] Every permanently-mounted layout child fetched its full data set on **every** DM page load, for panels nobody had opened. `DefaultLayout` keeps ten generator panels plus the chat widget mounted so background AI generation survives navigation — but their `useQuery` calls run at setup regardless of the panel's open flag, so loading e.g. the Atlas also pulled the entire item catalogue *and* the SRD item table (`CampaignChat`), every NPC row (appearance/personality/backstory/stat_block — the widest rows in the schema, ×4 callers), all locations (×3), all factions, party, and members. Added an optional `enabled` getter to `useNpcs` / `useParty` / `useAllLocations` / `useLocationTree` / `useAllFactions` / `useCampaignMembers` and an `enabled` field to `UseItemsOptions`, and wired each always-mounted caller to its own open flag. Query keys are unchanged and shared, so a page that genuinely needs the data still fetches it exactly once, and TanStack retains the cached rows when a panel closes. (`src/components/chat/CampaignChat.vue`, `src/components/{npcs,quests,factions,locations}/*GeneratorPanel.vue`, `src/composables/{useNpcs,useParty,useLocations,useFactions,useCampaignMembers,useItems}.ts`)

- [x] Edge-function CORS allowlist only covered `localhost:5173`/`4173` — when Vite auto-incremented past a busy `5173` (no `strictPort`), the dev origin silently drifted to an unlisted port and every edge-function call (e.g. `api-key-vault`) failed preflight with an opaque "blocked by CORS policy" error. Added a fixed `https://grimoire.localhost` origin to `ALLOWED_ORIGINS` in `supabase/functions/_shared/cors.ts` so local dev has a stable allowed origin independent of whichever port Vite happens to land on. Requires redeploying edge functions to take effect (the file is bundled per-function). (`supabase/functions/_shared/cors.ts`)

- [x] "CORS errors" after the app-subdomain cutover were neither CORS nor cutover — two stacked bugs surfaced by the move. **(1) Every edge-function error path returned `Response`s without CORS headers** — supabase.co was always cross-origin (even from the apex), so any 4xx/5xx rendered in the browser as an opaque "blocked by CORS policy: No 'Access-Control-Allow-Origin' header" instead of its real message; the allowlist itself was correct and already deployed. Fixed structurally with `withCors(handler)` in `supabase/functions/_shared/cors.ts`: answers OPTIONS preflights centrally, stamps CORS headers on **every** response via `headers.set` (handler-supplied headers stay harmless), and catches uncaught exceptions into a CORS-carrying JSON 500 — no future `return new Response(...)` can reintroduce the class. **(2) The actual hidden failure**: `generate-chronicle-text` validated raw session notes against `AI_PROMPT_LIMIT_LONG` (2000 chars) — session notes are long-form by design; raised to a dedicated `AI_PROMPT_LIMIT_CHRONICLE = 10000` (server + `src/ai/utils.ts` mirror) with a client-side pre-check in `useChroniclerTextGeneration` that fails fast with a readable "trim your notes" message. Deployed as generate-chronicle-text v15; remaining functions swept onto `withCors` in a follow-up. (`supabase/functions/_shared/cors.ts`, `supabase/functions/_shared/ai-prompt.ts`, `supabase/functions/generate-chronicle-text/index.ts`, `src/ai/utils.ts`, `src/ai/useChroniclerTextGeneration.ts`)

- [x] Edge Function dependencies had silently diverged into two copies of `supabase-js` — 26 files floated on `https://esm.sh/@supabase/supabase-js@2` (resolving to whatever 2.x was latest, currently 2.110.2) while 7 `_shared` modules pinned `@2.43.0`. A single deployed function therefore loaded both, and every call passing a client from an `index.ts` into a `_shared` helper was a type error (`SupabaseClient<any, "public", ...>` vs `SupabaseClient<any, "public", any>`): 96 of them, which had buried two real runtime bugs (above). Floating `@2` also meant an upstream release could change a deploy with no code change. Fixed by adding `supabase/functions/deno.json` (the Supabase-documented top-level Deno config) with an import map pinning `@supabase/supabase-js@2.110.2`, `stripe@14.25.0`, and `std@0.208.0`, rewriting all 61 remote URL specifiers across 33 files to bare specifiers, and committing `deno.lock` for integrity-pinning. `deno check` across all 34 non-test files now passes clean. Also added `deno 2.9.2` to `.tool-versions`.

- [x] Marketing/commercial pages (`/`, `/pricing`, `/privacy`, `/terms`) overflowed the viewport but could not scroll — the first thing a logged-out visitor lands on. Global CSS sets `html, body { overflow: hidden }` so all scrolling must happen inside per-layout scroll containers, but `MarketingLayout.vue` rendered its slot in a plain `min-h-screen` div with no scroll container (unlike `DefaultLayout`/`PlayerLayout`/`AuthLayout`). Changed the layout root to `h-screen overflow-y-auto` so it scrolls; the `fixed inset-0` noise overlay stays pinned to the viewport. (`src/layouts/MarketingLayout.vue`)

- [x] Vercel production build failed with `ERESOLVE could not resolve` — `package.json` had `vite@^8.0.8` but `vite-plugin-pwa@1.2.0`'s peer dep range stops at `^7.0.0` (no 1.x release supports vite 8 yet, and the package hasn't been touched in ~5 months). Rather than pin vite back, replaced the plugin outright with a hand-rolled service worker + a tiny in-repo vite plugin (`swPlugin` in `vite.config.ts`, ~60 lines) that walks `dist/` at `closeBundle`, hashes the filename+size list, and substitutes the list + hash into `scripts/sw-template.js` to emit `dist/sw.js`. The template handles install (precache), activate (claim + GC old caches), and fetch (SPA-nav fallback to cached `/index.html`, cache-first for precached assets, passthrough for cross-origin / non-GET). `main.ts` now explicitly registers `/sw.js` in production (was auto-injected by the plugin before) and keeps the existing `controllerchange` → reload. Removed 310 transitive packages (workbox + its toolchain); kept PWA install and offline-shell behaviour byte-for-byte. Revisit if we ever need background sync / push / runtime caching strategies (`vite.config.ts`, `scripts/sw-template.js`, `src/main.ts`)

- [x] Saving data often fails silently, and chat pushes land in a different window than the one that triggered them — root cause: `navigator.locks` contention across multiple open tabs. Every mutation called `supabase.auth.getUser()` which acquires the lock and makes a network round-trip; when another tab held the lock (e.g. during token refresh) this blocked for up to 5s, causing saves to appear to do nothing. Fixed by replacing all `getUser()` calls with `getSession()` (reads cached token from localStorage, no lock, no network). Also fixed: `campaign_messages` lacked `REPLICA IDENTITY FULL`, so Supabase Realtime couldn't evaluate RLS on WAL events and silently dropped them; added realtime reconnect + visibilitychange re-fetch as belt-and-suspenders.

- [x] saving in general often seems to hang before even going to a network call. after a refresh it always works, no errors are logged — TanStack Query networkMode:'always' prevents save queuing when browser briefly reports offline on tab focus

- [x] infinite spinner / no network requests after idle — `onAuthStateChange` callback called `loadMembership()` (→ `supabase.from()` → `getSession()`) while supabase-js still held the exclusive `navigator.locks` lock for the auth state notification. Fix: make the callback synchronous, defer `loadMembership` via `setTimeout(fn, 0)` so it runs after the lock is released.

- [x] chatMarkdown tests never ran — jsdom not a declared dependency (irongollem/grimoire#488) — `src/lib/chatMarkdown.test.ts` opens with `@vitest-environment jsdom` (DOMPurify strips *all* tags under the repo-default happy-dom, which would fail the markdown-preservation test), but `jsdom` was never in `package.json`, so vitest failed to start that worker and the file silently never executed while the suite still reported green. Added `jsdom` as a devDependency (the docblock documents why happy-dom won't do). Suite now runs 68 files / 669 tests with zero unhandled errors (was 59 files + 1 silent error).
