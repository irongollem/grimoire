# Fixes — Items & Workshop

Resolved bugs in the **Items & Workshop** area, newest first. Part of the Grimoire fix log — see the [log index](../index.md).

- [x] Loot dropped into campaign chat lost its "grabbed by X" indicator after a player claimed part of it — on refresh the DM saw only "N remaining" with no sign anyone had grabbed anything. Not a persistence bug: the grab is durably written to `campaign_messages.metadata.claims` by the `grab_item_drop` RPC and correctly re-derived on load. The gap was purely in rendering. `ChatItemDropMessage.vue`'s stacked-drop branch surfaced claimant names **only** when the stack was fully exhausted (`quantity_remaining === 0` → "All claimed — by X"); while any quantity remained it rendered just the remaining count + grab buttons and dropped `meta.claims` entirely. This bit the encounter **edit** screen specifically, since its loot widget is the app's main source of quantity ≥ 2 stacked drops — a single-item drop grabs to `quantity_remaining === 0` and shows fine, but a partial grab of a stack showed nothing. Added a "Grabbed by …" line to the still-available branch backed by a `grabbedSummary` computed that aggregates per-grabber totals from `meta.claims` (a player can grab more than once → `Name ×N`). No DB/RPC change — the data was always there. (`src/components/chat/ChatItemDropMessage.vue`)

- [x] Item-drop claims delivered the item via a post-hoc client write — a lost-item window (#527 item 6, item half; **closes #527**). `claim_item_drop`/`grab_item_drop` stamped the drop but left the `party_inventory` (or `npc_inventory`) insert to a separate client write, so a tab close / network drop between the two marked the drop claimed while the item was never delivered. Folded the delivery into both RPCs (`20260712000001`) so stamping + insert run in one transaction: `claim_item_drop` inserts the party_inventory row (or npc_inventory when `p_npc_id` is set), and `grab_item_drop` delivers the grabbed quantity — auto-stacking onto an existing carried backpack/belt row of the same item, else inserting — all inside the locked claim. Identification/container flags are derived from the drop metadata (per #520): a non-mundane item lands unidentified. Insert authz is the same the client relied on (`party_inventory` insert = `is_campaign_member`, already checked; `npc_inventory` = `user_id = auth.uid()`). `CampaignChat`'s `handleClaim`/`handleGrab`/`handleClaimToNpc` now just call the RPC + invalidate; the post-hoc insert, stack-merge, and their now-unused imports are gone. Verified in rolled-back txs: a claim delivers 1 row (`qty=2`, `is_identified=false` for a rare item), two grabs stack into one row (`qty=4`, `remaining=1`), and the drop is stamped claimed — all atomic. Body-only DEFINER change (anon still revoked, `search_path=public`). Applied to remote. **All 6 items of #527 are now fixed.** (`supabase/migrations/20260712000001_claim_item_drop_folds_inventory.sql`, `src/components/chat/CampaignChat.vue`)

- [x] Inventory mediums — equip atomicity + crafting ruin rule (#527, 2 more items). (equip) `equipToSlot` split a stack with a `Promise.all` of a decrement + an insert — a failure between them lost or duped the item, and the slot's occupancy wasn't re-checked so a realtime race let two items share one slot. Now re-checks `slotItem(slot)` right before writing (aborts if filled) and runs the decrement then insert sequentially with a best-effort rollback (restore the quantity if the insert throws). (crafting ruin) `useCrafting` ruined only on fail-by-5+, contradicting the "Critical Failure" label — and a natural 1 with a high modifier succeeded. Per the owner's decision the outcome now ruins on a **natural 1 OR a miss of 5+** (`roll === 1 ? 'ruin' : diff >= 0 ? 'success' : diff <= -5 ? 'ruin' : 'fail'`), so a nat-1 auto-fails regardless of modifiers. `vue-tsc -b` ok. (`src/composables/useInventorySlots.ts`, `src/composables/useCrafting.ts`)

- [x] Inventory mediums — coin-drop clamping, carry-weight container math, add-item validation (#527, 3 of 6 items; issue stays open for the rest). (coin drop) A negative coin drop (`-5` PP) passed the send validation, the sender wasn't deducted (the `>0` guard), but `handleClaimCurrency` did `member.pp + meta.pp` → the **claimer lost 5 PP**; fractional amounts flowed straight into wallets. Clamped each coin to a non-negative integer at both the source (`sendCurrencyDrop`) and the credit (`handleClaimCurrency`). (carry weight) A container's OWN weight (e.g. a 25-lb chest) was never counted, and a `stored` container's contents still counted toward encumbrance; `totalCarriedWeight` now sums only carried containers (`location !== 'stored'`) and adds each one's own weight alongside its contents (contents stay 0 for extradimensional bags, but the bag itself weighs). Still open on #527: equip atomicity (needs an RPC), crafting ruin rule (nat-1 vs fail-by-5 — a game-balance decision), folding claim side-effects into the claim RPCs. `vue-tsc -b` ok. - [x] Chat/loot-chest claimed items arrived pre-identified and lost container behavior (#520, High; identification bypass). - [x] Player-to-player sale never paid the seller + claim was a check-then-write race (#512, critical — money vanished). A player→player sale ran entirely on the buyer's client: after stamping the offer sold via a direct `campaign_messages` UPDATE, the buyer credited the seller by UPDATEing the seller's `party_members` row — but `party_members` UPDATE RLS only allows the row's `owner_user_id` or the campaign DM, so a fellow player's write matched **0 rows** and the seller was never paid, while the buyer had already been charged and the item transferred. The claim itself was a client-side check-then-write race (two buyers could both pass the local `sold_to_user_id is null` check), and the buyer deduction used `Math.max(0, wallet − price)`, clamping a stale-cache overspend to 0 (paying less than the price). Fixed with one row-locked `SECURITY DEFINER` RPC `claim_player_offer(p_message_id, p_buyer_name, p_party_member_id)` (`20260711000008`) that, under `FOR UPDATE` on the offer: authorizes via `auth.uid()` + `private.is_campaign_member`; validates the offer is unclaimed (closes the double-claim race); checks buyer funds and **rejects if insufficient — no clamp** (closes #527 M1); debits the buyer, credits the seller, and transfers the item row with `is_attuned=false` (attunement never carries to a new owner — closes #527 M2); stamps `sold_to_user_id = auth.uid()`. A null `p_party_member_id` is a DM purchase (money from thin air, item deleted) and is gated on `private.is_campaign_dm`. `claimPlayerOffer` (`useCampaignMessages.ts`) and `handleBuyPlayerOffer` (`CampaignChat.vue`) now just call the RPC and invalidate the party/inventory caches; the seller's client sees their new balance via `usePartyLive` realtime. With the last direct-UPDATE claim path gone, the `campaign_messages_claim` policy (narrowed to `player_offer` in `20260711000002`) is dropped, closing the last hole where a member could PATCH an offer's `sold_to_*`/price fields. Verified in a rolled-back transaction: buyer 10→5 gp / seller 0→5 gp / item transferred un-attuned + un-equipped to the buyer; double-claim, insufficient-funds, and player-passing-null all correctly rejected. `get_advisors({security})` shows only the intentional `authenticated_security_definer` class shared by every claim RPC. `vue-tsc -b` clean. Applied to remote via `supabase db push`. (`supabase/migrations/20260711000008_claim_player_offer_atomic.sql`, `src/composables/useCampaignMessages.ts`, `src/components/chat/CampaignChat.vue`)

- [x] Players saw ~50 `party_inventory` requests in the network tab after someone reordered the inventory — three compounding causes: (1) `handleReorder` re-numbered every item (`i * 100`) and `useReorderInventoryItems` sent one PATCH per row, so the dragging client issued N requests; (2) each UPDATE emitted a realtime `postgres_changes` event and `useCampaignLiveSync` called `invalidateQueries` immediately per event, so every connected client refetched the inventory once per row; (3) `PlayerInventoryView`/`DashboardView` mounted a second redundant subscription (`useInventoryLive`) on top of the layout-level live sync, doubling the refetches.
