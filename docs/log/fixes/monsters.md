# Fixes — Monsters & Bestiary

Resolved bugs in the **Monsters & Bestiary** area, newest first. Part of the Grimoire fix log — see the [log index](../index.md).

- [x] Roster NPCs in an encounter no longer got marked dead when they fell, nor revealed to players when the party saw them — two automated steps that had quietly stopped working. Root cause was a gap, not a break: the only surviving discovery path (`useAutoDiscoverMonsters`, on reveal-cycle + Go Live) filters on `c.monster_id`, but roster NPCs run as `type: "monster"` **with `npc_id`, never `monster_id`**, so both the reveal and the dead-marking slipped through every filter. `git log -S` across all of `src/`, migrations and edge functions confirmed NPC dead-marking had in fact never been wired anywhere. Fixed **live and event-driven** (the moment it happens, not at conclusion — mirroring monster discovery): a `watch` over the NPC combatants in `EncounterRunner.vue` reacts to two events via `src/lib/npcEncounterSync.ts` (`buildNpcSyncUpdate`, pure + 9 unit tests). the builder takes the NPC's current `{ seen, died }` state. **Reveal always requires being seen**: only a token at `reveal_state === "revealed"` joins the party's seen list, via a widening union on `npcs.player_visible_to` (+ `player_visible_fields` gains `name`/`portrait`, mirroring `NpcRevealSheet`; the reveal toggle already renders for any `type === "monster"` combatant, so roster NPCs are cyclable hidden → unseen → revealed just like monsters). **Death is a world fact**: a token at 0 HP is written `status: "dead"` seen-or-not — so a hidden NPC that dies is recorded dead but **not** disclosed; a seen one that dies is marked dead **and** revealed (with the `status` field so the death shows). `buildNpcSyncUpdate` returns `null` on a no-op and the watcher patches the local `store.availableNpcs` snapshot after each write, so writes happen only on real transitions (a reveal→hide→reveal or heal→re-kill cycle won't spam). `handleEndCombat` reverted to its player-only sync. (`src/lib/npcEncounterSync.ts`, `src/lib/npcEncounterSync.test.ts`, `src/components/encounters/EncounterRunner.vue`)

- [x] Clicking a monster's ability score or saving throw on `/monsters/:id` did nothing — the hover tooltip appeared, so the control looked alive, but no roll ever fired. `AbilityScoreTable` is emit-only: its buttons do dispatch (the `v-roll-mode` directive attaches a real click listener) and emit `roll-ability`/`roll-save`, relying on the parent to perform the roll. `StatBlockPanel` rendered the table with **no listeners at all**, so every click was silently discarded — and since `StatBlockPanel` is the shared stat block, the same dead click hit five surfaces: monster sheet (desktop + mobile), NPC detail (desktop + mobile) and the wildshape preview lightbox. The encounter runner's panels wire the emits themselves, which is why saves rolled there and nowhere else. Fixed in `StatBlockPanel` rather than per consumer: it now handles both emits through `usePromptedRoll` (d20 + bonus, posted to campaign chat) and takes a `name` prop so the roll is attributed to the creature rather than the DM. `PlayerBestiaryView`'s lightbox used `AbilityScoreTable` directly with the identical gap and got the same treatment via a local `rollCheck` mirroring its existing `rollAttack`. Right-click / long-press advantage-disadvantage now works too: the picker was already enabled (the directive treats an undefined `enabled` as on) but equally inert, so `:roll-mode-picker` is now explicit and the chosen mode is threaded through. Audited all 8 `AbilityScoreTable` consumers — none is left with a dangling emit. (`src/components/common/StatBlockPanel.vue`, `src/views/play/PlayerBestiaryView.vue`, + 5 call sites passing `:name`)

- [x] Wild Shape showed "no eligible forms" for every druid below level 8 — third distinct piece of #553-reseed fallout (after the stale discovery slugs and broken projections below). The Open5e v2 monster mapper mapped `speed_all` in preference to `speed` (`toSpeedString(monster.speed_all ?? monster.speed)`), but v2's `speed_all` bakes in **derived** half-speeds — every walker gets `swim`/`crawl` at walk/2 — so every reseeded beast's stat block gained a swim speed it doesn't have RAW ("Cat — 40 ft., swim 20 ft., climb 30 ft."). `isEligibleWildshapeForm` correctly excludes swim/fly forms below druid level 8, so the derived swim made **every** beast ineligible and the picker rendered empty (a Moon druid 3 saw nothing instead of Brown Bear/Ape/Wolf/…). Also corrupted the displayed stat blocks. Fixed by preferring native `speed` (falling back to `speed_all` only when absent), pinned by two mapper regression tests, and reseeding `srd_monsters` (656 rows, art backfill intact) — verified Cat back to "40 ft., climb 30 ft." and 20 eligible forms for the reporting druid. (`src/lib/open5eMonsterImport.ts`, `src/lib/open5eMonsterImport.test.ts`)

- [x] Multiclass Druid had no Wild Shape tab and the CR cap used total level (#518, High). `PlayerCharacterView` derived all Druid state from the legacy `member.class`/`subclass`/`level` strings: `isDruid` read `member.class`, so taking Druid as a *second* class (the level-up "add" op never rewrites `member.class`) hid the Wild Shape tab and left `wildshapeForms` empty; `wildshapeMaxCr` used the character's **total** level, so a Fighter 6 / Druid 2 got CR 1½ instead of CR ¼; and `isCircleOfMoon` read only the legacy subclass. Fixed by sourcing druid-ness, druid *class* level, and subclass from the `character_classes` rows via `useCharacterClasses(resolvedMemberId)` (a `druidRow` computed matching `class_name` includes "druid"), with the legacy fields as fallback — the same pattern `PlayerFeaturesTab.classLevel()` already uses for Barbarian/Monk/Fighter/Artificer. `wildshapeMaxCr`, `wildshapeMaxUses`, `canWildshape`, and the `isEligibleWildshapeForm` level gate now all use `druidLevel`. `vue-tsc -b` ok. (`src/views/play/PlayerCharacterView.vue`)

- [x] Player-visibility payload leak — custom monsters (#507 part 2, security). `monsters_player_select` (`20260507000013`) granted any campaign member the WHOLE custom-monster row as soon as **any** `discovered_monsters` row existed in the campaign — ignoring both this player's `visible_to` and the discovery's `reveal_stats` flag. So a player received the full `stat_block`, DM `description`, and DM `notes` of every custom monster discovered by anyone (mineable in devtools even for creatures whose stats the DM never revealed and which were shared with a different party member); the player bestiary sourced rows via the shared `useAllMonsters` base `select *`, so RLS was the only gate. Fixed exactly like the puzzle/NPC projections in `20260711000011_player_visible_monsters_projection.sql`: new `get_player_visible_monsters(p_campaign_id)` SECURITY DEFINER function returns only the custom monsters this player may see (discovered for them — `visible_to` null = whole party or contains their `party_member_id` — plus any pinned as a wild-shape form for them), **nulls `stat_block` unless the discovery `reveal_stats`**, and strips DM `notes`/`description`; the player branch of `monsters_player_select` is dropped (now owner-only) so the base table is no longer a devtools bypass. Pinned forms are returned with full stats (the DM shared them for wild-shape). SRD monsters (`srd_monsters`, public reference) are unaffected. Client: new `usePlayerVisibleMonsters` (SRD + projection custom; falls back to the base list in DM-preview mode, which the DM owns and needs for the "share all eligible beasts" affordance) replaces `useAllMonsters` in `PlayerBestiaryView`, `usePlayerEntityMentionItems`, and `PlayerJournalView`. Verified against live data by impersonating four players in a rolled-back tx: a member in `visible_to` sees the monster with `stat_block`/`notes`/`description` all nulled (reveal_stats=false); a member not in `visible_to` and an unlinked member see only whole-party discoveries; a non-member sees nothing; and a player's direct base-table read of a non-owned custom monster now returns 0 rows under RLS. `get_advisors({security})` shows only the intentional `authenticated_security_definer` class (anon revoke applied, no new `search_path` finding); `vue-tsc -b` ok. Applied to remote via `supabase db push`. Parts 3–8 of #507 (quest objectives, quests, locations, NPC over-return, item `dm_notes`, drop metadata) remain open. (`supabase/migrations/20260711000011_player_visible_monsters_projection.sql`, `src/composables/useMonsters.ts`, `src/views/play/PlayerBestiaryView.vue`, `src/views/play/PlayerJournalView.vue`, `src/composables/usePlayerEntityMentionItems.ts`)

- [x] Monsters/NPCs with a dice-based `hit_points` (e.g. spore servant `"2d8+2"`) spawned into encounters with a wildly wrong max HP — a spore servant showed **2 HP instead of ~11**. `stat_block.hit_points` is stored as a pure dice expression, but every combatant-spawn site computed max HP with `parseInt(String(hit_points).split(" ")[0], 10)`, which reads only the leading integer: `parseInt("2d8+2")` → `2`. It only ever produced a sane number for the `"11 (2d8+2)"` format where an average leads. Fixed by adding a shared `hitPointsToMax(hitPoints, fallback)` helper in `src/lib/dice.ts` that reuses the existing `parseExpression` + `averageExpression` (statistical average, 11 for `2d8+2`; handles the `"N (dice)"` wrapper, flat numbers, negative and compound modifiers; falls back on unparseable/missing input), and replacing the buggy idiom at all seven sites: `encounterRun.ts` (`addMonster`/`addNpc`/`spawnFromDef`), `EncounterRunView.vue` (monster + NPC hydration), the two wildshape handlers (`RunnerPcPanel.vue`, `PlayerCharacterView.vue`), and `CompanionForm.vue`'s `parseHpNum`. Kept the average (not a live roll) to match prior behavior. Regression + edge cases covered by new `src/lib/dice.test.ts` (7 tests). Note: only affects newly-spawned combatants; monsters already persisted at the wrong HP in a live encounter must be re-added. (`src/lib/dice.ts`, `src/stores/encounterRun.ts`, `src/views/encounters/EncounterRunView.vue`, `src/components/encounters/RunnerPcPanel.vue`, `src/views/play/PlayerCharacterView.vue`, `src/components/party/CompanionForm.vue`, `src/lib/dice.test.ts`)

- [x] Encounter runner "Choose Form" on a druid toggled the button to "Cancel" but showed no form list and no message (irongollem/grimoire#503) — the picker was an **inline block** inside the detail panel, whose `.detail-panel`/`.panel-shell` ancestors are `overflow: hidden`, so the (correctly populated) list was clipped out of view. Confirmed it wasn't data: queried the live DB + simulated the DM's RLS SELECT — all 46 campaign discoveries and ~18 eligible beasts were present. Fixed by teleporting the picker to `<body>` as a `position: fixed` floating popover anchored to the toggle button, immune to ancestor clipping: new pure `src/lib/floatingPosition.ts` (`computeAnchoredPosition`, 5 tests) + `src/composables/useAnchoredPopover.ts` (reposition on scroll/resize, outside-click + Escape dismiss). While in there: split the picker into available (discovered/pinned) vs pinnable sets with an inline "📌 Pin a form" affordance (`useTogglePinnedForm`) so an empty list isn't a dead end, and extracted the CR/speed/beast eligibility rules — previously copy-pasted across `RunnerPcWildshape.vue`, `PlayerCharacterView.vue`, `PlayerBestiaryView.vue` — into a tested `src/lib/wildshape.ts` (8 tests). NOTE: the same inline-inside-`overflow-hidden` clip risk applies to `ConditionPicker.vue` (uses `position:absolute; z-50`) — `useAnchoredPopover` is the reusable fix to apply there next.
