# Fixes — NPCs & Companions

Resolved bugs in the **NPCs & Companions** area, newest first. Part of the Grimoire fix log — see the [log index](../index.md).

- [x] Player world-locations NPC lightbox duplicated the shared component (#530 item). `PlayerLocationsView` had an inline NPC lightbox that re-implemented `PlayerPartyNpcLightbox` minus its badges / connection note / rating (a component-granularity violation), and it also rendered a name-hidden NPC without the `"???"` treatment the shared one has. Replaced the ~40-line inline block with `<PlayerPartyNpcLightbox :npc="selectedNpc" @close="…" />` (already used by `PlayerPartyView` + `PlayerLocationDialog`); removed the now-unused `getNpcDisplay*` imports. `vue-tsc -b` ok. (`src/views/play/PlayerLocationsView.vue`)

- [x] Player world-browsing — DM-preview NPCs empty + location "Share linked NPCs" did nothing (#528, the two remaining DB items; closes it). Both fixed by rewriting `get_player_visible_npcs` (`20260711000021`). (1) **DM Preview showed zero NPCs**: the row gate required `cm.party_member_id = any(player_visible_to)`, but a DM's `campaign_members` row has `party_member_id = null`, so `useSharedNpcs` returned `[]` in preview (People section, atlas "People in the Area", location-dialog NPCs). Added a `p_preview_member_id` param + an `is_campaign_dm` branch that projects exactly what the previewed member sees; `useSharedNpcs`/`useSharedNpcsByLocations` now pass `ui.dmPreviewPartyMemberId` (and key on it). (2) **"Share linked NPCs" location toggle did nothing** unless each NPC was also individually shared, contradicting `worldbuilding-atlas.md:39`. Per the user's decision, an NPC is now also visible when its OWN location (direct `location_id` match — **not** sublocations, so a hidden NPC in a child location like an assassin upstairs stays hidden) has `is_npcs_shared` on and is shared with the player. Field-level gating (`player_visible_fields`) is unchanged — flagged for the user: a location-shared NPC whose fields the DM hasn't shared still surfaces as a gated/unknown entry (the same-location-hidden case wants more design thought). Documented the new path in `npcs-visibility.md`. Verified by impersonation in a rolled-back tx: a player who is location-shared but NOT individually shared sees the NPC (via_location=1), turning the toggle off removes it (0), and DM-preview-as-member returns 58 NPCs (was 0). Recreated function keeps `search_path=public` + `anon` EXECUTE revoked (only the intentional `authenticated_security_definer` class); `vue-tsc -b` ok. Applied to remote. (`supabase/migrations/20260711000021_npc_projection_location_share_and_dm_preview.sql`, `src/composables/useNpcs.ts`, `src/manual/npcs-visibility.md`)

- [x] Player-visibility leak — NPC projection over-returned location + tags (#507 part 6, security). `get_player_visible_npcs` (`20260613000001`) gates most columns on `player_visible_fields`, but returned `location_id` and `tags` unconditionally: `location_id` leaked WHERE a shared NPC is even when the DM left the "Location" toggle off (`NPC_PLAYER_FIELDS` has a `location` key), and `tags` (DM categorisation with no player-facing toggle at all, never shown in a player view) shipped every time. Fixed in `20260711000015_npc_projection_gate_location_tags.sql` — a `create or replace` that gates `location_id` on `'location' = any(player_visible_fields)` and nulls `tags`; the rest of the body is byte-for-byte the original. The `p_location_ids` filter still uses the raw `n.location_id` inside the subquery, so `useSharedNpcsByLocations`/the player atlas keep working — only the OUTPUT is gated, so an NPC with the toggle off simply isn't pinned to its location in `PlayerLocationsView` (correct). No client change. Verified by impersonation: a shared NPC with the location toggle OFF now returns `location_id` null + `tags` null, while an NPC with the toggle ON still returns its `location_id`. Signature/grants/search_path unchanged (no new advisor surface). Applied to remote. **This closes #507 — all eight sub-leaks (puzzles, monsters, quest objectives, quests, locations, NPC over-return, item dm_notes, unidentified drops) are fixed.** (`supabase/migrations/20260711000015_npc_projection_gate_location_tags.sql`)

- [x] Player People (`/play/party`) tab crashed to a white screen when the campaign held an NPC whose name isn't player-visible. The server projection `get_player_visible_npcs` returns `name = null` in that case, but the shared `Npc` type declared `name: string` and `getNpcDisplayName()` returned `string`, so `PlayerPartyView`'s `sortedNpcs` comparator called `getNpcDisplayName(a).toLowerCase()` on a value the compiler swore was a string — at runtime it was `null`, `Array.sort` threw `Cannot read properties of null (reading 'toLowerCase')`, and the whole view blanked. Root cause was the lying type, not a missing guard. Fixed by making `getNpcDisplayName()` honest — param `name: string | null`, return `string | null` (no `?? ""` coercion, which would just re-hide the absence and invite the same class of bug elsewhere) — which made `vue-tsc` flag every consumer that had assumed a guaranteed string. The two unsafe string-op sites in `PlayerPartyView` were rewritten to handle null (sort: nameless NPCs sort last; search: skip when null); the ~7 leaf display sites resolve null to the codebase's existing `"???"` "name hidden" marker at the binding. (`src/lib/npcDisplay.ts`, `src/views/play/PlayerPartyView.vue`, `NpcList.vue`, `NpcDetailMobile.vue`, `PlayerNpcCard.vue`, `PlayerPartyNpcLightbox.vue`, `EncounterNpcLightbox.vue`, `PlayerLocationsView.vue`, `PlayerQuestDetailView.vue`)

- [x] NPC relevance stars were fiddly/unresponsive on iPad PWA (fine with a mouse) — the ★ glyphs were bare ~1rem text buttons with no padding, far below the ~44px touch-target guideline, so taps missed or hit the neighbouring star; rapid taps could also trigger iOS double-tap zoom and text selection. The star row was also copy-pasted in three places (PlayerNpcCard, PlayerPartyNpcLightbox, EncounterNpcLightbox), and the PlayerPartyNpcLightbox copy had a latent display bug: it read `ratingMap` from `usePlayerNpcRatings()` without passing an NPC list, so the map was always empty and the stars never rendered as filled there. Extracted a shared `NpcRatingStars.vue` (props: `npcId`, `size`) that adds `touch-manipulation` + `select-none`, pads each star, and bumps glyph size + padding on coarse pointers via Tailwind `pointer-coarse:` variants; all three call sites now use it and the lightbox rating displays correctly. (`src/components/play/NpcRatingStars.vue`)
