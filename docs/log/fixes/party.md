# Fixes — Party & Characters

Resolved bugs in the **Party & Characters** area, newest first. Part of the Grimoire fix log — see the [log index](../index.md).

- [x] `parseArmorClass` took the *first* digit sequence anywhere in the free-text `armor_class` string as the armor's base AC — a DM typing "+1 (12 + Dex modifier)" for a custom +1 studded leather got base **1**, so an `ac_formula: "armor"` character wearing it showed AC ≈ 3 across the tracker, runner and sheet export. The base is now anchored to a *leading* integer (`/^\s*(\d+)/`); unanchored strings return `null`, which safely falls back to the member's stored `ac` instead of deriving garbage. Tests added for both the prefix-bonus and suffix-bonus shapes. (`src/lib/armorAc.ts`, `src/lib/armorAc.test.ts`)

- [x] Removing a player from campaign settings orphaned their character — it kept showing on the dashboard Party grid and party tracker. **Player** (`campaign_members`) and **character** (`party_members`) are separate rows/caches; the "Remove Player" action only deleted the membership, leaving the linked/owned character (e.g. "zzzzzzzzzzz") behind with no owner but still rendered (both views read straight from `party_members`). Nothing tied the two deletions together, so every DM removing a player hit it. Fixed in the flow, not the DB: the "Remove Player?" dialog now computes the player's characters (their `party_member_id`-linked one plus any `owner_user_id`-owned) and shows a **checked-by-default** "Also delete their character(s) …" checkbox; on confirm it removes the membership then deletes those characters via `useDeletePartyMember` (which also cleans up portrait storage, invalidates `["party"]`, and live-syncs the removal to other clients). Unchecking keeps the character as an orphan NPC by choice. To close that loop (and clean up characters orphaned by past removals — the bug predates the fix), the Members tab now also renders a **"Characters without a player"** section listing any party character not attached to a member (unlinked + owner is null or a non-member, excluding DM-managed offered characters), each with a direct **Remove** (confirm via `useConfirm`). So an orphan is always visible and removable from the same screen where players are managed — no more hunting through Party → Edit → Remove. `vue-tsc` green. (`src/components/campaign/MembersTab.vue`)

- [x] Level-up could leave a character half-leveled. `useLevelUpConfirm.confirm()` applied a single level as 7+ separate, non-transactional Supabase writes across three tables — `updateMember` (party_members) → `addCharacterClass`/`updateCharacterClass` (character_classes) → N× `addSpell` (character_spells, once per picked spell/cantrip/subclass-grant/invocation) → a **second** `updateMember` for `level_choices`.
