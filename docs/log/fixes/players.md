# Fixes — Player Portal

Resolved bugs in the **Player Portal** area, newest first. Part of the Grimoire fix log — see the [log index](../index.md).

- [x] Every player-portal locations read had been failing since July 26 — the third stale-projection incident, and the first one the guard caught — `get_player_visible_locations` is a `returns setof locations` projection with a hand-maintained positional column list, and two later migrations widened `locations` without recreating it: `20260726000001` (era_start/era_end, the Atlas time-bound-locations feature) and `20260728000001` (audio_theme, soundboard phase 5). SQL function bodies only validate on execution, so every call threw `42P13 return type mismatch` — players lost shared locations, location detail and map pins, while the DM atlas (base-table reads) kept working, exactly the silent split that hid the July 20 monsters/items incident. This time the pgTAP guard (`player_projections.test.sql`, added with that fix) flagged it in the spell-database CI job on the next push to main rather than via player reports. Fixed by `20260729000001` recreating the projection with the full current row — era bounds pass through (shared chronology), `audio_theme` nulled as DM-only wiring like `notes` before it — applied to production and verified: the `42P13` is gone and a sweep executing every setof-table function in `public`/`private` against the live schema finds zero remaining stale projections. (`supabase/migrations/20260729000001_recreate_player_visible_locations_after_era_bounds.sql`)

- [x] A character sheet's "Choices" card showed a bogus "Noncantrip Spell Turn" row whose value was a raw `<encounter-uuid>:5:4` string — visible to the player on their own `/play` sheet. `PlayerChoicesCard.vue` rendered every `class_choices` entry through a **blacklist** (`key !== "metamagic_options" && …`) and dumped anything not excluded via `String(value)`, with the key title-cased into a label. But `class_choices` is a loose JSONB bag that also holds transient combat bookkeeping written by the spellcasting engine: `private.active_turn_key(campaign_id)` (`encounterId:round:combatantIndex`) is stashed under `noncantrip_spell_turn` / `bonus_action_spell_turn` / `spell_slot_cast_turn` / `arcane_apotheosis_turn` to enforce the one-leveled-spell-per-turn rule (migrations `20260720000021`, `20260720000039`; reset by `20260720000045`, which documents the convention: *any key ending in `_turn` is turn-scoped*). None were in the blacklist, so the marker leaked as a raw row. Flipped the fragile blacklist onto that same DB convention: extracted `isInternalChoiceKey` (`src/lib/classChoices.ts`, 4 unit tests) which hides any `*_turn` key plus the dedicated-card/applied keys, so no future engine bookkeeping key can ever leak again. No spell-name resolution was involved — the value was never a spell. Fixed two adjacent leaks in the same card while here: (a) `class_choices.feats` and custom `feature_pick` step values both store `class_features` UUIDs and were rendered raw — the card now resolves them to feature names via `useAllFeatures` (players can read system + their DM's features under the `class_features_select` policy; unresolved ids fall back gracefully); (b) custom `spell_pick` steps double-rendered — once (correctly) in `PlayerSpellChoices` and again as a raw value here — so `PlayerFeaturesTab` now passes the spell_pick step keys as `exclude-keys` and the card drops them. (`src/lib/classChoices.ts`, `src/lib/classChoices.test.ts`, `src/components/player/PlayerChoicesCard.vue`, `src/components/player/PlayerFeaturesTab.vue`)

- [x] Player Bestiary showed every discovered creature as "Unknown creature" — two independent bugs stacked, both fallout from earlier id/schema migrations that missed a dependent object. **(1) Stale discovery slugs**: the SRD v2 identity transition (#553, `20260722000002`) retired the v1 `srd_monsters` ids and remapped `character_spells`/`spell_cast_records`/`companions` (and `20260722000004` the art tables) — but missed `discovered_monsters.srd_slug`, so all 30 discovered SRD creatures pointed at retired ids. Fixed by `20260724000004` reapplying the same `'srd_' || old_id` prefix rule, scoped to unresolved slugs whose prefixed form resolves (idempotent; 30/30 remapped, 0 left). **(2) Broken player projections**: `get_player_visible_monsters` and `get_player_visible_items` are `returns setof <table>` with hand-maintained positional column lists; migration `20260720000018` widened `monsters` and `items` (versioning columns; `items.mastery` followed in `20260722000001`) without recreating them, so BOTH functions had been failing at runtime with `42P13 return type mismatch` since July 20 — silently breaking every real-player surface that resolves custom monsters (bestiary names, wild-shape eligible forms) or vault items, while DM preview (which reads the base tables) kept working, which is why it went unnoticed. Fixed by `20260724000005` recreating both with the full current row (gating logic unchanged; `lair_location_id` nulled as DM-only). **Structural guard**: new pgTAP test `supabase/tests/player_projections.test.sql` EXECUTES (limit 1) every setof-table function in `public` — SQL function bodies are only validated on first execution, so neither `create or replace` nor a LIMIT-0 plan catches the drift — meaning the next table widening that forgets its projections fails the spell-database CI job instead of production, with zero per-function registration. (`supabase/migrations/20260724000004_remap_discovered_monsters_srd_v2_ids.sql`, `20260724000005_fix_stale_player_projections.sql`, `supabase/tests/player_projections.test.sql`)

- [x] Tapping a revealed enemy in the player's encounter panel did nothing — no lightbox, so players couldn't enlarge a foe's portrait to read her face mid-combat. `PlayerEncounterPanel` was the only player-facing component still resolving NPCs through the DM-only `useNpcs()` raw `npcs` select; its `npcs_player_select` RLS policy only returns NPCs that list the tapping player in `player_visible_to`, which is the "party has met them" roster axis — *not* the encounter `reveal_state` axis. An enemy the DM revealed only inside the fight therefore came back empty, `find()` returned undefined, and `onCombatantClick` fell out of its `if (npc)` with nothing selected: a silent no-op. (It also leaked DM-only columns and the true identity of disguised NPCs for any NPC that *was* on the roster, since it bypassed the `get_player_visible_npcs` projection every other player view uses.) Fixed by (1) switching to `useSharedNpcs()` so met NPCs render through the projection, and (2) adding a fallback so a tap can never be a no-op: unmet NPCs and monsters now open `EncounterCombatantLightbox`, which renders name + portrait + focal point straight off the live combatant (the DM already authorised visibility via `reveal_state`, and it's the same data the row thumbnail draws) with a notes widget keyed on `npc_id`/`monster_id`. Dropped the old `monster_id` precondition too, so ad-hoc monsters spawned without a library row enlarge as well, and the lightbox now prefers a wildshaped combatant's beast image so the enlarged picture matches the tapped row. While in there, collapsed the near-duplicate `EncounterNpcLightbox` into `PlayerPartyNpcLightbox` (they differed only in prop type and a loading skeleton) and renamed it `PlayerNpcLightbox` now that party, atlas, location and encounter all share it; `EncounterMonsterLightbox` → `EncounterCombatantLightbox`. Every visible row is now `cursor-pointer`, matching the fact that all of them open something.
