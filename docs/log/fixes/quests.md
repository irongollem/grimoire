# Fixes — Quests

Resolved bugs in the **Quests** area, newest first. Part of the Grimoire fix log — see the [log index](../index.md).

- [x] Player-visibility payload leaks — quest objectives + quests (#507 parts 3 & 4, security; genuine DM narrative secrets). (1) **Secret quest objectives shipped** — `quest_objectives_player_select` gated only on the *quest* being player-visible (`q.player_visible_to`) and never checked the objective's own `is_player_visible` flag, so hidden objective text ("the informant is the killer") reached players of any quest they could see. (2) **Quest DM `notes` shipped** — `quests_select` handed the whole quest row (incl. DM `notes`, Tiptap JSON the player UI never renders) to any player in `player_visible_to`. Fixed in `20260711000012_player_visible_quests_projection.sql`: new `get_player_visible_quests(p_campaign_id, p_quest_id)` SECURITY DEFINER projection nulls `notes` and gates rows on the player's `player_visible_to`; the player branch of `quests_select` is dropped (now owner-only) so the base table can't be mined via devtools; `quest_objectives_player_select` now also requires `is_player_visible`. Dependency wrinkle handled: `quest_objectives_player_select` and `quest_refs_player_select` subquery `quests` in their RLS predicate (itself subject to quests RLS), so with quests now owner-only those subqueries would return nothing and players would lose *all* objectives/refs — the quest-visibility check moved into a `private.is_quest_player_visible(quest_id)` SECURITY DEFINER helper (per the RLS-helper convention; not exposed by PostgREST) that bypasses quests RLS. Client: `usePlayerVisibleQuests` (list) + new `usePlayerVisibleQuest` (detail) route through the RPC; `PlayerQuestDetailView` switched from `useQuest`→`usePlayerVisibleQuest` (and its `useMonsters`→`usePlayerVisibleMonsters`, a straggler from part 2 that would otherwise resolve monster-ref names to "???"). Verified by impersonating players in a rolled-back tx: a member in `visible_to` gets the quest with `notes` null, sees only 2 of 5 objectives (3 secret ones hidden), keeps its 1 ref; an unlinked member sees the quest not at all and 0 objectives; a player's direct base-table `quests` read returns 0 rows. `get_advisors({security})` clean (only the intentional `authenticated_security_definer` class; the private helper is unexposed); `vue-tsc -b` ok. Applied to remote. (`supabase/migrations/20260711000012_player_visible_quests_projection.sql`, `src/composables/useQuests.ts`, `src/views/play/PlayerQuestDetailView.vue`)

- [x] Player-journey audit — quest description + membership live-sync. (1) **Quest rich-text description never shown to players (#525)** — `PlayerQuestDetailView` rendered only `summary`; the full narrative `description` (Tiptap JSON, player-facing) was never surfaced despite being listed in the player-portal doc. Added a `RichTextViewer` block after the summary (`description` is player narrative, distinct from DM-only `notes` which stays unrendered; the `notes` payload leak is separate, #507). (2) **`campaign_members` missing from `useCampaignLiveSync` (#535, partial)** — added a `campaign_members` realtime handler invalidating `["campaign-members"]`, so a player renaming themselves (or being added/removed) propagates to every member's party/chat views without a manual refetch. The eject-on-removal half (redirect a just-removed player) is left open: realtime DELETE only carries the deleted row's PK unless the table is set to full replica identity, so reliably matching the current user's own removed row needs that config first. `vue-tsc -b` clean. (`src/views/play/PlayerQuestDetailView.vue`, `src/composables/useCampaignLiveSync.ts`)
