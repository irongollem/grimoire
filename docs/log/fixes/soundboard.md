# Fixes — Soundboard

Resolved bugs in the **Soundboard** area, newest first. Part of the Grimoire fix log — see the [log index](../index.md).

- [x] Restarting a live generator layer orphaned its timer, firing the sound on two schedules (#572) — `playAmbientPlaylist` built a fresh `SceneGenerator` and `sceneGenerators.set(id, gen)` over the top of any existing entry, but never cleared the outgoing object's `setTimeout`. The map lookup that `pauseGenerators`/`stopGenerators` use then only ever found the new object, so the old timer kept firing with nothing able to cancel it — a one-shot sounding at random intervals for the rest of the session, surviving pause, stop and scene change. Reachable when the same sound appeared twice in one scene's track list; the ordinary path was covered because starting a scene stops the previous one first. Surfaced by extracting the schedule into `src/lib/sceneGenerators.ts`, where a pool with an injectable clock and RNG made the case testable at all — the guard now clears the previous timer before re-scheduling. (`src/lib/sceneGenerators.ts`, `src/stores/soundboard.ts`)

- [x] `playAmbientPlaylist` shadowed the generator pool with a local variable of the same name (#572) — the local `const generators: Record<string, boolean>` mapping sound ID to "is this a generator layer" hid the store-level pool inside that function, so calls meant for the pool resolved to a plain object. Caught by the compiler during the phase-2 extraction rather than at runtime; renamed to `isGenerator`. (`src/stores/soundboard.ts`)

- [x] Widget claimed "No sounds playing" over a running scene, and hid Stop All with it (#572) — the empty state, the Stop All button and the nav badge all judged silence from `playbackStates` alone. A running playlist has no per-sound state of its own, and **generator layers never create one at all** since they fire one-shots directly — so a scene of nothing but generators reported an idle board while audibly playing. The Stop All case was the damaging one: audio running with no way to stop it from the widget. Adds `hasActiveAudio` (does anything at all make noise, accounting for unpaused playlists) and `activeAudioCount` (how many distinct things, counting a scene as one item rather than as its layers, since a badge reading "3" for a three-layer tavern is noise). (`src/stores/soundboard.ts`, `SoundboardWidget.vue`, `SoundboardWidgetToggle.vue`)

- [x] Spotify connect returned a bare 403 — root cause: the developer app declared only **Web API**, not **Web Playback SDK** (#574). Spotify used to present a single "Web" option under "Which API/SDKs are you planning to use?" and later split it in two; apps created before the split were left declaring Web API alone. We use both — `/v1/me` and playback endpoints via Web API, plus `sdk.scdn.co/spotify-player.js` for the actual player — so the moment the SDK was involved the request was refused, with `content-length: 0` and no explanation. Ticking Web Playback SDK resolved it. Setup instructions in `SpotifyTab` now spell out both easily-missed steps (declare both surfaces; add yourself under User Management), and the 403 hint in `SpotifyErrorBanner` / `readSpotifyError` names the API/SDK declaration first, since it is the one that catches out every pre-split app. Earlier suspicion that legacy Facebook-linked accounts could not be allowlisted was a red herring. (`src/components/campaign/SpotifyTab.vue`, `src/lib/spotifyAuth.ts`)

- [x] Spotify connection errors only appeared in the floating widget (#574) — `playError` was rendered solely inside `SoundboardWidget`, so a failure on the `/soundboard` page was invisible unless the DM happened to have the widget open. Extracted `SpotifyErrorBanner.vue` and mounted it in **both** surfaces. The banner also translates the two failures whose fix lives entirely outside this codebase into the action that resolves them: "Not allowed" → close the Spotify desktop app; 403 → add the signing-in account under User Management in the Spotify developer dashboard, since owning the app is not enough. That second case is the real-world one — a long-running app with an empty user list worked for years because Development Mode owners had implicit access, then began returning `403` on `GET /v1/me` once Spotify applied its stricter Development Mode rules to existing integrations on 9 March 2026 and the pre-existing token finally expired. (`src/components/soundboard/SpotifyErrorBanner.vue`)

- [x] Spotify vanished without trace on campaigns that had no Client ID — the connect control was wrapped in `v-if="spotifyStore.isEnabled"`, which is false whenever the active campaign has no `spotify_client_id` (Spotify is per-campaign BYOK). A DM who switched to an unconfigured campaign saw no Spotify UI at all and no hint that the feature existed or how to turn it on, which reads as a broken build rather than a missing setting. DMs now get a dashed "Set up Spotify" link deep-linking to the campaign settings Spotify tab. Players still see nothing, which is correct. (`src/views/soundboard/SoundboardView.vue`)

- [x] Spotify connection failures were undiagnosable — `exchangeCode`, `refreshAccessToken` and `fetchAccount` all did `if (!res.ok) return null` (or bare `return`), discarding the JSON body in which Spotify says exactly what is wrong. The UI could only offer "Token exchange failed. Please try again.", which sends the user round the same loop when the fix is in the Spotify dashboard. Adds `readSpotifyError()` handling both response shapes (`error_description` / flat `error` from `accounts.spotify.com`, nested `error.message` from `api.spotify.com`), surfaced in the callback view and via `playError`. A 403 additionally explains that the app is likely still in Development mode with the listening account not on its user list, since that is the most common cause and is not fixable in code. A missing PKCE verifier now names the origin mismatch explicitly — the verifier lives in per-origin `localStorage`, so a login begun on one host and returning to another (an apex → app redirect after the `app.dungeongrimoire.com` migration) loses it, which looks nothing like a Spotify problem from the outside. The callback screen also prints the exact redirect URI to register. (`src/lib/spotifyAuth.ts`, `src/stores/spotify.ts`, `src/views/soundboard/SpotifyCallbackView.vue`)

- [x] Music playlists stalled after an OS suspension and could not be recovered without touching the screen (irongollem/grimoire#572) — `resumeAudioEngine()` resumed the `AudioContext` but deliberately did not re-play elements iOS had paused, because doing so raced with the play → advance chain and could throw an `AbortError` that silently killed auto-advance. The transition-generation counter added for crossfading is what makes the re-play safe: the completion path checks it is still current, so a resume colliding with a swap or fade loses cleanly instead of stopping the wrong element. On return to the foreground the store now re-plays only the specific inconsistency an interruption leaves behind — it believes the track is playing while the element reports paused — and reports honestly (clearing `isPlaying`) if autoplay refuses, rather than leaving the lock screen and CarPlay claiming it is playing silence. A deliberately paused playlist is left alone. This matters beyond the table: the soundboard's music playlists are in daily CarPlay use, where the driver cannot safely poke at the screen to restart a dead playlist. (`src/stores/soundboard.ts`)

- [x] Blocked autoplay left the UI claiming a sound was playing — `play()` did `audio.play().catch(() => {})` and then set `state.isPlaying = true` unconditionally on the next line, so when the browser refused to start playback the card showed a playing sound while the room heard silence. An inline comment asserted the button stayed stopped; it did not. `isPlaying` now flips only inside the resolved branch and is cleared on rejection, so the control reflects what is actually audible. (`src/stores/soundboard.ts`)

- [x] Soundboard card badges ("No Safari", "Retry") overflowed narrow cards (#464) — conditional badges on sound cards were rendered in a non-wrapping `flex` container, causing wide badges to overflow the card's right edge on narrow screens (especially mobile). Fixed by adding `flex-wrap` to the container so overflowing badges wrap to the next line; normal cards with short content remain single-line and are visually unchanged. (`src/components/soundboard/SoundCard.vue`)

- [x] Soundboard pause button acted as stop — `togglePlay` called `stop()` which does `audio.pause() + currentTime = 0`, resetting position. Added a `pause()` action (pause only, no seek) to the store and updated `SoundCard.togglePlay` to call it. (#410)
