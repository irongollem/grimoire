# Fixes — Soundboard

Resolved bugs in the **Soundboard** area, newest first. Part of the Grimoire fix log — see the [log index](../index.md).

- [x] **CarPlay playback skipped 1–3 s chunks every few seconds; the same tracks played clean on a laptop** (user-reported: "as if bitrate is failing") — every sound routes through the Web Audio graph (`MediaElementAudioSourceNode` → filter/gain/bus chain), and the graph's `AudioContext` had exactly one resume path: `visibilitychange → "visible"` (`useMediaSession` → `resumeAudioEngine`). With the phone locked in the car that event never fires, so each iOS interruption of the context (screen-lock power management, Siri, a navigation prompt, an audio-route blip — iOS reports a non-standard `"interrupted"` state) muted the graph's output while the audio *element's* clock kept running underneath; when iOS let the context back, the track had jumped ahead by the length of the gap. Repeated brief interruptions = rhythmic skipping; a desktop gets no such interruptions, which is why the laptop was clean. `audioContext.ts` now listens to the context's own `statechange` and resumes immediately whenever the state leaves `running`/`closed` — gated on the store's `hasActiveAudio` (registered via `setAutoResumeGate`) so an idle page never holds the OS audio session open by resuming a context nobody is listening to. 4 vitest cases (suspended, iOS `interrupted`, idle-gate, settle-back-to-running). The gate also excludes direct output for the same reason it exists: nothing audible runs through the graph in that mode, so resuming would hold the audio session open for a context nobody is listening to — see the direct-output entry in the [feature log](../features/soundboard.md), which is the escape hatch if the skipping turns out to be [WebKit 221334](https://bugs.webkit.org/show_bug.cgi?id=221334) (a buffer underrun that breaks audio up without losing any) rather than this suspension gap (which necessarily drops chunks of music). (`src/lib/audioContext.ts`, `src/stores/soundboard.ts`)

- [x] **26 catalogue sounds named a licence you could not go and read** ([#567](https://github.com/irongollem/grimoire/issues/567)) — every `sound_library` row ingested from Wikimedia Commons had `license_url` null, so the card showed "CC-BY 4.0" (or CC-BY 2.0, or CC0) as bare text with nothing to click through to. A licence name on its own is not the notice CC-BY asks for. Backfilled from the licence name in migration `20260729000003`; the OpenGameArt rows already carried theirs. Found while building the Licences tab's audio section, which surfaced that 82 of the 802 shipped sounds are CC-BY and legally require credit — that credit previously appeared only on a sound's card once a DM had added it to a board, so a consolidated notice now lists all 82 lines in the Reliquary.
- [x] **The provider-registry test crashed CI at import — it pulled the real supabase client into an env-less process** (#572) — `registry.test.ts` imports the provider registry, which imports the grimoire library provider, which imports `@/lib/supabase` — a module that throws "Missing Supabase environment variables" at load time. Locally `.env` masks it; in the application CI job there is no env and the whole suite run failed. `freesound.test.ts` had already established the pattern for exactly this chain — `vi.mock("@/lib/supabase")` before a dynamic import — so the registry test now does the same. Verified by running the test with the env vars stripped. (`src/lib/soundProviders/registry.test.ts`)

- [x] **Dragging a card lit every page tab, and the moved/deleted card lingered until the DB replied** (#572, user-reported: "if i drag on the pages bar...ALL highlight?" and "the object only disappears after the DB write, but that makes it feel it failed initially") — two feedback gaps in the drag-to-page gesture. First: `highlightDrops` applied one identical ring to every tab, saying "drop targets exist" without ever saying which one the release would hit; the view now tracks the pointer during a drag (`dragover` for desktop, `touchmove` for Sortable's touch fallback, Sortable's ghost blinked out of `elementFromPoint`'s way) and the tab actually under the card gets a strong ring while the rest fade to a faint hint. Second: `useMoveSound`, `useDeleteSound` and `useDeletePlaylist` all waited for the round trip before invalidating, so Sortable snapped the dropped card back into its old slot — or a deleted card sat there — for the length of the write, reading as a rejection; all three are now optimistic (`onMutate` patches the cache, `onError` rolls back, `onSettled` reconciles). (`src/views/soundboard/SoundboardView.vue`, `src/components/soundboard/SoundboardPageTabs.vue`, `src/composables/useSounds.ts`, `src/composables/useSoundboardPlaylists.ts`)

- [x] **A "looping" bed died on its second pass — the gapless pair only ever swapped once** (#572, user-reported: night camp's cicadas and fireplace ended while the frog generator kept firing) — `attachHandlers`, which installs the `ontimeupdate` that drives `maybeSwapLoop`, was only called from `play()`. The visible half of a gapless pair got it; the shadow half was started with a raw `incoming.play()` inside the swap and never did. So the first wrap worked (driven by the visible half's handler), the shadow became the live half, played its full length with nobody watching, and the bed stopped — exactly two passes, ~56 s for a 28 s file — while generator layers, which never touch the pair machinery, kept firing on schedule. That asymmetry is what made it read as haunted rather than broken. One line (`attachHandlers(incomingId, …)` before the swap's play) plus a regression test that drives both wraps and asserts the shadow half is watched the same way the first one was. (`src/stores/soundboard.ts`, `src/stores/soundboard.test.ts`)

- [x] **Designer round-2 review: two ground-rule breaks and a find/replace that leaked into copy** (#572) — an icon-component rename had hit string literals, so a DM hovering Spotify's repeat control was told `IconRepeat: Off` and the play button `IconPause` (`SoundboardWidget`, `SoundCardSpotifyTransport`); the widget's repeat and shuffle used hover-only reveals with no `opacity-40` floor and no `[@media(hover:hover)]` guard, making them nonexistent on the tablet the app is run from — third recurrence of exactly this trap; and the Now rail, scene mixer and several absolutes used physical `border-l-*`/`left-*`/`right-*` where the spine-span pattern and logical `inset-s-*`/`inset-e-*` were specified. All three classes of slip fixed. (`SoundboardWidget.vue`, `SoundCardSpotifyTransport.vue`, `NowRail.vue`, `SceneMixer.vue`, `SoundPad.vue`, `SoundCard.vue`, `PlaylistCard.vue`, `SoundPaletteRow.vue`, `SoundProviderRow.vue`, `SoundboardView.vue`, `SoundLibraryCreditsView.vue`)

- [x] **A sound card's name was shown twice, and Arrange mode read as oversized** (#572) — found by the user in the live Arrange view: the redesigned pad (`SoundPad.vue`) carries the sound's name as its title, and the control strip welded underneath it (`SoundCardHeader.vue`) repeated the same name a second time as a static, non-interactive label, right below the pad title. `SoundCardHeader` is only ever rendered directly beneath the pad, so the second copy was pure redundancy rather than a name shown in a different context. Removed the static `<p>{{ sound.name }}</p>` — the rename input still opens in the same spot via the existing "Rename" pencil button. (`src/components/soundboard/SoundCardHeader.vue`)

- [x] **Applying an effect to a music or effects sound silently moved it onto the ambient bus** (#572) — found reviewing the unpushed branch before push. The store's `setEffect(soundId, fileUrl, preset)` hardcoded `engine.attach(soundId, audio, "ambient")` regardless of the sound's real category. Picking an effect preset on a playing music- or effects-category sound — including the currently-playing music-playlist track via `setMusicPlaylistEffect` — re-routed its graph node onto the ambient bus: it stopped responding to its own bus's volume fader, and an effects one-shot (normally exempt from ducking) became duckable, since `DUCKED_BUSES` is `["music", "ambient"]`. Untested — `soundboard.test.ts`'s bus-routing coverage only ever exercised `play()`. `setEffect` now takes the sound's category and attaches via `busForCategory()`; call sites (`SoundCardAudioTransport.vue`, `SoundboardWidget.vue`) pass `sound.category`, and `setMusicPlaylistEffect` passes `"music"` explicitly. (`src/stores/soundboard.ts`, `src/components/soundboard/SoundCardAudioTransport.vue`, `SoundboardWidget.vue`, `src/stores/soundboard.test.ts`)

- [x] **A pad tap stopped a one-shot instead of firing it again** (#572) — found reviewing the redesign. `SoundPad` was wired to `useSoundToggle`, which is *transport* semantics: whatever is audible gets paused, regardless of category. Right for a play/pause button, wrong for a fire target — hitting the thunderclap twice should give two thunderclaps, which is what the command palette has always done via `useSoundTrigger`. The two composables are indistinguishable from the outside and were **entirely untested**, which is exactly how the wrong one got picked; the rule is now pinned by tests covering refire-vs-pause per category, the blocked case, and Spotify (whose SDK owns its own transport and must never be restarted). Two more from the same pass: `CausedByChip` renders a release button, and in `SceneMixer` it sat **inside** the scene's expander button — invalid markup with ambiguous click behaviour — so it moved out to a sibling, and every chip call site was audited for the same nesting (the pad's is inside a button but passes `releasable: false`, so it renders no button at all). And the Spotify section on the music tab ignored the page filter, showing every campaign's tracks while the rest of the board was scoped to one chapter, which made the page tabs look broken. (`src/components/soundboard/SoundPad.vue`, `SceneMixer.vue`, `PlaylistsPanel.vue`, `src/composables/useSoundPlayback.test.ts`)

- [x] Restarting a live generator layer orphaned its timer, firing the sound on two schedules (#572) — `playAmbientPlaylist` built a fresh `SceneGenerator` and `sceneGenerators.set(id, gen)` over the top of any existing entry, but never cleared the outgoing object's `setTimeout`. The map lookup that `pauseGenerators`/`stopGenerators` use then only ever found the new object, so the old timer kept firing with nothing able to cancel it — a one-shot sounding at random intervals for the rest of the session, surviving pause, stop and scene change. Reachable when the same sound appeared twice in one scene's track list; the ordinary path was covered because starting a scene stops the previous one first. Surfaced by extracting the schedule into `src/lib/sceneGenerators.ts`, where a pool with an injectable clock and RNG made the case testable at all — the guard now clears the previous timer before re-scheduling. (`src/lib/sceneGenerators.ts`, `src/stores/soundboard.ts`)

- [x] `playAmbientPlaylist` shadowed the generator pool with a local variable of the same name (#572) — the local `const generators: Record<string, boolean>` mapping sound ID to "is this a generator layer" hid the store-level pool inside that function, so calls meant for the pool resolved to a plain object. Caught by the compiler during the phase-2 extraction rather than at runtime; renamed to `isGenerator`. (`src/stores/soundboard.ts`)

- [x] Widget claimed "No sounds playing" over a running scene, and hid Stop All with it (#572) — the empty state, the Stop All button and the nav badge all judged silence from `playbackStates` alone. A running playlist has no per-sound state of its own, and **generator layers never create one at all** since they fire one-shots directly — so a scene of nothing but generators reported an idle board while audibly playing. The Stop All case was the damaging one: audio running with no way to stop it from the widget. Adds `hasActiveAudio` (does anything at all make noise, accounting for unpaused playlists) and `activeAudioCount` (how many distinct things, counting a scene as one item rather than as its layers, since a badge reading "3" for a three-layer tavern is noise). (`src/stores/soundboard.ts`, `SoundboardWidget.vue`, `SoundboardWidgetToggle.vue`)

- [x] Spotify connect returned a bare 403 — root cause: the developer app declared only **Web API**, not **Web Playback SDK** (#574). Spotify used to present a single "Web" option under "Which API/SDKs are you planning to use?" and later split it in two; apps created before the split were left declaring Web API alone. We use both — `/v1/me` and playback endpoints via Web API, plus `sdk.scdn.co/spotify-player.js` for the actual player — so the moment the SDK was involved the request was refused, with `content-length: 0` and no explanation. Ticking Web Playback SDK resolved it. Setup instructions in `SpotifyTab` now spell out both easily-missed steps (declare both surfaces; add yourself under User Management), and the 403 hint in `SpotifyErrorBanner` / `readSpotifyError` names the API/SDK declaration first, since it is the one that catches out every pre-split app. Earlier suspicion that legacy Facebook-linked accounts could not be allowlisted was a red herring. (`src/components/campaign/SpotifyTab.vue`, `src/lib/spotifyAuth.ts`)

- [x] Spotify connection errors only appeared in the floating widget (#574) — `playError` was rendered solely inside `SoundboardWidget`, so a failure on the `/soundboard` page was invisible unless the DM happened to have the widget open. Extracted `SpotifyErrorBanner.vue` and mounted it in **both** surfaces. The banner also translates the two failures whose fix lives entirely outside this codebase into the action that resolves them: "Not allowed" → close the Spotify desktop app; 403 → add the signing-in account under User Management in the Spotify developer dashboard, since owning the app is not enough. That second case is the real-world one — a long-running app with an empty user list worked for years because Development Mode owners had implicit access, then began returning `403` on `GET /v1/me` once Spotify applied its stricter Development Mode rules to existing integrations on 9 March 2026 and the pre-existing token finally expired. (`src/components/soundboard/SpotifyErrorBanner.vue`)

- [x] Spotify vanished without trace on campaigns that had no Client ID — the connect control was wrapped in `v-if="spotifyStore.isEnabled"`, which is false whenever the active campaign has no `spotify_client_id` (Spotify is per-campaign BYOK). A DM who switched to an unconfigured campaign saw no Spotify UI at all and no hint that the feature existed or how to turn it on, which reads as a broken build rather than a missing setting. DMs now get a dashed "Set up Spotify" link deep-linking to the campaign settings Spotify tab. Players still see nothing, which is correct. (`src/views/soundboard/SoundboardView.vue`)

- [x] Spotify connection failures were undiagnosable — `exchangeCode`, `refreshAccessToken` and `fetchAccount` all did `if (!res.ok) return null` (or bare `return`), discarding the JSON body in which Spotify says exactly what is wrong. The UI could only offer "Token exchange failed. Please try again.", which sends the user round the same loop when the fix is in the Spotify dashboard. Adds `readSpotifyError()` handling both response shapes (`error_description` / flat `error` from `accounts.spotify.com`, nested `error.message` from `api.spotify.com`), surfaced in the callback view and via `playError`. A 403 additionally explains that the app is likely still in Development mode with the listening account not on its user list, since that is the most common cause and is not fixable in code. A missing PKCE verifier now names the origin mismatch explicitly — the verifier lives in per-origin `localStorage`, so a login begun on one host and returning to another (an apex → app redirect after the `app.dungeongrimoire.com` migration) loses it, which looks nothing like a Spotify problem from the outside. The callback screen also prints the exact redirect URI to register. (`src/lib/spotifyAuth.ts`, `src/stores/spotify.ts`, `src/views/soundboard/SpotifyCallbackView.vue`)

- [x] Music playlists stalled after an OS suspension and could not be recovered without touching the screen (irongollem/grimoire#572) — `resumeAudioEngine()` resumed the `AudioContext` but deliberately did not re-play elements iOS had paused, because doing so raced with the play → advance chain and could throw an `AbortError` that silently killed auto-advance. The transition-generation counter added for crossfading is what makes the re-play safe: the completion path checks it is still current, so a resume colliding with a swap or fade loses cleanly instead of stopping the wrong element. On return to the foreground the store now re-plays only the specific inconsistency an interruption leaves behind — it believes the track is playing while the element reports paused — and reports honestly (clearing `isPlaying`) if autoplay refuses, rather than leaving the lock screen and CarPlay claiming it is playing silence. A deliberately paused playlist is left alone. This matters beyond the table: the soundboard's music playlists are in daily CarPlay use, where the driver cannot safely poke at the screen to restart a dead playlist. (`src/stores/soundboard.ts`)

- [x] Blocked autoplay left the UI claiming a sound was playing — `play()` did `audio.play().catch(() => {})` and then set `state.isPlaying = true` unconditionally on the next line, so when the browser refused to start playback the card showed a playing sound while the room heard silence. An inline comment asserted the button stayed stopped; it did not. `isPlaying` now flips only inside the resolved branch and is cleared on rejection, so the control reflects what is actually audible. (`src/stores/soundboard.ts`)

- [x] Soundboard card badges ("No Safari", "Retry") overflowed narrow cards (#464) — conditional badges on sound cards were rendered in a non-wrapping `flex` container, causing wide badges to overflow the card's right edge on narrow screens (especially mobile). Fixed by adding `flex-wrap` to the container so overflowing badges wrap to the next line; normal cards with short content remain single-line and are visually unchanged. (`src/components/soundboard/SoundCard.vue`)

- [x] Soundboard pause button acted as stop — `togglePlay` called `stop()` which does `audio.pause() + currentTime = 0`, resetting position. Added a `pause()` action (pause only, no seek) to the store and updated `SoundCard.togglePlay` to call it. (#410)
